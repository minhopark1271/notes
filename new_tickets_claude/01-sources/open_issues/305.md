## 배경

프로젝트 내 Eigen 사용처를 전수 조사한 결과, 실제 선형대수 연산이 필요한 곳은 2곳이고 나머지는 단순 1차원 컨테이너 용도로 `Eigen::VectorXf`를 사용하고 있음. `std::vector<float>`를 쓰면 안 되는 필연적인 이유는 해당 사용처들에 없음.

## 조사 결과

### Eigen이 실제로 필요한 곳 (유지)

| 위치 | 용도 |
|---|---|
| `controller/DashMorphingController.cpp` (~L987) | RBF 그리디 핸들 선택. Wendland C2 커널 행렬 구성 후 `M.llt().solve(...)` (Cholesky), `A * coeff` 행렬곱 |
| `model/analyzer/DashPearsonPlotter.cpp` (~L103) | 공분산/상관행렬 `centered.transpose() * centered` |

### Eigen이 없어도 되는 곳 (단순 컨테이너 용도)

- `model/analyzer/DashBasePlotter.h` — `QMap<QString, Eigen::VectorXf> inputs/outputs`. analyzer 전체의 데이터 원본이며, 이 타입 때문에 하위 플로터들이 연쇄적으로 Eigen을 사용하게 된 구조.
- `model/analyzer/DashDataLoader.cpp` — 이미 `QVector<float>`로 읽은 컬럼을 원소 단위 루프로 `VectorXf`에 복사만 함. Eigen이 복사 비용을 추가하는 셈.
- `model/analyzer/DashBoxPlotter.cpp` — `std::sort(sorted.data(), ...)`, 인덱스 접근, `mean()`만 사용.
- `model/analyzer/DashParallelPlotter.cpp`, `DashScatter2DPlotter.cpp`, `DashScatter3DPlotter.cpp` — `minCoeff/maxCoeff`, `VectorXf::Constant`, 정규화만 사용.
- `model/analyzer/DashPlotterUtils.cpp` `normalize1d` — NaN 처리 때문에 min/max는 이미 수동 루프, Eigen 표현식은 마지막 한 줄만.
- `model/analyzer/DashXmlParser.cpp` — base64 디코딩한 numpy 버퍼를 `MatrixXf`에 담고 max/min/mean/std만 계산. shape는 별도 `QVector<int>`로 보관하므로 실질적으로 평탄 버퍼. numpy(row-major)와 Eigen(column-major) 차이 때문에 `Eigen::Map<RowMajor>`로 우회하는 코드가 있는데, 평탄 버퍼였다면 이 함정 자체가 없음.
- `view/analyzer/DashPearsonWidget.cpp` — `rawVectors`를 산점도 그리기용으로 읽기만 함.
- `controller/DashHandlePickingInteraction.cpp:16` — `#include <Eigen/Dense>`만 있고 실제 Eigen 심볼 사용 없음 (죽은 include).

### 왜 Eigen으로 되어 있는지 (추정)

analyzer 코드에 numpy 언급 주석이 여러 곳 있어, Python 원본을 포팅하면서 numpy 배열의 대응물로 `VectorXf`를 택한 것으로 보임. `mean()`, `minCoeff()` 같은 원라이너 편의성이 이유이고 성능/정밀도 요구 때문은 아님.

## 정리 시 기대 효과와 한계

**이점**
- analyzer 헤더 5개(`DashBasePlotter.h`, `DashDataLoader.h`, `DashPlotterUtils.h`, `DashXmlParser.h`, `DashParallelPlotter.h`)에서 `<Eigen/Dense>`가 빠져 이를 include하는 view/analyzer 위젯들의 컴파일 시간 감소.
- DataLoader의 불필요한 복사 단계 제거 (데이터 규모상 체감 성능 차이는 없음).
- row-major/column-major 같은 Eigen 특유의 주의점 제거, `QVector<float>` / `Eigen::VectorXf` / `std::vector` 혼재 상태 정리.

**한계**
- Morphing과 Pearson은 Eigen을 유지해야 하므로 external에서 Eigen 의존성 자체를 제거하는 목표는 달성 불가.
- 런타임 성능 향상은 사실상 없음. 사용자에게 보이는 결과 변화 없음.

**리스크**
- 자동화 테스트가 없어 Box / Parallel / Scatter2D / Scatter3D / Pearson 다섯 플로터의 출력 동일성을 실제 데이터로 눈으로 확인해야 함.
- `percentile`, `normalize1d`, `reduceStd` 재작성 시 부동소수 결과가 미세하게 달라질 수 있음.
- 변경 파일 약 12개.

## 제안

- 이 작업만 단독으로 진행하는 것은 권하지 않음. analyzer 모듈을 어차피 손대는 시점(예: viewmodel 마이그레이션에서 `DashBasePlotter`의 데이터 구조를 DTO로 옮길 때)에 함께 정리하는 것이 비용 대비 효과가 좋음.
- Pearson은 `Eigen::Map<const VectorXf>(vec.data(), vec.size())`로 `std::vector<float>`를 복사 없이 감쌀 수 있어 두 타입의 공존이 가능.
- `DashHandlePickingInteraction.cpp:16`의 죽은 include는 별도 시점 없이 바로 제거 가능.
