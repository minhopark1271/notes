## Goal
one-shot 실행의 공통 책임(exe 검증·env 구성·UTF-8 라인 조립·취소·자식 정리)을 한 곳에서 제공하는 공용 실행 엔진이 **`ProcessJob : public Job` 일체형(1회용)** 으로 도입된다 — `DashExtensionProcess` one-shot 경로에서 추출, `Job.h`(행위 없는 상태머신) 동반 도입 ([#205](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/205-5-w6-w10-async-minimal-example) 개정 2: 구 "러너 + Job 2층" 병합). `runAsync` 부분 수신 버그가 수리되고 재현 단위 테스트로 봉인되며, `killOrphans` 는 자기 PID 만 정리한다. **대기 모델 불변** — `Job.h` 는 행위 없는 구조라 W6 DoD 를 건드리지 않는다.

## Background
> source: `DashOpti_Docs/dashgui2-prioritized-backlog.md` 5-2절 W6 (개정 28) · `dashgui2-w6-w10-thread-execution-design.md` 2장 · `dashgui2-w6-w10-async-minimal-example.md` 2장

- **W6 (실행 경로 일원화) 분할 1/3 — 엔진.** QProcess 실행부가 6개 클래스에 산재해 각자 다른 품질로 기동 — 공통 책임이 제각각 구현되거나 누락. W10(이벤트 구동 전환)이 "한 곳만 고치면 되는" 상태를 만드는 전제.
- `runAsync` 는 stdout 결과 라인을 부분만 조립하는 결함이 있음 — **수리 없이 소비자를 확산하면 마커 잘림이 전 소비자로 번지므로 필수 선행**.
- `killOrphans` 는 exe 이름 기준 광역 taskkill — 같은 이름의 무관한 프로세스까지 죽일 위험.

## Technical Details
- **위임(composition) 이 구성 방식 정본** (백로그 개정 28)이되, 형태는 **실행 1회 = `new ProcessJob(exe, args)` 1개** ([#205](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/205-5-w6-w10-async-minimal-example) 개정 2) — 소비자는 `connect(Job::finished / outputLine)` 후 `start()`, 결과 상세(exitCode·stdout)는 finished 슬롯에서 pull 접근자로. **객체 자체가 식별자**라 `jobId` 다중화·잔류 상태(`m_buf` 미클리어) 버그 계급이 원천 소멸, 중복 실행 가드는 `state() != Pending` 검사로 자연 대체.
- **이중 재배선 제거** ([#205](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/205-5-w6-w10-async-minimal-example) 개정 2 근거 1): W6 에서 이미 Job 계약으로 배선이 끝나므로 W10 갈래 ①의 몫은 "호출부 블로킹 래퍼 제거"만 남는다 — 소비자 5~6곳의 2회 재배선(W6 러너 시그널 → W10 Job 시그널) 소멸.
- 상속 특수화 불요 — env·채널 모드는 **생성 파라미터/세터** (1회용 객체라 서브클래싱할 이유가 없음). stdout/stderr 분리(`DashModelBuilder` 의 `m_errorOutput` 등 소비자 3종 공통)는 채널 모드 Separate + `errorOutputLine`. 데몬 쪽 `DashSolverNxCad` 의 상속 특수화(`setupEnvironment`/`resolveExePath`)는 데몬 경로에 잔존.
- 부분 수신 재현 테스트: 라인 조립 로직을 순수 함수로 추출해 QTest 단위 테스트 — W9(회귀 안전망)의 첫 테스트 후보와 동일. W9 미착수 상태면 본 티켓에서 테스트를 작성한다.
- **대기 모델은 불변** — 본 티켓은 구조(where)만 바꾼다. 대기를 통지로 뒤집는 것(how)은 W10.

## Design

### 현황 분석
- `controller/DashExtensionProcess.h:106,111,116` — `runBlocking`(GUI 스레드 호출 금지 계약)·`runAsync`·`killOrphans` 이미 존재. 직렬 명령 큐(`m_commandQueue`) + `commandCompleted` 시그널의 완성형 비동기 인프라 보유.
- 문제 3건: ⑴ `runAsync` 부분 수신 결함 ⑵ 공통 책임 미집약(소비자마다 재구현/누락) ⑶ `killOrphans` 광역 taskkill.

### 대안 비교

| 방안 | 핵심 | 장점 | 단점 |
|---|---|---|---|
| A. 위임 (composition) | 소비자가 엔진 인스턴스를 HAS-A 소유 | 프로세스+데몬 동시 보유 소비자(`DashModelRunner`) 수용 · 도메인 시그널 표면 유지(상위 무수정) · 검증 선례 = MCU(`m_encodeHeaderProc->runAsync`) | 소비자마다 배선 코드 소량 |
| B. 상속 (IS-A) | 소비자가 엔진 서브클래스 | 배선 불필요 | 도메인 클래스는 프로세스가 아님(모델+프로세스+데몬 복합) — 다중 실행 표면 수용 불가 |

### 선택 — 방안 A (위임)

**선택 근거**: 백로그 개정 28 판정 그대로 — 도메인 클래스는 프로세스를 HAS-A 로 쓰고 일부는 프로세스+데몬을 동시 보유(`DashModelRunner`)하므로 IS-A 부적합.
**기각된 대안**: B 상속은 경로·환경 특수화(`DashSolverNxCad` 선례 — 데몬 경로) 한정으로만 유지.

#### 병합 판정 ([#205](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/205-5-w6-w10-async-minimal-example) 개정 2) — "러너 + Job 2층" 원안 폐기, ProcessJob 일체형

원안(W6 `ProcessRunner` 재사용 서비스 → W10 `ProcessJob` 이 래핑하는 2층)은 검토로 폐기, 한 클래스로 병합:

1. **이중 재배선 제거** — 원안대로면 소비자 5~6곳이 W6·W10 두 번 배선된다. 병합하면 W6 에서 Job 계약 1회 배선으로 끝.
2. **층의 정당성 부재** — W10 완료 후 러너의 유일 소비자는 ProcessJob (DaemonHost 는 명시적 비재사용). 소비자 1개짜리 층은 층이 아니다.
3. **1회용 의미론이 버그 계급을 없앤다** — 실행마다 `new ProcessJob`: 잔류 상태(`m_buf` 미클리어)·jobId 에코백이 원천 불요.
4. **`Job.h` 는 행위 없는 구조** — W6 동반 도입해도 "대기 모델 불변" DoD 무접촉.

시그널 충돌 해소: 러너 고유 `finished(bool,int,QString)`/`failed` 폐기 — 결과는 pull 접근자(finished 슬롯 시점엔 객체 생존 — `deleteLater` 전). 단 라이브 로그는 pull 불가 — one-shot 소비자 6파일 전부가 `readyReadStandardOutput` 라이브 구독 중(레포 실측 2026-07-21)이므로 **`outputLine` 시그널은 유지**.

#### 배선 코드 (위임의 실물 — MCU 선례, `model/DashModelBuilderMCU.cpp:338-361`)

위임 채택 시 소비자마다 붙는 연결 코드는 3종 — ① 멤버 생성 ② 시그널 연결 ③ 도메인 번역 슬롯. 이 소량의 배선이 도메인 표면(상위 호출부가 보는 시그널)을 그대로 유지시킨다. W6-2 는 이 패턴을 소비자 3종에 복제하는 작업. (아래는 병합 전 현행 선례 — 병합 후 최종 형태는 그 다음 블록)

```cpp
if (!m_encodeHeaderProc) {
    m_encodeHeaderProc = new DashExtensionProcess(               // ① 멤버 생성 (HAS-A)
        QLatin1String(DashExt::Path::EncodeHeaderTool), this);
    connect(m_encodeHeaderProc, &DashExtensionProcess::oneShotFinished,   // ② 시그널 연결
            this, [this](const QString& jobId, bool success, const QString& output) {
                onHeaderEncodeFinished(jobId, success, output);  // ③ 도메인 번역 슬롯
            });
}
...
m_encodeHeaderProc->runAsync(args, m_currentEncodeJob.headerPath);  // 호출 후 즉시 반환
```

병합 후 최종 배선 형태 ([#205](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/205-5-w6-w10-async-minimal-example) 2-1절) — 배선 3종의 정신(생성→연결→번역)은 동일하되 멤버가 1회용 Job 으로 바뀐다 (MCU 호출부도 재배선 대상):

```cpp
auto* job = new ProcessJob(solverExe, args, this);
connect(job, &Job::finished, this, &X::onDone);        // connect 먼저
connect(job, &ProcessJob::outputLine, this, &X::onLog);
job->start();                                          // start 나중 — W10 전에도 이미 Job 계약
```

#### 핵심 시그니처 ([#205](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/205-5-w6-w10-async-minimal-example) 3-1절·2-1절 — 개정 2)
```cpp
// controller/async/Job.h (신설 — 행위 없는 상태머신, W6 동반 도입)
class Job : public QObject {
    enum class State { Pending, Running, Succeeded, Failed, Cancelled };
    State state() const;                       // 늦은 구독자용 pull
    virtual void start() = 0;
    virtual void cancel() {}
signals:
    void started();
    void progressed(int percent);              // -1 = indeterminate
    void finished(State result, QString reason);
protected:
    void setState(State s, const QString& reason = {});  // 단일 전이점 + 터미널 잠금
                        // (터미널 도달 후 재전이 무시 — 취소 뒤 늦은 완료의 finished 이중 방송 차단)
};

// controller/async/ProcessJob.h (신설 — 러너 일체형·1회용, DashExtensionProcess one-shot 경로 추출)
class ProcessJob : public Job {
    ProcessJob(QString exe, QStringList args, QObject* parent = nullptr);
    // env·채널 모드(Merged/Separate)는 생성 파라미터/세터 — 상속 특수화 불요
    void start() override;      // exe 검증 → env·채널·UTF-8 → connect 먼저 → QProcess::start (부분 수신 수리 대상)
    void cancel() override;     // 추적 PID kill — 늦은 finished 는 터미널 잠금이 삼킨다
    int exitCode() const;       // 결과는 pull — finished 슬롯 시점(객체 생존 중)에 읽는다
    QString stdoutText() const;
signals:
    void outputLine(QString line);       // 라이브 stdout (소비자 6파일 실측 필요분)
    void errorOutputLine(QString line);  // Separate 모드 시 stderr — W6-2 소비자 3종 공통 요구
};
```

### 경과

### 문제 — 두 벌이 공유하는 전제

둘 다 `readAllStandardOutput()` 으로 **미완성 라인까지 Qt 채널 버퍼를 통째로 비워온 뒤**, 자체 버퍼에 다시 누적해 손으로 프레이밍한다. `QProcess` 는 `QIODevice` 라서 "구분자가 올 때까지 미완성 메시지를 보관" 하는 계층을 이미 갖고 있는데, 그것을 비워버린 다음 그 위에 같은 것을 다시 만든 구조.

| 책임 | 수동 구현 위치 | `readLine()` 이 제공 |
|---|---|---|
| 미완성 라인을 다음 read 까지 보관 | `m_daemonStdoutBuffer` / `LineAssembler::m_buf` | O (Qt 채널 버퍼) |
| `\n` 탐색·완성 라인 절단 | `processDaemonStdoutLines()` / `append()` | O (`canReadLine`+`readLine`) |
| `\r` 제거 (Windows CRLF) | 두 곳 각각 `chop(1)` | X — `QProcess` 는 텍스트 모드 아님 |
| 개행 없이 끝난 마지막 줄 배출 | `flush()` / `onDaemonFinished` | X — 종료 시 `readAll()` 필요 |
| UTF-8 디코드 | `fromUtf8` 호출 6곳 | X (`QByteArray` 반환) — 단 **호출 위치가 교정됨** |

### 변경

`QIODevice::canReadLine()` / `readLine()` 으로 **완성된 라인만 꺼내는** 방식으로 치환. 미완성 라인은 Qt 채널 버퍼에 그대로 둔다. 자체 버퍼 계층(`m_daemonStdoutBuffer`, `m_outAsm`, `m_errAsm`)이 소멸하고, 남는 책임 3개(`\r` 제거 · tail 배출 · 디코드)만 공용 헬퍼 `controller/async/LineReader.h` 로 수렴한다. `QIODevice*` 를 받으므로 `QProcess`(데몬·원샷)와 `QBuffer`(테스트)에 동일하게 적용된다.

### 부수 효과 — 단순 치환 이상 (UTF-8 경계 결함 해소)

라인 프레이밍 축에서는 두 벌 다 옳았지만, **UTF-8 디코드 축에서는 두 벌 다 틀렸다.** `QString::fromUtf8(chunk)` 를 청크 단위로 호출하므로 한글 3바이트가 read 경계에 걸치면 각 조각이 U+FFFD 로 깨진 뒤 이어붙는다. 해당 호출 6곳:

## 작업 2 — `forceKillPid` 에 `/T` 추가 (PyInstaller 손자 프로세스)

### 문제

#223 Phase 3 가 광역 `taskkill /IM` → `taskkill /F /PID` 로 축소하면서 **트리 kill 을 잃었다.** 대상 확장은 PyInstaller onefile exe 로 **부트로더 부모 + 실제 앱 자식** 2계층 구조이고, `QProcess::processId()` 가 주는 것은 부트로더 PID 다. 따라서 `/F /PID <부트로더>` 는 부트로더만 죽이고 실제 워커를 고아로 남긴다. 구 `/IM` 은 부모·자식이 같은 이미지명이라 둘 다 죽었으므로, 이 축에서는 후퇴다. `killOrphans` 자체가 그 안전망 역할이므로 영향이 크다.

### 변경

`controller/DashExtensionProcess.cpp:31` — `{"/F", "/PID", pid}` → `{"/F", "/T", "/PID", pid}`.

### `/T` 의 보장 범위 (명시)

`/T` 는 PPID 필드를 따라 프로세스 트리를 **재귀 워크**하므로 손자·증손자까지 내려가지만, 체인이 온전할 때만 성립한다. Windows 는 부모가 죽어도 자식을 reparent 하지 않으므로 아래 경우 도달 불가:

- 중간 프로세스 선종료 → 그 아래 손자의 PPID 가 죽은 PID 를 가리켜 트리 워크에서 이탈
- PID 재활용 → 트리 관계 오해석
- 스냅샷 레이스 → 워크 직후 태어난 손자 누락
- 체인 우회 생성 (`cmd /c start`, 서비스 경유, `DETACHED_PROCESS` + 중간 즉시 종료)

**단 PyInstaller onefile 은 부트로더 부모가 자식 종료까지 살아서 대기하므로 kill 시점에 체인이 온전하다.** 따라서 현재 케이스에는 `/T` 로 충분하다. 커널 보장이 필요하면 Job Object 뿐 — Follow-up 참조.

### 승인된 부작용

JournalLauncher 는 `--ansys-path` 를 받아 Ansys 를 구동하므로, Ansys 를 자식으로 띄우는 경우 `/T` 는 **Ansys 해석 프로세스까지 죽인다** (구 `/IM` 은 동명 이미지만 죽여 Ansys 는 생존). `killOrphans` 는 `startDaemon()` 에서만, 그것도 `stopDaemon()` 직후에 호출되므로 실질 위험은 낮다고 판단하고 수용한다.

### POSIX 분기는 유지

`kill -9 <pid>` 그대로. `/T` 대응인 프로세스 그룹 kill (`kill -9 -<pgid>`) 은 자식을 `setsid` 로 띄우는 것이 전제이고, 프로젝트 타깃은 Windows/MSVC 이며 POSIX 분기는 host 테스트 편의용이다. 따라서 손자 kill 봉인 테스트는 **Windows 한정**으로 표시한다.

### Progress: 2026-08-05 · 진행 중 (설계 전환 — MIN 안 채택)

앞선 코멘트에서 QIODevice 프레이밍(`readLine` + 채널 커서)과 수동 조립 유지 두 안을 비교했고, **스코프 최소화를 우선해 후자로 전환**했다. 커밋 `d98507b`.

**전환 근거**

결함은 "어느 읽기 함수를 썼나" 가 아니었다. 프레이밍 알고리즘은 두 벌 다 옳았고 실제 결함은 독립적인 두 개였다 — UTF-8 디코드 위치, 그리고 데몬 경로의 꼬리 유실. 이 둘을 직접 고치는 것이 프레이밍 주체를 프레임워크로 교체하는 것보다 변경 표면이 작고, **채널·읽기 커서라는 개념이 코드에 등장하지 않는다.**

| | QIODevice 프레이밍 | 채택안 (`LineAssembler`) |
|---|---|---|
| 프레이밍 코드 | 0줄 | 약 25줄 |
| UTF-8 | 정확 | 정확 (동일 조건) |
| 우리 쪽 상태 | 없음 | 버퍼 3개 |
| 등장 개념 | 채널·커서·복원 | 없음 |
| 함정 | "엔진에서 `readAll*` 금지" (같은 버퍼를 소비해 라인 중간을 훔친다) | 없음 |
| 단위 테스트 | `QBuffer` 필요 | 바이트→라인 순수 함수 |

`readLine()` 은 채널 암시적이라 stderr 를 읽으려면 커서를 옮겨야 한다 — `readLineStandardError()` 는 존재하지 않는다 (프레이밍 기계가 `QIODevice` 층에 있고 그 층은 "표준 에러" 를 모른다). 그 토글은 stderr 기능이 아니라 `readLine` 이주가 만드는 비용이었다.

대가는 멤버 버퍼 3개의 수명 관리이며, 봉인 테스트가 그 규칙을 고정한다.

**꼬리 유실의 정확한 원인 (앞선 서술 정정)**

종료 처리의 부재가 아니었다. 구 `onDaemonFinished` 는 파이프를 한 번 더 비우고 조립 함수를 다시 불렀다. 그런데 **같은 규칙(`while (indexOf('\n') >= 0)`)을 재사용**했으므로 `\n` 없는 조각은 몇 번을 다시 돌려도 나오지 않았고, 이어 `stopDaemon()` 의 `.clear()` 가 폐기했다.

필요했던 것은 장소가 아니라 그 장소에서의 다른 규칙 — "스트림이 끝났으므로 남은 것은 `\n` 이 없어도 완성된 라인이다". `ProcessJob` 은 그 예외(`hasPending()`/`flush()`)를 갖고 있어 꼬리를 잃지 않았다. 두 경로의 차이는 알고리즘이 아니라 종료 시점의 예외 유무였다.
