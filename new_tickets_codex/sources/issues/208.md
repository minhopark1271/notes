## Goal
model 계층의 단일 one-shot 소비자 3종(`DashModelRunner`·`DashModelBuilder`·`DashOptimizer`)이 자체 `QProcess` 를 생성·기동하지 않고 공용 실행 엔진(#207)에 위임한다. **3종 모두 수정 대상** — 이미 시그널 구동인 `DashModelRunner` 도 포함되며, 이 경우 행위는 그대로 두고 공통 책임 재구현분(자체 `QProcess` 소유 `:179`·에러 번역 `:185-209`·env 구성 3곳)만 엔진 위임으로 걷어내는 구조 정리다. 도메인 시그널 표면(`predictionSucceeded`·`trainingSucceeded` 등)은 유지 — 상위 소비자 무수정.

## Background

- **W6 분할 2/3 — model 소비자.** 3클래스가 각자 `QProcess* m_process` 를 소유하고 exe 검증·env·UTF-8·정리를 제각각 구현(또는 누락). 결함 수정이 N곳에 반복 필요 — 산재는 진행형(QProcess 123→137, 4일 사이).
- `DashModelRunner` 는 유일한 모범(`m_process` start 3곳·QProcess 참조 24회에도 `waitFor*`/`processEvents` 0회 — 완전 시그널 구동)이지만, 공통 책임 재구현분은 엔진 위임으로 정리한다.

## Technical Details
- **배선 패턴** ([#205](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/205-5-w6-w10-async-minimal-example) 2-1절 — 개정 2): 실행 1회마다 `new ProcessJob(exe, args)` → `connect(Job::finished / outputLine / errorOutputLine)` → `start()`. 완료 슬롯에서 결과 pull(`exitCode()`·`stdoutText()`) 후 도메인 시그널로 번역. W6 에서 이미 Job 계약이라 W10 재배선 없음.
- **채널 모드 Separate 는 3종 공통 요구** — 3종 모두 `setProcessChannelMode(SeparateChannels)` + stderr 수신 슬롯 보유 (`ModelRunner :180` / `ModelBuilder :31` / `Optimizer :82`). 엔진의 Separate 모드 + `errorOutputLine` 시그널(#207 Phase 2 산출) 사용. `DashModelBuilder` 특이사항은 stderr 를 `m_errorOutput` 으로 축적해 실패 메시지로 쓰는 것(`:1280-1284`) — 번역 슬롯에서 유지.
- **ModelRunner 의 데몬 축(Sensitivity)은 범위 밖** — DashManager 소유 엔진(`sensitivityDaemon()`)을 구독하는 이미-위임 구조(`DashModelRunner.cpp:215,:226`). 본 티켓은 자기 소유 one-shot 축(`m_process` — prediction `:957,:1834,:1927`)만 전환. 데몬 축의 다음 변화는 W10-c.
- **파싱·렌더 등 도메인 로직 불변** — QProcess 실행부만 교체.
- **대기 모델 불변** — 시그널 구동 전환(W10)은 범위 밖.

**분석 — 3종 구조 비교**

세 클래스 모두 생성자에서 `m_process` 1개를 소유하고 `SeparateChannels` + stdout 라인 파싱 + `finished` 번역을 각자 구현한다. 위임 전환에 영향을 주는 차이는 2건이다.

| | 실행 디렉터리 | stderr 취급 | 기동 대기 | busy 가드 |
|---|---|---|---|---|
| `DashOptimizer` | exe 디렉터리 | 수신 즉시 폐기 | 없음 | 없음 |
| `DashModelRunner` | **프로젝트 경로** | 수신 즉시 폐기 | 없음 | ND·1D 2곳 (predict 무가드) |
| `DashModelBuilder` | exe 디렉터리 | `m_errorOutput` 축적 | `waitForStarted(10000)` | 없음 |

1. **실행 디렉터리** — `ProcessJob::start()` 는 `QFileInfo(exe).absolutePath()` 로 고정한다. `DashModelRunner` 만 프로젝트 경로를 쓰므로 **엔진에 `setWorkingDirectory()` 를 추가**한다 (미지정 시 현행 exe 디렉터리). 이 setter 없이는 예측 3경로의 상대 경로 해석이 바뀐다.
2. **stderr** — `Runner`/`Optimizer` 의 `onReadyReadStandardError()` 는 읽고 버린다. Python 도구가 진행바를 stderr 로 내보내는 것을 실패 메시지에서 차단하는 의도로 보이므로 `errorOutputLine` 을 구독하지 않아 폐기를 유지한다(엔진이 파이프를 대신 비우므로 블로킹 위험 없음). `DashModelBuilder` 의 축적만 구독으로 이어받는다.

- `m_process` 는 `DashModelBuilder` 에서 protected 지만 `DashModelBuilderMCU` 는 참조하지 않는다 (`m_errorOutput`·`m_statusCheckTimer` 만 사용) — 파생 클래스 영향 없음.

**엔진에 추가한 것 — `setWorkingDirectory()`**

`ProcessJob::start()` 는 작업 디렉터리를 exe 디렉터리로 고정한다. `DashOptimizer`·`DashModelBuilder` 는 그 값이 맞지만 `DashModelRunner` 만 **프로젝트 경로**에서 도구를 돌린다(인자의 상대 경로가 그렇게 해석된다). setter 없이 위임하면 예측 3경로의 경로 해석이 조용히 바뀐다.

봉인 테스트로 고정했다. 되돌리면 실제로 깨지는 것을 확인했다.

```
setWorkingDirectory 되돌린 상태
└─ workingDirectoryOverrideIsHonoured .... FAIL  (Compared values are not the same)
   workingDirectoryDefaultsToExeDir ...... PASS  (기본값은 그대로여야 하므로 통과가 정상)
```

**설계 판단 3건**

1. **stderr 구독 여부를 소비자별로 갈랐다.** 3종 모두 Separate 모드를 쓰지만 `errorOutputLine` 을 구독하는 것은 `DashModelBuilder` 뿐이다. `Runner`/`Optimizer` 의 기존 `onReadyReadStandardError()` 는 읽고 버렸는데, 도구가 진행 표시를 stderr 로 내보내므로 실패 메시지에 섞이지 않게 하려는 의도로 읽었다. 엔진이 파이프를 대신 비우므로 구독하지 않아도 블로킹 위험은 없다.

2. **`DashModelBuilder` 의 기동은 함수 마지막으로 옮겼다.** `QProcess::start()` 는 CreateProcess 실패를 그 자리에서 `errorOccurred` 로 알리고 엔진은 곧바로 `finished(Failed)` 를 방출한다. 기존 위치에서 기동하면 실패 번역이 뒤따르는 "In Progress" 상태 기록·타이머 기동보다 먼저 끼어든다. `waitForStarted` 가 early return 으로 지켜주던 순서를 배치로 지킨다.

3. **실패 메시지 조립.** 종료 코드가 있으면 기존 도메인 문구를 그대로 쓰고, 프로세스가 뜨지 못한 경우(`exitCode() < 0`)에만 엔진 사유를 쓴다. 기존에는 `waitForStarted` 실패 메시지가 그 자리를 채웠다.

**동작 변화 2건** (둘 다 Issue 가 승인한 방향)

- **predict 버튼 경로에 실행 중 가드가 생긴다.** 기존 가드는 ND(`:1758`)·1D(`:1851`) 2곳뿐이고 predict(`:957`)는 무가드였다. `m_currentJob` 핸들 1개로 단일화하면서 3경로가 같은 판정을 쓴다 (본문 Phase 1 저자 확정 결정).
- **기동 실패 시 도메인 실패 시그널이 방출된다.** 기존 `errorOccurred` 람다는 `logMessage` 만 냈고 `QProcess::finished` 는 오지 않아 `predictionFailed` 가 방출되지 않았다. 이제 엔진이 `finished(Failed)` 로 통지해 `predictionFailed` 까지 이어진다 — 위젯이 에러 다이얼로그를 띄운다.
