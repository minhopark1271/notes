# #224 N1-a: 증분 빌드 시간 단축 — extensions 트리 배포 게이팅 (636s -> 60s 목표)

- URL: https://github.com/NumeRealWorks/DashOpti_GUI/issues/224
- Board status: Done
- Labels: ['performance', 'infra']

## Goal

증분 빌드 **636초 → 60초대**. `.cpp` 1개 수정에 10분 넘게 걸리는 상태를 해소한다.

N1(의존성·빌드 인프라 정비, [#200](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/200-3-prioritized-backlog) 5-4절)의 작업 ⑤ "DLL 복사 ~220행 대체" 를 vcpkg 전환과 분리해 조기 실행한다. N1 본체는 내부 포트 7종의 저장소 협의 리드타임이 지배하지만, 이 문제는 CMakeLists 안에서 바로 해결된다.

## Background — 실측

2026-08-03, #223(W6-1) 작업 중 측정. Windows 11 / MSVC 19.50 / Ninja / Release / NVMe SSD / Defender 실시간 검사 ON.

| 단계 | 소요 | 비중 |
|---|---|---|
| **`extensions/` `copy_directory` (7.22GB / 23,737 파일)** | **563.9초** | **88.6%** |
| DLL 개별 복사 1,197개 프로세스 (25ms/개) | ~31초 | 4.8% |
| 컴파일 + 링크 + windeployqt + resources | ~42초 | 6.6% |
| **`.cpp` 1개 수정 후 재빌드 합계** | **636.5초** | |

no-op 빌드는 0.2초다. ninja 의존성 그래프는 정상이고, 비용은 전부 **재링크마다 무조건 실행되는 POST_BUILD 배포**에 있다.

## Technical Details — 원인

`add_custom_command(TARGET ... POST_BUILD)` 형식에는 **`OUTPUT` 도 `DEPENDS` 도 없다.** 링크 명령 뒤에 무조건 따라붙는 부록이라 최신성 판단 자체가 불가능하다. 배포 대상은 빌드가 생성하지도 않는 읽기 전용 vendored 입력인데, 앱 소스 변경에 반응한다.

```cmake
# CMakeLists.txt 468-475 — 조건 없는 전량 복사
add_custom_command(TARGET ${PROJECT_NAME} POST_BUILD
        COMMAND ${CMAKE_COMMAND} -E copy_directory
        "${DashOptiPythonExtensions_DIR}" "$<TARGET_FILE_DIR:${PROJECT_NAME}>/extensions")
```

`copy_if_different` 와 달리 `copy_directory` 에는 "다를 때만" 이라는 개념이 없다. 7.2GB 중 99.2%가 `deep_opt/_internal`(PyTorch + CUDA 런타임, 23,546 파일)이다.

**복사 방식을 바꾸는 접근은 전부 기각됐다.** `file(COPY)`(타임스탬프 스킵) 504초, `copy_directory_if_different` 는 내용 비교라 7.2GB 재읽기. 파일당 고정 비용 약 21ms x 23,737개가 남기 때문이다. **23,737개 파일을 아예 건드리지 않는 것이 유일한 해법이다.**

## Implementation Plan

배포를 링크의 부산물에서 **자체 입력을 갖는 독립 산출물**로 바꾼다. 실제 산출물이 파일 수만 개라 ninja 에 지목할 대상이 없으므로, 빈 stamp 파일을 대역으로 두고 명령 끝에 `touch` 한다. **stamp 자체에는 지능이 없고 조건은 전부 `DEPENDS` 에 들어간다.**

**본 Issue 의 작업 범위는 ① 하나다.** 초안의 ②는 구현·측정까지 마친 뒤 기각했다(사유는 아래).

### ① `extensions/` 배포 게이팅 — 채택

구현된 형태:

```cmake
if(EXISTS "${DashOptiPythonExtensions_DIR}")
    # 목적지에 $<TARGET_FILE_DIR:${PROJECT_NAME}> 를 쓸 수 없다. 타깃을 참조하는 genex 는
    # deploy_extensions -> ${PROJECT_NAME} 의존을 만들어, 아래 add_dependencies 와 순환을 이룬다.
    # 타깃 참조 없이 같은 경로를 계산한다.
    get_property(_dash_multi_config GLOBAL PROPERTY GENERATOR_IS_MULTI_CONFIG)
    if(_dash_multi_config)
        set(_dash_bin_dir "${EXECUTABLE_OUTPUT_PATH}/$<CONFIG>")
    else()
        set(_dash_bin_dir "${EXECUTABLE_OUTPUT_PATH}")
    endif()

    file(GLOB_RECURSE _ext_files CONFIGURE_DEPENDS "${DashOptiPythonExtensions_DIR}/*")
    set(_ext_stamp "${CMAKE_CURRENT_BINARY_DIR}/deploy_extensions_$<CONFIG>.stamp")
    add_custom_command(OUTPUT "${_ext_stamp}"
            COMMAND ${CMAKE_COMMAND} -E copy_directory
                    "${DashOptiPythonExtensions_DIR}" "${_dash_bin_dir}/extensions"
            COMMAND ${CMAKE_COMMAND} -E touch "${_ext_stamp}"
            DEPENDS ${_ext_files}
            COMMENT "Copying DashOptiPythonExtensions to bin (원본 변경 시에만)...")
    add_custom_target(deploy_extensions DEPENDS "${_ext_stamp}")
    add_dependencies(${PROJECT_NAME} deploy_extensions)
endif()
```

- 23,736개 전부 감시해도 **no-op 0.9초**.
- `CONFIGURE_DEPENDS` 는 파일 **추가/삭제** 추적용. `file(GLOB_RECURSE)` 만으로는 configure 이후 추가된 파일이 목록에 안 들어온다.
- **깊은 파일 mtime 변경 / 파일 추가 / 파일 삭제** 모두 실제 빌드로 트리거 확인.
- `copy_directory` 는 유지 — 원본이 바뀔 때만 도는 명령이다.

초안 대비 정정 2건:

| 초안 | 문제 | 정정 |
|---|---|---|
| 목적지 `${EXECUTABLE_OUTPUT_PATH}/extensions` | 멀티컨피그에서 실제 출력은 `bin/Release` — MSBuild 빌드로 확인 | `GENERATOR_IS_MULTI_CONFIG` + `$<CONFIG>` 로 계산 |
| 대안으로 `$<TARGET_FILE_DIR:${PROJECT_NAME}>` | 타깃 참조 genex 가 `deploy_extensions -> DashOptGUI` 의존을 만들어 `add_dependencies` 와 순환. CMake 가 생성 거부 (`strongly connected component (cycle)`) | 위와 동일 |

stamp 파일명에 `$<CONFIG>` 접미사를 붙여 컨피그 전환 시 재배포 누락을 막는다.

### ② DLL 배포 게이팅 — 구현·측정 후 기각

동일 패턴을 configure-time glob DLL 772개에 적용해 실제로 구현하고 측정했다. **31초를 벌지만 유지관리 복잡도가 그 값을 넘어서 되돌렸다.**

| | ①만 (채택) | ①+② |
|---|---:|---:|
| 증분 빌드 | 63.3s / 61.2s | 31.3s / 20.5s |
| no-op 빌드 | 0.9s / 0.9s | 1.0 ~ 1.6s |
| 복사 시점 | POST_BUILD 파이프라인 내 (변경 없음) | 파이프라인 밖 독립 타깃으로 분리 |
| 변경 규모 | +24 / −5, 1블록 | +74 / −73, 10블록 |

**판단 기준: 게이팅할 산출물이 다른 공급원과 이름을 다투는가.**

현행 배포 순서는 `CMakeLists.txt` 를 위에서 아래로 읽으면 그대로 드러난다 — `POST_BUILD` 가 선언 순서대로 실행되는 단일 파이프라인이기 때문이다. 게이팅은 작업을 그 파이프라인 **밖**의 독립 타깃으로 꺼내므로 배포가 두 메커니즘으로 갈라지고, 둘 사이의 상대 순서는 소스 어디에도 적혀 있지 않다. **같은 이름의 산출물을 여러 공급원이 내놓는 경우, 최종 내용을 결정하는 것은 실행 순서다.**

DLL 배포가 그 경우다 — 대상 1,196개 중 이름이 겹치는 그룹이 264개, 그중 **156그룹은 내용까지 다르다.** 어느 공급원을 어느 쪽 메커니즘에 넣느냐가 `bin/` 최종 내용을 바꾸고, 틀려도 빌드는 성공한다. 충돌하는 공급원 일부를 `POST_BUILD` 에 남기면 순서는 지켜지지만 **그 규칙이 코드에 없다** — 새 DLL 공급원을 추가하는 사람이 규칙을 모른 채 게이팅 쪽에 넣으면 잘못된 DLL 이 조용히 배포된다.

반면 ①의 배포 대상은 **단일 공급원**이라 순서 계약에 참여하지 않고, 변경도 1블록으로 닫힌다.

가성비도 같은 방향이다. ①만으로 636.5초 → 62초로 이미 목표 구간에 들어오므로, ②는 31초를 위해 배포 루프 9곳을 개조하고 위 복잡도를 상시 떠안는 거래가 된다.

> 구현 중 겪은 사례: 누적 헬퍼를 `macro()` 로 쓰면서 `foreach(x IN LISTS ARGN)` 을 썼는데, `macro` 의 `ARGN` 은 변수가 아니라 텍스트 치환이라 루프가 무동작한다. configure 는 성공했고 경고도 없었으며 **DLL 772개가 통째로 배포에서 빠졌다.** 진단용 `message()` 를 넣어 뒀기에 발견했다.

> 초안의 배치화 기각 근거는 **틀렸다.** "CMake 가 `cmd.exe /C` 로 감싸 실질 한도 8,191자" 라고 적었으나, 실제로는 CMake 가 긴 커스텀 커맨드를 자동으로 `.bat` 파일로 분리한다 — 현행 `post-build.bat` 이 1,568행 / 319KB 로 이미 존재한다. 커맨드라인 한도는 애초에 제약이 아니었다. 결론(배치화 안 함)은 같지만 이유가 다르다.

> `$<TARGET_RUNTIME_DLLS:tgt>` 는 CMake 3.21+ 공식 관용구지만 링크된 `SHARED` 타깃만 훑어 런타임 조건부 로드 DLL(OCCT 3rdparty, `external/additional`)이 조용히 누락되므로 N1 범위로 넘긴다.

**산출물 동일성** — clean build 후 `bin/` 전수 대조 (루트 832개 SHA256 + `extensions/` 23,737개 크기):

├─ 한쪽에만 있음 ............... 0
└─ 양쪽 존재, 내용 상이 ........ 4  (DashOpti.exe/.pdb, DashUiPreview.exe/.pdb)

이 4건은 MSVC 링크 비결정성이다. 추정이 아니라 실증했다 — 소스를 전혀 바꾸지 않고 재빌드해도 exe 해시가 매번 바뀐다(PE 헤더 타임스탬프/GUID). `.exe` 는 크기가 바이트까지 동일하다. **배포된 외부 파일 24,565개는 전부 일치**하며, 순서 계약이 걸린 충돌 DLL(`libEGL` `libGLESv2` `fmt` `spdlog` `vtk*`)의 승자도 동일하다 — ②를 넣지 않았으므로 애초에 순서를 건드리지 않았다.

**트리거 검증** — 실제 빌드 (`ninja -n` 은 RERUN_CMAKE 장벽에서 멈춰 무의미하므로 실빌드로 확인)

| 테스트 | 시간 | ext 재배포 | 재configure |
|---|---:|---|---|
| 외부 DLL mtime 변경 | 32.2s | ✗ | ✗ |
| `extensions/` 깊은 파일 변경 (`deep_opt/_internal/_asyncio.pyd`) | 487.1s | **✓** | ✗ |

DLL 변경이 7.2GB 트리를 건드리지 않고 완전히 격리된다. 삭제가 3.0초인 것은 정상이다 — 입력이 줄면 스탬프보다 새로운 입력이 없어 재배포할 이유가 없다. 배선은 `ninja -t query` 로도 확인했다(입력 23,736개, 여분 없음).

### 알려진 한계 — 재configure 동반 빌드

`CMakeLists.txt` 수정 등으로 configure 가 다시 도는 빌드는 `extensions/` 를 전량 재배포한다(~500-660초). 결정적으로 재현된다.

배제한 원인: 스탬프보다 새로운 입력(23,736개 전수 mtime 비교 → 0개), 숨은 입력(`ninja -t query` → 여분 없음), 명령 실변경(`build.ninja` 바이트 동일 확인).

ninja 가 답한 이유는 `command line changed for deploy_extensions_Release.stamp` 인데, **같은 빌드에서 본 변경과 무관한 기존 규칙도 동일하게 보고한다**:

```
ninja explain: command line changed for deploy_extensions_Release.stamp
ninja explain: command line changed for DashOptGUI_autogen/timestamp     <- 기존 AUTOMOC
ninja explain: command line changed for DashUiPreview_autogen/timestamp  <- 기존 AUTOMOC
```

`build.ninja` 가 동일한데도 `.ninja_log` 해시가 불일치로 판정되는 것으로, **재configure 시 CMake+Ninja 가 커스텀 커맨드 계열 엣지를 무효화하는 기존 동작**이다. 본 변경이 만든 문제가 아니며, 변경 전에는 매 빌드가 어차피 전량 배포라 드러나지 않았을 뿐이다.

**퇴행 아님** — 모든 시나리오에서 변경 전보다 빠르거나 같다.

| 시나리오 | 변경 전 | ① 적용 후 |
|---|---:|---:|
| `.cpp` 1개 수정 (압도적 다수) | 651.9s | 63.3s |
| 재configure 동반 (`CMakeLists` 수정 등) | 651.9s | ~500-660s |
