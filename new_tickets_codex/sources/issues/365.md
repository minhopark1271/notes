## Goal
deck 의 content uuid 가 원장의 레코드가 된다 — 경로가 바뀌어도 항목이 신원을 이어받을 자리가 생기고, 세션 내부 저장소였던 `AnalysisModelIdentity.json` 이 폐기된다.

## Background
> source: wiki [Project-Manifest-4-Ticket-Slicing](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/Project-Manifest-4-Ticket-Slicing) "PR 상세" G6 절

`AnalysisModelIdentity.json` 은 `rwResolveContentIdentity` 안에서만 읽고 쓰는 세션 내부 저장소다 — 저장 uuid 가 있으면 그 값을 쓰고 없으면 발급해 기록한다 (코드 재실측 — 문서 1 3절의 "write-only" 서술은 실측과 다르다). 키가 canonical 절대경로라 파일·프로젝트가 이동하면 항목을 못 찾아 새 uuid 가 발급되고 옛 항목은 잊힌다 — uuid 가 사실상 경로의 함수다. 원장이 uuid 를 들면 키가 루트 상대경로로 내려가 프로젝트 이동에 견디고, 발급 책임이 세션 내부에서 호출자(원장)로 올라간다.

두 티켓은 **한 포맷 이동의 두 반쪽**이다 — 가르면 두 저장소가 공존하는 과도기가 생긴다 (S3a 성격의 짝이라 위반 기록 없음).

**uuid 는 원장의 1차 키다(D24).** 발급·영속은 T9(#364) 소관이고, 이 PR 의 T12 는 **소비 전환**만 한다 — 세션·모듈이 원장 키를 content uuid 로 쓰고, 경로 파생 재계산 경로를 없앤다.

## Technical Details

### as-is
- uuid 는 `AnalysisModelIdentity.json`(키 = canonical 절대경로) 조회 우선, 미스 시 canonical 절대경로 v5 파생으로 발급 후 기록된다. 같은 경로면 저장값과 파생값이 같아 동작상 경로의 함수다
- `controller/DashRwSession.cpp` 가 신원 해석을 자체 보유 — `rwResolveContentIdentity`(`:1092-1148`) · `rwIdentityStorePath`(`:1070`) · `rwConfigsDirFromProject`(`:1080`) · `rwFileSha256`(`:1032`)
- `DashRwSession::open` 은 `(filePath)`·`(filePath, identityStoreDir)` 2 오버로드(`:1150`·`:1158`) — contentUuid 인자가 없다
- 원장 키가 이미 uuid 다 (T9 — D24). 발급·영속은 끝나 있고 소비 측이 아직 경로 파생을 쓴다

### to-be
- `resolveUuid(relPath)` 정착 — 원장 `path` 스캔이 히트하면 그 키(uuid), 미스면 상대경로 v5 파생 1회. 이후 재계산하지 않는다
- **소비 전환** — 세션·모듈이 원장 키를 content uuid 로 받아 쓰고, 경로 파생 재계산 경로를 제거한다
- 원장에 없는 deck(morph 산출물·프리뷰)도 같은 산식으로 파생하되 **원장에 쓰지 않는다**
- `DashRwSession::open(filePath, contentUuid)` — 호출자가 uuid 를 제공한다
- 해석 3함수 삭제, `rwFileSha256` 은 호출자 쪽으로 이동. `AnalysisModelIdentity.json` 폐기

### not-to-be
- reader-writer DLL — 손대지 않는다. `ContentInfo::uuid`(`IRWModule.hpp:106-115`)의 계약이 "호출자가 덱 파일당 안정적으로 유지·제공할 책임" 이고 원장이 그 책임을 진다
- 마이그레이션 코드 — DV-Condition 은 조건 이름으로 키가 잡혀 있고 로더 폴백(`model/DashConditionParameterization.cpp:495-497`)이 이미 있으며, backfill 은 다음 저장 때 `syncDvFromCheckedFeConditions` 가 수행한다(주석 `:444-446`)
- rename 내성 — 이 PR 은 프로젝트 이동에 견디는 데까지다. rename 복구는 후속작업 1(sha256 이관). D24 로 그 반경이 **원장 `path` 필드 1개 갱신**으로 좁혀졌다 — 모듈 JSON 은 손대지 않는다

## Design

### uuid 해석 (문서 1 5절 · D11)
```
resolveUuid(relPath)                          — 등록·적재 시점 전용
├─ 1. 원장의 path 필드 스캔 -> 히트면 그 항목의 키(uuid)
└─ 2. 미스면 신규 발급: from_namespace(ns, relPath)
      └─ 이 시점 이후 이 값은 다시 계산되지 않음 (원장 밖 deck 은 파생만)
```

**선택 근거**: 난수여도 되지만 파생이면 원장이 유실되거나 같은 경로로 재등록해도 같은 값이 나온다. 기존 v5 발급과 같고 네임스페이스 입력만 절대경로 → 상대경로다.

**주 조회는 uuid 직조회다** (D24 개정) — 모듈·스탬프·`activeModel` 이 uuid 로 원장 항목을 O(1) 로 찾고 `path` 필드로 파일에 닿는다. path 방향 스캔은 위 등록 멱등 판정과 원장 유실 폴백에서만 쓴다. 원장이 프로젝트당 한 자리수라 선형 스캔으로 족해 별도 인덱스를 두지 않는다.

#### 핵심 시그니처
```cpp
QString resolveUuid(const QString& relPath);   // 원장 path 스캔 우선, 미스 시 v5 파생 1회 (원장 밖 deck 은 쓰지 않음)
bool DashRwSession::open(const QString& filePath, const QString& contentUuid);
```
