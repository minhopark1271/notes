# #553 DashAsyncJobRunner: 콜백 3개를 준비/실행/완료 훅 구조로 재구성한다

## 현상

`DashAsyncJobRunner::run()` 이 위치 인자 람다 3개를 받는다 (`controller/async/DashAsyncJobRunner.h:48-50`). 문제 셋.

**1. 호출부가 안 읽힌다.** `run(work, onSuccess, onFailure)` 는 위치로만 구별된다. 슬롯이 늘면 더 나빠진다.

**2. 준비 단계에 슬롯이 없어 흩어져 있다.** 유일한 실호출부에서 `dataPath` 추출·동기/비동기 판정·조기 반환(`view/DashResultsAnalyzerWidget.cpp:3552-3562`)과 `QPointer` 확보·클로저 조립(`:3565-3574`)이 전부 `run()` **바깥**에 있다. 로직을 Job 단위로 쪼개려면 이것이 슬롯이어야 한다.

**3. `onSuccess`/`onFailure` 분기가 실제 호출부와 안 맞는다.** 그 호출부는 양쪽에서 같은 `buildAndShow()` 를 부른다(`:3583-3590`). 프리페치 실패는 동기 경로로 떨어지는 것이지 분기가 아니기 때문이다.

## 기대

`UI조작 → 준비 → 비동기실행 → 결과` 를 `비동기작업준비 → 비동기작업 → 비동기실행결과` 슬롯으로 고정한다.

```cpp
/// preExecution 이 런너에게 주는 지시. 결과 보고가 아니라 분기 결정이다.
enum class DashJobPreparation
{
    Proceed,        ///< execution 을 돌린다
    SkipExecution,  ///< execution 을 건너뛴다 (→ Job::State::Skipped)
    Abort,          ///< 그만둔다 (→ Job::State::Aborted)
};

/// GUI 스레드. 검증·스냅샷·페이로드 조립. UI 차단과 단일 슬롯 게이트를 지난 뒤 돈다.
using DashJobGuiStep = std::function<DashJobPreparation()>;

/// 워커 스레드. 위젯·VTK 렌더 객체·GUI 전용 싱글턴을 만지지 마라.
using DashJobWorkerStep = std::function<DashJobResult()>;

/// GUI 스레드. 어떤 상태로 끝나도 반드시 불린다 — 취소·중단 포함.
using DashJobGuiFinish = std::function<void(Job::State, const QString&)>;

struct DashAsyncJobHooks
{
    DashJobGuiStep    preExecution;   ///< 비우면 Proceed 로 친다
    DashJobWorkerStep execution;      ///< 필수
    DashJobGuiFinish  postExecution;  ///< 필수
};

QUuid run(DashAsyncJobHooks hooks);   // 인자 3개 → 구조체 1개
```

C++23 이라 designated initializer 로 호출부가 스스로를 설명한다.

```cpp
runner.run({
    .preExecution  = [&]{ ... return DashJobPreparation::Proceed; },
    .execution     = [path]{ ... return DashJobResult::ok(); },
    .postExecution = [self](Job::State state, const QString& reason) { ... },
});
```

### 스레드 어피니티는 타입이 진다

슬롯마다 스레드가 고정(`pre`=GUI, `execution`=워커, `post`=GUI)이므로 런타임 필드로 들고 있지 않는다. 필드로 두면 `Worker→Main→Worker` 처럼 blocking bridge 또는 future 체인이 필요한 조합까지 표현되고, 그 경우 `drainAll()` 이 GUI 스레드에서 막혀 있는 동안 워커가 GUI 를 기다려 교착한다. alias 이름과 `Q_ASSERT` 로 충분하다.

`pre` 와 `execution` 은 반환 타입이 실제로 다르므로(`DashJobPreparation` vs `DashJobResult`) 혼용이 타입으로 막힌다. 슬롯별 래퍼 구조체는 필요 없다.

### Job::State 확장

```cpp
enum class State
{
    Pending, Running, Succeeded, Failed,
    Skipped,    ///< 할 일이 없다고 판단해 실행하지 않았다. 실패가 아니다
    Aborted,    ///< 시작 전에 그만뒀다
    Cancelled,
};
```

`setState` 의 터미널 락 조건에 둘을 추가한다. 이름을 일반어로 두는 것은 `Job` 이 `ProcessJob` 과 공유하는 기반이라서다 — 둘 다 프로세스 작업에도 뜻이 통한다(산출물이 이미 최신이면 `Skipped`, 실행 파일이 없으면 지금 `Failed` 인 `ProcessJob.cpp:61` 이 `Aborted`).

**`DashJobResult` 는 바뀌지 않는다.** execution 의 결과는 성공/실패 둘뿐이라 `bool success` 가 정직하고, 단계 정보는 `Job::State` 가 진다. `postExecution` 이 `Job::finished` 와 시그니처가 같아져 런너가 변환 없이 그대로 넘긴다.

값 추가로 깨지는 곳은 없다. `Job::State` 소비자가 전부 `== Job::State::Succeeded` 한 줄 비교이고 exhaustive switch 가 하나도 없다 — `controller/DashTopOptPostprocessRunner.cpp:54`, `model/DashModelBuilder.cpp:677`, `model/DashModelBuilderMCU.cpp:369`, `model/DashModelRunner.cpp:207`, `model/DashOptimizer.cpp:271`·`:346`. 런너의 switch 는 `default: break;` 를 갖고 있다(`DashAsyncJobRunner.cpp:66`).

### 얻는 것 — 동기 분기가 런너 안으로 들어온다

`DashResultsAnalyzerWidget.cpp:3552-3562` 의 조기 반환 블록이 `return DashJobPreparation::SkipExecution;` 한 줄이 된다. `data` 가 박혀 있거나 `.json` 이면 비동기가 필요 없는 것이지 준비 실패가 아니고, `post` 가 `Skipped` 를 받아 플롯을 그린다. 호출부가 한 갈래가 된다.

### 규약 — 데이터는 캡처로 흐른다

페이로드 타입을 일일이 지정하지 않으려고 캡처를 쓴다. 타입이 안 막아주는 자리가 거기 생기므로 규약으로 적는다.

- `execution` — 값 또는 `shared_ptr<페이로드>` 만. QObject 파생·VTK 객체 금지
- `pre`/`post` — GUI 객체는 `QPointer` 로

`pre → execution → post` 가 직렬이고 사이에 제출과 큐 시그널이 끼므로 페이로드 자체는 경합이 없다.

### 반드시 같이 할 것

`preExecution` 은 `run()` 안에서 인라인으로 돈다. 예외를 던지면 GUI 이벤트 루프로 그대로 빠져나가고 **UI 는 막힌 채, 슬롯은 물린 채** 남는다. execution 이 이미 갖고 있는 예외 정규화(`DashAsyncJobContext.cpp:31-40`)를 pre 에도 건다. 같은 모양의 결함이 PR #545 1차 리뷰에서 execution 에 대해 한 번 잡혔다.

### 안 하는 것

- **훅 간 데이터를 시그니처 인자로 넘기기** (`std::function<Out(In)>` 체이닝). 런너 전체가 `In`/`Out` 으로 템플릿화되고 `QHash<QUuid, DashAsyncJobContext*>` 의 타입 소거가 깨진다.
- **슬롯별 래퍼 구조체.** 반환 타입이 이미 다르다.
- **단일 슬롯 반려를 훅으로 흘리기.** 지금은 널 QUuid + 로그이고 훅이 하나도 안 돈다. `run()` 의 계약이 바뀌므로 예약/취소 정책이 정해질 때 같이 본다.

### 위험

공유 기반의 enum 을 넓히므로, 나중에 `ProcessJob` 이 `Skipped` 를 쓰기 시작하면 위 6개 호출부가 그것을 **조용히 실패로 취급한다** (`== Succeeded` 가 거짓이므로). 지금은 아무도 안 쓰니 무해하다. enum 주석에 "Skipped 는 실패가 아니다" 를 적고, `ProcessJob` 에 그 값을 도입할 때 호출부를 같이 본다.
