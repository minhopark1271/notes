# #544 비동기 실행층 도입과 대용량 XML 파싱 워커 이관

- Board status: Done

## 배경

Analyzer 에서 플롯을 그릴 때 대용량 XML 의 I/O 와 파싱이 GUI 스레드에서 돈다. 실측: `26_KU_ILJIN_TensionLink_1-250` 의 `PART-1-1_1_20_PEEQ.xml`(4.1GB)에서 **11.4초** 동안 창이 멈춘다. 그 사이 창 이동·탭 전환이 안 되고 제목에 "응답 없음" 이 붙는다.

이 작업은 두 가지를 한다.

1. **범용 비동기 실행층을 세운다** — 이후 다른 프리즈 지점도 같은 형태로 옮길 수 있게
2. **그 첫 소비자로 XML 파싱을 워커로 보낸다**

목표는 **체계를 준비하는 것**이지 병목마다 비동기를 적용하는 것이 아니다. 소비자는 XML 파싱 하나로 끝낸다.

## 실행층 — `DashAsyncJobRunner`

```
DashAsyncJobRunner (싱글턴, 공개)
  run(work, onSuccess, onFailure) -> QUuid
  isRunning(QUuid) · anyRunning() · drainAll()
  setUiBlockHooks(onBlock, onUnblock)
   └ DashAsyncJobContext : Job        (내부. 헤더에 전방 선언만)
```

- `work` 는 **워커 스레드**, `onSuccess`·`onFailure` 는 **GUI 스레드**. `onSuccess` 만 필수.
- 기존 `controller/async/Job` 을 상태 기계로 쓴다. `Job` 은 State 전이와 terminal lock 만 갖고 실행 기제를 모르므로, 지금은 `QtConcurrent` 로 짓지만 나중에 전용 스레드 파생형으로 바꿔도 공개 표면이 안 바뀐다.
- 의존은 **Qt Core + `Job.h` + 로거**까지다. VTK·DashManager·reader-writer SDK·QtWidgets 에 기대지 않는다. UI 차단이 훅인 이유가 이것이다 — 실제 위젯 조작은 `DashMainWindow` 가 등록한다.

### 한 번에 하나만 돈다

이미 도는 작업이 있으면 `run()` 이 사유를 로그에 남기고 널 `QUuid` 를 돌려준다. work 도 훅도 돌지 않는다.

프리즈가 사라지면 그동안 프리즈가 우연히 직렬화해 주던 재진입이 열린다. **정책을 고르지 않으면 기제의 기본값이 정책을 대신한다.** 고른 것은 "거부" 다 — 취소 수단이 없어 "현재 것을 drop" 은 선택지가 아니고, 큐는 깊이 상한·합치기·대기 중 취소·순서 네 가지를 끌고 온다. 자원별 배제 키도 두지 않았다: 비동기 진입점이 하나인 동안은 쓰이지 않을 일반화다.

### 두지 않은 것

- **`waitFor(QUuid)`** — 소비자가 없고, GUI 스레드에서 부르면 이 축이 없애려는 프리즈 그 자체다. 동기 대기는 종료 경로의 `drainAll` 하나로 족하다.
- **취소 훅** — 실행 기제(`QtConcurrent::run`)에도 reader-writer SDK 에도 취소 수단이 없다. 도달 불가한 표면이었다.
- **종료 시 `contexts_` 회수** — 하지 않는 것이 의도다. `drainAll` 은 future 는 기다리지만 `QFutureWatcher::finished` 는 GUI 큐에 걸린 채 이벤트 루프가 끝난다. 소멸자에서 지우려 들면 `QApplication` 소멸 이후의 QObject 삭제·QThreadPool 정리와 얽힌다.

## XML 파싱 이관 — 캐시를 워커에서 데운다

느린 것은 `DashXmlParser::loadFromXml()` 이다(파일 전체 읽기 + base64 디코딩 + Eigen 할당). 같은 파서의 `extractVariablesFromXml()` 은 첫 샘플만 스트리밍으로 읽어 싸고, `extractAllReducedValues()` 는 이미 로드된 트리만 순회한다.

플롯 팩토리 11개(`buildScatter2DPlot` 등)를 쪼개는 대신 **캐시를 워커에서 데우고 기존 동기 경로가 캐시 적중으로 끝나게** 했다.

```
[워커]  DashDataLoader::prefetchXml(dataPath)   ← 파싱 1회, 캐시 충전
[GUI]   기존 DashPlotRequestHandler::build()    ← 캐시 적중으로 즉시 끝남
        → onPlotWindowReady(container)
```

성립 근거는 `model/analyzer/DashDataLoader.cpp` 의 계약이다 — **한 번의 파싱이 그 파일의 전 변수 × 전 축약(Max/Min/Mean/Std)을 캐시에 심는다.** 요청된 변수만 채우는 것이 아니다. 그래서 워커에서 아무 키로든 한 번 태우면 이후 GUI 가 어떤 변수를 요청하든 적중한다.

**이 설계는 `#410`(PR #515)이 넣은 `DashFileResourceRegistry` 캐시 계약에 얹혀 있다.** 그 계약이 바뀌면 이 변경이 조용히 무효가 되고 파싱이 GUI 로 돌아온다. 테스트가 그것을 고정한다(아래).

결과적으로 `DashPlotWidgetFactory` 와 `DashPlotRequestHandler` 는 **한 줄도 바뀌지 않았다.**

## UI 차단

작업이 도는 동안 사용자 조작을 막고, 살아 있음을 보이는 최소 장치를 넣었다 — 최상단 위젯 `setEnabled(false)` + 상태바 무한 진행바. 러너가 훅으로 부르고 `DashMainWindow` 가 등록한다.

`setEnabled(false)` 는 이벤트 루프를 막지 않는다. 입력 이벤트 배달만 막고 Paint·Timer 는 그대로 가므로 화면은 계속 그려진다.

**진행 문구·취소·창 이동 유지 등 UI/UX 정리는 `#543` 소관이다.** 여기서는 최소 기능만 둔다.
