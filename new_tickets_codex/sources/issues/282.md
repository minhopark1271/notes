### #281 A안 확정 — 본 티켓 델타 1건

- **`morphingSerialPool` 은 `maxThreadCount = 1` 로 유지**(A안). 배경 풀 신설과 무관하다.
- **문서 텍스트 충돌 1곳** — 절은 갈리지만(#280·#281 = 2·3절 격리 규범 / 본 티켓 = 7절), 7절 **소비자 목록**(`:177-180`)은 #281 Phase C·D·E 가 모핑 풀 소비자를 늘리는 자리이고 본 티켓이 배경 풀 항을 더하는 자리다. 같은 문단이라 랜딩 순서에 따라 한쪽이 rebase 로 해소한다.

### #277 에서 전달 — 2건

#277(PR #286) 이 머지됐다. 본 티켓이 선행으로 지목한 **전환 계약 5항목**의 형식이 코드로 섰고(⑴ 페이로드 채널 `shared_ptr<Payload>` · ⑵ 쓰기 소유 GUI 완료 슬롯 · ⑶ 취소 폴링 지점 · ⑷ `ProgressSink` · ⑸ 증명 값 이동), `WorkerJob::Task` 는 `(const std::atomic<bool>&, const ProgressSink&)` 2인자다. 그 위에서 본 티켓에 걸리는 것 2건.

#### ⑴ `Job::progressed` — 본 티켓이 **첫 프로덕션 소비자**다. 회귀 가드 1건 요청

본 티켓 Phase 2 는 "결과는 `shared_ptr<FemParseResult>` out-param, **진행은 `Job::progressed`**" 다. #277 시점까지 `Job::progressed` 의 프로덕션 소비자는 0곳이었다.

#277 자체 리뷰에서 이 채널의 결함 1건을 고쳤다 — `WorkerJob` 의 relay 연결 해제가 **객체 소멸에만** 의존해, `cancel()` 이 상태를 터미널로 옮긴 뒤에도 `progressed`/`logged` 가 계속 방출됐다. 즉 **`Job::finished` 뒤에 `progressed` 가 뜰 수 있었다.** `WorkerJob::detachRelay()` 를 신설해 `cancel()`·`onWatcherFinished()` 의 `setState` **뒤에** 부르는 것으로 닫았다.

```cpp
// controller/async/WorkerJob.cpp (머지됨)
void WorkerJob::detachRelay()
{
    if (m_relay) {
        disconnect(m_relay.get(), nullptr, this, nullptr);
    }
}
// cancel() · onWatcherFinished() 모두 setState 직후에 호출한다.
// 호출을 setState **앞**으로 옮기면 정상 완료 통지까지 끊긴다 — 순서가 계약이다.
```

**요청**: 그 순서를 잡는 회귀 테스트가 없다. `setState` 앞으로 옮겨도 현재 테스트는 전부 통과한다. 본 티켓이 `tests/tst_worker_job.cpp` 를 이미 참조하고(`:262` 실행 중 파괴 검증) 진행률을 실제로 소비하는 첫 티켓이므로, Phase 2 에 테스트 1개를 얹는 것을 제안한다 — *취소 후 도착한 sink 통지가 `finished` 뒤에 방출되지 않는다*.

없으면 사용자에게 보이는 증상은 "파싱을 취소했는데 진행률이 계속 올라간다" 다. 본 티켓의 "정밀 취소 미구현"(다이얼로그를 닫아도 워커는 완주) 정책과 겹쳐 관측 가능성이 높다.
