`stpPath` 만 실어 보내도 부족하다. 브로드캐스트 핸들러가 **남이 낸 요청을 대신 받기** 때문에 비교 기준을 만들 수 없다.

|---|---|---|
| `view/DashModelRunnerWidget.cpp:454` | 자기 자신 `:230` | O |
| `view/DashMainWindow.cpp:2284` (loadPrt) | 자기 자신 `:277` | O |

### 부채가 자라는 방식
소비자가 1종(대화형)에서 2종(대화형+배치)이 되자 시그널이 2종 증설됐다. 표면이 소비자 수에 비례해 늘어나는 구조다. `nxCadParametersJson` 도 식별자 없는 상시 브로드캐스트라 동일 계열의 결함이다.

### 같은 원칙, 다른 증상 — 모핑 경로(#260)와의 대조

증상 기준으로는 하자 4종 중 어느 것도 모핑 경로에 그 형태로 없지만, **원칙 2종은 성립한다.** 이것이 #260 을 본 티켓의 선례로 삼는 근거다.

## Technical Details

### 초판 철회 — 사실이 아닌 근거 2건 (재실측)

- **[철회] "빈 commandId 로 배치 실패가 대화형 모달로 오라우팅된다"**: 초판은 `DashExtensionProcess` 의 실패 방출 중 `:346`(데몬 조기 종료)·`:359`(프로세스 에러) 가 `m_currentCommandId` 를 비운 뒤라 빈 문자열을 싣는다고 적었다. **두 시점 모두 clear 전에 `id` 를 지역 변수로 캡처했으므로 당시에도 사실이 아니다.** 현재도 성립하지 않는다 — 실패 방출 3곳 전부 실제 commandId 를 싣는다:
  - `drainCommands` in-flight (`DashExtensionProcess.cpp:254`) — `inFlightId` 를 `:243` 에서 캡처, clear 는 `:250`
  - `drainCommands` 큐 잔여 (`:257`) — 각 `PendingCommand` 자신의 `commandId`
  - `handleDaemonLine` 데몬 ERROR 응답 (`:421`) — `id` 를 clear 전 캡처

  이 근거로 티켓을 정당화하지 말 것. 폴백 규약이 필요한 이유는 아래 빈 경로 케이스다.
- **[정정] `sendCommand` 3번째 인자**: 초판의 `expectedOutputs` 가 아니라 `filesToDelete` — 송신 직전 삭제 목록이다 (`DashExtensionProcess.h:119-120`, 삭제 실행 `DashExtensionProcess.cpp:346-347`). 태그를 넣을 자리가 `commandId` 뿐이라는 결론은 그대로다.

### 태그 분해 폴백이 필요한 실제 케이스
`outputStpPath` 가 빈 호출이면 commandId 가 `"loadPrt:"` 로 경로 필드 없이 조립된다 — 두 enqueue 가 이 경우를 이미 분기로 다룬다(`DashSolverNxCad.cpp:145`·`:164` `outputStpPath.isEmpty()`). 그 상태로 완료가 오면 `QFileInfo::exists("")` 가 false 라 성공이 실패로 뒤집힌다. **동사만 있고 경로가 빈 commandId, 그리고 진행 커맨드가 없는 시점의 통지**에 대한 폴백을 명시한다 (권장: 어느 구독자에게도 귀속시키지 않고 로그만).

### 실패 fan-out 이 늘었다 (#212 산물 — 신규 고려 사항)
`drainCommands`(`DashExtensionProcess.cpp:240-259`) 는 데몬 1회 사망에 in-flight 1건 **+ 큐 잔여 N건**을 각각 `commandFailed` 로 통지한다("무음 폐기 금지" — `DashExtensionProcess.h:198`). #212 이전 `onDaemonFinished` 는 `m_commandQueue.clear()` 로 큐를 조용히 버려 통지가 1건이었다. → 대화형 요청 2건이 큐에 쌓인 상태(.prt 클릭 직후 Preview 등)에서 기동이 실패하면 **모달이 2회** 뜬다. 태그 필터는 이 fan-out 을 줄이지 않는다 — 배치 경로만 경로 가드로 1건으로 수렴하고, 대화형 N회는 현행 동작으로 유지한다(축소는 범위 밖).

### `nxCadParametersJson` 태그는 실측 없이 붙는다 — 초판의 선결 조건 해제
초판은 "DOE 배치의 `updatePrtGeometry` 가 파라미터 JSON 을 출력하는가" 를 NX 환경 실측 후 진행으로 걸어 두었다. #212 가 `currentCommandId()` 를 public 으로 노출해(`DashExtensionProcess.h:122-124`, 주석: "원시 stdout 을 파싱하는 소비자가 어떤 명령의 출력인지 상관시킬 때 쓴다") **실측 없이 태그를 실을 수 있다** — 출력 여부와 무관하게 같은 필터로 막히므로 선결 조건이 아니다. 선례로 `DashModelBuilderMCU.cpp:173` 이 이미 이 상관 패턴을 쓴다.

순서 근거: `tryParseJsonFromLine` 은 `outputLine`(`DashExtensionProcess.cpp:386`) 경로에서 돌고, 이는 `[FINISHED]` 판정(`:404`)보다 **먼저**라 커맨드 출력으로 들어온 JSON 은 `m_currentCommandId` 가 살아 있는 동안 파싱된다. 남는 실측 항목은 하나 — **JSON 이 `[FINISHED]` 뒤 라인으로 오는 경우** 태그를 못 얻어 기하 파라미터 표 갱신이 끊긴다. 회귀 확인 대상(AC).

### 구분자 `:` 는 실제로는 무해 — 그래도 `|` 로 간다
`"updatePrt:C:\dir\a.stp"` 를 `indexOf(':')` 로 자르면 **첫 콜론이 항상 동사 구분자**(동사에 콜론이 없으므로)라 드라이브 문자 콜론은 두 번째로 밀린다. 현행 파싱은 정확하다. 다만 필드를 3개로 늘리면 `split(':')` 형태를 쓰게 되어 그때부터 실제로 깨지므로, 확장 시 `|` 채택은 유지한다. *(참조: "Windows 경로 때문에 현재 파싱이 이미 틀렸다"는 서술은 오류 — 그 이유로 이 티켓을 정당화하지 말 것.)*

### `loadPrtFailed` 축소의 파급 (놓치기 쉬움)
이 시그널을 loadPrt 전용으로 좁히면, 현재 update 실패 모달을 담당하는 `DashMainWindow:271` 이 update 실패를 받지 못한다. → `updatePrtGeometryFailed` **신규 구독을 추가**해야 대화형 update 실패 모달이 유지된다 (Phase 2).

### 주석·서술 정합 (누락되기 쉬움)
시그널명·모드 플래그가 사라지면 함께 고쳐야 하는 서술 — `DashSolverNxCad.h:41-45`(배치 전용 시그널 주석) · `:73-74`(`commandId format:` 규약) · `DashSolverNxCad.cpp:216-217`(`emitFailure` 주석) · `DashJobRunner.cpp:2536-2537`("실패는 케이스별로 batchFailed 로 온다") · `:2723-2725`("그 커맨드가 batchFailed 로 통지되니") · `DashOptimizerWidget.cpp:1625-1626`(구독 경로 설명). AC 의 grep 이 `updatePrtGeometryBatch` 만 보면 `batchFailed`·`batchCompleted` 단독 문자열은 걸리지 않는다 — 패턴을 넓혀 둔다.

### 태그 enum 은 메타타입 등록이 **필수** (#213 재검증에서 추가)
구독 9곳 중 `DashJobRunner` 의 4곳이 **`Qt::QueuedConnection` 명시**다 — `:2307`(json) · `:2312`(loadPrtCompleted) · `:2625` · `:2628`. 큐드 연결은 인자 타입이 메타타입으로 등록돼 있어야 하고, 네임스페이스 스코프의 맨 `enum class` 는 등록되지 않는다. 그대로 두면 **컴파일은 통과하고 런타임에 `QObject::connect: Cannot queue arguments of type 'NxCadRequester'` 로 슬롯이 아예 안 불린다** — DOE 배치가 워치독 타임아웃까지 멎는다.

→ `NxCadRequester` 를 `DashSolverNxCad` **클래스 내부에 선언하고 `Q_ENUM(NxCadRequester)`** 를 붙인다. Qt 5.15 에서 `Q_ENUM` 은 `QMetaType` 등록까지 겸하므로 별도 `qRegisterMetaType` 호출이 필요 없다. 선례 — `controller/async/Job.h:25` `Q_ENUM(State)`, 그리고 이 클래스는 이미 `enum class JobType` 을 내부에 둔다(`DashSolverNxCad.h:58`). 호출부 표기는 `DashSolverNxCad::NxCadRequester::Batch`.

### 컴파일 안전 / 런타임 위험
시그널 시그니처 변경은 PMF `connect` 라 불일치가 **컴파일 에러**로 잡힌다. 실제 위험은 컴파일러가 못 잡는 둘 — (1) 위 메타타입 미등록으로 큐드 연결 4곳이 런타임에 죽는 것, (2) 필터 조건을 잘못 걸어 대화형 기능(미리보기 STEP 로드 · 파일테이블 등록 · 실패 모달 · 기하 파라미터 표 갱신)이 **조용히 죽는 것**. 둘 다 NX 설치 환경에서 수동 확인이 필요하다. 비용의 대부분이 코드가 아니라 회귀 확인이다.

### #213(W10-d) 와의 관계 — 교집합 1건
#213 은 `docs/ThreadingContract.md` 와 `DASH_ASSERT_MAIN_THREAD` 를 세웠으나 본 티켓 대상 8파일 중 어느 것도 만지지 않았고(`view/DashModelRunnerWidget.cpp` 은 본 티켓 관심 라인 밖), NX CAD 파사드를 워커로 옮기지도 않았다. ## Design

### 현황 분석
- 파사드 표면과 구독 관계는 Background "현황" 표 참조. 신설할 인프라는 없다 — 상위 클래스가 이미 식별자를 갖춘 일반형이므로 **정보를 버리지 않는 것**이 과제다.
- `commandId` 규약은 이미 `"<verb>:<stpPath>"` 로 존재하고 `sendCommand(commandLine, commandId, filesToDelete)` 3인자 형태다. 태그를 넣을 자리는 `commandId` 문자열이며 상위 클래스 변경은 불필요.
- 요청-응답 짝이 아닌 stdout 부산물(`nxCadParametersJson`)도 #212 가 공개한 `currentCommandId()`(`DashExtensionProcess.h:124`) 로 진행 커맨드에 상관시킬 수 있다 — 파사드에 새 상태를 두지 않는다.

### 대안 비교

| 방안 | 핵심 | 장점 | 단점 |
|---|---|---|---|
| **A. 요청 태그 왕복 (commandId 필드 확장)** | `enqueue*` 가 태그를 받아 `commandId` 에 싣고, 완료/실패 시 그대로 되돌려줌 | 파사드 무상태(모드 플래그 소멸) · 요청 단위 정확 · 상위 클래스 무변경 · 소비자 N 종 확장 가능 | `commandId` 규약·파싱 변경 · 구독자에 필터 추가 |
| B. `stpPath` 만 보존 | 실패 시그널에도 경로를 실어 구독자가 자기 요청 경로와 비교 | 파사드 변경 최소 | **미완결** — `DashMainWindow:278`·`:271` 은 요청자가 아니라 비교 기준이 없다. 요청자에게 구독을 넘기려면 MainWindow 소유 3D 뷰 렌더링 호출 경로를 새로 뚫어야 해 더 침습적 |
| C. 현행 유지 (배치 전용 시그널) | #210 상태 그대로 | 추가 작업 0 | 소비자마다 시그널 증식 · `m_batchMode` 잔존 · 계층 누출 유지 |
| D. 파사드에 `QHash<commandId, tag>` 보관 | 태그를 문자열에 싣지 않고 파사드 상태로 관리 | `commandId` 규약 불변 | 파사드가 다시 상태를 가짐(정리 시점·누수 관리) — 모드 플래그를 맵으로 바꾼 것에 가깝다 |

### 선택 — 방안 A (요청 태그 왕복)

**선택 근거**: 하자 4종이 모두 "요청 식별자를 버린다" 는 한 원인에서 파생되므로, 원인 지점 하나(`commandId` 보존)를 고치면 함께 해소된다. 파사드가 무상태가 되어 배치 중 대화형 요청이 끼어드는 오억제도 구조적으로 불가능해진다. 상위 `DashExtensionProcess` 는 손대지 않는다.
**기각된 대안**: B 는 브로드캐스트 핸들러를 못 다뤄 미완결 · C 는 부채 유지 · D 는 상태를 형태만 바꿔 이관.

**시그널 형태 — 대칭 4종 선택**: 성공/실패를 경로별로 대칭 배치해 대칭 붕괴와 `loadPrtFailed` 명칭 부정확을 동시에 해소한다. 통합 1종(`updatePrtGeometryFinished(tag, path, ok, detail)`)도 검토했으나 슬롯 안에 `if (ok)` 분기가 생기고 Qt 관용(성공/실패 분리 방출)과 어긋나 기각. `nxCadParametersJson` 은 요청-응답 짝이 아니므로 이 대칭 집합에 넣지 않고, 태그만 얹어 필터 대상에 편입한다.

#### 구독자 필터 규약
- 대화형 구독자: 슬롯 진입부에 `if (requester != DashSolverNxCad::NxCadRequester::Interactive) return;` 한 줄 (클래스 내부 enum 이라 외부 호출부는 클래스 한정자를 붙인다). 자기 요청 경로를 아는 `DashModelRunnerWidget` 은 기존 경로 비교 병행 유지
- 배치 오케스트레이터: `if (requester != Batch || stpPath != m_stpBatch.current.stpPath) return;` — #210 의 귀속 가드를 태그 기준으로 승계. 실패 슬롯도 같은 형태로 통일한다 (현행 `onStpCaseFailed` 는 `runKey.isEmpty()` 만 보고 경로를 확인하지 못한다 — `DashJobRunner.cpp:2689`).
- 상시 구독 금지 원칙([#194](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/194-1-async-execution-patterns) 4절) 유지 — 배치는 시작 시 connect, 종료 시 disconnect.
