## Original Request
> rw-actor 변경사항을 async-execution으로 병합하는 계획을 issue로 발행하고, wiki에 작성했던 계획 1, 2 드래프트 및 계획 통합문서는 제거.

## Goal

`feat/rw-actor` 4커밋을 `refactor/async-execution` 에 흡수해 **단일 브랜치 좌표를 세운다.** 완료 시점에 RW DLL 배제는 전용 스레드 감금 1벌로 통일되고, DOE 배치는 GUI 와 분리된 전용 `DashRwSession` 에서 돌며, async 의 워커화(`PrepareBatch`/`RunOneSample`·`MorphingGate`·장부) 는 원복 없이 전량 존치한다.

## Background

두 브랜치가 분기점 `7d6a987` 에서 각각 8커밋·4커밋으로 갈렸고, 같은 문제(모핑 실행 중의 상태 오염)에 서로 다른 층의 답을 냈다. 9개 파일에서 만난다.

```
7d6a987  (merge-base)
├─ refactor/async-execution @ 0320683   +8커밋 · 56파일 +6954/-2841 · 테스트 6종 신설
│                                        워커화 축 — 직렬 풀 3종 · 게이트 2종 · 장부 · 종료 4단계
└─ feat/rw-actor            @ 66c126c   +4커밋 · 20파일 +2259/-1419
                                         RW 격리 축 — 세션 추출 · 배치 전용 세션 · actor 전용 스레드
```

두 방향은 대립하지 않는다. rw-actor 는 **무엇을 격리하는가**, async 는 **어떻게 실행하는가** 에 답했다. 겹치는 축은 하나뿐이고 거기서는 rw-actor 를 택한다.

병합 전에는 두 축의 후속 작업 어느 쪽도 좌표를 확정할 수 없다. #280 · #281 이 각각 "브랜치 병합이 선행" 이라 적어 두었으나 소유자가 없었고, 본 티켓이 그 선행을 소유한다. 두 티켓은 병합 결과에 맞춰 개정한다 (`Related` 의 인계 목록).

`origin/refactor/async-execution` 은 0/0 동기 상태이며, 좌표는 2026-08-20 실측이다. 착수 시 `git merge-tree --write-tree --merge-base` 로 재실측한다.

## Technical Details

### as-is

- **배제 기제 2벌 미완**: async 는 `DashPools::rwSerialPool()`(`ThreadPools.cpp:30`) 을 세웠으나 **실 소비자 0건** — 참조는 정의 · 배수(`:56`) · `ThreadPools.h:19` 주석 · 테스트 2곳(`tst_worker_job.cpp:173`·`:296`) 뿐이고, 나머지 절반인 `RwGate` 는 미구현이다. rw-actor 는 `DashRwActor` 전용 스레드 감금으로 워커·GUI 양축을 이미 덮었다.
- **배치가 GUI 세션을 공유**: `DashMorphingRunContext.h:45` 의 `DashAnalysisModelContextPtr analysisContext` 를 `DashJobRunner::runNextMorphSample` 이 값 캡처해(`DashJobRunner.cpp:1388`) `morphingSerialPool` 워커에 태운다. 원복 장치(`MeshInjection`·`ConditionDvInjection`) 로 되돌리는 구조.
- **변이 창 키가 canonical path**: `DashContextMutationScope`. 실 소비자는 `DashConditionParameterization.cpp:347` 1곳.
- **사유 통로는 완성**: `captureReason`(`DashMorphingDoeExecutor.cpp:344`) → `DashSampleResult`(`DashMorphingRunContext.h:49`) → `WorkerResult`(`DashJobRunner.cpp:1403`) → `setState`(`WorkerJob.cpp:121`) → 장부. rw-actor 의 판정을 태울 통로가 이미 있다.
- **`ThreadingContract` 는 병합 시 자기모순**: rw-actor 가 2절("RW DLL 실행 스레드" 신설)·3절, async 가 7절을 각각 고쳐 자동 병합이 통과하지만 내용이 충돌한다.

### to-be

- **RW DLL 배제 = 전용 스레드 감금 1벌.** `rwSerialPool` 삭제, `RwGate` 는 세우지 않는다 (#280 Phase 3 폐기).
- **배치 전용 세션.** `DashMorphingRunContext` 의 컨텍스트 필드가 `DashRwSessionPtr session` 이 되고, 실행기는 GUI 층에 컴파일 타임으로 접근할 수 없다. 원복 장치 전량 소멸.
- **변이 창 키 = 세션 객체.** `DashRwSession::MutationScope(session)` · `session->isMutating()`.
- **타입이 두 증명을 동시에 요구.** `RunOneSample(const MorphingGate::Witness&, ..., const DashRwSessionPtr&)`.
- **조용한 폴백 3종이 샘플 실패로 승격** (`f63bc5d`).
- **`ThreadingContract` 7절 정정** — 두 직렬 풀 · 게이트 두 벌 · 배제 기제 목록에 감금 추가.

### not-to-be

| 항목 | 이유 |
|---|---|
| async 워커화 원복 | **없음.** `PrepareBatch`/`RunOneSample` · `DashJobRunner` · `MorphingGate` · `DashBatchLedger` · `AppShutdown` · view 4파일 · 테스트 6종 전량 존치 |
| `AppShutdown` 에 RW 스레드 축 추가 | **추가하지 않는 것이 답.** ⑶ 앞은 교착(워커가 `invokeOnActor` 의 `BlockingQueuedConnection` 대기 중), ⑶ 뒤는 `DashRwActor` `Holder` 소멸자가 이미 `quit`+`wait`, ⑷ `_Exit(1)` 은 의도된 포기 |
| `DashAnalysisModelContext` 의 RW 위임 래퍼 삭제 | GUI 표현 경로가 계속 쓴다 |
| `DashContextMutationScope` 완전 소멸 | 러너·옵티마이저 전용 세션 이주가 선행. #281 Phase B2 존치 |
| `ThreadingContract` 3절 격리 규범 전면 재작성 | 새 교리 집필. 본 티켓은 7절 정정까지 → #280 Phase 4 로 축소 이관 |
| `get_symbol_detail` 캐시 승격 · `tests/rw/` 하네스 · 레지스트리 빈 키 폴백 · 단건 모핑 워커화 | 신규 작업. #280 · #281 소유 |

경계 기준 하나 — **두 브랜치를 합친 직접 귀결이면 본 티켓, 새로 만드는 것이면 후속.**

### 선택 — 방안 B

**선택 근거**: 기제 비용이 가장 낮다. fast-forward 로 끝나 force-push 가 없고, 머지된 PR 8건의 커밋이 살아 있고, 해소 단계가 C 의 절반이다. C 의 유일한 실질 이점(`f63bc5d` 무분할)은 **커밋 ③ 을 쪼개지 않음**으로써 B 에서도 취한다. `feat/rw-actor` 자체는 건드리지 않고 별도 통합 브랜치에서 재작성하므로, C 가 주장하는 "다른 저자 커밋 보존" 의 실효는 히스토리 저작 표시 수준이다.

**기각 사유** — A: 리뷰 단위가 커지고 해소 내용은 B 와 동일. C: force-push + PR 커밋 orphan + 해소 단계 2배. D: dev 오염만 추가.

```bash
git switch -c integration/rw-into-async feat/rw-actor
git rebase --onto refactor/async-execution 7d6a987
```

### 축별 채택 판정

같은 질문에 다른 답을 낸 축은 11개 중 **1개뿐**이다.

| 축 | rw-actor | async | 채택 | 근거 |
|---|---|---|:---:|---|
| RW DLL 배제 기제 | 전용 스레드 감금 | `rwSerialPool` + `RwGate`(계획) | **rw-actor** | **유일한 정면 경쟁.** 감금 1벌이 워커·GUI 양축을 덮는다(풀=워커축, 게이트=GUI축으로 2벌 필요). 게이트는 진입점 전수 등록을 요구. 구현 완료 vs 미구현 |
| 배치↔GUI 세션 격리 | 전용 세션 | 공유 + 원복 장치 | **rw-actor** | 원복은 세 구멍을 못 막는다 — 워커가 GUI 표시 deck 변이 · `getPartData` alias 가 렌더 루프와 경합 · 제자리 정밀도 변환은 창 밖이라 원복 대상도 아니었다 |
| 변이 창 키 | 세션 객체 | canonical path | **rw-actor** | 전용 세션 도입 순간 경로 키는 오답 — lost update 가 물리적으로 불가능한데도 같은 deck 의 GUI 편집을 계속 막는다 |
| 조용한 폴백 3종 | 실패 승격 | 유지 | **rw-actor** | 원복이 없으면 스킵은 "직전 샘플 값으로 export" = 성공처럼 보이는 틀린 deck |
| 레지스트리 반복당 누수 | 임시 세션 | — | **rw-actor** | 무경쟁. per-iteration 출력 deck 은 캐시 히트 0인데 모듈 인스턴스만 쌓였다 |
| 배치 실행 구조 | `Execute` 단일 루프 | `PrepareBatch`+`RunOneSample`+샘플 Job | **async** | rw-actor 는 이 축에 결정을 내리지 않았다 |
| 모핑 DLL 배제 | — | `MorphingGate` Claim/Reservation | **async** | 세션 격리는 RW 축만 해결. 모핑 DLL 은 프로세스 전역 1벌 |
| 앱 종료 순서 | — | `AppShutdown` 4단계 | **async** | 무경쟁. RW 축 부재는 결함이 아니다 (`not-to-be`) |
| `DashDoeIoPaths` 위치 · BOM | — | `DashMorphingRunContext.h` · BOM 제거 | **async** | 무경쟁 |
| 완결 판정·사유 전파 | `statusCallback` 로그 | `DashSampleResult` → `WorkerResult` → 장부 | **합집합** | 층이 다르다 — rw-actor 는 *어디서* 실패로 판정할지, async 는 *어떻게* 나를지 |
| 계약의 타입 강제 | `DashRwSessionPtr` | `Witness` protected 생성자 | **양쪽** | 합치면 두 증명을 동시에 요구 |

**격리·정책 5축 rw-actor, 실행 구조·배제 보조 4축 async, 완결 판정 1축 합집합, 타입 강제 1축 양쪽.**

> `Execute` 훅에서 async 골격을 택하는 것이 rw-actor 를 버리는 것이 아니다. rw-actor 가 그 함수에 가한 변경의 전량은 시그니처 1행 · 가드 1행 · 루프 내 호출 인자 2곳이고, 루프 구조·경로 조립·`runKey` 생성·conditionOnly 분기는 한 줄도 건드리지 않았다. 그 4곳의 주장은 `PrepareBatch`/`RunOneSample` 위에서 그대로 관철된다. `DashManager.cpp` 도 같다 — rw-actor 의 변경 전량이 `registry.getOrLoad` → `DashRwSession::open(canonicalPath, ioPaths.configsDir)` 이다.

### 최대 위험 — 컴파일러가 판정을 강제하지 않는다

**`controller/DashMorphingRunContext.h:45` 이 유일한 조용한 실패 지점이다.**

```cpp
struct DashMorphingRunContext {
    ...
    DashAnalysisModelContextPtr analysisContext;   // → DashRwSessionPtr session
};
```

이 파일은 async 가 신설했고 `feat/rw-actor` 는 존재조차 모른다. **어느 rebase 방향에서도 충돌로 드러나지 않는다.** 그런데 이 필드가 격리 설계의 정본이다 — 이 필드가 컨텍스트인 한 워커가 GUI 공유 RW 모듈을 변이한다.

rw-actor 의 `DashAnalysisModelContext` 는 RW 메서드를 표면에 남긴 채 `m_rw->` 로 위임한다.

```cpp
vtkUnstructuredGrid* DashAnalysisModelContext::getPartData(const QString& partName) const {
    return m_rw->getPartData(partName);
}
```

따라서 async 의 `analysisContext->getPartData(...)` 는 **rebase 후에도 그대로 빌드된다. 빌드 green 이 격리 성립의 근거가 되지 않는다.** 조용히 회귀하는 것 — 배치가 GUI 공유 세션 변이(격리 무효) · per-sample 원복 의존 부활(GUI 편집 lost update) · `66c126c` 의 VTK aliasing 안전 전제("배치는 자기 세션에서만 돈다") 붕괴.

남은 보호 장치가 둘 다 이것을 막지 못한다.

| 장치 | 막는 것 | 이 경로를 막는가 |
|---|---|:---:|
| `MorphingGate` | 모핑 DLL 진입점 | X — 렌더 루프·GUI 의 RW 읽기는 대상 밖 |
| `DashContextMutationScope` | 실 소비자 `DashConditionParameterization.cpp:347` 1곳 | X — 셀 편집 하나만 거부 |

**대응: 이 한 줄을 가장 먼저 바꾼다.** 그러면 나머지 소비 지점(`ctx.analysisContext` 3곳 등)이 전부 타입 오류로 드러난다. 반대로 충돌 9훅을 "구조도 타입도 async" 로 일관 해소하면 빌드는 통과하고 레이스만 남는다. 자동 검출에 기대지 않는다.

**폐기** — rw-actor 쪽 껍데기. 커밋 ③ 충돌 해소의 실질이다.

### 자료 구조 · 세션 수명

**open 지점 = `DashManager::PrepareDoeMorphingBatch`** (GUI 스레드, `DashManager.cpp:994`). 그 함수가 `MakeMorphingInputSnapshot()` 과 `DashProjectManager` 를 이미 만지므로 GUI 스레드가 확정이고 `ioPaths.configsDir` 도 바로 위에서 해석돼 있다. 기존 `registry.getOrLoad(canonicalPath)` 자리의 1:1 치환.

```cpp
const DashRwSessionPtr session = DashRwSession::open(canonicalPath, ioPaths.configsDir);
if (!session) { return reject(...); }
auto runContext = executor->PrepareBatch(samples, partConfigPath, ioPaths, session, ...);
```

배치당 세션 1개가 샘플 전체에 유지되는 근거 — `runNextMorphSample` 이 `DashMorphingBatchHandle` 을 **값으로 캡처**하므로(`DashJobRunner.cpp:1388`) 각 워커 태스크가 같은 세션의 `shared_ptr` 사본을 든다. 러너가 `m_morphBatch` 를 비운 뒤에도 태스크의 세션은 살아 있다. `morphingSerialPool()` 이 직렬이고 모든 RW 호출이 RW 스레드로 마샬링되므로 동시 접근이 없다.

`MutationScope` 는 rw-actor 도 async 와 같은 두 지점에 두었다 — `ExecuteOneSample`(async 943 / rw-actor 842) · `ExecuteOneSampleConditionOnly`(1020 / 915). 1:1 치환이며 별도 판단이 필요 없다. `mutationDepth` 가 `std::atomic` 이라 워커 개시와 GUI 조회의 교차도 안전하다.
