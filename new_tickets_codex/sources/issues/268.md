# #268 STP 타임아웃 후 데몬 무응답 시 A 배치 영구 정지 — 워치독 재무장 부재

## Goal

STP 케이스 타임아웃 후 NX CAD 데몬이 응답하지 않을 때 A(wbpj) 배치가 `Stp` phase 에 영구 정지하는 것을 막는다.

> **좌표 기준**: `refactor/async-execution` @ `3666dd7`

## Background

> **범위 축소 (2026-08-18).** 초판은 `startNextMotionLauncher:777` 과 `onStpCaseTimeout` 무전이 2건을 담았으나, 코드 확인 결과 **둘 다 결함이 아니었다.** 아래 "무효 판정" 참조. 실제로 남는 위험 1건으로 재정의한다.

## Technical Details

`onStpCaseTimeout`(`DashJobRunner.cpp:3006-3024`)은 케이스 전이를 하지 않고 데몬만 세운다. 이것은 **의도된 설계**다 — 주석이 명시한다.

> 데몬 큐는 직렬이라 멈춘 커맨드 뒤에 다음 케이스를 넣어도 실행되지 않는다. 데몬을 세우면 그 커맨드가 `batchFailed` 로 통지되니, 케이스 실패 회계는 그 통지 하나가 맡는다(여기서 직접 전이하면 이중 계상). 재기동은 다음 케이스의 enqueue 가 맡는다.

문제는 **그 전제가 깨졌을 때 복구 수단이 없다**는 것이다.

```
onStpCaseTimeout()
├─ nxCad->stop()
└─ (전이 없음 — batchFailed 통지를 기다린다)
      ├─ 데몬이 batchFailed 를 냄 → onStpCaseFailed → setStageState(Failed) → 정상
      └─ 데몬이 응답 없음 (크래시 · 행)
            └─ m_stpWatchdog 는 setSingleShot(true) (:244) → 재무장 없음
                  └─ 케이스가 Running 에 고정 → 장부가 안 닫힘 → 배치 영구 정지
```

`m_wbpjBatch.phase` 가 `Idle` 로 돌아가지 않으므로 `batchActive()`(`h:56`)가 계속 true 를 반환해 **다음 실행도 재진입 가드(`:2668`)에 막힌다.** 앱 재시작 외에 탈출구가 없다.

#264 가 런처 키 카운터를 삭제하면 최후 보루가 사라져 이 경로가 그대로 노출된다.

## 무효 판정 — 전건 close

초판 2건은 본문 "무효 판정" 표가 이미 기각했고, 재정의로 남긴 1건(**데몬 무응답 시 `batchFailed` 미도착 → 케이스 Running 고정**)도 성립하지 않는다. `#264` 구현(`91e78f9`) 위에서 전 고리를 코드로 확인했다.

### 근거 — `stop()` 이 데몬 응답과 무관하게 동기로 실패 통지를 만든다

```
onStpCaseTimeout (DashJobRunner.cpp:3055)
└─ nxCad->stop()
     └─ DashExtensionProcess::stop() (:121)
          ├─ reconcile()       "exit\n" 쓰기 + stop-timer 무장 — 비동기, 결과와 무관
          └─ drainCommands()   (:240) ← 조건 없이 실행
               └─ emit commandFailed(inFlightId, "Daemon stopped before command finished.") (:254)
                    └─ DashSolverNxCad::onCommandFailed (:209)   ← 생성자 :22-23, Direct 연결
                         └─ emitFailure(isUpdate=true, stpPath, msg) (:220)
                              └─ m_batchMode==true → updatePrtGeometryBatchFailed (:223)
                                   └─ onStpCaseFailed → setStageState(Failed) → runNextStpCase()
```

통지를 만드는 주체는 데몬이 아니라 **Qt 측 큐 배출**이다. 데몬이 크래시했든 행이든 `exit` 에 응답하지 않든 통지가 나온다. `DashExtensionProcess.h` 클래스 주석이 이미 계약으로 명시한다 — *"데몬이 죽거나 기동에 실패하면 진행 중·대기 명령이 전부 commandFailed 로 통지된다(무음 폐기 금지)."*

### 전수 확인

| 항목 | 확인 범위 | 결과 |
|---|---|---|
| 통지 없이 명령이 소멸하는 경로 | `m_waitingFinished` 대입 4곳 · `m_commandQueue` 변형 5곳 전수 | `shutdownBlocking()`(:292-293, 앱 종료) 1곳뿐 |
| `commandFailed` → `onCommandFailed` 배선 | `DashSolverNxCad.cpp:22-23` | 같은 객체·스레드 → Direct |

| `stpPath` 왕복 일치 | commandId `updatePrt:%1` 원본 보존 · `toNativeSeparators` 는 커맨드 라인에만 적용 | 귀속 성립 |

### 초판 주장별 판정

| 주장 | 판정 |
|---|---|
| `m_stpWatchdog` 가 `setSingleShot(true)` → "재무장 부재" | **오독.** 케이스 단위로 재무장한다 — `runNextStpCase:3000` 이 착수마다 `start()`. 직렬 실행이라 in-flight 는 1건이고 single-shot 이 정확한 의미다. 재무장하지 않는 유일한 시점은 "다음 케이스 없음" 으로 정상 |

### STP 단계 이탈구는 전부 유한하다

```
케이스 착수 후
├─ [FINISHED] 파일 有  → batchCompleted        → Done
├─ [FINISHED] 파일 無  → emitFailure           → Failed
├─ [ERROR]             → commandFailed         → Failed
├─ 데몬 사망 · 기동실패 → reportDeath → drain   → Failed
├─ 워치독 600s         → stop() → drain        → Failed
└─ exit 무응답         → m_stopTimer → kill()  → finished → 위로 수렴
   연속 실패 k회 → m_batchConsecFail 차단기 → finishStpPhase → 배치 종결
```

`kill()` 조차 실패해 데몬이 `Stopping` 에 영구히 갇힌 최악의 경우에도, 후속 명령은 큐에 래치되고 다음 워치독의 `drainCommands` 가 상태와 무관하게 배출한다. 케이스당 600s 를 태우지만 차단기가 배치를 유한 시간에 닫는다. "영구 정지" 상태는 구성할 수 없다.
