## Goal
DOE 배치 경로(`runWbpjDoeAsync`)의 **Step 1(STP 생성)** 을 파일 존재 폴링(`waitForFile`)에서 **NX CAD 파사드(`DashSolverNxCad`) 완료/실패 시그널 구독**으로 전환하고, 케이스 반복을 **pending 큐 + 완료 슬롯 연쇄**로 재구성한다. 취소·실패 정책(P1~P3·P5, [#194](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/194-1-async-execution-patterns) 4-1절)을 이 배치 흐름에 반영한다.

**전환 대상은 Step 1 한 곳이다.** Step 2(Journal 실행)는 `DashManager::enqueueLaunch` → journal 데몬(`DashExtensionProcess`) 큐로 이미 이벤트 구동이므로 로직은 그대로 두고 호출 위치만 완료 연쇄 뒤로 옮긴다. (두 단계가 쓰는 데몬은 다르다 — Step 1 = `DashSolverNxCad` 도메인 파사드, Step 2 = `journalDaemon` + `DashManager` 래퍼.)

**갈래 ②(데몬 명령) — `Job`/`ProcessJob` 을 하나도 생성하지 않는다.** 두 단계 모두 이미 떠 있는 데몬에 명령 한 줄을 보내는 실행이라 감쌀 프로세스 수명이 없다. 갈래 ①(one-shot exe → ProcessJob)은 W6-1(#207)·W6-2(#208) 소관이며 본 티켓 코드 경로에 등장하지 않는다. 신규 클래스 0 · JobManager/스케줄러/우선순위 큐/작업 트리/재시도 정책 도입 없음([#205](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/205-5-w6-w10-async-minimal-example) 개정 2).

### 변경의 실체
통지 채널(파사드 시그널)은 이미 존재하므로, 실제 작업은 **호출부 한 곳의 반복 구조 교체**다.

1. **진행 촉발 주체 이전**: "다음 케이스를 언제 시작하는가" 의 결정권이 동기 `for` 루프에서 완료 시그널을 받은 슬롯으로 넘어간다. 실행 순서(케이스 1→2→3)는 불변 — 바뀌는 것은 촉발 시점의 소유자(호출부 → Qt 이벤트 루프)뿐이다. ("제어 흐름 역전" 은 흐름 방향이 뒤집힌다고 오해되므로 쓰지 않는다.)
2. **루프 상태의 수명 재배치 (규모의 본체)**: 폴링 방식은 함수가 반환하지 않아 스택 프레임이 배치 상태 저장소를 겸했다(루프 인덱스·실패 카운터·현재 케이스). 이벤트 방식은 1건 착수 후 즉시 반환해 그 프레임이 사라지므로, 배치 종료까지 살아야 하는 값은 `DashJobRunner` 멤버로 옮긴다. 정책 검사 지점도 여기 붙는다 — 슬롯 진입마다 취소 플래그(P2)·연쇄 실패 차단기(P3) 확인.
3. **블로킹 제거는 부수 효과가 아니라 정의**: 대기 구간(`QThread::msleep` + `processEvents`) 자체가 소멸하므로 GUI 이벤트 루프가 배치 내내 정상 회전한다. 단, 폴링이 겸하던 **케이스별 상한(600s)도 함께 사라지므로 타임아웃을 별도로 복원**해야 한다.

## Background
> source: `DashOpti_Docs/dashgui2-async-execution-patterns.md` 7절 서브태스크 a · `dashgui2-w6-w10-thread-execution-design.md` 3장 · `dashgui2-w6-w10-async-minimal-example.md` 3장

- **W10 (이벤트 구동 전환) 분할 a (1/6) — 외부 축의 기반.** 서브태스크 분할 정본 = [#194](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/194-1-async-execution-patterns) 7절 (의존: a → b·c 병행, d → e → f 직렬).
- **DOE 배치가 이 레포 블로킹의 무게중심이다.** 대기 안티패턴(`waitForFile`·`waitForVtuFileComplete`·motion-writer 대기 루프·다수 `processEvents`)은 거의 전부 `DashJobRunner` 의 DOE/배치 흐름에 몰려 있다. 단건 소비자(예측 `DashModelRunner`)는 #208 에서 실행 엔진 위임으로 전환돼 `Job::finished` 구독(`model/DashModelRunner.cpp:199`) 기반이라 뒤집을 블로킹이 없다. W10 이 고쳐야 할 대기(how)는 본질적으로 배치 모양이며, DOE 는 그 대표 표본이다.
- **같은 파일에 단건 연쇄 선례가 있다**: `runDirectJobs` .wbpj 경로(`model/DashJobRunner.cpp:2296-2304`)는 `loadPrtCompleted` 를 `Qt::QueuedConnection` 으로 구독해 다음 단계를 연쇄한다 — GUI 블로킹 0. 단 **배치 선례는 아니다**: 파일별로 새 람다를 connect 하고 첫 완료에서 `disconnect(nxCad, &…::loadPrtCompleted, this, nullptr)` 로 전량 해제하므로, .wbpj 2건 이상이면 나머지 구독이 함께 끊긴다(기존 결함, 범위 밖). 배선 순서("connect 먼저, enqueue 나중")와 경로 귀속 가드(`canonicalFilePath` 비교)만 차용한다.
- **미전환 경로 = `runWbpjDoeAsync`(`:2643`)**: `enqueueUpdatePrtGeometry` 직후 `waitForFile(stpOutputPath, 600)` 로 폴링한다. 완료 시그널을 "무시" 하는 것이 아니라, **자신이 STP 루프 전에 켠 `setBatchMode(true)`(`:2555`) 가 방출 자체를 막아 구독할 시그널이 없는 상태**다 (아래 Technical Details 참조). 이름만 Async.
- **W6-1 ProcessJob 에 대한 하드 의존은 없다.** 본 파일럿이 쓰는 완료 시그널(`updatePrtGeometryCompleted`)은 `controller/DashSolverNxCad.cpp:198` 에 이미 존재한다. W6 그룹(#207~#209)은 one-shot exe 실행 경로를 정비할 뿐 데몬 경로(`DashSolverNxCad`)는 명시적으로 손대지 않으므로(#207: "데몬 경로에 잔존"), 본 티켓은 W6 완료를 하드 선행으로 요구하지 않는다. (실행 경로 일원화가 먼저 서는 편이 낫다는 소프트 순서 선호만 유지.)

## Technical Details
- **완료 처리 표준 = Qt 시그널** ([#194](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/194-1-async-execution-patterns) 3절 판정): 본 파일럿에서는 데몬 파사드(`DashSolverNxCad`)가 이미 Qt 시그널로 완료를 통지한다. C 콜백은 경계 어댑터 한정, 코루틴은 보류(Qt 5.15 — QCoro 최신판이 Qt 6.8+ 전용).
- **완료 슬롯의 책임 교체**: 현재 STP 완료 판정은 `waitForFile` 폴링 → 전환 후에는 완료/실패 슬롯이 (a) 케이스 결과 기록(P1) (b) 다음 케이스 착수 (c) 정책 검사(P2·P3)를 담당한다. GUI 갱신(`caseStatusUpdated`)은 이미 시그널 기반이라 그대로 유지.
- **[구현 블로커] 배치 모드가 완료 방출을 막는다 — 가드 해제로는 못 푼다**: `DashSolverNxCad::onCommandCompleted`(`controller/DashSolverNxCad.cpp:196-199`)는 `if (!m_batchMode)` 로 **배치 모드에서 `updatePrtGeometryCompleted` 를 방출하지 않는다.** `runWbpjDoeAsync` 가 STP 루프 전 `setBatchMode(true)`(`:2555`)를 켜므로 — 이것이 현재 폴링이 필요한 근본 이유다.
  - **단순 가드 해제(1줄)는 불가**: 이 시그널의 대화형 구독자가 3D 미리보기 STEP 로드(`view/DashMainWindow.cpp:271`)와 모달 경고(`view/DashModelRunnerWidget.cpp:225`)를 띄운다. 케이스마다 모달이 뜨면 완료 슬롯 연쇄(continue-on-error)가 막혀 티켓 자신의 수용 기준을 깬다.
  - **따라서 배치 전용 완료/실패 시그널을 분리**해 오케스트레이터에게만 보낸다(대화형 시그널과 배타적 방출). → **`controller/DashSolverNxCad.{h,cpp}` 도 변경 대상**이다.
- **실패 시그널 = `loadPrtFailed`** (load/update **경로** 겸용 — 성공 통지는 겸하지 않는다): update 전용 실패 시그널이 없어 파일 미생성(`:188-191`)·커맨드 실패(`:205-207`)가 모두 `loadPrtFailed(message)` 로 나간다. 상위 `DashExtensionProcess::commandFailed` 는 `commandId` 를 실어 보내지만 파사드가 **버린다**(`onCommandFailed(const QString& /*commandId*/, …)`, `:205`). 데몬 큐가 순차 처리(한 번에 1건)라 실패는 현재 진행 케이스에 귀속되지만, 배치/대화형 경로를 나누려면 `commandId` 의 `updatePrt:` 접두어를 살려 판정해야 한다. (`loadPrtFailed` 명칭이 update 경로엔 부정확하나 리네이밍은 범위 밖.)
- **계약 4종** ([#194](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/194-1-async-execution-patterns) 4절): 취소(협조적) · 진행(`[PROGRESS]` additive 마커는 W11 몫) · 실패(파사드 실패 시그널 → 결과 기록) · 구독("connect 먼저 start 나중" · `state()` pull 병행 · 전역 이벤트 버스 금지).
- **취소·실패 정책 P1~P3·P5** ([#194](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/194-1-async-execution-patterns) 4-1절) 를 배치 오케스트레이터 구현 규칙으로 흡수: 완료분 보존·중단분 폐기(P1), 배치 취소 = 가장 이른 지점 중단 + 잔여 미시작(P2), continue-on-error + 연쇄 실패 차단기 k=3(P3), 자동 재시도 없음(P5).
  - **P1 은 절반 기존 구현**: 케이스별 종료 상태는 이미 `configManager.setSampleStatus(runKey, "Done"/"Failed", …)` + `caseStatusUpdated` 로 기록 중(`:2634`·`:2648`·`:2763`·`:2775`·`:2780` 등). 본 티켓의 몫은 신규가 아니라 **이벤트 구동 흐름에서 일관 유지**(완료 슬롯에서 동일 기록 경로 재배선).
  - **단순화 검토 결과 = 현행 유지** (P1 제거·P3 fail-fast 안 기각): 파일럿이 **DOE(설계실험) 배치**라 부분 결과·부분 실패가 1차 용도다. P1 은 "완료 시 결과 append"라 사실상 공짜이고 제거하면 완료분을 능동 폐기(60/100 취소 시 수 시간 계산 낭비) · P3 개별 샘플 실패(나쁜 파라미터 → 솔버 발산·메시 실패)는 예상 정상 범위라 fail-fast 면 샘플 1건이 실험 전체를 죽인다. 배치별 all-or-nothing 요구가 실제로 생기면 그때 배치별 정책으로 분기 (요약 문서 "단순화 검토" 섹션).
- **취소 모델 = 데몬 협조적 취소 (PID kill 아님)**: 데몬 명령이므로 ProcessJob PID kill 이 적용되지 않는다. 현재 상태는 "커버 안 됨" 이 아니라 **과잉 커버**다 — `cancelAllRuns()`(`:902`) 말미가 이미 `nxCad->stopDaemon()` + `journal->stopDaemon()` 을 무조건 호출한다(`:995-1002`).
  - **문제**: `DashExtensionProcess::stopDaemon()`(`:189`)은 `m_commandQueue`·`m_waitingFinished`·`m_currentCommandId` 를 먼저 비우므로(`:191-193`), 이어지는 `onDaemonFinished` 의 `wasWaiting`(`:329`)이 false 가 되어 **진행 중 커맨드를 `commandFailed` 로 회수하지 않는다.** 즉 배치 중 데몬을 죽이면 진행 1건이 성공도 실패도 통지되지 않아 연쇄가 조용히 멈추고, 완료분 보존(P1)도 깨진다.
  - **따라서 배치 진행 중 취소는 `stopDaemon()` 을 호출하지 않는다**: 플래그로 다음 케이스 미착수(P2) + 진행 1건은 완료 수용(P1). 데몬 전체 종료는 배치가 아닐 때 / 타임아웃 회수 시에 한정.
  - `DashExtensionProcess` 에는 per-command cancel 도 clearQueue 도 없다(공개 API 는 `stopDaemon()` 뿐).
- **케이스 타임아웃은 폴링과 함께 사라진다**: `waitForFile(path, 600)` 이 겸하던 상한이 없어지므로 케이스별 single-shot 타이머로 승계한다. 타임아웃 처리는 `stopDaemon()` 후 위 사유로 실패 회계를 **직접** 기록해야 한다(자동 `commandFailed` 없음).
- **범위 밖 명문화** ([#205](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/205-5-w6-w10-async-minimal-example) 개정 2): JobManager·스케줄러·우선순위 큐·Job 트리·재시도 정책은 도입하지 않는다. 신규 클래스 0 — 기존 데몬 파사드 + `DashJobRunner` 멤버(데이터)만으로 구현.
- **규모 근거**: 위 "변경의 실체" 2번(상태 수명 재배치)이 W6 1.5주 vs W10 4주 격차의 본체이며, 코루틴 보류 판정([#194](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/194-1-async-execution-patterns) 3-3절)과 같은 지점이다.

## Design

### 현황 분석
- 필요한 비동기 배관은 이미 있다: `DashExtensionProcess` 직렬 명령 큐(`m_commandQueue`) + `commandCompleted`/`commandFailed`, `DashSolverNxCad` 도메인 큐/시그널(`updatePrtGeometryCompleted`·`loadPrtCompleted`·`loadPrtFailed`). 문제는 큐가 아니라 **큐를 우회하는 호출자**(폴링·busy-wait). (완결된 것은 "정상 완료 통지" 뿐 — 취소 세분화와 강제 종료 시 회수는 위 Technical Details 대로 빠져 있다.)
- 파사드 완료 시그널은 존재(`DashSolverNxCad.cpp:198`)하고 단건 연쇄 선례도 있다(`runDirectJobs` `:2296-2304`). **신설할 공통 표면은 없다** — 필요한 건 배치/대화형 방출 경로 분리와 호출부 재구성뿐.

### 대안 비교 (완료 원천 전파 방식)

| 방안 | 핵심 | 장점 | 단점 |
|---|---|---|---|
| A. Qt 파사드 시그널 구독 | 파사드가 방출하는 완료/실패 시그널을 오케스트레이터가 구독 | 네이티브 · QueuedConnection 자동 마샬링 · 수신자 소멸 시 자동 disconnect · 일대다 구독(W11/W12 재사용) · 내부 선례(`runDirectJobs`) | 배치 모드 방출 경로 분리 필요 (가드 1줄 해제로는 불가 — 위 참조) |
| B. C 콜백 직접 전파 | 함수 포인터 체인 | C API 경계와 균질 | 스레드 문맥 불명 · dangling 위험 · 일대일 |
| C. 코루틴 (co_await) | 순차 오케스트레이션 선형화 | 가독성 | Qt 5.15 어댑터 부재(QCoro 최신판 Qt 6.8+) · 지금 넣으면 같은 코드 2회 재작성 |

### 선택 — 방안 A (파사드 시그널 구독)

**선택 근거**: [#194](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/194-1-async-execution-patterns) 3절 판정 그대로 — 스레드 경계 자동 처리·수명 안전·일대다 구독·검증된 내부 선례. 파사드 시그널이 이미 있어 추가 인프라가 필요 없다.
**기각된 대안**: B 는 경계 어댑터로만 · C 는 Qt 6 이행 시 additive 승격 가능하므로 보류.

#### 자료 구조 (신규 클래스 없음 — 오케스트레이터 멤버 + 보조 struct)
```cpp
// model/DashJobRunner — for 루프 스택 프레임에 살던 상태를 멤버로 이관
struct StpCase  { QString runKey; QString stpPath; QJsonObject config; };
struct StpBatch {
    /* 배치 불변 입력: wbpj·prt·ansysPath·outputBaseDir·analysisType·doeJsonPath … */
    QStringList    activeRunKeys;   // Step 2 대상 (미착수분 제외)
    QList<StpCase> pending;         // 착수 대기 (DOE 활성 샘플 → case descriptor)
    StpCase        current;         // 진행 1건 (실패 귀속 · 취소 대상)
    QStringList    failedKeys;      // 배치 종료 시 실패 요약
    int  consecFail = 0;            // P3 연쇄 실패 차단기
    bool active     = false;        // 재진입 가드
    bool cancelled  = false;        // P2 협조적 취소
};
StpBatch m_stpBatch;
QTimer*  m_stpWatchdog = nullptr;   // 케이스별 상한 (구 폴링 600s 승계)
```
케이스별 종료 상태는 별도 결과 배열을 두지 않고 기존 `setSampleStatus` + `caseStatusUpdated` 경로에 그대로 기록한다(P1 — 신규 저장소 추가 없음). 배치 종료 요약에 필요한 실패 목록만 `failedKeys` 로 남긴다.

#### 배치 오케스트레이션 골격 (Phase 1·2 의 본체)
순서는 `for` 루프가 아니라 완료 슬롯이 결정한다. 데몬 명령이므로 Job 을 만들지 않고 파사드 시그널을 직접 구독한다.

```cpp
// 배치 시작 시 1회 배선 — connect 먼저, 첫 enqueue 나중
// QueuedConnection 필수: 완료 시그널은 데몬 stdout 핸들러 콜스택에서 방출되므로
// 직접 연결이면 다음 케이스 enqueue 가 그 핸들러 안에서 재진입한다.
connect(nxCad, &DashSolverNxCad::updatePrtGeometryBatchCompleted, this, &DashJobRunner::onStpCaseCompleted,
        static_cast<Qt::ConnectionType>(Qt::QueuedConnection | Qt::UniqueConnection));
connect(nxCad, &DashSolverNxCad::updatePrtGeometryBatchFailed,    this, &DashJobRunner::onStpCaseFailed, /* 동일 */);
startNextStpCase();

void DashJobRunner::startNextStpCase() {
    if (m_stpBatch.cancelled || m_stpBatch.pending.isEmpty()) { finishStpPhase(); return; }  // P2
    m_stpBatch.current = m_stpBatch.pending.takeFirst();
    m_stpWatchdog->start(kStpCaseTimeoutMs);                                 // 구 폴링 상한 승계
    nxCad->enqueueUpdatePrtGeometry(prt, m_stpBatch.current.stpPath, m_stpBatch.current.config); // 즉시 반환
}
void DashJobRunner::onStpCaseCompleted(const QString& stpPath) {
    if (!m_stpBatch.active || stpPath != m_stpBatch.current.stpPath) return;  // 지연·오귀속 방어
    m_stpWatchdog->stop();
    m_stpBatch.consecFail = 0;                       // P1 기록은 기존 setSampleStatus 경로
    startNextStpCase();                              // ← 순서의 실체
}
void DashJobRunner::onStpCaseFailed(const QString& msg) {   // continue-on-error
    if (!m_stpBatch.active) return;
    m_stpWatchdog->stop();
    m_stpBatch.failedKeys.append(m_stpBatch.current.runKey);                  // P1
    if (++m_stpBatch.consecFail >= kStpConsecFailLimit) { finishStpPhase(); return; }  // P3 (k=3)
    startNextStpCase();                                                       // P5: 재시도 없음
}
void DashJobRunner::onStpCaseTimeout() {   // stopDaemon 은 commandFailed 를 안 내므로 직접 회계
    nxCad->stopDaemon();
    onStpCaseFailed(QStringLiteral("timed out"));
}
```
`finishStpPhase()` 는 워치독 정지 · 배치 시그널 disconnect · `setBatchMode(false)` · 미착수 키를 `activeRunKeys` 에서 제거하고 `Cancelled` 표시 · 실패 요약 로그 후, 취소/전건 실패가 아니면 Step 2 를 착수한다.

#### 두 단계 구조
`runWbpjDoeAsync` 는 두 단계이며 **전환 대상은 Step 1 뿐**이다:
- **Step 1 (STP 생성, `:2513-2672`)** — 케이스별 `enqueueUpdatePrtGeometry` + `waitForFile` 폴링. ← 위 골격으로 교체.
- **Step 2 (Ansys Journal, `:2674-2810`)** — 전체 케이스에 대해 `mgr->enqueueLaunch` **1회**(`:2808`) + `DashManager::journalLaunchCompleted`/`journalLaunchFailed` 를 그보다 앞서 connect(`:2735`·`:2738`·`:2786`). **이미 이벤트 구동이라 로직 무변경** — 본문을 별도 함수로 떼어 `finishStpPhase()` 뒤에서 호출하는 이동만 발생. (per-case 체인이 아니라 배치 1회 launch — 골격의 케이스 연쇄는 Step 1 에만 해당.)

#### 대안 검토 — 배치 오케스트레이션 (요지)
현재안(pending 큐 + 완료 슬롯 연쇄)은 **Qt 5.15 + I/O 바운드(외부 프로세스/데몬) 오케스트레이션의 최소 적합해**다.
- **코루틴 `co_await`** — 유일하게 엄밀히 더 읽기 좋으나 Qt 5.15 어댑터 부재 → Qt 6 이행 시 additive 승격으로 보류 ([#194](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/194-1-async-execution-patterns) 3-3절).
- **`QFuture::then()`** (Qt 6.0 도입 — 5.15 에 없음) · **`QStateMachine`**(선형 큐에 프레임워크 과함 — 수기 슬롯 연쇄가 이미 최소 상태머신) · **워커 스레드 + 동기 for 루프**(오케스트레이션이 I/O 바운드라 CPU 이득 0 + GUI 공유상태 접근 시 스레드 안전 자초) 모두 부적합.
- **재사용 `BatchRunner` 추출** — 다른 설계가 아니라 같은 패턴의 리팩터. 파일럿 1건뿐이라 지금 추출은 조기 추상화([#205](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/205-5-w6-w10-async-minimal-example) JobManager/스케줄러 배제 원칙과도 정합). 세 배치 공존 시(#215) rule of three 로 재검토 — #215 후속작업.

상세 표: 요약 문서 "배치 오케스트레이션 (pending 큐·완료슬롯 연쇄)" 및 "BatchRunner 추출" 섹션.
