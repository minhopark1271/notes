# #394 SaveProjectAs 가 모든 실패를 무시하고 true 를 반환하는 문제

https://github.com/NumeRealWorks/DashOpti_GUI/issues/394

## 요약

- SaveProjectAs 에, 오류를 발생 시킬 수 있는 정책 요소가 발견되어 이를 제거하려고 함.
- 제거할 경우, 이미 Project 이름의 폴더가 있을 시 이를 삭제하고 다시 쓰는 동작 (Overwrite 라고 코드는 주장하나, 실제론 그렇지 않음) 이 제거됨.

제목

SaveProjectAs 가 모든 실패를 무시하고 true 를 반환한다 — 자기 자신에 덮어쓰면 프로젝트가 소실된다

대상 심볼

- DashProjectManager::SaveProjectAs(const QString&) — controller/DashProjectManager.cpp
- 호출부: DashMainWindow::onFileSaveAs() — view/DashMainWindow.cpp
- 관련: DashProjectManager::GetProjectPath(), DashProjectManager::GetProjectFolderPath()

1. 반환값을 전부 버리고 무조건 true

SaveProjectAs 는 아래 호출들의 반환값을 하나도 검사하지 않고 마지막에 무조건 return true 한다.

호출부 DashMainWindow::onFileSaveAs() 는 이 반환값으로 분기해 "Project saved successfully." 와 "Failed to save project." 를 고른다. 즉 실패 경로가 코드상 존재하지만 도달 불가능하다. 사용자는 항상 성공을 본다.

2. removeRecursively() 는 비원자적이라 중간 실패 시 복구 경로가 없다

removeRecursively() 는 부분 성공이 가능하다. 파일 몇 개를 지우다 실패해도 이미 지운 것은 돌아오지 않고, 반환값도 버려지므로 그대로 다음 단계로 진행한다. 이때 연쇄가 고약하다 — QFile::copy() 는 대상 파일이 이미 존재하면 덮어쓰지 않고 false 를 반환하므로, 삭제에 실패해 남은 옛 파일들은 새 파일로 교체되지 않고 그대로 남는다. 결과는 옛 잔해와 새 파일이 섞인 폴더이고, 보고는 성공이다.

여기서 "삭제 전에 권한을 확인하자" 는 해법이 되지 않는다. Windows 에서는 권한이 있어도 다른 프로세스가 핸들을 잡고 있으면 삭제가 실패하고, 사전 검사와 실제 삭제 사이에 상태가 바뀌는 TOCTOU 라 검사를 정교화해도 보장이 생기지 않는다. 삭제를 시작한 시점에 이미 안전한 fallback 이 없다는 게 문제의 핵심이다.

3. 자기 자신에 덮어쓰면 프로젝트가 소실된다 — 기본값 그대로 진행하면 발생

DashMainWindow::onFileSaveAs() 가 만드는 기본값이 정확히 현재 프로젝트를 가리킨다.

- QFileDialog::getExistingDirectory() 의 시작 위치 = GetProjectFolderPath() 의 부모 디렉터리
- QInputDialog::getText() 의 기본 입력값 = GetProjectFolderPath() 의 폴더 이름

따라서 사용자가 두 대화상자를 기본값 그대로 확인만 하면 destFolderPath 가 현재 프로젝트 폴더와 정확히 일치한다. "Folder X already exists. Overwrite?" 에 Yes 를 누르면 (같은 이름이 보이므로 자연스러운 선택이다) SaveProjectAs 안에서 이렇게 진행된다.

1. sourceProjectDir = GetProjectPath() = destFolderPath/.<name>.dproj — 원본이 대상 폴더 안에 있다
2. destBaseDir.removeRecursively() 가 대상 폴더를 지운다 = 원본을 지운다
3. QDir::mkpath(newProjectPath) 가 .dproj 를 빈 폴더로 다시 만든다
4. QDirIterator 가 그 빈 폴더를 순회한다 → 복사 목록이 비어 있다 → 파일이 하나도 복사되지 않는다
5. return true → UI 는 "Project saved successfully."

프로젝트 데이터 전체가 사라지고 성공으로 보고된다.

3 단계에서 핸들이 잡혀 삭제가 부분 실패하면 소실 대신 손상이 되지만, 어느 쪽이든 보고는 성공이다.

`#377` 의 새 WARN 이 이 경우를 잡지 못한다
                                                                                                                                                                                                                                                               #377 은 IsProjectOpen() 에 있던 디스크 확인을 SaveProjectAs 끝의 Inconsistent state WARN 으로 옮겼다. 방향은   검사는 newProjectPath 의 존재 여부만 보는데, 위 4 단계 시점에 .dproj 폴더는 3 단계에서 재생성되어 존재한다. 안이비어 있어도 WARN 은 찍히지 않는다. 즉 최악의 경우가 진단에서 빠진다.

제안

- 대상 폴더가 이미 존재하면 SaveProjectAs 는 아무것도 건드리지 않고 false 를 반환한다. removeRecursively() 호출을 제거하고, DashMainWindow::onFileSaveAs() 의 Overwrite 확인 대화상자도 함께 제거해 "이미 존재하는 이름입니다. 다른 이름을 사용하세요" 안내로 바꾼다. 3 번 시나리오와 2 번의 복구 불가 상태가 함께 사라진다.

- **Overwrite 동작을 삭제한다.**
   이유는 다음과 같다 :
      - 원자적이지 않다. 삭제에 실패하면 어중간한 상태가 된다. (TOCTOU) temp folder 를 만들고 원자적으로 교체하는 방법도 있으나 정책의 효용성에 비해 비용이 비싸보인다.
      - 사용자 의도를 완벽하게 반영하지 않는다. Overwrite 가 무엇을 말하는지 확실하지 않다. 이미 있는 project file 을 덮어쓴다는 의미라면 폴더의 존재를 확인하는 현재의 코드는 이를 위반하는 것이 아닌가?
