## Original Request

## Goal
실행 버튼 1회로, DOE 조합에 들어 있는 **서로 다른 조건 해석파일마다** batch run 이 자동으로 돈다 — 실행 수 = 서로 다른 해석파일 수, 같은 해석파일을 쓰는 세트들은 한 번의 실행으로 합쳐진다(D23). 현행 방식(라디오에서 파일 1개 선택 → 1회 실행 → 라디오 바꿔 수동 반복)을 자동화한다.

**편의 기능이다** — #491 의 치환부(실행 시 해당 세트의 변수만 값 치환)가 결과 정합성을 이미 보장하므로, 이 자동화 없이도 라디오 전환 + 재실행으로 옳은 결과가 나온다. 착수 전에 실효(Optimizer 가 여러 해석의 성능지표를 실행 1회로 얻는 가치) 대비 비용을 다시 판단한다.

## Background
> source: #367 구판 Phase 4(T26)에서 값 치환·매칭 전환을 #491 로 이관하고 남은 부분

실측 — 해석파일별 반복은 원래 없던 로직이다:
- Reference File 라디오가 단일 선택이라(`getSelectedReferenceFiles` `view/DashReferenceFileWidget.cpp:101-130`) 실행 버튼이 넘기는 템플릿 목록은 항상 1개다(`view/DashAnalysisLauncherWidgetBase.cpp:193-215`)
- `generateInputCases` 의 `.first()`(`model/DashJobRunner.cpp:1290`)로 잘리는 것이 실제로는 없다 — 여러 해석파일은 사용자가 라디오를 바꿔 N회 재실행했다
- 실행 산출물 폴더는 해석파일 이름(analysisType)으로 구분돼 충돌이 없다

## Technical Details

### as-is
- `generateInputCases(templateFilePaths, …)` 가 `.first()` 만 쓴다 — 실행 1회 = 해석파일 1개
- 여러 해석파일 실행 = 라디오 전환 + 재실행(수동). #491 이후 값 치환은 실행 대상 해석파일에 속한 세트로 옳게 한정된다

### to-be
- 실행 1회가 조합의 **서로 다른 조건 해석파일 집합**을 구해 파일별로 `generateInputCases` 를 반복한다 — 반복은 호출부에 좁혀 넣는다. 값 치환·morph 매칭은 #491 산출물 그대로 쓰고, 실행 대상 파일만 반복 변수가 된다
- 해석파일 집합의 출처는 DOE Table 열의 `{set, key}` → 각 세트의 `referenceModel.uuid`(#491·#366) — **T20 의 `parameterization` 기록에 의존하지 않는다**(T20 이 먼저 들어와 있으면 그 기록을 써도 된다, 착수 시 선택)
- 실행 폴더 이름은 현행(해석파일 이름) 그대로 — 파일별 1회라 충돌 없음

### not-to-be
- 실행 차단·입력 검증 — 기록만, 검증 없음(D21) 유지
- 조건 해석파일이 아닌 템플릿(`.stli`·`.wbpj`·`.dfsxml`)의 반복 확대 — 현행 단일 실행 유지
- 값 치환·매칭 로직 변경 — #491 완료분

### 착수 시 결정
- 라디오의 역할 재정의 — 반복이 조합에서 실행 대상을 구하면 라디오의 "실행 템플릿 지정" 역할과 겹친다. 라디오를 조건 해석파일 이외의 템플릿 전용으로 좁힐지, "조합 실행/단일 실행" 모드 전환으로 둘지 확정한 뒤 착수한다
