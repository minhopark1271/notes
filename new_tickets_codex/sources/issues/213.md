## Goal
WorkerJob 투입 전 공유 상태 선결 조건 6건(D1·D2·D3·D5·D6·D7)이 해소된다. 배치·모핑·컨텍스트 경로가 지금 사고를 안 내는 이유는 전부 GUI 스레드에서 돌아 자동 직렬화되기 때문 — 이 정리 없이 워커를 넣으면 **프리즈가 레이스로 바뀐다**.

- **#212 머지 후 재확인**: 데몬 기동 비동기화는 새 스레드를 만들지 않고 Qt 이벤트 루프 위에서만 돈다. controller 계층 `processEvents` **0건 유지**, 1st-party 중첩 `QEventLoop::exec` **0건** — D3 의 "오늘 도달 불가" 논거는 그대로다. 다만 `~DashManager()` 가 블로킹 종료를 갖게 돼 D1 소멸 경로 검토 항목이 하나 늘었다(Design "D1 — 소멸 경로" 참조).

## Technical Details

### as-is

**D1 — 싱글톤 lazy-init**
- `DashManager::Mgr()`(`controller/DashManager.cpp:205-212`) · `DashProjectManager::Instance()`(`controller/DashProjectManager.cpp:15-20`) 둘 다 raw static 포인터 lazy-init — 락·atomic·magic static 없음
- `DashProjectManager::Instance()` 는 **이미 워커 스레드에서 호출된다** — `runAnalysisInThread`(`model/DashAnalysisLauncher.cpp:284`, `QtConcurrent::run` `:233`)의 `:287`, 그리고 `saveResultsAsDvTable:269`→`saveDoeToCsv:1471`
- 소멸 경로 비대칭: `DashManager` 는 `atexit(Destroy)`(`:208`) + 헤더 inline `Destroy(){ delete m_instance; }`(`DashManager.h:63`)로 heap 포인터 전제. `DashProjectManager` 는 atexit 미등록 + `Destroy()`(`.h:25`) 참조 0건 + `delete` 호출 0건 → 소멸자 `~DashProjectManager()`(`.cpp:29-33`, `CloseProject()` + `m_project`/`m_ioController` delete)가 한 번도 실행되지 않음

### to-be

- **(D1)** 두 싱글톤을 `main()` 초기에 메인 스레드에서 선-초기화 + 생성자 메인스레드 assert → 2차로 magic static 전환, 소멸은 정적 소멸 역순에 위임하고 `atexit(Destroy)`·inline `Destroy()` 제거
- **(D2)** 배치 엔진을 executor 소유(per-Job)로 격상 — 변이 표면 11곳이 per-call 인스턴스 위에서만 일어남. `m_morphingOperator` 를 소유 스마트포인터로 전환
- **(D3-M1)** `getOrLoad` 를 `try_emplace` + **맵 인스턴스 반환**으로 교정 — 자료구조 변경 없이 선적용
- **(D3-M2)** 캐시 값 타입을 `shared_future<shared_ptr<DashAnalysisModelContext>>` 로 전환(per-key 단일 로드), 반환형 파급 28곳 수렴
- **(D3 규약)** 양층 확립 — 심층 변이(`Update()`·`editFeConditionEntry`·export)는 직렬 풀 큐 전용, 메인(위젯·렌더)은 읽기 스냅샷만. 기존 위반자 `DashConditionParameterization.cpp:362` 는 큐 경유 또는 배치 중 편집 차단으로 처리

- **(D6)** `RunVolumeMorphing` 을 "DashManager 상태 무참조 + 인자 전달" 오버로드로 분리, 배치 입력은 DeepCopy 스냅샷으로 진입, 결과 메시에 `m_inputVTU`/`m_originalQuadraticCells` 인스턴스를 심지 않는 조립 경로 사용
- **(D7)** inject→export→restore 를 직렬 큐의 단일 원자 작업 경계로 묶고, 메시·조건 DV 복원을 scope guard 로 전환 — 변이 창 닫힘을 문장 순서가 아니라 스코프 수명에 묶음

## Design (결정 델타 · 실패 모드; 대안 매트릭스는 정본 [#203](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/203-2-worker-preconditions-analysis) 재사용)

### D2 — 엔진 소유: per-Job 확정
- **결정**: 배치 엔진을 실행 주체(executor) 소유로 격상(per-Job). 프리뷰(메인)는 `DashManager` 소유 유지.
- **근거**: 배치 executor 가 이미 스택 지역 객체(선언 `DashManager.cpp:977`·`:1033`, 호출 `:978`·`:1034`)라 엔진을 멤버로 올리면 별도 구조 없이 per-call 격리. executor 의 싱글톤 접근 제거(6곳)는 D5·D6 과 동일 수술. ("프리뷰/배치 named 2-instance" 는 배치 동시 실행 시 스케줄러 설정에 정확성이 의존해 기각.)
- **주의**: per-Job 엔진만으로는 D6 이 안 풀린다 — executor 가 `RunVolumeMorphing`(`:832`)을 경유하는 한 `DashManager` 의 `m_inputVTU`/`m_linearizedVTU`/`m_originalQuadraticCells` 를 계속 읽고 그 배열을 결과에 심는다. **D2 와 D6 은 같은 커밋에서 함께 처리**한다.

### D3 — M1 안전핀: 기전과 함정
- dangling 의 실제 기전은 "지역 `unique_ptr` 이 스코프 끝에서 소멸"이 아니라 "libstdc++/libc++ 의 `emplace`(`:44`)가 **중복 키 검사 전에 노드를 구성**하며 `ctx` 를 이미 move-out 시켜 폐기 노드와 함께 소멸"이다. 관측 결과는 같으나 수정 근거를 설명할 때 틀리기 쉽다.
- 따라서 `emplace`→`try_emplace` **교체만으론 미해소** — 사전 캡처한 raw(`:41`)를 그대로 반환하면 경합 시 여전히 폐기 노드를 가리킨다. 반환도 맵 이터레이터 경유여야 한다.
```cpp
auto [it, ok] = m_contexts.try_emplace(canon, std::move(ctx));
return it->second.get();
```
- 이 안전핀은 M2 자료구조 전환과 **독립** — 먼저 적용해도 무방.

### D3 — 접근 규약 = 양층(택일 아님) + 캐시 자료구조
- **접근 규약**: 심층 변이는 **직렬 풀 큐 전용**, 메인(위젯·렌더)은 **읽기 스냅샷만**. ([#203](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/203-2-worker-preconditions-analysis) "4-3" — either/or 아님.)
- **기존 위반자 존재**: `DashConditionParameterization`(`QAbstractTableModel`)이 메인 스레드에서 `editFeConditionEntry`(`:362`)로 심층 변이한다. 규약 도입 시 이 경로를 **큐 경유로 바꾸거나 배치 중 편집 차단** 둘 중 하나로 처리해야 한다 — "메인=읽기 전용"을 선언만 하고 두면 즉시 거짓이 된다.
- **캐시 값 타입**: `std::unordered_map<QString, std::shared_future<std::shared_ptr<DashAnalysisModelContext>>, QStringHash>` — 소유를 future 에 실어 dangling 원천 소거. **파급 목록(28곳)**:

### D3+D5 — 공용 읽기 스냅샷 (방향만)
- 메인 전달용 읽기 스냅샷을 D3·D5 가 **공용 값 복사 구조체 1종**으로 공유(핸들 poly DeepCopy·고정점 ID·표시용 요약 성격). 필드 스키마 확정은 구현 시 — 티켓 단계에선 "공용 1종" 만 못박음.

### D5 — 산출물의 성격
- D5 의 산출물은 수정 diff 가 아니라 **집행 가능한 규약(파라미터 금지 타입 화이트리스트) + 가드(assert)** 다. 규약만으로는 재발을 못 막고, assert 만으로는 무엇이 금지인지 안 남는다.

### D6 — 실패 모드 (처방 근거)
- 엔진 operator 의 3단 시퀀스(`SetInitialHandles`→`SetTargetHandles`→`Morph`)가 비원자다. 워커가 이 사이에 있을 때 메인이 프리뷰 모핑(`DashGeometryParameterWidget.cpp:1352`·`:1355`)을 돌리면 **크래시 없이 남의 핸들로 모핑한 형상이 그 케이스의 결과로 기록된다** — 조용한 오답이라 크래시보다 나쁘다.
- `m_midNodeMap` 순회 중 `assign`/`clear` 가 끼면 이터레이터 무효화 — 순수 UB.
- **처방**: 배치 경로가 만지는 그리드는 입력 스냅샷(DeepCopy)으로 진입하고, 결과 메시는 공유 셀배열을 심지 않는 경로로 조립. `RunVolumeMorphing` 을 배치용으로 쓰려면 "DashManager 상태를 읽지 않고 인자로만 도는" 오버로드가 필요하다 — D2 의 per-Job 엔진과 같은 수술 자리.

### D7 — 변이 창 처리: 원자 구간 + scope guard 복원
- **실패 모드**: 변이 창이 `exportSolverInput` 전체를 감싸므로, 워커 도입 시 메인 읽기(`getFeConditionValueString` · `activeContext` 경유 위젯 8곳)가 **주입값을 참값으로 관측**하고, 메인 편집(`DashConditionParameterization.cpp:362`)은 뒤따르는 restore 에 **덮여 소실**된다(lost update). D2·D6 을 다 해도 남는다 — 여기서 공유되는 것은 엔진·그리드가 아니라 **컨텍스트 그 자체**다.
- **결정**: inject→export→restore 를 D3 직렬 풀 큐의 **단일 작업 경계** 안에 넣고, 복원을 scope guard 로 옮긴다. 컨텍스트 사본 분리(배치 전용 인스턴스)는 2차 후보 — `.dat` 재파싱 비용과 `updateMeshPoints` 재적용 비용을 측정한 뒤 판단.
- **근거**: 사본 분리는 근본적이지만 컨텍스트 로드가 무겁고(레지스트리 캐시의 존재 이유) 배치 샘플 수만큼 반복된다. 원자 구간화는 기존 큐 인프라(D3 M2)를 그대로 쓰고 추가 자료구조가 없다.
- **주의**: 원자 구간을 택하면 "배치 실행 중 조건 편집 UI 는 비활성 또는 큐 대기"가 **사양**이 된다 — D3 양층 규약의 기존 위반자 처리와 같은 결정이다.

### D1 — 소멸 경로
- 두 싱글톤 모두 magic static, 소멸은 언어(정적 소멸 역순)에 위임([#203](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/203-2-worker-preconditions-analysis) "2-3" 방안 A).
- **주의**: `DashProjectManager::~DashProjectManager()`(`DashProjectManager.cpp:29-33`)가 현재 **미실행** → magic static 전환 시 정적 소멸에서 **최초 실행**되어 Qt/VTK teardown 순서와 상호작용 → 정적 소멸 안전성 확인 후 수렴.
- **#212 델타**: `~DashManager()`(`DashManager.cpp:126-144`)가 `stopDaemon()` → **`shutdownBlocking()` ×4**(QProcess 유한 동기 대기)로 바뀌었다. 현행 `atexit(Destroy)` 도 `main()` 반환 후 — `QApplication` 소멸 이후 — 에 돌므로 시점 자체는 magic static 과 사실상 동일하지만, "정적 소멸 중 블로킹 프로세스 종료"가 명시 사양이 된다. `Destroy` 제거 시 4개 데몬이 실제로 종료되는지(고아 프로세스 0건)를 D1 M2 검증 항목에 포함한다.

이 소멸자는 본 티켓의 magic static 전환으로 **생애 최초 실행**된다. 앞선 F3(a) 선-초기화 순서 반전(`Mgr()` → `Instance()`)은 `~DashModelRunner()` 의 `DashManager::Mgr()` 참조를 살리려는 것이었으나, 그 대가로 데몬 수거를 이 깨지는 체인 뒤로 밀어버렸다. 트레이드오프 판단 오류였다.

### 수정 (`2e27140`)

`~DashProjectManager()` 에서 `delete m_project` 제거. 자식 소멸자에 저장·flush 부작용이 없어(`delete m_configManager` · `m_preprocessor->Clear()` · 시그널 disconnect · job 취소) 프로세스 종료 시 OS 회수에 맡기는 편이 안전하다. `CloseProject()` 는 `m_project` 를 계속 사용하므로 유지.

## 후속 대상 (본 티켓 범위 밖) — 종료에 약 5초 소요

종료가 즉시 걸리지 않고 **live 데몬 수 × 최대 5초**가 걸린다. 원인을 직접 확인했다 — 실제 데몬 exe 가 stdin `exit` 를 **무시**한다:

```
DashOptiSensitivityEngine.exe daemon 에 "exit\n" 전송
→ 종료=False, 경과=9029 ms  (kill() 로만 정리됨)
```

`DashExtensionProcess::shutdownBlocking()` 은 `write("exit\n")` → `waitForFinished(kStopTimeoutMs=5000)` → 타임아웃 → `kill()` 순서라, 정상 종료 협상이 매번 실패하고 5초를 버린 뒤 kill 로 떨어진다. `tests/daemon_stub.cpp:146` 이 프로토콜을 명시하고 있다 — *"stop() writes 'exit'; without it the stop path degrades to kill."* 즉 스텁은 지키고 실제 데몬은 안 지킨다.

**분류: #212 기존 동작.** `shutdownBlocking()`·`kStopTimeoutMs` 는 #212 에서 도입돼 base(`b6d2cf6`)에 이미 있고, 그때도 `atexit(Destroy)` → `~DashManager()` 가 같은 경로를 탔다. 본 티켓 not-to-be 의 "데몬 종료 경로 재설계 없음" 에 해당해 여기서 고치지 않는다.

**출하 빌드 영향**: `BUILD_Dev=OFF` 는 `/SUBSYSTEM:WINDOWS` 라 콘솔이 없다. 창은 즉시 사라지고 프로세스만 조용히 5초 남다 종료되므로 사용자에게는 거의 보이지 않는다. 재실행 시 `reapDaemons()` 가 stale PID 를 정리하므로 상태 오염도 없다.

**후속 수정 후보**
1. 데몬 측에서 stdin `exit` 를 처리 (정공법 — 데몬 exe 는 별도 소유)
2. 앱 측에서 종료 경로의 정상 종료 협상을 생략하고 바로 `killProcessTree(m_daemonPid)` — 협상이 항상 실패하므로 5초가 순수 낭비다. `killProcessTree()` 는 같은 파일에 이미 있고 `reapDaemons()` 가 사용 중이며, `QProcess::kill()` 보다 견고하다(자식 트리까지 정리)
3. 타임아웃을 300ms 수준으로 축소 후 kill
