## Goal
케이스마다 **STP 생성 → 해석 실행** 두 단계를 거치는 DOE `.wbpj` 배치에 대해, 세 가지 표준을 세운다.

1. **이벤트 완전성** — 배치를 끝낼 수 있는 이벤트를 남김없이 열거하고, 전부 **단일 종료 지점**으로 수렴시킨다. `return` 으로 빠져나가는 경로 0.
2. **발신/수신 규약** — 모든 완료·실패 통지가 식별자를 동반하고, 수신 슬롯은 `귀속 → 전이 → 다음 행동` 3단 구조를 예외 없이 따른다.
3. **상태 표현** — **발신자 쪽**에 케이스 상태(단계 × 결과)와 배치 상태를 각각 단일 값으로 세우고, 전이는 단일 함수로만 일어난다. 수신자의 표현 층위(UI 라벨 어휘)는 현행 그대로 두고 투영으로 잇는다.

결과로 **모든 케이스가 정확히 한 번 종료 상태에 도달한다** — 배치를 떠나는 어떤 경로에서도.

> **범위 축소 — 규약 3축의 레퍼런스 구현이 #260 으로 이동 (2026-08-13 결정).** 위 3축은 **경로에 무관한 규약**이고, #260(모핑 DOE 배치 per-sample 분해)이 **환경 무의존 경로에서 먼저 구현·검증**한다. 근거: A 경로는 Step 1 이 NX, Step 2 가 Ansys 에 묶여 기능 검증이 환경 확보 시점까지 밀리는데, 모핑 stage 0 은 in-process 라 외부 설치 없이 전 AC 를 돌 수 있다 — 검증 불가 티켓을 먼저 랜딩하면 미검증 규약 위에 후속을 얹게 된다([205-4 (wiki)](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/205-4-morphing-pilot-work-redistribution) 3-4절·6-1절).
>

### 실행 흐름 (실측)

사용자는 **Start 를 한 번 누른다.** 두 단계는 내부 구조이며 사용자가 나눠 실행하지 않는다.

```
[사용자] Start 1회
   │   DashAnalysisLauncher::runDoeAsync(:1069) → generateInputCases(:1092, 동기)
   │   → DashJobRunner::generateInputCases(:1285 전 케이스 "Enqueued") → runWbpjDoeAsync(:1410)
   ▼

[Step 1] STP 생성 — 케이스별 순차
   │   stp1 → 완료 시그널 → stp2 → 완료 시그널 → … → stpN
   │   NX 데몬 큐가 직렬이라 한 번에 1건씩 처리된다
   │   ※ 케이스마다 완료/실패 이벤트가 온다
   ▼

[Step 2] 해석 — 전 케이스를 한 번에 넘김
   │   mgr->enqueueLaunch(...) 딱 1회 (:2940)
   │   페이로드 = DOE Table 전체 (전 케이스의 파라미터 값)
   │   ※ 케이스별 이벤트가 없다 — 완료 통지도 배치 단위 1건뿐
   ▼

[결과 판정] journalLaunchCompleted 1회 수신 후
       activeRunKeys 를 순회하며 각 run 디렉터리에서 .dat / .rst 존재를
       확인해 케이스별 Done/Failed 를 사후 판정한다 (:2883-2914)
```

두 단계의 **이벤트 입자 크기가 다르다**는 점이 이 티켓의 설계 전반을 좌우한다:

| | Step 1 (STP 생성) | Step 2 (해석) |
|---|---|---|
| 실행 단위 | 케이스 1건씩 순차 | 전 케이스 1회 launch |
| 진행 이벤트 | 케이스별 완료/실패 | **없음** — 완료 통지 1건뿐 |
| 케이스별 성패 판정 | 이벤트로 즉시 | **끝난 뒤 파일 스캔으로 사후** |
| 개별 케이스 중단 | 가능 (다음 케이스 미착수) | **불가** — 저널 데몬 종료뿐 |
| 대기 상한 | 케이스별 워치독 600s | **없음** — 통지가 안 오면 배치 전체 정지 |

GUI 는 DOE Table 전체를 한 번 던지고 완료 통지 1건을 받을 뿐이므로, 저널이 내부적으로 순차인지 병렬인지는 **GUI 가 알지 못한다.**

### 근본 원인 — 발신자가 사실(fact)을 들지 않고 표현(projection)만 던진다

**소유권 배치 자체는 정상이다.** 케이스 상태를 관리하는 것은 수신자(`DashAnalysisLauncher`)의 일이고, 발신자(`DashJobRunner`)의 일은 자기 진행을 이벤트로 알리는 것이다. `caseStatusUpdated` 를 사후 알림으로 읽는 것도 옳다. 문제는 **발신자가 알릴 내용을 스스로 알지 못한다**는 데 있다.

수신자 `DashAnalysisLauncher::onCaseStatusUpdated`(`model/DashAnalysisLauncher.cpp:1051`)는 받은 라벨 하나로 네 가지를 처리한다 — 네 가지 전부 **라벨만의 함수**라 수신측 처리에는 결함이 없다:

| 수신자가 하는 일 | 위치 |
|---|---|
| ① DOE JSON 의 해당 케이스 status 갱신 | `:1054` → `setSampleStatus`(`:997`) |
| ② `✓ 완료` / `✗ 실패` 로그 출력 | `:1035-1046` |
| ③ DOE Cases 표 갱신 | `:1048` → `DashDoeCasesWidget::updateCaseStatus`(`view/DashDoeCasesWidget.cpp:276`) |
| ④ **끝난 케이스 수 집계** — `Done`·`Failed`·`Cancelled` 이면 카운트 +1, 예정된 케이스가 전부 차면 `analysisFinished()` 발화 | `:1056-1066` |

④ 는 Start/Stop 버튼을 되돌리는 **경로 중 하나**다(`DashAnalysisLauncherWidget.cpp:486`). 나머지 둘은 `jobFinished`/`jobFailed` 직결이다 — 상세는 결함 3. 따라서 수신자의 상태는 **발신자가 보낸 것만큼만** 정확하다.

그런데 발신자에게는 케이스 진행을 담는 사실 층위의 장부가 없다. 그래서 장부를 거치지 않고 **표현(UI 라벨)을 직접** 방출하고, 저장은 별개로 `DashDoeConfigManager::setSampleStatus` 를 직접 부른다. 그 결과 상태를 바꾸는 지점 8곳이 셋 중 하나로 갈린다:

| 지점 유형 | 벌어지는 일 |
|---|---|
| 직접 저장 + 시그널 (5곳) | 같은 값이 **두 번** 저장된다 — 자기가 한 번, launcher 가 다시 한 번 |
| 시그널만 (3곳) | launcher 가 대신 저장하지만 **다른 경로**에 저장한다 (결함 1) |
| 둘 다 없음 | 케이스가 끝났는데도 ④ 의 카운트가 올라가지 않는다 (결함 3) |

어느 유형이 되는지를 강제하는 규칙이 없고, 그 자리에서 어떻게 썼느냐로 정해진다. 결함 5종은 전부 이 한 원인에서 파생된다:

```
발신자가 사실을 안 들고 표현만 던진다
   ├─ 자기 진행을 질의할 대상이 없다          → 결함 4 (Done·Cancelled 을 배치가 모른다)
   ├─ 방출 내용이 규칙이 아니라 작성 시점 판단  → 결함 1 (8곳이 5/3 으로 갈림)
   ├─ 방출을 빠뜨리면 수신자 회계가 멈춘다      → 결함 2·3
   └─ 남이 낸 통지를 자기 표현으로 접수한다      → 결함 5 (취소가 Failed 로 굳는다)
```

**"이벤트가 한 덩어리" 라는 관점에서 보면** — 라벨로 접는 것 자체는 오늘의 경계에서 무손실이다. 수신자가 하는 네 가지가 전부 라벨만의 함수이고, ④ 의 `Done||Failed||Cancelled` 문자열 비교도 현행 어휘 안에서는 종료 판정으로 정확하다. 실제로 덩어리가 무는 곳은 셋이다:

| | 실체 | 결과 |
|---|---|---|
| ① Step 2 이벤트 | 전 케이스에 대해 **배치 단위 1건** | per-case 성패를 이벤트가 아니라 **파일 스캔으로 사후 판정**해야 한다. 이 티켓 설계 전반을 좌우한다 |
| ② 실패 시그널 | `updatePrtGeometryBatchFailed(message)` — 식별자 없음 | 수신자가 귀속을 걸 수 없다 → D3 |
| ③ 라벨 어휘 | **단계**와 **사유**가 경계에서 소실 | STP 생성 실패도 `✗ ... analysis failed` 로 찍힌다. `caseLogUpdated` 가 상세를 따로 날라 완화되며, 잔여분은 범위 밖 |

### 결함 5종 (실측)

#### 1. 같은 "상태 바뀜" 인데 하는 일이 제각각이다

배치가 케이스 상태를 바꾸는 지점은 8곳이다(#212 의 STP 재사용 정책 변경으로 10곳에서 축소). **5곳은 화면 통지와 DOE JSON 기록을 둘 다 하고, 3곳은 화면 통지만 한다**(`:2616` 은 `"Running"`, `:2678` 은 `"Running"`, `:2755` 는 `"Cancelled"`).

| 지점 | 라벨 | 기록 |
|---|---|---|
| `:2616` STP 재사용 | `Running` | 시그널만 |
| `:2678` STP 성공 | `Running` | 시그널만 |
| `:2699`·`:2703` STP 실패 | `Failed` | 둘 다 |
| `:2755` 미착수 | `Cancelled` | 시그널만 |
| `:2894`·`:2895` DAT 없음 | `Failed` | 둘 다 |
| `:2906`·`:2907` RST 있음 | `Done` | 둘 다 |
| `:2911`·`:2912` RST 없음 | `Failed` | 둘 다 |
| `:2934`·`:2935` Journal 실패 | `Failed` | 둘 다 |

통지만 하는 3곳도 값 자체는 대개 맞게 저장된다 — launcher 가 통지를 받아 대신 기록해 주기 때문이다. 문제는 그 기록이 **다른 구현으로 다른 파일 경로**에 간다는 것이다. 직접 기록하는 5곳은 `DashDoeConfigManager::setSampleStatus`(`model/DashDoeConfigManager.cpp:526`)로 실행 시작 시점에 고정한 경로(snapshot)에 쓰고, launcher 는 **자체 구현**(`DashAnalysisLauncher::setSampleStatus`, `:997-1049` — `DashDoeConfigManager` 와 별개 코드)으로 지금 선택된 Set 의 경로(live `m_doeJsonPath`)에 쓴다. 실행 중 Set 을 바꾸면 두 경로가 갈라진다.

*(참조: "통지만 하는 3곳은 디스크에 안 남는다"로 읽으면 틀린다 — `onCaseStatusUpdated:1054` 이 첫 문장에서 기록하므로 **여덟 곳 다 저장된다**. 진짜 문제는 미기록이 아니라 **5곳의 이중 기록과 경로 이원화**다.)*

결국 "상태를 바꾼다" 는 한 가지 개념이 **서로 다른 부작용 조합 두 종류**로 나뉘어 있고, 어느 쪽인지가 규칙이 아니라 그 자리에서 어떻게 썼느냐에 달려 있다. 코드를 고칠 때마다 "여기서도 기록해야 하나" 를 매번 다시 판단해야 한다.

#### 2. Step 1 에서 취소하면 화면이 "Running" 에서 멈춘 채 끝난다

100건짜리 DOE 를 60건째에 취소하면 이렇게 된다:

| 케이스 | 결과 |
|---|---|
| 아직 시작 안 한 40건 | `Cancelled` — 정상 (`:2755`) |
| 이미 STP 를 만든 59건 | **`Running` 인 채로 방치** |

취소되면 `finishStpPhase`(`:2769-2776`)가 Step 2(해석 실행)를 건너뛰고 배치를 끝낸다. 그런데 그 59건의 최종 성패(`Done`/`Failed`)는 **Step 2 만이 정할 수 있다.** Step 2 가 돌지 않으니 아무도 이 케이스들을 마무리해 주지 않고, DOE Cases 표에도 DOE JSON 에도 `Running` 으로 남는다. 프로젝트를 다시 열어도 그대로다.

**이 경로는 어떤 job 시그널도 내지 않는다** — `jobFinished`/`jobFailed` 가 없어 Start 버튼도 잠긴 채 남는다(결함 3 과 동일 증상). `activeRunKeys` 가 빈 경우의 조기 이탈(`:2777-2782`)도 같다.

#### 3. 배치를 떠나면서 아무 통지도 하지 않는 지점이 7곳이다

Start 버튼을 되돌리는 경로는 **3개**이고, 셋 다 발신자의 방출에 의존한다:

| 경로 | 배선 | 발신 지점 |
|---|---|---|
| `jobFinished` → `analysisFinished` | `DashAnalysisLauncher.cpp:55` | `launchWbpjJournal:2915` (Step 2 완료 람다) |
| `jobFailed` → `analysisFailed` | `:56` | `launchWbpjJournal:2937` (Step 2 실패 람다) |
| 케이스 전원 종료 집계 | `:1056-1066` | `caseStatusUpdated` 방출 전부 |

*(정정: 이슈 초안의 "④ 가 유일한 정상 경로" · "`analysisFailed()` 도 없다" 는 오류다. 배선은 셋 다 존재하고, 문제는 **조기 이탈 지점이 셋 중 아무것도 발화하지 않는 것**이다.)*

배치를 떠나면서 케이스도 job 시그널도 건드리지 않는 지점이 7곳이다:

| 위치 | 조건 | 시점의 배치 상태 |
|---|---|---|
| `runWbpjDoeAsync:2444` | DashManager 없음 | 컨텍스트 미구성 |
| `:2450` | NX solver 없음 | 컨텍스트 미구성 |
| `:2456` | ANSYS 경로 미설정 | 컨텍스트 미구성 |
| `:2549` | **NX 설치 경로 미설정 + STP 부재** | 컨텍스트 미구성 |
| `launchWbpjJournal:2792` | DashManager 없음 | **Step 2 진입 후** |
| `finishStpPhase:2775` | 취소 | Step 1 종료 후 |
| `finishStpPhase:2781` | `activeRunKeys` 비어 있음 | Step 1 종료 후 |

이미 `analysisStarted()`(`DashAnalysisLauncher.cpp:1091`)로 버튼은 잠긴 상태다. 앞 4곳은 끝난 케이스 수가 0/100 에서 멈춰 `analysisFinished()` 가 영영 나오지 않는다. 결과는 **Start 는 비활성, Stop 은 활성인 채로 고정** — 앱을 다시 켜야 한다. NX 미설치·경로 오설정 환경에서는 매번 재현된다.

`launchWbpjJournal:2792` 는 이미 Step 1 을 마친 뒤라 전 케이스가 `Running` 으로 남고 결함 2 를 Step 2 에 그대로 재현한다. `finishStpPhase` 의 두 곳은 케이스 라벨은 확정되지만 job 시그널이 없어 집계 경로에만 의존한다 — `m_isLauncherRunTracking` 이 꺼져 있거나 `m_expectedRunKeys`(`:1071-1090`)와 키가 어긋나면 복구가 없다.

*(참조: `:2549` 는 #212 가 도입한 **설정 판정**이다. 기동 판정(`isDaemonReady()`)은 `start()` 가 비동기가 되면서 의미를 잃어 제거됐다.)*

#### 4. 케이스 상태를 알려면 네 군데를 뒤져야 한다

"이 케이스 지금 무슨 상태냐" 의 답이 한 곳에 없다. 리스트 4개의 소속으로 간접 표현된다 (`DashJobRunner.h:145-162`):

| 알고 싶은 것 | 확인해야 하는 곳 |
|---|---|
| 착수 대기 중인가 | `pending`(`:156`) 에 들어 있나 |
| 지금 진행 중인가 | `current`(`:157`) 인가 |
| STP 를 확보했나 | `activeRunKeys`(`:155`) 에 들어 있나 |
| 실패했나 | `failedKeys`(`:158`) 에 들어 있나 |
| **끝났나 (Done)** | **어디에도 없다** |
| **취소됐나** | **어디에도 없다** |

`Done` 과 `Cancelled` 은 화면에 쏘고 끝이라 배치 자신은 모른다. 그래서 **"모든 케이스는 반드시 한 번 끝난다" 같은 규칙을 쓸 대상 자체가 없다** — 검사할 상태값이 존재하지 않기 때문이다. 결함 2·3 이 오래 드러나지 않은 이유가 이것이다.

#212 가 부분 방어를 넣었다 — `current` 를 마감(`m_stpBatch.current = StpCase{}`, `:2680`·`:2695`)해 늦은 통지가 다음 케이스를 오판정하지 못하게 한다. 다중 소스 문제 자체는 그대로다.

#### 5. Analysis 단계 취소가 `Cancelled` 이 아니라 `Failed` 로 굳는다 (#212 이후 신규)

`cancelAllRuns:1002-1004` 는 배치 여부와 무관하게 `journal->stop()` 을 부른다. #212 이후 이 호출은:

```
cancelAllRuns:1003  journal->stop()
   │   DashExtensionProcess::stop(:121) → drainCommands(:240)
   ▼   emit commandFailed(launchId, "Daemon stopped before command finished.")
DashManager:114-116  → emit journalLaunchFailed(id, msg)
   ▼
launchWbpjJournal:2918 실패 람다 → 전 activeRunKeys 를 "Failed" 확정 (:2934-2935)
   ▼   emit jobFailed(:2937) → analysisFailed
```

전 구간 `AutoConnection` + 동일 스레드라 **`cancelAllRuns` 호출 스택 안에서 동기 실행된다.** 즉 사용자가 Stop 을 누른 결과가 DOE JSON 과 표에 `Failed` 로 기록된다.

버튼은 복구되므로(#212 의 개선분) 결함 2 의 Step 2 측면은 해소됐으나, **라벨이 취소가 아니라 실패다.** 본 티켓의 Q1-b(미완 케이스 `AnalysisCancelled`)를 그대로 구현하면 **순서에 따라 결과가 갈린다** — 스윕보다 `stop()` 이 먼저면 S2(종료 단조성)가 취소 스윕을 무시해 `AnalysisFailed` 로 굳는다. 순서 규약이 필요하다(Q1-b).

### 종합 — 두 단계 배치를 다루는 표준 3가지가 없다

위 결함들은 서로 다른 버그가 아니라, **각 케이스가 두 단계를 거치는 배치**를 다룰 때 필요한 표준 세 가지가 각각 비어 있어서 생긴다.

#### 축 1. 모든 이벤트를 고려하지 않는다

이벤트를 성격별로 나누면 빈틈이 드러난다.

| 분류 | 정의 | 이 배치에서의 실례 | 현행 |
|---|---|---|---|
| **진행** | 케이스가 앞으로 감 | STP 성공/실패 (케이스별) · Journal 성공/실패 (**배치 단위 1건**) | 처리됨 |
| **부재** | 와야 할 것이 안 옴 | 케이스 타임아웃 · 데몬 소실 · **착수 자체 불가** · **Journal 무응답**(= 배치 전체 정지) | 타임아웃 · 데몬 소실 (#212 로 통지됨) |
| **개입** | 배치 밖에서 들어옴 | 사용자 취소 · 재진입 요청 · Set/프로젝트 전환 | 취소 (Step 1 협조적 / Step 2 는 결함 5) |

현행은 **진행 이벤트만 1급으로 다루고** 나머지 둘은 임시 처리다. 그래서 조기 이탈은 이벤트가 아니라 그냥 `return` 이 되고(결함 3), Step 2 에는 대기 상한 자체가 없다. 데몬 소실은 #212 가 `commandFailed` 로 수렴시켜 이 축에서 빠졌다.

**Step 2 통지의 추가 결함 (실측)**: journal 완료·실패 핸들러 4곳이 전부 `launchId` 를 **무명 파라미터로 버린다** — `launchWbpjJournal` 의 `:2872`·`:2920`, `launchAnsysJournalDirect` 의 `:2388`·`:2411`. 다른 launch 의 완료/실패가 도착해도 그대로 수용된다. 배치 수명이 Step 2 까지 연장되면(Q1·Q2 귀결) 재진입 가드가 새 배치를 막아 주지만, `launchAnsysJournalDirect` 는 그 가드 밖이라 두 경로가 겹치면 오귀속이 가능하다.

**단, 대조할 식별자 자체가 배치를 식별하지 못한다** — `launchWbpjJournal:2940` 이 넘기는 `launchId` 는 `analysisType`, 즉 **템플릿 파일 basename**(`:1271`)이고 `launchAnsysJournalDirect:2422` 는 리터럴 `"Ansys"` 다. 같은 템플릿의 재실행은 동일 값이 되고, `.wbpj` 이름이 `Ansys.wbpj` 면 두 경로도 충돌한다. → 축 2 규약 **E1 을 Step 2 에 적용하려면 고유 launchId 발급(D7)이 선행**돼야 한다. `journalLaunch*` 의 소비자는 위 4곳뿐이고 전부 값을 버리므로(다른 구독자 0), 값 변경은 무영향이다.

#### 축 2. 이벤트를 발신/수신하는 표준이 없다

- **발신**: 성공 시그널은 `stpPath` 를 싣는데 실패 시그널은 `message` 만 싣는다(`DashSolverNxCad.h:44-45`). 수신자가 "이게 어느 케이스 것인가" 를 판별할 수 없다.
- **수신**: 슬롯 구조가 제각각이다. 완료 슬롯은 `stpPath` 대조(`:2669`), 실패 슬롯은 `current` 공백 검사(`:2689`) — #212 가 넣은 부분 방어이며 기준이 다르다. 정책 판단도 흩어져 있다 — 연쇄 실패 차단기는 `onStpCaseFailed` 안에(`:2707`), 취소 확인은 `startNextStpCase` 안에(`:2641`) 있다.
- **대기 상한**: Step 1 에만 워치독이 있고(`:2662`) Step 2 는 무제한이다.

#### 축 3. 발신자 쪽 상태 표현 표준이 없다

여기서 세울 표준은 **발신자의 사실 층위**다. 수신자의 표현 층위(라벨)는 이미 서 있고 바꾸지 않는다.

결함 4가 케이스 층위의 문제라면, **배치 층위에도 같은 문제가 있다.** 배치 자신의 상태가 `bool active` + `bool cancelled` 두 플래그로 흩어져 있어(`DashJobRunner.h:160-161`) "지금 Step 2 진행 중" 을 표현할 방법이 없다. 그래서 Step 2 도중 취소가 들어오면 처리할 자리가 없다 — 결함 5 가 이 빈자리에서 나온다.

## Technical Details

### 결정 사항

- **Analysis 단계 취소 = 즉시 중단, 스윕 먼저 (Q1-b)**: `cancelAllRuns()` 의 기존 `journal->stop()`(`:1002-1004`) 무조건 호출을 유지하되, **미완 케이스를 `AnalysisCancelled` 로 확정한 뒤에 `stop()` 을 부른다.** 순서가 규약이다.
  - **순서가 결과를 바꾼다 (결함 5)**: `stop()` 이 먼저면 그 호출 스택 안에서 drain → `journalLaunchFailed` → 전 케이스 `AnalysisFailed` 가 확정되고, 뒤이은 취소 스윕이 S2(종료 단조성)에 걸려 무시된다. 스윕이 먼저면 반대로 늦게 오는 `journalLaunchFailed` 가 S2 에 걸러진다.
  - **구조적 근거**: Step 2 는 전 케이스를 1회 launch 하므로 **개별 해석만 골라 취소할 수단이 애초에 없다.** 취소는 저널 데몬 종료뿐이고, 그러면 진행 중인 전 케이스가 동시에 죽는다. 협조적 취소가 선택지가 아니다.
  - **정책적 근거**: ANSYS 해석은 수 시간 돌 수 있어, 진행 중인 것을 끝까지 기다리는 것이 취소의 의미를 잃게 한다.
- **Step 2 대기 상한은 범위 밖 (Q2)**: 규약 E4("응답을 기다리는 모든 구간에 상한") 위반으로 **명시만** 하고 도입하지 않는다. Journal 해석의 현실적 상한값 산정 근거가 이 티켓 밖이다. → 별건.
  - 다만 **위험도는 Step 1 보다 높다**는 점을 기록해 둔다. Step 1 은 워치독이 케이스 단위로 끊어 배치가 계속 진행되지만, Step 2 는 완료 통지가 배치 단위 1건뿐이라 그것이 오지 않으면 **전부-아니면-전무**로 배치 전체가 멈춘다.
- **[Q1·Q2 의 귀결] 배치 수명이 Step 2 까지 연장된다**: `BatchPhase` 가 `Analysis` 를 표현해야 그 단계의 취소를 처리할 수 있으므로, 배치는 `journalLaunchCompleted`/`Failed` 까지 살아 있다. 대가로 **Step 2 상한이 없는 상태에서 Journal 이 응답하지 않으면 배치가 `Analysis` 에 갇혀 이후 실행을 막는다.** 탈출구는 Stop 버튼(`cancelAllRuns` → 강제 종결)이며, 이것이 유일한 회복 수단임을 명문화한다. Step 2 상한이 별건으로 들어오면 자동 해소된다.
  - 부수 이득: 배치가 Step 2 까지 살아 있으므로 재진입 가드가 Step 2 구간도 덮는다. 현행은 `finishStpPhase:2739` 가 `active` 를 내려 Step 2 진행 중 새 DOE 실행이 통과해 `m_stpBatch` 를 덮어쓴다.
  - 부수 단순화: 배치가 항상 살아 있으므로 Step 2 완료 람다도 `setCaseState` 를 직접 쓸 수 있다. 배치 수명 밖에서 쓸 무상태 전이 함수를 따로 둘 필요가 없다.
- **이중 기록은 유지한다 (D1)**: `DashJobRunner` 는 **snapshot** 경로(`m_stpBatch.doeJsonPath`)에 쓰고, 시그널을 받은 launcher 는 **live** `m_doeJsonPath` 에 다시 쓴다. 두 값은 정상 상황에서 같지만, 실행 중 Set 을 바꾸면 launcher 쪽이 다른 파일에 쓴다. JobRunner 직접 기록이 정본이므로 그대로 두고 균일 적용한다. launcher 의 live-path 기록 위험은 다른 5개 실행 경로에도 걸쳐 있어 범위 밖.
  - 부수 사실: 두 경로가 **서로 다른 뮤텍스**로 같은 파일을 지킨다 (`DashDoeConfigManager.cpp:23`·`:528` `g_statusFileMutex` vs `DashAnalysisLauncher.cpp:1002` `m_statusFileMutex`). 현재는 동일 스레드 순차 호출이라 경합이 없다.
- **조기 이탈은 이벤트로 승격한다 (D2)**: **7곳**이다 — `runWbpjDoeAsync` 의 `:2444`·`:2450`·`:2456`·`:2549`, `launchWbpjJournal` 첫머리의 `!mgr`(`:2792`), `finishStpPhase` 의 취소(`:2775`)·`activeRunKeys` 공백(`:2781`). 전부 `finishBatch(reason, sweepAs)` 로 수렴시키고, 이를 위해 배치 컨텍스트 구성(`:2552-2563`)을 앞 4곳보다 **앞으로** 옮긴다. 재진입 가드(`:2436`)는 살아 있는 배치가 있는 경우이므로 대상이 아니다 — 거부만 하고 반환한다.
  - `launchWbpjJournal:2792` 가 특히 중요하다. 이 시점엔 이미 `phase == Analysis` 라 그냥 `return` 하면 **배치가 `Analysis` 에 갇히고 전 케이스가 미종료로 남아 결함 3 을 Step 2 에 그대로 재현**한다.
  - `finishStpPhase` 의 두 곳은 케이스 라벨은 이미 확정돼 있지만 job 시그널이 없다 → `finishBatch()` 경유로 D8 을 함께 얻는다.
  - **범위 경계**: `DashManager::enqueueLaunch` 첫머리의 `if (!m_journalDaemon) return;`(`controller/DashManager.cpp:161-163`)은 아무 시그널도 내지 않는 **진짜 무음 경로**다. 본 티켓의 수정 대상 파일 밖이라 여기서 고치지 않지만, `launchWbpjJournal` 이 그 뒤로 완료 통지를 영영 못 받아 배치가 `Analysis` 에 갇힌다 — Step 2 상한 부재(Q2)와 같은 계열의 잔여 위험으로 기록한다. (#212 가 그 아래 기동 게이트를 제거해 "매 실행 즉시 실패" 위험은 해소됐다.)
- **배치 실패 시그널에 `stpPath` 를 실는다 (D3)**: 현재 `updatePrtGeometryBatchFailed(message)`(`DashSolverNxCad.h:45`)는 경로가 없어 실패 슬롯이 완료 슬롯과 같은 기준으로 귀속할 수 없다. `setBatchMode(true)`(`:2544`)가 첫 `connect`(`:2625`)보다 앞서므로, 데몬 큐에 남은 대화형 `updatePrt` 실패가 배치 케이스 1건에 오귀속될 수 있다. `emitFailure` 호출 2곳(`DashSolverNxCad.cpp:193`·`:211`) 모두 경로를 이미 갖고 있어 순변경 ~6줄이며, #249 의 태그 필터로 **그대로 승계**된다.
  - #212 가 넣은 `current` 공백 검사(`:2689`)는 늦은 통지 일부를 막지만 **기준이 완료 슬롯과 다르다** — 진행 케이스가 살아 있는 동안 도착한 남의 실패는 그대로 수용된다. D3 이 이 비대칭을 없앤다.
- **★ 타임아웃·데몬 소실 처리 (구 D4) — 폐기 (근거 교체)**
  - **결론**: `died()` 를 구독하는 `onNxDaemonStopped()` 신설안은 **폐기**한다. `onStpCaseTimeout`(`:2717-2734`)은 **무수정**이다.
  - **폐기 근거 (#212 랜딩 후 사실)**: `stop()` 과 사고사 모두 `drainCommands`(`DashExtensionProcess.cpp:240-259`)로 진행 중·대기 명령을 `commandFailed` 로 통지한다. 그 통지는 `DashSolverNxCad::onCommandFailed`(`:209-212`) → `emitFailure`(`:218-225`) → `updatePrtGeometryBatchFailed` 로 접혀 **기존 `onStpCaseFailed` 로 귀속과 함께 들어온다.** 별도 `died()` 구독은 중복 회계다.
  - **`onStpCaseTimeout` 이 무수정인 이유**: #212 가 이미 자기 실패 확정을 제거했다. 현행은 `stop()`(`:2731`)만 부르고 실패 회계를 drain 통지에 위임하므로, 축 3 의 `setCaseState` 단일 출구가 `onStpCaseFailed` 하나만 고쳐도 타임아웃 경로에 자동 적용된다. **이 슬롯에 전이문이 없다** — 넣으면 이중 계상이 된다.
  - **본 티켓에 남는 몫**: ⑴ 축 3 의 `setCaseState` 단일 출구로 실패 확정 경로를 하나로 모으고, ⑵ **D3** 로 어떤 실패 통지든 엉뚱한 케이스에 붙지 않게 막는다.
- **구독·batchMode 수명은 배치가 아니라 단계 scope 다 (D5)**: NX 구독과 `setBatchMode(false)` 는 현행처럼 **Step 1 종료(= `Stp → Analysis` 전이)** 에서 해제하고, Journal 구독만 `finishBatch()` 에서 해제한다.
  - **배치 수명(Q1·Q2 의 귀결)을 그대로 따라 `finishBatch()` 로 미루면 대화형 NX 가 죽는다.** `m_batchMode == true` 동안 `onCommandCompleted`(`DashSolverNxCad.cpp:202`)가 **모든** `updatePrtGeometry` 완료를 배치 시그널로 돌리는데, 대화형 호출자가 3곳 살아 있다 — `view/DashGeometryParameterCADWidget.cpp:798` · `view/DashModelRunnerWidget.cpp:454` · `view/DashOptimizerWidget.cpp:1624`. 해석 수 시간 동안 사용자가 지오메트리를 갱신하면 미리보기 STEP 로드(`view/DashMainWindow.cpp:278`)가 조용히 오지 않는다.
  - **해제 순서 규약 (신규)**: 단계 전이·종결에서 `setBatchMode(false)` 는 **`stop()` 보다 나중**이다. 현행 `finishStpPhase` 는 `:2748` 에서 `setBatchMode(false)` 를 한 뒤 취소 경로 `:2772` 에서 `stop()` 을 불러 순서가 뒤집혀 있다. 그 사이 in-flight 가 남아 있으면 drain 통지가 `emitFailure` 의 `else` 분기로 빠져 **`loadPrtFailed` → `DashMainWindow.cpp:271-276` 의 `QMessageBox` 모달**이 뜬다. 현행은 취소 경로 진입 시 `current` 가 이미 마감돼 미발현이지만, 규약으로 고정해 재발을 막는다.
  - `finishBatch()` 는 `phase` 를 먼저 `Idle` 로 내린 뒤 데몬 정지를 호출한다 — 그래야 자기 유발 정지가 만드는 뒤늦은 통지가 `phase` 가드에 걸러진다.
- **`cancelAllRuns` 의 NX 데몬 정지 조건 (D6)**: 현행은 `!stpBatchRunning` 일 때만 `nxCad->stop()` 을 부른다(`:997-1001`). 이 조건이 `phase != Idle` 로 바뀌면 **Analysis 단계 취소 시 NX 데몬이 살아남는다** (현행은 `active` 가 이미 false 라 죽는다). Step 2 구간의 NX 데몬은 유휴이므로 그대로 두는 것이 P1(완료분 보존) 정신에 맞고, 다음 배치가 재사용한다. 의도된 변화로 명시한다.
- **고유 launchId 를 발급한다 (D7 · 신규)**: `launchWbpjJournal` 이 `enqueueLaunch` 에 넘기는 식별자를 `analysisType` 에서 **배치별 고유값**으로 바꾼다(단조 증가 seq 를 붙인 `doe:{analysisType}:{n}` 형태). 그러지 않으면 E1 의 Step 2 대조가 같은 템플릿의 재실행을 가르지 못한다.
  - `journalLaunchCompleted`/`Failed` 의 소비자는 `DashJobRunner` 의 4곳(`:2387`·`:2410`·`:2870`·`:2918`)뿐이고 전부 값을 버리므로, 값 규약 변경은 다른 코드에 무영향이다. `DashManager` 는 식별자를 echo 만 하므로 무변경.
  - `launchAnsysJournalDirect`(`:2422`)의 `"Ansys"` 는 본 티켓 범위 밖이다 — 대조 추가만 하고 발급 규약은 건드리지 않는다.
- **`finishBatch()` 가 job 시그널을 낸다 (D8 · 신규)**: 종결 시 `jobFinished()`(정상 완료) 또는 `jobFailed(reason)`(착수 불가·**취소**·전건 실패)를 방출한다. **취소가 실패 채널인 것은 G2 의 결정이며, 초안의 "취소 = 정상 채널" 은 폐기됐다.** 이미 배선된 `analysisFinished`/`analysisFailed`(`DashAnalysisLauncher.cpp:55-56`)를 타므로 **Start 버튼 복구가 케이스 스윕·집계와 독립적으로 보장**된다. 스윕(S3)은 표·DOE JSON 정합성 몫으로 남는다.
  - 현행 Step 2 완료 람다의 `jobFinished`(`:2915`)·실패 람다의 `jobFailed`(`:2937`)는 `finishBatch()` 로 이관해 방출 지점을 하나로 만든다.
- **배치 스코프 상태는 장부 옆 한 벌이다 (D9 · 2026-08-17 추가)**: 장부를 A·C·F 공용으로 만든 뒤에도 **취소 플래그와 P3 카운터가 경로별로 두 벌** 남으면 결함 4(다중 소스)가 형태만 바꿔 재발한다. 배치는 동시에 하나뿐이므로(재진입 가드가 강제) 한 벌로 합친다.
  - `m_morphCancelled` + `StpBatch::cancelRequested` → **`m_batchCancelled`** · `m_morphConsecFail` + `StpBatch::consecFail` → **`m_batchConsecFail`** · `kMorphConsecFailLimit` + `kStpConsecFailLimit` → **`kBatchConsecFailLimit`**
  - **케이스 상한 2종(`kStpCaseTimeoutMs` · `kMorphSampleBudgetMs`)은 합치지 않는다** — 값이 같은 것은 우연이고 재는 대상이 다르다(NX 데몬 응답 vs in-process 샘플 실행). 합치면 한쪽 조정이 다른 쪽을 끌고 간다.
  - **`beginBatch(keys, stages, terminal, ctx)` 신설** — 장부와 배치 스코프 상태를 세우는 **단 한 곳**이며 `finishBatch()` 가 비우는 단 한 곳과 짝을 이룬다. A 는 `phase` 를 그 호출 옆에서 세워 `phase` 와 `hasBatch()` 가 갈리는 틈을 없앤다.
  - 부수 효과: P3 카운터가 `m_stpBatch` 밖으로 나가면서 **"전이가 배치를 종결시키면 카운터가 리셋된다"** 는 순서 의존이 사라진다 (구현 중 잡은 결함 3의 구조적 제거).
  - 이관으로 이름이 사실과 어긋난 둘도 바로잡는다 — `morphingBatchActive()` → **`batchActive()`**(장부가 공용이라 A 도 포함), `solverStage()` → **`morphSolverStage()`**(스테이지 번호는 경로마다 뜻이 달라 모핑에만 유효).
- **활성 케이스 0건도 종결 이벤트다 (D10 · 2026-08-17 추가)**: 활성 케이스가 0건이면 `begin()` 이 **빈 장부**를 만들어 `hasBatch()` 가 거짓이 된다. 종결 판정을 `hasBatch()` 로 하면 job 시그널 없이 `return` 해 Start 가 잠기고 이후 실행이 재진입 가드에 영구 차단된다 — 본 티켓이 없애려는 결함 3 그 자체다.
  - 판정 기준은 **"이 배치가 아직 안 끝났는가"(`phase == Stp`)** 이지 "장부에 키가 있는가" 가 아니다. 스윕이 마지막 케이스를 닫았으면 그 자리에서 종결돼 `phase` 가 `Idle` 로 내려가므로 이중 방출도 함께 막힌다.

## Design

### 현황 분석

- 케이스 상태가 `StpBatch` 의 컨테이너 4개(`pending`·`current`·`activeRunKeys`·`failedKeys`, `DashJobRunner.h:155-158`)에 분산돼 있고, `Done`/`Cancelled` 은 배치 장부에 표현조차 없다.
- 배치 상태가 `bool active` + `bool cancelled`(`:160-161`)로 흩어져 `Analysis` 단계를 표현하지 못한다. 결함 5(Analysis 취소가 `Failed` 로 굳음)가 이 빈자리에서 나온다.
- 배치를 끝내는 경로가 정상 완료 · 취소 · 연쇄 실패 차단 · nxCad 소실 · 조기 이탈 7곳으로 갈리는데 수렴 지점이 없다.
- 타임아웃 경로(`:2717-2734`)는 `stop()` 만 부르고 실패 회계를 drain 통지에 위임한다 — #212 가 정리한 형태이며 축 3 의 단일 출구와 이미 정합하다. **본 티켓 무수정.**
- 실패 슬롯 `onStpCaseFailed`(`:2685`)의 가드는 `!active || current.runKey.isEmpty()`(`:2689`)로, 완료 슬롯(`:2669`)의 `stpPath` 대조와 **기준이 다르다.** 이는 슬롯 잘못이 아니라 **연결된 시그널(`updatePrtGeometryBatchFailed(message)`)에 식별자가 없기 때문**이다 — 상류 `DashSolverNxCad::onCommandFailed`(`:209-212`)가 `commandId` 를 동사 판별에만 쓰고 경로를 버린다. D3 이 고치는 지점이 정확히 여기다.
- 두 단계의 이벤트 입자 크기가 다르다 (Step 1 = 케이스별, Step 2 = 배치 단위 1건 + 파일 스캔 판정). 규약은 이 비대칭을 인정한 위에서 세워야 한다 — 저널에 per-case 통지를 요구하는 방향은 범위 밖이다.
- **입자 비대칭의 표본이 2종으로 늘어난다 (#260 후).** 본 티켓 초안은 A 1표본으로 비대칭을 기술했으나, #260 이 C·F 를 per-sample 로 분해하면 조합이 갈린다 — **A = "per-case → 배치"**, **F = "per-case → per-case"**(`startNextMotionLauncher:835`, `m_motionLauncherQueue` 가 `runKey` 별). 규약이 두 조합을 다 통과해야 일반화되므로, 일반성 서술 보강은 본 티켓 착수 시 수행하고 BatchRunner 추출 티켓의 근거로 넘긴다.
- **#260 이 같은 규약을 먼저 구현했다 (랜딩 완료, b2b8e7f).** 모핑 경로의 해당 결함은 증상이 다르고 원인이 같았다 — 조기 이탈 7곳(파사드 3 + executor 3 + 루프 1)이 케이스 통지 0건 · 성공 통지 0건(실패 전용 6곳) · 상태 변경이 `setSampleStatus` 직접 호출로 산발. 본 티켓의 조기 이탈 6곳과는 **다른 집합**(A 경로 `runWbpjDoeAsync`)이므로 계수를 혼동하지 말 것.
- **A 는 C 와 같은 2칸 격자다 (이관 근거).** `DashBatchLedger::begin(keys, 2, 1)` 이 그대로 맞고, 251 초안의 flat enum 8종이 `2 × (Pending + 결과 4종)` 에 손실 없이 들어간다. `terminalStage` 를 stage 0 으로 낮추면 G1 의 "STP 만 생성" 배치가 되고, 이는 #260 의 "모핑만" 배치(`:2100`·`:2131`)와 동일 기전이다.
- **다만 장부가 못 답하는 질문이 하나 있다** — "지금 stage 0 을 돌고 있는 케이스가 누구인가". `currentStage()` 는 *Done 이 아닌 첫 칸*을 줄 뿐 그 칸의 상태를 주지 않아, 워치독이 진행 케이스를 특정할 수 없다. M2 접근자가 이 구멍을 메우며, 없으면 인덱스 멤버가 부활한다.
- **`caseLogUpdated` 는 현재 A 경로 전용이다** — `setStageState`(`:1138-1166`)는 `logMessage` 만 내고 케이스별 로그를 내지 않는다. 이관 시 M1 없이는 표의 로그 열이 죽는다.
- Step 2 식별자가 배치를 식별하지 못한다 (`analysisType` = 템플릿 basename). E1 적용에 D7 이 선행한다.
- 수신측(표현 층위)은 이미 완비 — `DashAnalysisLauncher` 가 기록·로그·표 갱신·완료 집계를 모두 수행하고, 넷 다 라벨만의 함수라 손댈 곳이 없다. `jobFinished`/`jobFailed` 배선(`:55-56`)도 이미 있어 D8 은 방출만 추가한다. **비어 있는 것은 발신측의 사실 층위이며, 신설할 인프라 없이 규약만 세우면 된다.**
- 영향 심볼: `DashJobRunner::{runWbpjDoeAsync, startNextStpCase, onStpCaseCompleted, onStpCaseFailed, finishStpPhase, launchWbpjJournal, cancelAllRuns}` · `DashSolverNxCad::emitFailure`.

### 대안 비교 — 케이스 상태 표현 (축 3)

### 선택 — 방안 F(배열형 장부 이관) + 3축 규약

**선택 근거**: 결함 5종이 모두 "발신자가 사실을 안 들고 표현만 던진다" 는 한 원인에서 나오므로, 세 축에 각각 규약을 세우면 함께 해소된다. **3축 규약 자체는 무변경이고, 사실 층위를 어디에 두느냐만 바뀐다** — #260 이 랜딩한 `DashBatchLedger` 가 이미 축 1(단일 종료 지점 `finishBatch`)·축 3(단일 전이 `setStageState`, 종료 단조성 `closed`)을 구현했고, A 가 그 위에 얹힌다. 축 2(귀속 → 전이 → 다음 행동)는 A 고유분이라 4de56d7 의 슬롯 구조를 그대로 쓴다.

방안 A(flat enum)를 버리는 결정타는 셋이다 — ⑴ `finishBatch` 오버로드 충돌로 **머지 후 컴파일이 안 된다** ⑵ 어휘 2벌은 개명으로 안 없어진다 ⑶ 251 을 #260 뒤로 미룬 이유가 "환경 무의존 검증" 이었는데, flat enum 은 A 의 상태 층위를 NX·ANSYS 환경 확보 시점까지 미검증으로 남긴다.

층위가 이렇게 갈린다 — `DashBatchLedger::apply()` 가 경계의 투영 함수이고, `caseStatusUpdated` 시그니처를 바꾸지 않는 근거가 여기 있다:

```
발신자 (DashJobRunner)          사실   DashBatchLedger        ← #260 이 신설, 본 티켓이 A 를 얹음
                                       케이스당 stage 배열 (A = 2칸)
        │
        │ apply() → Transition{applied, status, caseClosed}
        │            투영 (사실 → 표현) · applied 일 때만 방출
        ▼
수신자 (DashAnalysisLauncher)   표현   Running/Done/Failed/Cancelled   ← 현행 유지
                                → 기록 · 로그 · 표 · 종료 집계 (넷 다 라벨만의 함수)
```

**A 의 8종 ↔ 장부 대응** (손실 0 · 불가능 조합 0):

| 251 초안 `CaseState` | 장부 |
|---|---|
| `StpPending` | stage 0 `Pending` — `begin()` 초기값, 통지 없음 |
| `StpRunning` | stage 0 `Running` |
| `StpFailed` · `StpCancelled` | stage 0 `Failed` · `Cancelled` (둘 다 `caseClosed`) |
| `AnalysisPending` | stage 0 `Done` → `"Running"`, `caseClosed = false` |
| `AnalysisSucceeded` | stage 1 `Done` → `"Done"`, `caseClosed` |
| `AnalysisFailed` · `AnalysisCancelled` | stage 1 `Failed` · `Cancelled` |

**기각된 대안**: A 는 위 셋 · B 는 실패 분해 실패 + 발명 용어 · C 는 불가능 조합 허용 · D 는 전제 오류(소유권은 이미 launcher 에 있다) · E 는 부채 존치.

### 축 1 규약 — 이벤트 완전성

- **A1 수렴** — 배치를 끝낼 수 있는 모든 이벤트가 `finishBatch()` **한 지점**으로 모인다. `return` 으로 빠져나가는 종료 경로 0. 종결 시 job 시그널 1건을 반드시 낸다(D8). 도달 경로는 둘뿐이다:
  - **자연 종결** — 마지막 케이스가 터미널에 닿는 순간 `setStageState` 안에서(`:1163`). A 는 Step 2 완료 람다가 전 케이스를 순회 전이하므로 마지막 케이스에서 자동으로 난다 — 별도 종결 호출이 필요 없다.
  - **강제 종결** — `abortBatch(reason, state)` 가 `openKeys()` 전량을 닫고 `finishBatch(reason)` 로 떨어진다. 251 초안의 `finishBatch(reason, sweepAs)` + S3 스윕이 여기에 **그대로 흡수**된다.
- **A2 부재의 명시화** — "안 오는 것" 을 이벤트로 승격한다.
  - **케이스 타임아웃** → 현행 경로 유지. `stop()`(`:2731`) → drain → `commandFailed` → `onStpCaseFailed` → `setStageState(key, 0, Failed)` → `advance()` 로 수렴 (슬롯 무수정 — 구 D4 참조)
  - **데몬 소실** → 위와 동일 경로. #212 의 `reportDeath`(`DashExtensionProcess.cpp:233-238`)가 `drainCommands` 로 `commandFailed` 를 내므로 **즉시** 실패로 확정된다. 별도 구독 없음
  - **착수 불가** → `abortBatch(reason, Failed)` (조기 이탈 6곳)
  - **Step 2 오귀속** → 고유 launchId 발급(D7) + 핸들러 4곳에서 대조 (E1)
  - Journal 무응답 → **미처리**. 규약 E4 위반으로 명시 (Q2 제외)
- **A3 개입의 단계별 정의**

| 개입 | `BatchPhase::Stp` | `BatchPhase::Analysis` |
|---|---|---|
| 사용자 취소 | 협조적 — 진행 1건 완료 수용(P1), 잔여 미착수(P2). NX 데몬 유지 | **즉시 중단** — `abortBatch("cancelled by user", Cancelled)` **먼저**, 그 다음 `journal->stop()` (Q1-b). NX 데몬은 유휴이므로 그대로 둔다 (D6) |
| 재진입 요청 | 거부 | 거부 |
| Set/프로젝트 전환 | 범위 밖 (snapshot 이 부분 방어) | 범위 밖 |

`abortBatch` 의 스윕은 `openKeys()` 순회 + `currentStage(key)` 귀속이라 **미착수분은 stage 0 `Cancelled`, STP 확보분은 stage 1 `Cancelled`** 로 자동으로 갈린다 — 251 초안이 `sweepAs` 3항 연산자로 하던 분기가 장부 질의로 대체된다(`tst_batch_ledger::abortPattern_closesEveryOpenKeyExactlyOnce` 가 잠근 형태).

### 축 2 규약 — 발신/수신

- **E1 발신** — 모든 완료·실패 통지는 `(식별자, 결과, 상세)` 를 동반한다. 식별자 없는 방출 금지. → D3 로 실패 시그널에 `stpPath` 부여, D7 로 Step 2 식별자를 배치 고유값으로. 궁극 형태는 #249 의 요청 태그 왕복.
  - 식별자의 **입자 크기는 이벤트가 실제로 갖는 단위**를 따른다. Step 1 은 케이스(`stpPath`), Step 2 는 배치다. Step 2 의 케이스별 성패는 이벤트가 아니라 파일 스캔에서 나오므로 E1 의 대상이 아니다 — 저널에 per-case 통지를 요구하는 것은 이 티켓의 범위가 아니다.
- **E2 수신** — 슬롯은 `귀속 확인 → 상태 전이 → 다음 행동` 3단 고정. **슬롯 안에서 정책을 판단하지 않는다.**
- **E3 구독·모드 수명 = 단계 scope** — 구독은 **자기가 속한 단계**가 끝날 때 해제한다. 배치 scope 가 아니다 (D5).
  - NX 구독 + `setBatchMode(false)` → `Stp → Analysis` 전이에서 해제 (현행 `finishStpPhase:2743-2749` 위치 유지)
  - **해제 순서**: 같은 지점에서 데몬을 세운다면 `stop()` 이 `setBatchMode(false)` 보다 **먼저**다 — 뒤집히면 drain 통지가 `loadPrtFailed` 로 빠져 대화형 모달이 뜬다 (D5)
  - Journal 구독 → `releaseStpBatch()`(M4, `finishBatch()` 가 호출)에서 해제. 현행은 완료/실패 람다 **안에서** 각자 해제해(`:2873-2878`·`:2921-2926`) 취소 경로가 새는데, 이를 종결 단일 지점으로 옮기고 heap `QMetaObject::Connection*` 3개(`:2863-2865`)를 멤버 2개로 줄인다 (빈 람다 `connLog` 삭제)
  - 상시 구독 금지 ([#194](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/194-1-async-execution-patterns) 4절)
- **E4 대기 상한** — 응답을 기다리는 모든 구간에 상한. **Step 2 미충족** (Q2 로 제외, 별건).

E2 를 적용하면 슬롯이 이렇게 된다. 차단기·취소 확인·종료 판정이 전부 `advance()` 한 곳으로 모인다:

```cpp
void DashJobRunner::onStpCaseFailed(const QString& stpPath, const QString& message)
{
    const QString key = m_stpBatch.runKeyForStp(stpPath);     // 1. 귀속 (완료와 동일 기준)
    if (key.isEmpty()
        || m_ledger.stageState(key, kStpStage) != DashStageState::Running) {
        return;                                               //    남의 실패 · 늦은 통지
    }
    m_stpWatchdog->stop();
    setStageState(key, kStpStage, DashStageState::Failed, message);   // 2. 전이
    advance();                                                        // 3. 다음 행동
}
```

귀속이 `stpPath → runKey` 역인덱스 + **stage 0 이 `Running` 인가** 두 조건으로 바뀐다. 251 초안의 `runningIndex()`(StpRunning 인 유일 케이스 선형 탐색)와 판정 내용은 같고, 상태 소스가 장부로 옮겨간 것뿐이다. M2 접근자가 필요한 자리가 여기와 `onStpCaseTimeout` 이다.

### 축 3 규약 — 상태 표현

세 규약 전부 **#260 이 랜딩한 `DashBatchLedger` 에 이미 구현돼 있다.** 본 티켓은 A 를 그 위에 얹을 뿐 새로 세우지 않는다.

- **S1 단일 출구** — 케이스 전이는 `setStageState()` 만. 사실(장부)을 갱신하고 그 **투영**(기록·통지)을 같은 자리에서 내보낸다 — 표현이 사실을 앞지르는 경로를 없앤다. 장부의 `Transition{applied, status, caseClosed}` 가 "전이 1회 = 통지 1회" 를 판정한다.
  - **초안의 "빈 라벨이면 생략" 은 폐기한다 (G4).** 그 조항은 "빈 문자열 emit 이 `DashDoeCasesWidget:300` 의 `setText("")` 로 `Enqueued` 표기를 지운다" 는 사고를 막는 우회로였는데, 장부는 `Pending` 전이를 `applied = false` 로 아예 버리므로(`DashBatchLedger.cpp:80-81`) **같은 사고가 구조적으로 불가능**하다. 대신 stage 0 `Running` 이 `"Running"` 을 내므로 표기가 STP 성공이 아니라 **착수 시점**에 바뀐다 — C·F 와 같은 타이밍이다.
  - `BatchPhase` 는 케이스 상태가 아니라 A 의 **단계 컨텍스트**다. 부작용이 없어 전용 setter 를 두지 않고, 리셋은 `releaseStpBatch()`(M4) 한 곳이 맡는다.
- **S2 종료 단조성** — 터미널 도달 후 재전이는 `applied = false` 로 무시된다(`DashCaseRecord::closed`, `apply:67-69`). 늦은 시그널이 확정된 상태를 되돌리지 못한다. **Analysis 취소의 정확성이 여기에 걸려 있다** — `abortBatch` 로 stage 1 `Cancelled` 을 확정한 뒤 도착하는 `journalLaunchFailed` 를 이 규약이 걸러야 취소가 `Failed` 로 덮이지 않는다(결함 5). (완료 집계의 중복은 이미 `m_completedRunKeys` 가 `QSet`(`DashAnalysisLauncher.h:202`, insert `:1058`)이라 방어된다 — S2 의 실효는 상태 되돌림 차단 쪽이다.)
  - 초안이 요구한 "경고 로그" 는 두지 않는다. 장부는 조용히 버리며, A 의 정상 경로(취소 후 늦은 통지)가 **기대되는** 무시라 경고가 오히려 소음이다.
- **S3 종료 스윕** — `abortBatch(reason, state)` 가 `openKeys()` 전량을 `currentStage()` 칸에 귀속시켜 확정하고 `finishBatch(reason)` 로 떨어진다. 스윕은 표·DOE JSON 정합성 몫이고, 버튼 복구는 D8 의 job 시그널이 독립적으로 보장한다.

#### 케이스 상태 전이

stage 2칸 · 각 칸 `DashStageState` 5종. `terminalStage = 1` (G1 로 0 하향 가능).

```
[종결] 마지막 케이스가 터미널에 닿으면 setStageState 안에서 finishBatch() (D8)
```

**stage 1 에 `Running` 을 쓰지 않는다** — Step 2 는 전 케이스를 1회 launch 하고 **케이스별 진행 신호가 오지 않으므로**, `Pending` 과 구분할 정보가 애초에 존재하지 않는다 (실행 흐름 표 참조). stage 0 `Done` 이 이미 `"Running"` 을 냈으므로 UI 표기도 부족하지 않다. 저널이 per-case 통지를 내게 되면 그때 additive 추가.

#### 배치 상태 전이

```
Idle ─runWbpjDoeAsync─→ Stp ─전 케이스 stage 0 마감─→ Analysis ─journalLaunch 완료/실패─→ Idle
        │                 │   (NX 구독·batchMode 해제)         │
        └─────────────────┴─────────────────────────────────────┴──→ Idle
                                       (모든 종료가 finishBatch() → releaseStpBatch() 경유)
```

`Finished` 상태는 두지 않는다 — 관측자가 없다. 재진입 가드는 `phase != Idle`, 이중 종료는 `finishBatch()` 선두의 `if (!m_ledger.hasBatch()) return;`(`:1186`, #260 이 이미 가진 것)로 충분하다. **결함 5 의 이중 종결(취소 처리 + 뒤이은 `journalLaunchFailed`)을 막는 것이 이 가드다.**

`phase` 와 `m_ledger.hasBatch()` 는 **같은 지점에서만** 바뀐다 — `runWbpjDoeAsync` 가 둘을 함께 세우고, `finishBatch()` 가 `m_ledger.clear()` 와 `releaseStpBatch()`(M4)를 나란히 부른다. 두 번째 소스가 아니라 **같은 소스의 두 뷰**임을 이 배치로 강제한다.

취소는 단계와 직교하므로(어느 단계에서든 올 수 있다) 상태로 접지 않고 플래그로 둔다. #260 의 `m_morphCancelled` 와 같은 역할이라, **D9 로 둘을 `m_batchCancelled` 한 벌로 합쳤다**.

## Acceptance Criteria

**축 0 — 장부 단일화 (신규 · 이관의 핵심 판정)**
- `DashJobRunner` 안에 케이스 상태 저장소가 **`m_ledger` 하나**뿐 — `CaseState`·`uiLabel`·`isTerminal`·`setCaseState`·A 전용 `finishBatch` 심볼 0건, `finishBatch` 오버로드 1개
- `tests/tst_batch_ledger.cpp` 전항 통과 + M2 케이스 1건 추가분 통과
- M1 적용 후 **모핑 경로(C·F)에서도 케이스별 로그가 DOE Cases 표에 뜬다** (이관 전에는 wbpj 전용)
- `phase != Idle` 과 `m_ledger.hasBatch()` 가 갈리는 코드 경로 0건 — 둘을 세우는 지점(`beginBatch()` 호출 + 바로 옆 `phase` 대입)과 비우는 지점(`finishBatch()` → `releaseStpBatch()`)이 각각 1곳
- **배치 스코프 상태가 경로별로 두 벌이 아니다 (D9)** — 취소 플래그 1개 · P3 카운터 1개 · 차단기 상수 1개. `m_morphCancelled`·`cancelRequested`·`m_morphConsecFail`·`StpBatch::consecFail`·`kMorphConsecFailLimit`·`kStpConsecFailLimit` 심볼 0건
- **이름이 사실과 어긋나는 심볼 0건** — `morphingBatchActive`(A 도 포함) · `solverStage`(모핑 전용) 잔존 참조 0건

**축 1 — 이벤트 완전성**
- 배치를 끝내는 경로가 `finishBatch()` **한 곳**으로 수렴 — `runWbpjDoeAsync`·`finishStpPhase`·`launchWbpjJournal` 을 통틀어 배치를 종료하면서 `finishBatch()`/`abortBatch()` 를 거치지 않는 `return` 0건
- 배치 종료 이벤트 6종(정상 완료 · 사용자 취소 · 연쇄 실패 차단 · 케이스 타임아웃 누적 · 데몬 소실 · 착수 불가) 각각에 대해 **전 케이스가 터미널에 도달**함을 추적으로 확인
- **조기 이탈 6곳**(DashManager 없음 / NX solver 없음 / NX 설치 경로 미설정 / `launchWbpjJournal` 의 DashManager 없음 / 취소 / STP 확보분 0건)에서 `jobFinished()` 또는 `jobFailed()` 발화 → Start 버튼 정상 복구 (현재는 잠김)
- **배치 진입 전 무음 이탈 3곳**(`generateInputCases` wbpj 분기 `:1902`·`:1919`·`:1923`)이 `jobFailed()` 발화 — wbpj 경로에서 job 시그널 없이 `return` 하는 지점 0건 (G5)
- **활성 케이스 0건인 배치도 job 시그널을 낸다 (D10)** — 전 케이스를 비활성화하고 Start 를 눌러도 Start 가 복구되고 다음 실행이 재진입 가드에 막히지 않는다. 종결 판정이 `m_ledger.hasBatch()`(빈 장부에서 거짓)가 아니라 `phase == Stp` 다
- 버튼 복구가 **케이스 집계와 독립** — `m_expectedRunKeys` 가 비어 있어 집계 경로가 꺼진 상태에서도 조기 이탈 6곳 + 진입 전 3곳이 버튼을 되돌린다
- NX 데몬 크래시·타임아웃 시 진행 케이스가 **즉시** stage 0 `Failed` 로 종료 (#212 의 drain 통지 경유 — 워치독 만료를 기다리지 않는다)
- **타임아웃 직후 착수한 다음 케이스가 오귀속 실패하지 않음** — 데몬 정지 1회당 실패 확정 1건, 대상은 정지 시점의 진행 케이스
- **Step 2 완료·실패 핸들러가 배치 고유 `launchId` 를 대조** — 무명 파라미터로 버리는 지점 0건, 대조 대상이 `analysisType` 같은 비고유값인 지점 0건

**축 2 — 발신/수신 규약**
- 파사드의 모든 배치 완료·실패 방출이 `stpPath` 동반 — 식별자 없는 방출 0건
