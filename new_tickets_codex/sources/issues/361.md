# #361 G2 렌더 커서 저장을 프로젝트 루트 상대경로로 통일 (T2)

- URL: https://github.com/NumeRealWorks/DashOpti_GUI/issues/361
- Board status: Done
- Labels: ['feature', 'split-group:360']

## Original Request
> Project-Manifest-4-Ticket-Slicing.md 기반으로 issue 생성

## Goal
Registry 의 두 커서가 같은 저장 규약(프로젝트 루트 상대경로)을 쓰고, 경로 표현이 Registry 안의 구현 세부로 남는다. 호출자는 상대·절대를 몰라도 된다.

## Background
> source: wiki [Project-Manifest-4-Ticket-Slicing](https://github.com/NumeRealWorks/DashOpti_GUI/wiki/Project-Manifest-4-Ticket-Slicing) "PR 상세" G2 절

G1 이 기준모델 층을 루트 상대경로로 저장하게 만든 뒤, 렌더 커서만 canonical 절대경로로 남으면 한 클래스에 저장 규약이 둘이 된다. T1 이 만든 해석 헬퍼를 렌더 층에도 적용해 규약을 하나로 만든다 (D12).

**G1 이 선행인 이유(R1)** — `activeFilePath()` 의 외부 소비자 5곳 중 3곳(좌표 1·2·4)이 반환값을 `QFile::exists`·`refreshFromFile`·`QFile::copy` 에 쓰고, 좌표 8 람다는 `activeContextChanged` payload 를 `refreshFromFile` 에 민다. 상대경로 전환이 이들보다 먼저 가면 경로가 CWD 기준으로 풀려 S2 를 어긴다. G1 이 넷을 기준모델 층으로 옮긴 뒤에는 남는 소비자가 이 PR 이 손대는 자리와 정확히 일치한다.

## Technical Details

### as-is
- `setActiveContext`(`controller/DashAnalysisModelContextRegistry.cpp:50-63`)가 canonical 절대경로를 `m_activeFilePath` 에 저장한다 — canonical 산출·비교·대입 구간은 `:54-60`
- 비교 2곳(`view/DashMainWindow.cpp:2436`·`:2463`)이 `activeFilePath() != filePath` 로 문자열을 직접 견준다
- `onActiveContextChanged`(`view/DashModelingTreeWidget.cpp:472-490`)가 payload 를 그대로 쓰는데 `:481` `addFileToTreeWithStructure` 의 `exists()` 검사와 `:485` `UserRole` 비교는 절대경로를 요구한다
- 트리 `UserRole` 은 `setData(filePath, Qt::UserRole)`(`DashModelingTreeWidget.cpp:248`)로 raw 경로를 넣는다 — 커서의 canonical 값과 우연히 같은 값이 흘러 들어가 맞고 있다

### to-be
- `setActiveContext` 가 절대경로 대신 루트 상대경로를 저장한다. 정규화 지점은 그대로 이 함수 하나
- `activeFilePath()`(상대) 옆에 `activeAbsolutePath()`(절대)를 둔다. `activeContext()` 는 내부에서 해석해 `get()` 에 절대경로를 넘긴다
- `isDisplaying(const QString& path)` 신설 — 인자를 상대·절대 가리지 않고 정규화해 비교. 비교 2곳이 이 호출로 바뀐다
- `onActiveContextChanged` 진입에서 payload 를 절대화한다
- `DashMainWindow.cpp:2439`·`:2467-2468` 에 `activeContext()` 널 검사 + early return (T6 흡수분) — 첫 블록의 무검사 역참조는 자식 루프 안 `:2451` 이다

### not-to-be
- `active*` → `displayed*` 개명 — G3
- `onActiveContextChanged` 의 `:477` — 같은 함수가 `:477` 은 이름으로(`findItems`), `:485` 는 경로로 판정해 갈라져 있다. 표현 문제가 아니라 로직 결함이라 섞으면 S1 을 어긴다. 후속작업
- 호출부에서의 경로 변환 — 호출부에 `QDir(...).relativeFilePath(...)` 가 보이면 잘못 간 것이다

## Design

### 확정 결정 — D12 (문서 4 "이 문서에서 나온 결정 1건")
```
저장   m_displayedFilePath · m_referenceFilePath   프로젝트 루트 상대
노출   displayedFilePath()   / referenceFilePath()        상대
       displayedAbsolutePath() / referenceAbsolutePath()  절대
비교   isDisplaying(path)                                 인자 표현 무관
```

**선택 근거**: 저장 규약이 하나가 된다. D9 가 해석 헬퍼를 이미 만들었으므로 절대 접근자는 그 재사용이다. 렌더 커서 경로의 외부 소비자 5곳 중 셋은 G1 에서 기준모델 층으로 떠나고, 남는 비교 2곳은 이 PR 이 `isDisplaying()` 으로 감싼다.

**성립 조건**: 커서에 꽂히는 경로가 전부 프로젝트 루트 내부여야 한다. 쓰기 4곳 실측 — Load(`DashMainWindow.cpp:2267`)·체크박스(`:2437`·`:2464`)는 프로젝트 트리 경로, 프리뷰(`view/DashOptimizerWidget.cpp:1558`)가 넘기는 경로는 `QDir(optimizerDir).filePath(...)`(`:1500`) 산출이고 `optimizerDir` 이 `{ProjectRootDir}/{Module}_{Set}/` 다. 루트 밖 경로가 들어오면 `../` 로 표현된다 — 현행에 사례가 없다는 것은 **정적 확인**이다.

**딸린 이득 1건**: `isDisplaying` 이 양쪽을 정규화하면 트리 `UserRole` 의 raw 경로와 커서 canonical 값이 우연히 일치하던 것에 안 기댄다.
