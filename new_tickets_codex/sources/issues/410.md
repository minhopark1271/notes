## 현상

사용자의 **한 번의 조작**이 같은 XML 파일을 2회 이상 파싱한다. 파싱 결과를 들고 있는 곳이 아무 데도 없다.

## 근거

**경로 1 — 데이터셋 선택 후 플롯 생성 = 같은 파일 2회 파싱**

```
데이터셋 콤보 선택
  └ extractVariablesFromXml            ← 파싱 1회 (변수 목록)
      view/analyzer/DashPlotWidgetFactory.cpp:1181  ┐
      view/DashResultsAnalyzerWidget.cpp:712        ┴ 둘 다 view/analyzer/DashAnalyzerUtils.cpp:337 래퍼 경유

플롯 생성
  └ DashDataLoader::load
      └ DashXmlParser::loadFromXml     ← 파싱 2회 (같은 파일)
          model/analyzer/DashDataLoader.cpp:192
```

**경로 2 — 플롯 옵션 변경마다 재파싱**

플로터 5종이 각자 스택에 `DashDataLoader` 를 만들어 `load` 를 부른다 — [DashScatter2DPlotter.cpp:38](model/analyzer/DashScatter2DPlotter.cpp:38) · [DashScatter3DPlotter.cpp:36](model/analyzer/DashScatter3DPlotter.cpp:36) · [DashBoxPlotter.cpp:23](model/analyzer/DashBoxPlotter.cpp:23) · [DashPearsonPlotter.cpp:37](model/analyzer/DashPearsonPlotter.cpp:37) · [DashParallelPlotter.cpp:24](model/analyzer/DashParallelPlotter.cpp:24). (2026-09-21 정정: 이전 본문의 `view/analyzer/plotter/` 는 없는 경로다.) 축 변수·색상 변수만 바꿔도 같은 파일이 다시 파싱된다. 플롯 종류를 바꿔 비교하는 것이 Analyzer 의 정상 사용 패턴이라 **반복 횟수가 곧 사용 시간에 비례해 는다.**

**같은 파일이 세 가지 문자열로 돌아다닌다** (2026-09-21 확인)

| 갈래 | 만드는 곳 | 구분자 |
|---|---|---|
| 변수 목록 | `absoluteFilePath()` (`view/DashResultsAnalyzerWidget.cpp:701`) | `/` |
| scatter 2D/3D | 원본 그대로 (`:2166`) | `/` |
| 나머지 플롯 | `toNativeSeparators()` (`:2347`, `model/analyzer/DashPlotSpecBuilder.cpp:28`) | `\` |

정규화 없이 키를 만들면 같은 파일이 두 벌로 캐시되고 **플롯 종류를 바꾸는 순간 미스가 난다** — 하필 이 티켓이 고치려는 동작이다.

**캐시가 없다**

`DashDataLoader` · `DashXmlParser` 모두 상태를 갖지 않는다. `DashAnalysisModelContextRegistry::getOrLoad`([controller/DashAnalysisModelContextRegistry.cpp:23](controller/DashAnalysisModelContextRegistry.cpp:23))는 `.dat`/`.inp` 전용이고 이 경로에는 상응하는 것이 없다. 위키 `Project-Store-Survey-Inputs-Payloads-Runtime` §4.5 도 같은 결론 — "캐시가 없어 플롯 요청마다 반복한다".

OS 파일 캐시가 물리 I/O 는 흡수하므로 반복 비용은 **파싱 CPU** 다.

## 방향

파일 경로를 키로 하는 **한시 캐시** 하나.

- **캐시 대상은 축약 결과** (`extractReducedValues` 출력 = 변수당 벡터) 와 **변수 목록**이다. 원본 텐서/`XmlValue` 트리는 캐시하지 않는다 — 그쪽을 들고 있으면 메모리에서 지는 거래가 된다 (트리 상주는 303MB다)
- **단위는 요청이 아니라 파일이다** (2026-09-18 정정). 한 번 열 때 **전 변수 × 4 reduction(Max/Min/Mean/Std)을 한 번에** 계산해 담는다. (변수, reduction) 단위로 요청 시점에 계산하면 축 변수나 리덕션을 바꾸는 순간 파일 열기 비용을 다시 낸다 — 4GB 실기 파일에서 11.5초다. 277k 벡터 4개를 축약하는 비용은 토큰화에 비해 공짜다
- **소유와 위치** (2026-09-21 개정): **`model/registry/DashFileResourceRegistry`** — 독립 싱글턴 레지스트리다. 플로터 5종이 호출마다 `DashDataLoader` 를 새로 만들어 모델 계층에 소유자가 없다는 것이 함수-로컬 static 을 고른 이유였는데, 레지스트리 자체가 소유자가 되면 그 이유가 사라진다. 기존 `DashAnalysisModelContextRegistry`(controller, `.dat`/VTK 등 관할)와의 통합은 나중 몫이다. (**2026-09-21 정정**: 이전 본문은 "`model/` 이 `controller/` 를 include 하지 않으므로 흡수 방향이 하나뿐" 이라고 적었는데 틀렸다 — `model/` 하위 19개 파일이 `controller/` 를 include 한다(`model/DashAnalysisLauncher.cpp:6`, `model/DashDataProcessor.cpp:4` 등). 계층이 통합 방향을 제한하지 않는다)
- **키** (2026-09-21 개정): 신원은 **프로젝트 루트 상대경로**다 — 절대경로가 아니다. 프로젝트 디렉터리가 따로 관리되고 있기 때문이고, 루트가 바뀌면 캐시를 통째로 비우는 것이 자연스러운 무효화 경계가 된다. 루트는 레지스트리가 스스로 찾지 않고 **초기화 시점에 주입받아 멤버로 캐시**한다 — 계층 제약 때문이 아니라 테스트 가능성과 싱글턴끼리 얽히지 않기 위해서다. 기준 루트는 **`DashIOController::getProjectRootDir()`**(실제 데이터 파일 위치)이며 `DashProject::GetProjectPath()`(`.dproj` 폴더)가 아니다. 주입·무효화 훅은 `controller/DashProjectManager.cpp:39–66`(`SetProjectDirectory`) — 프로젝트를 열거나 만들 때 `DashIOController` 인스턴스 자체가 교체된다. 검증값(`size`·`mtime`·`usn`)은 신원이 아니므로 키에 묶지 말고 엔트리 필드로 나눠 둔다
- **파생물 키는 네 축**: (변수, 샘플 선택, 성분 선택, 축약). 샘플=전체 + 축약=이름 이 지금 쓰는 조합이고, 샘플=하나 + 축약=없음 이 나중의 원본 텐서다. **텐서는 이번 티켓에서 다루지 않는다** — 단, 축을 지우지 말 것. 키는 문자열 조립이 아니라 구조체로 둔다
- **반환은 `shared_ptr<const T>`**. 값 복사는 매 플롯마다 수백 KB 를 복사하고, raw 포인터는 퇴출 도입 시 소비자가 댓글링된다(#389 리뷰 미결 항목)
- **축약은 열린 집합이다.** 현재 코드의 3종/3종은 오늘의 상태일 뿐 닫힌 집합이 아니다. 매개변수를 받는 축약(분위수 등)도 키에 실릴 수 있어야 한다
- **신원은 윈도 파일시스템 의미로 정의한다** (2026-09-21 확정) — 대소문자 무시, 구분자 무관, 처음 본 표기는 표시용으로만 보관. 같은 파일을 다르게 적은 것(`\` vs `/`, 대소문자, 드라이브 문자, `./`·`//`·`sub/..`)은 예외 없이 같은 파일이다. 신원과 검증이 같은 문자열을 보도록 stat 도 정규형으로 한다. 파일시스템 별칭(8.3 단축이름·정션·심링크·하드링크·UNC vs 매핑 드라이브)은 표기 차이가 아니므로 접지 않는다
- **무효화**: 경로 변경 · 파일 내용 변경 · 데이터셋 재선택 · 프로젝트 닫기(루트 교체). 파일 변경 감지는 **USN 을 1차, `size`+`mtime` 을 폴백**으로 한다 (2026-09-21 추가):

  ```
  USN 을 얻을 수 있나?
    ├ 예     → USN 으로만 비교
    └ 아니오 → size + mtime 으로 비교
  ```

  엔트리는 셋을 다 저장하고(못 얻으면 `usn = 0`) **비교만 택일**한다. 저널이 꺼진 볼륨은 양쪽 다 0 이라 비교가 저절로 size+mtime 으로 축소되고, 나중에 저널이 켜지면 0 → 비(非)0 불일치로 한 번 재생산된 뒤 안정된다. **기존 동작을 전혀 해치지 않으면서 저널을 켜 둔 환경만 추가 이득을 본다.**

  구현은 파일 핸들에 `FSCTL_READ_FILE_USN_DATA` 를 부르므로 관리자 권한이 필요 없다(볼륨 핸들이 아니다). **저널을 켜려는 시도는 하지 않는다** — `FSCTL_CREATE_USN_JOURNAL` 은 관리자 권한이 필요하고, 저널을 켜고 끄는 것은 환경의 선택이다. 가용성 판정을 볼륨별로 캐시하지도, 검증자 종류를 엔트리에 들고 있지도 않는다
- **레지스트리는 transient 다** — 프로세스 수명 동안만 살고 디스크에 아무것도 쓰지 않는다. 영속화하면 무효화 규약과 스키마 마이그레이션이 따라붙는데 지금 얻을 것이 없다
- 항목 수 상한은 **지금 단계에선 근거가 약하다** (2026-09-21 정정). payload 가 변수당 4KB(250샘플 × float × 4종)라 변수 1000개여도 4MB 다 — 크기가 설계를 제약하지 않는다. 바이트 예산과 퇴출은 **텐서가 payload 로 들어올 때** 필수가 되며, 그것은 이번 티켓 밖이다

`getOrLoad` 형태를 그대로 따르면 무효화 규약까지 선례가 있다.

## 축약 4종 합집합 (2026-09-21 확인·범위 확정)

본문이 말하는 "전 변수 × 4 reduction" 은 **지금 코드 어느 쪽에도 없는 합집합**이다. `applyReduction`(`model/analyzer/DashXmlParser.cpp:356`) 은 Max/Min/Mean 이고 Std 가 없으며, `computeFieldStatistics`(`:376`) 는 max/mean/std 이고 min 이 없다. `reduceMax/Min/Mean/Std` 는 넷 다 있으므로 한 패스에서 넷을 부르는 경로 하나를 추가한다.

**범위: 신규 경로 하나만 추가하고 기존 `applyReduction`·`computeFieldStatistics` 는 그대로 둔다** (2026-09-21 결정, 수정 범위 최소화). 셈을 하나로 합치면 `FieldStatistics`(3필드) 소비자까지 번지므로 이번에는 하지 않는다. 같은 계산이 세 군데 살아 있게 되는 것은 알고 감수하는 빚이다.

### 범위 밖 — 캐시와 별개의 결함 둘 (2026-09-21 결정)

아래 둘은 캐시 도입과 무관한 기존 결함이다. **이 티켓에서 고치지 않는다** — 특히 첫째는 무음 Max 를 받아 쓰던 경로가 있으면 동작이 바뀜는 변경이라 캐시와 섞으면 리스크가 섮인다. 기록을 위해 남긴다:
- `applyReduction` 은 모르는 이름이 오면 `// Fallback: return max` 로 **조용히 Max 를 돌려준다**(`:372`). 축약이 열린 집합이 되는 순간 새 축약을 추가하고 이 함수를 안 고치면 전부 Max 가 나온다. 명시적 실패로 바꾸어야 한다
- `pickReduction`(`model/analyzer/DashDataLoader.cpp:193`)이 `"None"` 과 빈 값을 전부 `"Mean"` 으로 바꿔버려 **"축약 없음"을 표현할 방법이 없다**. 원본 텐서 경로를 나중에 열려면 이 매핑부터 풀어야 한다

## 확인

`loadFromXml` 진입에 호출 카운터를 두고, **한 번의 데이터셋 선택 + 플롯 3회 변경**에서 카운터가 `1` 인지 본다. 지금은 `4` 이상이다.

무효화 회귀: 파일을 덮어쓴 뒤 같은 데이터셋을 다시 그리면 **새 값**이 나와야 한다. USN 경로와 폴백 경로를 둘 다 덮어야 한다 — 이 기계의 `D:` 는 NTFS 지만 저널이 비활성이라(`fsutil usn queryjournal D:` → 1179) USN 경로는 시스템 볼륨의 임시 디렉터리에서 돌리고, 폴백 경로는 강제 스위치로 덤는다.

### 설계 선례 (2026-09-21 정정)

이전 본문은 위키 `minhopark/Project-Store-Design-Layer-Cut` 의 `derived` 층이 **그대로 이 캐시**라고 적었는데, 그것은 과하다. 둘은 다른 개체다:

| | `derived` (Layer-Cut) | #410 레지스트리 |
|---|---|---|
| 사는 곳 | `project.json` 의 `references[]` 안 — **영속 필드** | **인메모리** |
