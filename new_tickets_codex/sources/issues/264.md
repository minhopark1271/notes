# #264 장부 밖 경로를 장부로 통합 — 종결 지점 2곳 확정 · 런처 키 카운터 삭제

## Original Request

#251 구현 후 독립 에이전트 3대(어휘·명명 / 상태 모델 / 단순성·주석)로 재검토하는 과정에서, #251 이 A(wbpj) 경로에 세운 "단일 종료 지점" 이 **장부 밖 경로에는 적용되지 않았다**는 사실이 드러났다. #251 에서 처리한 2건(M3 취소 역전 회귀 · M5 술어 불일치)을 제외한 잔여 3건이 본 티켓이다.

> **개정 이력**
> - **v2** — 초안을 독립 에이전트 3대(신호 배선 / 상태·영속화 / 범위·잔여 위험)로 교차 검증. 초안 M1 의 `beginBatch → jobStarted` 안과 M2 의 "`setSampleStatus` 삭제" 안이 각각 신호 이중 방출과 UI 회귀를 낳는 것을 확인.
> - **v3 (현재)** — 신호 체인 대안 5개를 비교한 결과, **장부 밖 경로를 전부 장부로 올려 런처 키 카운터를 삭제**하는 안이 최적으로 판정. 카운터를 남긴 채 우회하던 v2 의 `batchActive()` 가드·`DashRunTracker` 추출이 불필요해졌다. M2(JSON 이중 기록)는 DOE JSON 의 "설정 파일이 실행 상태 저장소를 겸한다" 는 설계 문제라 후속 티켓으로 분리.

## Goal

**배치 종결 신호를 내는 곳을 `finishBatch` / `abortBatch` 둘로 확정한다.** `analysisStarted` 를 낸 모든 실행 경로가 장부를 거쳐 `analysisFinished` 또는 `analysisFailed` 중 하나로 끝나고, 두 세대의 종결 메커니즘(런처 키 카운터 · 장부) 공존이 해소된다. 결과로 "Start 가 영구히 잠겨 앱 재시작 외에 탈출구가 없는" 상태와 "전건 실패 배치가 성공 채널로 보고되는" 상태가 함께 사라진다.

> **좌표 기준**: `refactor/async-execution` @ `3666dd7` (#251 은 #262 로 머지 완료)

## Background

종결 메커니즘이 **두 세대 공존**하고 있는 것이 세 증상의 공통 뿌리다.

```
1세대  런처 키 카운터        기대 키 N개를 세다 다 차면 analysisFinished     장부 도입 이전부터 존재
       DashAnalysisLauncher::onCaseStatusUpdated:1053-1063
2세대  장부 + finishBatch    마지막 케이스가 닫히면 jobFinished/jobFailed    #251 이 도입
       DashJobRunner::setStageState:1203-1205
```

#251 이 2세대를 넣으면서 1세대를 지우지 않았다. 못 지운 이유는 하나뿐이다 — 카운터가 **장부 밖 경로(템플릿 치환 폴백 · FE-safe · Direct Launcher)의 유일한 Start 복구 수단**이라서. 그래서

- 장부 경로에서는 둘 다 도는데, 카운터가 **성공 채널만 알아서** 전건 실패에도 `analysisFinished` 를 먼저 낸다 (M1)
- 장부 밖 경로에서는 카운터가 유일한 종결자인데, 통지를 안 내는 지점이 많아 카운터가 영영 안 찬다 (H3)

본 티켓은 장부 밖 경로를 장부로 올려 **1세대를 삭제**한다. #214·#215 와 겹치지 않아 병렬 구현이 가능하다.

## Technical Details

### 0. 신호 체인 정리

**as-is** — `jobStarted` 는 장부 층 사실, `analysisStarted` 는 UI 층 사실인데 릴레이가 둘을 묶었다.

```
DashJobRunner::jobStarted      방출 1곳 — runDirectJobs:2510 (taskCount>0, 함수 끝)
  └─ 릴레이 DashAnalysisLauncher.cpp:53 ──→ analysisStarted        ← 층을 뛰어넘는 지점
DashAnalysisLauncher::analysisStarted   방출 3곳 — :233 샘플링 · :1088 DOE · :1138 direct
  └─ Widget:474 — Start 비활성 / Stop 활성
DashJobRunner::jobFinished / jobFailed  방출 6곳 — finishBatch:1253,1255 · abortBatch:1269
                                        · launchAnsysJournalDirect:2527,2595,2610
  └─ 릴레이 :54/:55 ──→ analysisFinished / analysisFailed
```

direct 경로는 `:1138` 과 `:2510→릴레이` 로 **지금도 `analysisStarted` 가 2회** 나간다.

**to-be** — 위층으로 올라가는 신호를 없애고, 아래층 종결 지점을 둘로 모은다.

```
analysisStarted        런처 소유 · "사용자가 실행을 눌렀다" · 액션당 1회. 방출 3곳 유지
jobFinished/jobFailed  러너 소유 · 방출 2곳 — finishBatch · abortBatch
                       릴레이 :54/:55 는 signal→signal 그대로 유지 (해제할 상태가 없다)
jobStarted             삭제 — :2510 제거 후 방출처 0곳. 릴레이 :53 · 선언 h:81 · 주석 :2523 함께
launchAnsysJournalDirect 의 자체 방출 3곳  삭제 — reportCaseStatus 만 남기고 종결은 장부에 맡긴다
런처 키 카운터          삭제 — m_isLauncherRunTracking / m_expectedRunKeys / m_completedRunKeys
```

**검토했으나 채택하지 않은 대안**

### H3 — 장부 개설 전 착수 거부에 종결 신호가 없다

**as-is**

"장부 밖 경로" 는 `emit` 이 안 되는 경로가 아니라, **종결 신호를 낼 주체가 없는** 경로다. `caseStatusUpdated` 는 일부가 낸다. 장부에 케이스가 등록돼야 마지막 케이스가 닫힐 때 `finishBatch` 가 자동으로 종결을 내는데, 등록이 없으면 그 트리거가 없다.

```
runDoeAsync → emit analysisStarted (DashAnalysisLauncher:1088)   ← 여기서 Start 잠김
  └─ generateInputCases — 장부 개설 전 무신호 return 7곳
       1757 ProjectManager 없음 / 1763 IOController 없음 / 1768 프로젝트 미개방
       1779 config 열기 실패 / 1834 템플릿 경로 없음 / 1870 FE-safe 템플릿 없음
       2214 템플릿 읽기 실패
```

`abortBatch` 는 장부 유무로 갈린다. 착수 거부 7곳은 **아직 아무것도 세우지 않은 시점**이라 아래 위쪽 분기만 타므로 그대로 쓸 수 있다 — #251 이 `.wbpj` 분기 3곳에 이미 적용한 형태와 같다.

```
abortBatch(reason)
├─ 로그 1줄 (:1262)
├─ 장부 없음 → releaseWbpjBatch() + emit jobFailed → 끝     ← 초기화할 배치 상태가 애초에 없음
└─ 장부 있음 → 열린 키 전부 cancelSolverTaskForKey + setStageState(Failed)
              → finishBatch → m_ledger.clear() · releaseMorphBatch()
                              · m_motionLauncherQueue.clear() · releaseWbpjBatch()
```

**도달 가능성** — 7곳 중 다수는 방어 코드다. 위젯이 이미 게이트하고 있다 (`Widget:834` DOE JSON 존재 확인, `:846` 템플릿 선택 확인).

| 지점 | 조건 | 도달 |
|---|---|---|
| 1757 | `ProjectManager::Instance()` == null | ❌ 싱글턴. 앱 살아있으면 항상 non-null |
| 1763 | `GetIOController()` == null | ❌ 프로젝트 열 때 생성(`DashProjectManager.cpp:78`). `Widget:834` 통과 = 프로젝트 열림 |
| 1768 | 프로젝트 미개방 | ❌ 위와 같음 |
| 1779 | config 열기 실패 | ⚠️ 파일 존재는 확인됨. 권한·잠김일 때만 |
| 1834 | 템플릿 경로 없음 | ❌ `Widget:846` 이 막음 |
| 1870 | FE-safe 템플릿 없음 | ⚠️ 선택 후 파일이 삭제된 경우 |
| 2214 | 템플릿 읽기 실패 | ⚠️ 권한·잠김 |
| **활성 케이스 0건** | 사용자가 샘플 전부 비활성 | ✅ 쉽게 재현 |

**7곳을 바꾸는 근거는 도달 가능성이 아니다.** 각 1줄이고, `generateInputCases` 안에 무신호 `return` 이 하나도 없다는 불변식을 grep 으로 검증 가능하게 만드는 것이 목적이다. 방어 코드가 실제로 걸리면 조용히 죽는 대신 사용자에게 보인다.

**활성 케이스 0건이 무신호인 근거** — `DashBatchLedger.h:55` `hasBatch() = !m_order.isEmpty()` 이므로 활성 키 0건이면 `beginBatch` 후에도 `hasBatch() == false` 이고 `finishBatch:1226-1228` 이 조용히 return 한다. 모핑 `beginBatch`(:2107) 직전 · 폴백 루프 진입 전 · FE-safe `isStli` 분기(:1867) 진입부 **3곳**에 검사가 필요하다.

**to-be** — 착수 거부 7곳 + 활성 0건 3곳을 `abortBatch(reason)` 으로 수렴한다. 기존 `emit logMessage("ERROR: …")` 는 제거한다 (`abortBatch:1262` 가 사유를 낸다).

### M1 — 장부 밖 경로를 장부로 올린다

**as-is** — 장부를 개설하지 않는 실행 경로가 셋이다.

| 경로 | 위치 | 케이스 상태 통지 | 종결 |
|---|---|---|---|
| 템플릿 치환 폴백 | `:2206-2313` | `configManager.setSampleStatus` 직접. `continue` 5곳은 **무통지** | 없음 |
| FE-safe (`.stli`) | `:1867-1940` | `setSampleStatus` + `caseStatusUpdated` 쌍 5곳. 완료 콜백 `:339-350` | 없음 |
| Direct Launcher | `:2315-2511` | `caseStatusUpdated` 4곳 | `launchAnsysJournalDirect` 가 자체 방출 (`.wbpj` 만) |

폴백 루프의 무통지 `continue` 5곳 — `2251` mkpath 실패 / `2262` `writeCaseDat` 실패 / `2267` `!h` / `2272` 생성 파일 없음 / `2300` 태스크 생성 실패. **재현**: DOE JSON 에 `rawSamples` 없음(→ `m_cachedSamples` 빔) + `.dat` 템플릿 + ANSYS 경로 미설정 → 모핑 분기 조건 불성립 → 폴백 진입 → `ensureLauncherInitialized()` 실패로 `h == nullptr` → 활성 샘플 전건이 `continue` → `"0/N tasks submitted"` 로그 후 return → **앱 재시작 전까지 Start 비활성**.

Direct 는 `runDirectJobs:2509` 의 `taskCount == 0` 에서도 종결이 없다 — `:1138` 이 무조건 `analysisStarted` 를 냈는데 장부도 통지도 없어 오늘도 Direct 탭이 영구 잠긴다.

**to-be** — 세 경로 모두 `beginBatch` 로 장부를 열고 상태 통지를 `setStageState` 로 바꾼다. 마지막 케이스가 닫히면 `finishBatch` 가 자동으로 종결을 낸다.

**⚠ stage 인덱스 정합 (구현 시 최우선 주의)**

`beginBatch(keys, 1, 0, ctx)` 로 1칸 장부를 열면 **동작하지 않는다.** 완료 콜백 `onFeTaskCompletedQueued:1156` 이 `morphSolverStage()` 를 쓰는데 그 값이 `isDfsxml ? kMotionLauncherStage(2) : kPostMorphStage(1)` 로 **절대 0 이 아니다**. 1칸 장부는 `stages.size() == 1` 이라 `DashBatchLedger::apply` 가 `stage >= it->stages.size()` 로 전이를 버리고(`DashBatchLedger.cpp:70-72`), 케이스가 영영 안 닫혀 Start 가 잠긴다.

→ **`onFeTaskCompletedQueued` 가 `m_ledger.terminalStage(key)` 를 쓰도록 바꾼다** (1줄). 1칸 장부에서는 0, 모핑 배치에서는 솔버 칸으로 해석되어 양쪽이 맞는다. 솔버 미설정으로 터미널이 낮춰진 배치(`:2145`/`:2176`)는 솔버를 제출하지 않으므로 이 콜백이 오지 않는다.

**솔버 런처 미초기화(`!h`)는 실패가 아니다** — `:2217-2219` 가 `"Only input files will be generated"` 를 의도적으로 로그하고 `writeCaseDat`(`:2259`)가 검사보다 앞이다. 입력 파일 생성이 그 배치의 산출물이므로 `setStageState(key, 0, Done)` 으로 닫는다. 모핑 경로가 솔버 미설정 시 `setTerminalStage` 로 칸을 낮추는 것(`:2145`/`:2176`)과 같은 형태다.

**Direct 경로의 키 규칙** — `.dat`/`.inp`/`.dfsxml` 은 파일 basename, `.wbpj` 는 **prt basename**(`:2471`)이다. 현재 런처의 기대 키는 wbpj basename(`DashAnalysisLauncher.cpp:1131`)이라 어긋나 있는데, 러너가 키를 직접 만들게 되면서 이 불일치가 해소된다. `launchAnsysJournalDirect` 의 자체 종결 방출 3곳(`:2527`/`:2595`/`:2610`)은 제거하고 `reportCaseStatus` 만 남긴다 — 이 함수는 `:2499` 에서만 호출되는 direct 전용이다.

**결과** — 종결 신호 방출 지점이 `finishBatch` · `abortBatch` 둘로 확정되고, 런처 키 카운터가 삭제 가능해진다. 카운터가 없으므로 릴레이 `:54/:55` 는 signal→signal 그대로 유지한다 (해제할 상태가 없다).
