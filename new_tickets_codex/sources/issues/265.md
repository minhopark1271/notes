## Goal

DOE·모핑·Direct 세 경로가 각자 구현한 솔버 제출 코드를 솔버별 한 벌로 합친다. direct `.wbpj` 는 DOE wbpj 배치 기제로 올려 Journal 진입점을 하나로 만든다.

> **좌표 기준**: `refactor/async-execution` @ `77d7371` (#214 머지분 · PR #272). 라인 참조 전량이 그 기준의 실측이다. **#214 머지 완료 — 착수 가능**

## Background

세 경로의 차이는 **입력 파일이 어디서 오느냐** 하나뿐이다.

```
DOE 경로     DOE JSON 샘플 → 템플릿 치환 → runDir 에 입력파일 생성 ─┐
모핑 경로     DOE JSON 샘플 → 모핑 실행 → runDir 에 입력파일 생성 ──┤
Direct 경로   사용자가 고른 기존 파일 ─────────────────────────────┘
                                                                    ↓
                                          솔버에 제출하고 완료를 기다린다  ← 여기부터 동일
```

#264 가 세 경로의 상태 보고를 전부 `setStageState` 로 통일했으므로, 병합 지점마다 판단할 것이 없다.

`submitAnsysTaskForSample:1768` 과 `runDirectJobs:2455-2478` 를 나란히 두면 `DashFL_Ansys_AnalysisConfig` 를 채우고 `CreateAnalysisTask` 를 부르고 `m_activeTasks` 에 넣고 `setStageState(Running)` 하는 것이 글자만 다르고 같다. 완료 콜백 람다(`handleTaskCompletion` 호출 + `DashFL_FreeAnalysisResult`)는 세 벌이 **문자 단위로 동일**하다.

**제출 stage 는 이미 장부에서 유도 가능하다.** 세 지점의 stage 가 전부 `m_ledger.terminalStage(runKey)` 와 일치한다 — 모핑 dat/inp 배치는 2칸·terminal `kPostMorphStage`(`:2206`), 폴백·direct 는 1칸·terminal 0. 솔버 미설정으로 terminal 이 낮춰지는 경우(`:2206`/`:2237`)엔 제출 자체가 오지 않는다. #264 가 `reportCaseStatus:1217` 에서 이미 같은 규칙을 쓴다.

**wbpj 두 경로의 차이 — 6개. 1~5 는 "direct 가 배치 기제를 안 물려받아서" 이고, 6 은 별개다**

| # | DOE 배치 (`launchWbpjJournal:3233`) | direct (`launchAnsysJournalDirect:2664`) |
|---|---|---|
| 1 | `updatePrtGeometry` + `setBatchMode(true)`(`:2990`) | `loadPrt`(`:2651`), batchMode 미설정 → 실행 중 `DashMainWindow:271` 모달 경고 · `:277` 3D 미리보기 로드가 발화한다 |
| 2 | 실패를 `updatePrtGeometryBatchFailed(stpPath, msg)` 로 케이스 귀속 (`DashSolverNxCad.h:47`) | `loadPrtFailed(message)` 는 식별자가 없다 (`h:38`) → **다건 불가** |
| 3 | `m_stpWatchdog` 케이스 타임아웃(600s) + 연속실패 서킷브레이커(`kBatchConsecFailLimit`) | 둘 다 없음 |
| 4 | launchId = `doe:{analysisType}:{seq}` 배치 고유 | 상수 `kDirectJournalLaunchId` — 취소로 배치가 닫힌 뒤 도착한 지각 통지가 다음 direct 실행에 오귀속될 여지 |
| 5 | `.dat` 확인 후 `.rst` 판정 (2단) | `.rst` 만 |
| 6 | `target_component` = prt **basename**(`:3299` ← `:2049`) | `target_component` = wbpj 디렉터리 기준 **상대경로**(`:2704`) — 같은 JSON 키에 다른 종류의 값. `.prt` 가 `.wbpj` 와 같은 폴더일 때만 우연히 일치한다 (→ 미확인 전제 ⑵) |

#264 가 direct `.wbpj` 를 1건 제한으로 만든 결과, 지금 direct wbpj 는 **1샘플짜리 DOE wbpj 배치와 구조가 같다** (STP 1건 → Journal 1회).

**#264 가 남긴 잔여** — `kDashDirectWbpjRunLimit = 1`(`model/DashDirectJobPlan.h:17`)이 착수분을 1건으로 자르고 `runDirectJobs:2591-2595` 이 초과분을 `Failed` 로 닫는다. 그 헤더의 주석이 이유를 위 2번으로 명시한다 — 해소되지 않는 한 풀 수 없어 채택한 우회다.

### to-be

- ANSYS `.dat` 제출 1벌 · Abaqus `.inp` 제출 1벌. 완료 콜백 람다도 각 1벌
- **제출 헬퍼는 stage 를 받지 않는다** — `reportCaseStatus:1217` 와 같은 규칙으로 `m_ledger.terminalStage(runKey)` 에서 유도한다
- direct `.wbpj` 를 wbpj 배치 기제로 올린다 — `updatePrtGeometry` + `setBatchMode(true)` + `m_stpWatchdog` + 서킷브레이커 + 배치 고유 launchId + 2단 판정을 그대로 물려받는다
- `launchAnsysJournalDirect` 삭제. `launchWbpjJournal` 이 두 경로의 유일한 Journal 진입점
- direct `.wbpj` 1건 제한 해제 — `kDashDirectWbpjRunLimit` · `DashDirectJobPlan::wbpjRunnable` · `wbpjExcessKeys` 를 걷어내고 다건 동시 실행 복원
- `WbpjBatch` 가 wbpj·prt·**Journal 샘플 행**을 케이스별로 든다 (아래 Design 제약 1·2)
- **혼합 direct 배치는 거부한다** — `.wbpj` 를 다른 확장자와 함께 선택한 배치를 Start 에서 사유와 함께 막는다. direct 배치는 wbpj-only 또는 non-wbpj-only 뿐이다 (아래 Design "혼합 direct 배치는 지원하지 않는다")

### not-to-be

- Motion 제출 경로 — 이미 통합. 손대지 않는다
- direct Motion 의 `emit caseStatusUpdated(key, "Pending", …)`(`:2571`) — Pending 은 장부 전이가 아니라 큐 대기 표시라 의도적 예외로 유지한다
- `loadPrtFailed` 시그니처 변경 · `m_batchMode` 제거 — **#249 소유**. 본 티켓은 기존 배치 시그널을 쓰기만 한다. `m_batchMode` 가 전역이라 배치 중 대화형 NX 완료가 배치 채널로 새어 `attributeRunningStpCase` 가 조용히 버리는 창(#268 종결 코멘트의 "범위 밖 관찰")이 direct 실행에도 열리는데, `finishStpPhase:3176` 가 `releaseNxCadBatchMode()` 를 이미 부르므로 **노출은 direct 의 STP 구간에 한정**된다 — 수용하고 #249 를 기다린다
- **혼합 direct 배치 지원** — 위 to-be 대로 거부한다. 지원하려면 `firstStpKey` · `finishStpPhase` x2 · `launchWbpjJournal` · `cancelAllRuns` 를 wbpj 케이스 집합으로 좁히고 2칸 장부 분기를 넣어야 한다. 필요해지면 별건
- DOE JSON 이 설정과 실행 상태를 겸하는 문제 — #266
- `generateInputCases` 워크플로 분기 해체 — #269
- direct `.dfsxml` 이 `monitorMotionLauncherOutput:821` 에서 `m_doeJsonPath` 의 DOE 표와 키를 대조해 조기 완료 감지가 항상 불발하는 건 — 프로세스 종료 핸들러가 케이스를 닫으므로 매달리지 않는다. #266 계열

## Design

### 현황 분석

- 솔버 제출은 `DashJobRunner` 안에서만 일어난다. 외부 계약 변경 없음
- `WbpjBatch`(`DashJobRunner.h:239`) 는 **wbpj 1개 · prt 1개 · outputBaseDir 1개를 배치 전체가 공유**한다고 전제한다. 케이스별로 다른 것은 `StpCase{runKey, stpPath, config}` 뿐
- `firstStpKey:3086` 는 `m_ledger.openKeys()` 전체를 훑고 `stageState(key, kStpStage)` 를 본다
- `kStpStage = 0` · `kAnalysisStage = 1` (`h:223-224`)

### 대안 비교

| 방안 | 핵심 | 장점 | 단점 |
|---|---|---|---|
| **A. direct 를 STP 배치 기제로 승격** | direct `.wbpj` 가 `updatePrtGeometry` + 배치 시그널 + 워치독을 쓰고 `launchWbpjJournal` 로 합류 | 위 차이 1~5 + 다건 제한이 한꺼번에 사라진다. Journal 진입점 1개 | `WbpjBatch` 를 케이스별 wbpj/prt/샘플행 으로 확장해야 한다. 미확인 전제 2건 (아래) |
| B. Journal 런치 헬퍼만 추출 | `enqueueLaunch` + launchId 대조 구독 + run 디렉터리 사후 판정만 공통화, 진입점 둘 유지 | 변경 폭이 작다. `WbpjBatch` 무변경 | 차이 4·5 만 해소. 모달 발화 · 워치독 부재 · 1건 제한은 그대로. 진입점이 둘로 남아 #269 가 다시 만진다 |

### 선택 — 방안 A

**선택 근거**: 차이 1~5 가 전부 같은 뿌리(배치 기제 미상속)에서 나오므로 뿌리를 없애는 쪽이 총 변경량이 작다. 차이 6 은 뿌리가 다르지만 통합하면 **어차피 하나로 수렴해야 하므로** 여기서 함께 닫힌다. #264 의 1건 제한 우회도 이 방향으로만 풀린다 — B 로는 `loadPrtFailed` 의 식별자 부재가 남아 다건이 여전히 불가능하다. `WbpjBatch` 확장은 `StpCase` 에 필드 4개를 옮기고 Journal 샘플 행 2개를 더하는 일이고, DOE 경로는 전 케이스가 같은 값을 들어 거동이 바뀌지 않는다.

**기각된 대안**: B 는 진입점을 둘로 남겨 #269(워크플로 분기 해체)가 같은 자리를 다시 만지게 된다.

#### 구조적 제약 2건 (구현 시 최우선)

**제약 1 — 배치 하나에 wbpj 가 여럿이면 Journal 런치도 여럿이다.**
DOE 는 wbpj 1개에 샘플 N개라 `enqueueLaunch` 1회지만, direct 는 wbpj N개 × 각자의 prt 다. `wbpjPath` / `prtPath` / `targetComponent` / `outputBaseDir` 를 `WbpjBatch` 에서 `StpCase` 로 내리고, Step 2 는 **wbpj 별로 묶어 launchId 를 하나씩** 발급한다. 완료 핸들러는 `m_ledger.openKeys()` 가 아니라 **그 launchId 에 속한 케이스 집합**만 판정해야 한다 — 지금 `openKeys()` 로 되어 있는 것(`:3321`)은 배치에 wbpj 가 하나뿐일 때만 우연히 맞는다.

**제약 1-a — launchId 와 구독이 배치 스칼라다.**
`m_wbpjBatch.launchId`(`h:249`) · `m_journalCompletedConn` / `m_journalFailedConn`(`h:259-260`)이 전부 1개다. **단일 구독을 유지한 채 `QHash<QString launchId, QStringList caseKeys>` 를 든다** — 완료·실패 람다가 launchId 로 자기 케이스 집합을 조회한다. 그룹마다 `connect` 를 새로 거는 안은 `launchAnsysJournalDirect:2713-2714` 의 `new QMetaObject::Connection` 수명 관리를 되살리므로 채택하지 않는다(본 티켓이 지우는 코드다). Journal 데몬은 `sendCommand` 직렬 큐이므로 N건을 한꺼번에 넣어도 통지는 하나씩 온다 — `releaseWbpjBatch()` 의 해제도 커넥션 2개 그대로다.

**제약 2 — `StpCase` 가 Journal 샘플 행까지 든다.**
`launchWbpjJournal:3256-3293` 은 배치 필드 `initIndParam` + `rawDoeTable` 로 `rawSamples` 를 만들고, direct `:2688-2695` 는 `nxParams` 로 `{active, key, slice, values}` 를 합성한다. 경로만 케이스로 내리고 표를 배치에 남기면 통합 함수가 **"DOE 표가 있나?" 분기를 다시 갖는다** — 본 티켓이 없애려는 그 분기다. 따라서 `StpCase` 가 **완성된 sample row + headers** 를 들고, `launchWbpjJournal` 은 그룹의 케이스에서 행을 모으기만 한다(분기 0). `WbpjBatch::initIndParam` / `rawDoeTable` 은 준비 단계 지역변수로 내려가고 필드에서 삭제된다.

> `active` / `slice` 를 런치 시점에 합성하는 안은 기각 — DOE 는 그 둘을 원본 샘플에서 가져오므로(`:3282-3284`) 합성하면 값이 버려져 **거동이 바뀐다**.

#### 혼합 direct 배치는 지원하지 않는다 (2026-08-18 확정)

Direct Launcher 는 Input Cases 표의 **전 행을 한 배치로** 돌리고(`DashAnalysisLauncherWidget.cpp:899`), 파일 추가는 `getOpenFileNames` 다중 선택에 필터가 `"Input Files (*.dat *.inp *.dfsxml *.wbpj)"` **하나**라(`:1213`) `.dat` 와 `.wbpj` 를 한 번에 담을 수 있다. 확장자 균일성 검사는 어디에도 없다.

오늘 그 조합이 동작하는 이유는 direct 가 `m_wbpjBatch` 를 **안 쓰기** 때문이다 — `.wbpj` 는 `launchAnsysJournalDirect` 로 빠지고 `phase` 는 Idle 로 남아 `firstStpKey` · `finishStpPhase` 가 애초에 안 돈다. Phase 4 가 direct 를 STP 배치 기제에 태우면 그 전제가 깨지고, 아래 5지점이 전부 "배치 = wbpj 전용" 을 전제하므로 함께 고쳐야 한다.

| 지점 | 현재 | 혼합 배치에서 깨지는 방식 |
|---|---|---|
| `firstStpKey:3088` | `m_ledger.openKeys()` 순회 | `kStpStage == 0` 이라 `.dat` 키를 STP 착수 대상으로 집는다 → `caseFor()` null → `finishStpPhase()` 조기 호출 |
| `finishStpPhase:3166` | `openKeys()` 를 `ready` / `unfinished` 로 가름 | 실행 중인 `.dat` 케이스가 `unfinished` 로 분류돼 `Cancelled` 로 쓸린다(`:3192`) |
| `finishStpPhase:3196` | `ready.isEmpty()` → `abortBatch` | wbpj 가 전건 실패하면 정상 진행 중인 `.dat` 케이스까지 배치째 닫는다 |
| `launchWbpjJournal:3321` | `openKeys()` 전량 판정 | 남의 케이스를 RST 유무로 재판정한다 |
| `cancelAllRuns:947-975` | `wbpjPhase` 로 갈리는 if / else-if 체인 | `wbpjPhase == Stp` 분기만 타고 `else if (m_ledger.hasBatch())` 의 `m_motionLauncherQueue.clear()` 를 건너뛴다. 게다가 Stp = 협조적 / Analysis = 즉시 중단이라 **혼합 배치의 Stop 이 P1 을 지킬지 말지가 정의되지 않는다** |

**선택 — 혼합 금지.** Start 에서 `.wbpj` 가 다른 확장자와 함께 선택된 배치를 거부한다(사유 통보 + 착수 없음). 근거:

- 위 5지점 수정의 **비용 전부**가 혼합 배치 하나를 위한 것이다. 금지하면 direct 배치는 wbpj-only 또는 non-wbpj-only 뿐이라 "배치 = wbpj 전용" 전제가 그대로 산다 — 2칸 장부 분기(구 제약 2)도 불요다
- wbpj-only 배치에는 정리할 motion 케이스가 없으므로 `cancelAllRuns` 의 `Stp` 분기가 큐를 안 비워도 무해하다 → **분기를 배타 → 병렬로 바꿀 필요가 없고, 그 결과 #214 와의 직렬화 요구도 사라진다**
- 대가는 오늘 되던 조합 1건의 회귀다. 사용자 결정으로 **수용**한다 (2026-08-18). 두 번 나눠 실행하면 같은 결과를 얻는다

**금지가 아닌 것**: `.wbpj` **여러 개**를 한 배치로 돌리는 것은 지원한다(#264 의 1건 제한 해제가 본 티켓 몫이다). 서로 다른 확장자를 **순차 배치**로 번갈아 돌리는 것도 종전대로 동작한다 — 재진입 가드는 동시 실행만 막는다.


#### 미확인 전제 2건 — 착수 전 실측

direct 는 PRT 의 현재 파라미터(`nxCadParametersJson`)로 Journal config 의 headers/values 를 만든다(`:2677-2684`). 그 JSON 은 `loadPrt` 가 낸다. `updatePrtGeometry` 도 내는지는 데몬(`DashOptiCADNX.exe`, 레포 밖) 실측이 필요하다 — `tryParseJsonFromLine`(`DashSolverNxCad.cpp:244`)은 커맨드와 무관하게 파싱하므로 데몬이 출력만 하면 성립한다.

**안 나와도 폴백이 무해하다**: 그 값들은 PRT 의 *현재* 값이라, Journal 이 그대로 되적용하는 것과 아예 적용하지 않는 것이 같은 형상이다. 현행 코드도 `nxParams` 가 비면 headers/values 를 비운 채 진행한다(`:2677`). 즉 최악의 경우 headers/values 가 비는데, 그것이 "direct = 이 파일을 그대로 돌린다" 의 정확한 의미다. 착수 시 실측하고, 안 나오면 빈 배열로 확정한다.

**⑵ `target_component` 의 값 종류가 두 경로에서 다르다.** 같은 JSON 키에 서로 다른 종류의 값이 들어간다 — 차이 표(5건)에 없던 6번째다.

| 경로 | 값 |
|---|---|
| DOE 배치 `:3299` | `m_wbpjBatch.targetComponent` = **basename** (`:2049` `QFileInfo(prtAbsPath).completeBaseName()`) |
| direct `:2704` | wbpj 디렉터리 기준 **상대경로** (`relativeFilePath(prtAbsPath)`) |

두 값은 `.prt` 가 `.wbpj` 와 같은 폴더일 때만 우연히 같다. **통합하면 하나로 수렴해야 하므로, 어느 쪽이 Journal 데몬 계약인지 모르고 합치면 그 자체가 회귀다.** 실측 방법: `.prt` 를 `.wbpj` **하위 폴더**에 둔 구성으로 DOE 배치 1회 — 두 값이 갈리는 유일한 구성이다.

| 데몬이 기대하는 값 | 처분 |
|---|---|
| 상대경로 | DOE 가 basename 을 넣는 것이 기존 결함 — 상대경로로 통일하며 함께 고쳐진다 |
| 컴포넌트 이름 | direct 가 틀린 것 — basename 으로 통일 |
| 둘 다 수용 | 상대경로로 통일 (더 일반적인 표현) |

어느 쪽이든 **`StpCase::targetComponent` 가 어느 종류의 값인지 주석 한 줄로 못 박는다.**
