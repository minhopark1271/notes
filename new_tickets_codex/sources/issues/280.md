## Goal

RW 배제가 게이트가 아니라 **격리 + 감금 두 벌**로 성립한다. `DashRwActor` 가 `IRWModule` 을 독점 소유하고 각 작업이 자기 `DashRwSession` 을 들어 배제 기제·원복 기제·거부 UX 가 함께 소멸한다. `RwGate` 는 세우지 않는다.

봉인의 뼈대는 병합된 4커밋이 이미 세웠다. 본 티켓의 잔여는 셋이다 — ⑴ 읽기 축의 actor 왕복을 캐시로 걷어내 **감금이 만든 병목(단일 RW 스레드)** 을 완화하고 ⑵ 레지스트리 빈 키 버그를 닫고 ⑶ `ThreadingContract` 에 **배제 기제 선택 규칙**을 세운다. 게이트 전제로 세워 둔 `rwSerialPool` 제거와 7절 정정은 #290 이 병합 귀결로 수행 완료(`eaa77a6`).

사용자 관점의 결과는 한 문장이다 — **DOE 배치가 도는 동안 어떤 모델도 열고 편집할 수 있다.** 종전 계획의 "그 배치가 쓰는 모델만 못 연다" 는 거부 자체가 사라졌다. 러너·옵티마이저 모핑은 아직 GUI 세션을 쓰므로 그 2 경로에만 변이 창이 남는다 — 소멸은 #281 Phase B2 소유다.

> **유보 1건** — VTK 자체의 전역(오브젝트 팩토리·SMP 백엔드)은 남는다. RW 가 만지지 않으나 두 스레드가 동시에 VTK 객체를 만드는 것은 VTK 계약 문제다. 단 **오늘 이미 모핑 워커가 VTK 를 만지므로** 본 티켓이 새로 만드는 위험이 아니다. 281-1 감사가 이 유보를 모핑 축에서 실현된 것으로 확정했다(`vtkSMPToolsAPI` 무동기 전역).
>
> 2행("다른 인스턴스는 독립")이 격리 설계의 전제다. 1행("같은 인스턴스 동시는 불안전")은 격리가 성립하면 발동하지 않는다. 3행("스레드 이동 안전")이 `DashRwActor` 의 전용 스레드 이주를 가능하게 했다. **벤더 문서 근거가 없어 등급 2 판정 자체는 유지**되고, 감금이 그 판정을 스레드 1개로 봉인한다(`ThreadingContract:151-153`).

> **봉인은 이미 접근 경로 부재로 성립한다** — `controller/`·`model/`·`view/` 전역에서 actor 외의 `module->` 직접 접근이 **0건**(실측)이고 `IRWModule` 은 actor 만 소유한다. 게이트 설계가 시그니처 `Witness` 로 얻으려던 것을 actor 경계가 더 강하게 준다(누락이 컴파일 에러가 아니라 **접근 경로 자체가 없다**).

**감금이 만든 병목 — RW 실행 스레드가 하나다**

`DashRwActor::instance()` 의 `Holder` 가 전용 스레드 하나를 기동하고(`controller/DashRwActor.cpp:24-53`) 모든 `DashRwClient` 호출이 `invokeOnActor` 의 `BlockingQueuedConnection` 으로 그 스레드에 마샬링된다. **세션이 격리돼도 실행은 직렬화된다.** 오늘은 전 호출자가 GUI 스레드라 종전과 같은 시간만 블록하지만(`b837552` 이 "이 커밋만으로는 런치 프리즈가 풀리지 않는다" 로 명시), **#281 이 모핑을 워커로 올리는 순간 경합이 생긴다** — 워커의 `getPartData`·`updateMeshPoints`·`exportSolverInput` 뒤에 GUI 의 짧은 호출이 줄 선다.

> 감금의 대가는 하나 더 있다 — **RW 축의 병렬화가 닫힌다.** 스레드를 늘리면 감금이 깨져 등급 2 봉인이 되돌아간다. 281-1 wiki 가 모핑 축에서 같은 성질을 지적했다(B·C 안은 배치 병렬화를 영구히 닫는다).

실 왕복 수는 덱 1개 로드당 `get_symbol_detail` 최대 **4N**(N = 조건 수)이다.

| 소비자 | 호출 | 수 |
|---|---|---|
| `DashConditionParameterization:134` | `getFeConditionTypeString` | N |
| `DashConditionParameterization:136` | `getFeConditionEntries` | N |

> **게터 대부분은 모듈을 부르지 않는다** — `getPartNames`(`:267`) · `getFeConditionNames`(`:336`) · `getFeConditionUuid`(`:586`) · `getFeConditionNameByUuid`(`:595`) 등은 로드 시 채운 앱 측 맵(`feConditionUuids` — `:1124` 에서 채운다)을 읽는다. 읽기 축의 actor 접촉은 **`get_symbol_detail` · `get_edit_schema` 2 primitive** 로 수렴하고, 후자는 이미 캐시가 있다.

창은 세션 객체 단위 판정이므로(`17aed65`), **DOE 배치가 전용 세션으로 도는 동안 GUI 편집은 막히지 않는다.** 오늘 `isMutating()` 이 참이 되는 유일한 경로는 위 2 호출부가 GUI 세션을 executor 에 넘긴 구간이다. 즉 **창의 잔존 이유는 그 2곳뿐**이고, #281 Phase B2 가 전용 세션으로 옮기면 창이 무의미해진다.

**게이트 전제로 세워 둔 잔여물 — #290 에서 전부 해소됨** (회귀 확인용 기록)

## Design

### 현황 분석

같은 문제에 두 답이 나왔고, 병합 4커밋이 실측으로 하나를 골랐다.

| | 게이트 (본 티켓 원안) | 격리 + 감금 (병합분) |
|---|---|---|
| 답의 형태 | 공유하되 동시 접근을 거부 | 애초에 같은 인스턴스를 안 쓰고, 실행 지점도 1개로 감금 |
| 근거 | 등급 판정 1행(같은 인스턴스 동시는 불안전) | 격리 = 2행(다른 인스턴스는 독립) · 감금 = 3행(스레드 이동 안전) + 벤더 근거 부재 |
| 원복 장치 | 계속 필요 (공유하니까 되돌려야 한다) | 소멸 — `17aed65` 가 3종 제거 |
| 거부 UX | 신설 필요 (`Rejected` · 통보 정책 · 위젯 상태 불변) | 0건 |
| 변이 창 | 존치 (경로 키) | 개설 2곳이 남고 참이 되는 조건은 GUI 세션 전달 2 호출부뿐 — #281 B2 가 없앤다 |
| 봉인 층 | 타입(시그니처 `Witness`) 1층 | 접근 경로 부재 — 비-actor `module->` grep 0건 |
| 남는 대가 | 공유 유지 비용 전부 | **RW 실행 스레드 1개 — actor 점유 경합 · 병렬화 봉인** |

> 281-1 wiki 가 이 착지를 **"B형"** 으로 분류했다 — RW 가 실증한 것은 격리 단독(A′형)이 아니라 격리 + 감금이다. 모핑 축이 A′ 를 시도했다가 기각된 것과 대비된다.

### 대안 비교 — actor 점유 경합을 무엇으로 완화하는가

| 방안 | 핵심 | 장점 | 단점 |
|---|---|---|---|
| **A. 읽기 캐시 승격** | `get_symbol_detail` 결과를 세션 캐시로, 로드 시 워밍 | 왕복 자체를 없앤다. `editSchemaCache` 선례 존재. `b837552` 의 aliasing 감사를 다시 하지 않아도 된다 | 무효화 규약 필요(편집 시 1곳) |
| B. 세션별 워커 스레드 | actor 를 세션당 스레드로 분할 | 병렬성 최대 | LEAF·교착 없음 근거가 "GUI 가 RW 스레드에 블록되고 RW 는 GUI 를 부르지 않는다" 인데, 스레드가 여러 개면 그 논증을 다시 세워야 한다. aliasing 감사 재수행 |
| C. 비블로킹 읽기 경로 | 스냅샷 반환으로 GUI 블록 제거 | 근본 | `b837552` 이 명시적으로 "이 판단을 다시 해야 한다" 로 지목한 변경 |

### 선택 — 방안 A · B·C 는 계측 후 별건

**선택 근거**: 경합의 실체는 "왕복 횟수 × 왕복 비용" 인데, 조건 테이블 렌더가 조건마다 `get_symbol_detail` 을 타는 구조라 **횟수 쪽이 지배적**이다. 캐시는 그 횟수를 로드 시 1회로 접고, actor 의 스레드 구조·aliasing 판정·LEAF 논증을 하나도 건드리지 않는다. B·C 는 `b837552` 이 세워 둔 안전 논증을 재수행해야 하므로 **#281 Phase D·E 의 계측값**을 보고 판단한다(#281 Follow-up ⑵ 가 같은 항목을 등재).

**기각된 대안**: B 는 actor 의 교착 없음 근거를 무너뜨린다 — 단일 RW 스레드가 GUI 를 되부르지 않는다는 것이 지금의 안전 논증이다. C 는 aliasing 감사의 명시적 재검토 트리거다.

### 배제 기제 선택 규칙 (Phase 4 산출물)

기제는 3종이 아니라 4종이고, 각각 다른 것을 없앤다. 현행 7절 박스가 격리를 빠뜨렸다.

| 기제 | 무엇을 없애는가 | 성립 조건 | 실례 |
|---|---|---|---|
| **격리** (인스턴스·세션 분리) | 상태 공유 자체 | 프로세스 전역 가변 상태 0 · 인스턴스 독립 | `DashRwSession` |
| **감금** (전용 스레드 1개) | 동시 진입 — 워커·GUI 양축을 한 벌로 | 스레드 이동 안전 · LEAF | `DashRwActor` |
| **풀** (직렬 풀 `max=1`) | 워커 ↔ 워커 동시 진입 | 전 진입점이 워커 | `morphingSerialPool` · `preprocessorSerialPool` |
| **게이트** (Claim / Witness 증명) | 워커 ↔ GUI 동시 진입 | 진입점 전수 등록 가능 | `MorphingGate` · `PreprocessorGate` |

판정 순서 —

```
1. 프로세스 전역 가변 상태가 있는가?
   ├─ 있다 → 격리 불가. 3 으로.
   │        (모핑: vtkSMPTools::LocalScope 5곳이 무동기 전역 싱글턴을 write-restore)
   └─ 없다 → 격리. 상태 공유가 사라지므로 배제 기제가 불요해진다.
             2 로 — 격리만으로 끝나는지 확인한다.

2. 등급 판정이 벤더 근거로 확정됐는가?
   ├─ 예   → 격리 단독으로 종결.
   └─ 아니오 → 감금을 겹친다. 실측이 뒤집힐 때의 보험이다. ← RW 축이 여기다

3. 스레드 이동이 안전하고 LEAF 인가?
   ├─ 예   → 감금 1벌. 워커·GUI 양축이 한 벌로 덮인다.
   └─ 아니오 → 풀 + 게이트 2벌. 워커로 안 올라가는 GUI 동기 진입점이
               남는 한 풀만으로는 성립하지 않는다. ← 모핑·preprocessor 축이 여기다
```

대가도 규칙에 담는다 — **감금은 그 서브시스템의 병렬화를 영구히 닫는다.** 스레드를 늘리면 감금이 깨지므로 둘은 양립하지 않는다. RW 축은 그 대가를 지불했고 Phase 1 의 캐시가 완화책이다.
