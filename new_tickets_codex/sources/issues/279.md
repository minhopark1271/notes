`runKpiAutoTest` 처분은 #277 이 본 티켓에 위임한 판단이다("되살릴지 지울지는 #279 가 view pE 분류와 함께 판단"). `createRunsFolders` 와 조건이 동일하므로 처분도 동일하게 간다.

**`DashAnalysisLauncher::createRunsFolders` 는 무접촉** — 이름만 같고 pE 를 갖지 않아 규칙 ⑴ 에 해당하지 않는다. #215 논외 목록에 있다.

### to-be

- **DoD 의 규범이 좌표 목록에서 검사 절차로 바뀐다.** 다섯 명령과 처분 범주 4종이 규범이 되고, 목록은 착수 시 실측이 생성한다. 제3자가 같은 명령으로 같은 판정에 도달할 수 있다.
- **대기 축 명령이 계급의 세 형태를 모두 잡는다** — ⑵a 호출 · ⑵b Blocking 마샬링 · ⑵c 스레드 join. 축을 넓히는 것이 아니라 이미 정의된 계급의 미포착 형태를 회수한다.
- **⓶ 근거의 상한 요건이 개정된다** — "GUI 스레드 대기는 상한 필수" 를 **"상한, 또는 무상한 수용의 근거 + 계측 소유자"** 로 넓힌다. RW 감금 2건이 첫 적용이고, 이것 없이는 #290 이 채택한 설계가 DoD 를 원리적으로 통과할 수 없다.
- **비실행 히트가 범주를 갖는다.** 주석뿐 아니라 **선언·정의 시그니처**도 대기가 아니다. ⑵a 를 호출 한정으로 좁혀 시그니처를 애초에 배제하고, 그럼에도 남는 비실행 형태(블록 주석 연속행 · 문자열 리터럴)는 ⓸ 로 받는다. ⑵b·⑵c 는 산문에 그대로 등장하는 토큰이라 같은 확인을 받는다.
- **model `processEvents` 실호출 0** — 본 티켓 소유 1곳(`createRunsFolders`) 삭제로 확정. 전수는 1(#277 이 남긴 설계 기록 주석 · ⓸).
- **view `processEvents` 전량 귀속** — 실호출 7곳이 ⒜ 0 / ⒝1 3 / ⒝2 1 / ⒞ 3 으로 전부 갈리고 미분류 0건.
- **`docs/ThreadingContract.md` 최종 통합** — 4자 공유 절(풀 배치 규약)의 최종 상태를 확정하고 DoD 검사 절차를 신설한다. #290 이 정정하고 남긴 잔여 좌표와 종료 대기 서술의 사실 오류를 함께 고친다.
- **게이트 최종 상태가 A안으로 확정된다** — 2벌(`MorphingGate` 증명형 · `PreprocessorGate`) 존치 + `RwGate` 폐기 기록. 종전의 "공용화 판단(3벌 유지 vs 공용 기제 추출)" 은 판단 대상이 아니라 확정 사실이 됐다.
- **후속 인계 목록 산출** — ⒝2 와 ⓷ 판정된 ⒝1 각 건의 소유 함수·현재 목적·필요한 조치.

### not-to-be

- **선행이 예고한 좌표를 본문에 복사하지 않는다.** 형제의 제거 예정 줄번호를 옮겨 적으면 그쪽 구현이 바뀔 때마다 본 티켓이 틀린다. 본 티켓은 착수 시점 실측만 규범으로 쓴다. (2026-08-19 재구성 근거 — 종전 본문의 존치 6곳 줄번호 목록이 이미 #282 의 제거 계획과 어긋나 있었다.)
- **선행 산출물 재작업 없음.** 실측이 예상과 다르면 본 티켓에서 보정하지 않고 해당 선행으로 되돌린다 — 봉인 티켓이 남의 산출물을 고치면 DoD 의 의미가 사라진다.
- **DoD 축 확장 없음.** 대기 축의 3분지는 확장이 아니다 — 계급의 정의("호출 스레드를 멈춘다")를 만족하는 형태를 명령이 못 잡던 것을 고치는 것이고, 계급 자체는 #215 가 정한 그대로다. 반대로 `reader->Update()` 계열 GUI 프리즈는 이벤트를 펌핑하지도 다른 스레드의 완료를 기다리지도 않는 **연산 자체의 소요**라 어느 축에도 걸리지 않는다(#215 "잔여 관찰"). 성격은 응답성이며 W11 소관. 중첩 `exec()` 도 같다 — 재진입 창은 같은 계급이나 DoD 를 넓히지 않고 각 자식이 자기 함수에서 확인한다(#215 공용 판정 ⒠). 단 그 **확인 결과의 수집**은 본 티켓이 한다(AC 참조).
- **주석 삭제 없음.** ⓸ 판정의 산출물은 통지이지 삭제가 아니다. 선행이 pE 를 걷으며 남긴 설명 주석은 그 선행의 설계 기록이고, 봉인 티켓이 지우면 위 조항을 정면 위반한다. 사라진 코드를 현재형으로 서술하는 주석은 해당 선행에 통지한다. (예외 1건 — Phase 4 ⑷ 의 종료 대기 서술은 본 티켓 census 가 반증한 사실 오류이고 대상 문서가 본 티켓 소유다.)
- **⒝ 제거 없음** — 배관 신설·워커화는 후속 scope. 본 티켓은 판정과 목록화만 한다.
- **RW 감금의 무상한 대기를 고치지 않는다.** ⓶ 로 받고 근거를 기록한다. 상한을 씌우거나 비블로킹으로 바꾸는 것은 #290 이 채택한 설계의 재판정이고, 계측은 #281 Phase D·E 가 소유한다.
- **A′ 전환 작업 없음** — 모핑 DLL `LocalScope` 수정을 전제하는 게이트 철거는 우리 레포 밖 선행에 걸려 있다(281-1 "수정안"). 본 티켓은 A안 상태를 문서에 확정하고 재개정 조건만 남긴다.
- **CI 게이트 신설 없음** — W9 게이트는 선택. 수동 검사로 하되 CI 화가 가능한 형태로 문서에 남긴다.

## Design

### 현황 분석

- 종전 본문은 **좌표 목록을 규범으로** 삼았다 — 존치 `waitFor*` 6곳 · 주석 5줄 · view 7곳을 줄번호로 못박고 DoD 를 "그 목록을 제외한 나머지가 0" 으로 정의했다.
- 그 목록이 선행 구현 계획과 이미 4건 어긋나 있었다: ⑴ 존치로 적은 2곳을 #282 가 제거한다 ⑵ `ThreadPools`/`AppShutdown` 5곳이 census 에서 빠졌다 ⑶ #281 이 없앨 pE 를 설명하는 주석이 제외 목록에 남는다 ⑷ 풀 개수를 3으로 적었으나 선행이 더한다.
- 원인은 개별 실수가 아니라 **구조**다. 마무리 티켓이 선행의 산출물을 좌표로 예측해 본문에 복사하면, 선행이 구현 중 방식을 바꿀 때마다 봉인 티켓이 틀린다. 그리고 틀렸다는 사실은 착수 후에야 드러난다.
- **절차로 옮긴 뒤에도 같은 결함이 2차로 남았다**(2026-08-20 교정). 처분 표가 아종별 결론을 미리 채워(⒝ → ⓷ 고정) 판정 여지를 닫았고, 범주 4종이 명령이 실제로 뱉는 것을 다 담지 않았다 — 선언·정의 시그니처가 어느 범주에도 안 들어가 "미분류 0건" 이 원리적으로 불가능했다.
- **3차 결함은 그 짝이다**(2026-08-21 개정). 범주가 명령의 출력을 다 받는 것만으로 부족하고 **명령이 계급의 전 형태를 잡아야** 한다. #290 이 `BlockingQueuedConnection`(GUI 무상한 블록)과 `QThread::wait()` 을 들였는데 `waitFor*` 패턴이 둘 다 놓쳐, census 가 0건을 보고하는 동안 프로덕션 RW 호출 전량이 그 지점을 통과하고 있었다. 셋을 한 줄로 묶으면 — **계급 정의 · 명령의 포착 범위 · 범주의 수용 범위가 서로 닫혀야 "미분류 0건" 이 의미를 갖는다.**

### 대안 비교

| 방안 | 핵심 | 장점 | 단점 |
|---|---|---|---|
| A. 좌표 목록 유지 | 선행 진행에 맞춰 본문 좌표를 계속 갱신 | 착수 즉시 무엇이 남는지 보인다 | 선행 3~4건이 움직이는 동안 갱신이 상시화. 갱신 누락이 곧 DoD 실패. 이미 4건 어긋남 |
| B. 판정 규칙 + 착수 시 생성 | 명령·처분 범주만 규범으로 두고 목록은 착수 시 실측이 만든다 | 선행이 무엇을 어떻게 없애든 무효화되지 않는다. 절차 자체가 산출물이라 CI 화·재검증이 가능 | 착수 전에는 잔여 목록을 알 수 없다(파일 해상도 기준선으로 보완) |

### 선택 — 방안 B

**선택 근거**: 본 티켓의 산출물은 잔여 코드가 아니라 **봉인의 증명**이다. 증명은 "이 목록만 남았다" 가 아니라 "이 명령의 모든 히트가 설명된다" 여야 제3자가 재현할 수 있고, 후자는 좌표에 의존하지 않는다. 부모가 요구한 것도 그것이다 — #215 AC 는 성립 조건을 기록할 뿐 검증하지 않는다고 명시하고 검증을 본 티켓에 넘겼다. 부수 효과로 선행 티켓이 구현 중 방식을 바꿔도 본 티켓을 고칠 일이 없다.

**기각된 대안**: A 는 선행 3건이 동시에 움직이는 국면에서 갱신 비용이 무한하고, 갱신 실패가 조용히 DoD 실패가 된다.

**방안 B 의 성립 조건 3항** — 위 현황 분석의 2·3차 결함이 가르쳐준 것.

- **명령은 계급의 전 형태를 잡아야 한다.** 계급을 구문 패턴 하나로 대리하면, 같은 계급의 새 형태가 들어올 때 census 가 조용히 0건을 보고한다.
- **범주는 명령의 출력을 전부 받아야 한다.** 어느 히트도 4범주 밖으로 떨어지지 않아야 "미분류 0건" 이 달성 가능한 목표가 된다.
- **표는 판정 결과를 미리 채우지 않는다.** 아종은 판별 기준까지, 처분은 후보까지만 규범으로 둔다. 확정은 착수 시 건별로 한다.

#### 처분 범주 — 모든 히트는 넷 중 하나로 귀속된다

| 범주 | 정의 | 산출물 |
|---|---|---|
| ⓵ 소멸 | 선행 또는 본 티켓이 없앴다 | 계수만 |
| ⓶ 항구 존치 | 프로덕션 경로의 의도적 동기 | 건별 근거 1줄 — **기능 · 스레드 · 상한** → `ThreadingContract` |
| ⓷ 후속 인계 | 제거 대상이나 처분이 본 티켓 scope 밖 | 위치 · 소유 함수 · 현재 목적 · **필요한 조치** → 인계 목록 |
| ⓸ 비실행 히트 | 주석 · 선언/정의 시그니처 · 문자열 리터럴 | 없음 (계수 제외). 존치 사유 1줄 판정 후 필요 시 선행에 통지 |

**DoD = 다섯 명령의 전 히트가 4범주로 귀속되고 미분류 0건.** 계급별 추가 조건: pE 는 model 계층에 ⓵ 외 실호출 0건 · ⒜ 아종 0건, 대기는 3형 합쳐 ⓷ 0건(전부 ⓶), 슬립은 전 범주 0건.

⓶ 근거에 스레드를 함께 적는 이유는 명령이 계층으로 긋기 때문이다. 계층은 스레드를 판정하지 않으므로, GUI 스레드 대기와 워커 스레드 대기를 건별 근거가 갈라야 한다.

**상한 필드의 규칙** — GUI 스레드 대기는 상한을 적는다. **상한이 없으면 무상한 수용의 근거와 계측 소유자를 적는다** — "적을 수 없으면 ⓷" 가 아니다. `eaa77a6` 의 ⑵b·⑵c 가 그 형태이고, 그것을 ⓷ 로 밀면 #290 이 채택하고 규범으로 적은 설계가 처분 불가가 된다.

#### 검사 명령

```bash
L="model/ view/ controller/ viewmodel/"
# 여집합: main.cpp · ui/ · tools/ · resources/ · cmake/ 는 5축 전부 0 (eaa77a6 실측).
#         tests/ · build*/ · external/ 은 프로덕션 밖.

# (1) 재진입 창 — 전수 / 실호출 / 선행 // 주석
grep -rn "processEvents" $L
grep -rn "processEvents" $L | grep -v ":[0-9]*: *//"
grep -rn "processEvents" $L | grep    ":[0-9]*: *//"

# (1-b) 아종 판별 — 입력을 배달하는 실호출 = ⒜/⒞ 후보. 나머지가 ⒝ 후보
grep -rn "processEvents" $L | grep -v ":[0-9]*: *//" | grep -v "ExcludeUserInputEvents"

# (2a) 동기 블로킹 대기 · 호출형 — 선언·정의 시그니처를 배제한다
grep -rnE "(->|\.|::)waitFor[A-Za-z]*\(" $L

# (2b) 동기 블로킹 대기 · Blocking 마샬링 — 호출자가 타 스레드의 완료를 기다린다
grep -rn "BlockingQueuedConnection" $L | grep -v ":[0-9]*: *//"

# (2c) 동기 블로킹 대기 · 스레드 join
grep -rnE "(->|\.)wait\(\)" $L | grep -v ":[0-9]*: *//"

# (3) 슬립
grep -rn "msleep\|QThread::sleep\|::usleep" $L
```

**기준선** — `b579bcf`: ⑴ = 44/42/2 · ⑵a = 14 · ⑶ = 0. ⑴ 의 44·42·2 는 #215 as-is 실측과 일치해 명령의 타당성이 확인된다. `0320683`(#277): ⑴ = 23/20/3 · ⑴-b = 16(Exclude 4) · ⑵a = 15 · ⑶ = 0. `eaa77a6`(#290, 현행): ⑴ = 23/20/3 · ⑴-b = 16(Exclude 4) · ⑵a = **14** · ⑵b = **1** (주석 3) · ⑵c = **1** · ⑶ = 0.

**주석 식별의 한계를 절차가 인정한다.** ⑴ 의 세 번째 명령은 **선행 `//` 만** 잡는다 — 후행 주석 안에만 있는 경우, 블록 주석 연속행(` * processEvents`), 문자열 리터럴은 실호출로 오계수된다. `eaa77a6` 의 3건이 전부 선행 `//` 인 것은 우연이고, 선행 3건이 pE 를 걷으며 붙일 주석의 형태는 통제할 수 없다. 따라서 **⑴ 의 두 번째 명령 출력은 실호출 후보 목록이며 확정 목록이 아니다** — 착수 시 눈으로 훑어 비선행-`//` 형태를 ⓸ 로 수동 귀속한다. ⑵a 는 호출 한정 패턴이라 산문 주석 대부분이 걸리지 않으나 `waitForFinished()` 처럼 괄호를 포함한 주석은 걸릴 수 있고, ⑵b·⑵c 는 산문에 그대로 등장하는 토큰이라(`eaa77a6` 에서 ⑵b 주석 3건) 같은 확인을 반드시 받는다.
