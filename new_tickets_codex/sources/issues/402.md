# #402 DashXmlParser: 텐서 파싱이 블롭 크기의 5~6배를 복사한다 (int32 미처리·경계 검사 누락 동반)

- URL: https://github.com/NumeRealWorks/DashOpti_GUI/issues/402
- Board status: Done
- Labels: ['in-progress', 'performance', 'split-group:413']

## 현상

Analyzer 가 DataPreprocessor 산출 XML 을 읽을 때 대용량 파일에서 체감 성능이 크게 떨어진다.

## 비용 구조 — 정정됨 (2026-09-18 측정)

**최초 본문의 비용 모델은 틀렸다.** 원문은 "`QXmlStreamReader` 는 pull 파서라 진입점 자체는 문제가 아니다. 비용은 전부 `parseTensor` 에 몰려 있다" 고 적었다. 측정이 정면으로 반박한다.

측정은 모두 같은 기계, 같은 파일(`PART-1-1_1_20_PEEQ.xml`, 4.01GB, 250샘플), 2회차 값이다. 절대 시간은 기계 의존이므로 비율과 전후 비교로만 읽는다.

| 구간 | ms | 전체 대비 |
|---|---|---|
| `loadFromXml` 전체 (PR #424 적용 후) | 11,491 | 100% |
| 그 중 `parseTensor` 누적 | 1,959 | 17% |
| `QXmlStreamReader::readNext()` 만 (요소 해석·base64 디코딩·행렬 할당 전부 없음) | 10,400 | 90% |
| QFile 1MB 청크 순차 읽기 (파싱 없음) | 1,464 | 13% |

토큰화 대상이 무엇인지 (샘플 0, 17.24MB):

| 키 | shape | base64 길이 | 샘플 바이트 비중 | Analyzer 소비자 |
|---|---|---|---|---|
| `connectivity` | [212373, 10] int32 | 11,326,640 | **65.7%** | 0건 |
| `node_location` | [277127, 3] float32 | 4,434,113 | **25.7%** | 0건 |
| `PEEQ` | [277127, 1] float32 | 1,478,093 | 8.6% | 축약 후 float 1개 |

바이트의 **91.4% 가 아무도 읽지 않는 메시**이고, 시간의 90% 가 그 바이트를 UTF-16 으로 토큰화하는 데 든다. `skipCurrentElement()` 는 이 비용을 피하지 못한다 — Qt 는 건너뛰는 `Characters` 토큰도 내부 버퍼로 전부 디코딩한다. 리더에 토큰화 없이 바이트를 건너뛰는 수단은 없다.

즉 비용은 디스크도 텐서 디코딩도 아니고 **4GB 를 `QXmlStreamReader` 에 통째로 밀어 넣는 토큰화 자체**다. 아래 원문의 사본·패스 분석(블롭 크기의 5~6배가 동시 생존, 4회 패스)은 `parseTensor` 안에서는 사실이지만, 그 `parseTensor` 자체가 전체의 17% 였다.

## 부수적으로 확인된 결함

같은 함수에서 같이 나온 것들이라 함께 적는다.

**1. `int32` dtype 이 처리되지 않는다 — 초기화 안 된 행렬이 통과한다**

쓰는 쪽(`DashResultXmlWriter`)은 `connectivity` 를 `int32`, `shape="[numCells, paddingTarget]"` 로 내보낸다. 그런데 `parseTensor` 는 `float32`/`float64` 만 분기한다. 결과적으로 base64 디코딩 비용은 전부 치르고, `matrix.resize(rows, cols)` 로 거대한 행렬을 잡은 뒤 **아무것도 채우지 않고** 반환한다. 에러 로그도 없다.

**2. `Eigen::Map` 앞에 경계 검사가 없다 — OOB read**

```cpp
const float* fdata = reinterpret_cast<const float*>(decoded.constData());
Eigen::Map<...> mapped(fdata, rows, cols);
```

`decoded.size()` 를 확인하지 않는다. 터지는 경로:

- base64 가 잘리거나 손상된 경우. `fromBase64` 는 기본 옵션이 관대해서 잘못된 문자를 무시하고 *짧은* 배열을 조용히 돌려준다 → 경계 밖을 읽는다
- `shape` 속성이 실제 데이터와 불일치하는 경우
- `parseShape` 가 `toInt()` 를 무검증으로 써서 쓰레기 shape 가 0/음수로 통과 → `resize(음수)`
- `rows*cols` 가 `int` 산술이라 큰 텐서에서 오버플로

**3. 잘린 파일이 정상 결과로 보고된다**

`loadFromXml` 의 성공 경로가 루프 안에서 `return result;` 로 빠져나가므로 아래 `xml.hasError()` 검사에 **절대 도달하지 않는다.** 파일이 중간에 잘려도 부분 트리가 에러 없이 반환된다. 대용량 파일일수록 잘림 확률이 높은데 하필 그 경우가 조용히 통과한다.

## 개선 방향 — 처분 (PR #424)

### 이번 범위 8항목의 결과

| # | 항목 | 결과 |
|---|---|---|
| 1 | `readElementText()` 의 UTF-16 왕복 제거 | **폐기** (아래) |
| 2 | `.trimmed()` 제거 | 완료 |
| 3 | 중복 `resize()` 제거 | 완료 |
| 4 | 경계 검사 + `qsizetype` 산술, 실패 시 1×1 영행렬 | 완료 |
| 5 | `int32` 분기, 미지 dtype 은 실패 경로 | 완료 |
| 6 | `parseShape` 를 `toInt(&ok)` 로 강화 | 완료 |
| 7 | `parseElement` 의 per-element `QString` 제거 | 완료 (`QStringView` + 삽입 이동) |
| 8 | 죽은 `hasError()` 검사 복구 | 완료 |

**항목 1 폐기 근거.** 위 측정에서 디코딩 축 전체가 ≤10% 로 확정됐고, 항목 1 은 그 안에서도 소비되는 텐서(`PEEQ`, 샘플 바이트의 8.6%)에만 해당한다. `xml.text()` 도 파서 내부 UTF-16 버퍼를 가리키므로 항목 1 은 토큰화를 없애지 못한다. 항목 1 의 근거로 이 본문이 든 "동시 생존 5~6B" 는 소비자 없는 텐서를 건너뛰는 것으로 이미 사라졌다 — 피크 3,134.5MB → 303.4MB.

### 실제로 얻은 것

| | 시간 | 피크 메모리 |
|---|---|---|
| 변경 전 | 30,593 ms | 3,134.5 MB |
| 변경 후 | 11,491 ms | 303.4 MB |

이득은 이 본문이 "이번 범위 밖" 으로 분리해 둔 항목 — 소비자 없는 텐서 건너뛰기와 첫 샘플 스트리밍 스캔 — 에서 나왔다. 그 둘은 #409 의 내용이며 같은 함수를 만져 분리 비용이 이득보다 커서 PR #424 에 함께 담았다. #409 도 그 PR 로 닫힌다.

### 범위 밖 — 후속

남은 축은 별 티켓으로 뗐다 — 원하는 `dict_item` 만 바이트로 잘라 파서에 넣는 것은 #426, 그 밖은 부모 #413 의 축 표를 참고.

## 확인 — 결과

본문이 지정한 확인 절차(`parseTensor` 에 누적 타이머를 두고 호출부의 전체 시간과 비율을 비교, 비율이 낮으면 병목이 파서 밖이므로 방향을 다시 잡는다)를 2026-09-18 에 수행했다. **비율은 17% 로 낮게 나왔고, 그 판정에 따라 항목 1 을 폐기하고 방향을 다시 잡았다.** 숫자는 위 "비용 구조" 절에 있다.

기능 확인으로 남은 것: 소비자 없는 텐서를 건너뛴 상태에서 Analyzer 를 실제로 띄워 플롯 값이 맞는지 확인한 적이 없다. 파서 레벨 테스트(`tests/TestXmlParser.cpp`)와 앱 빌드·링크는 통과했다.
