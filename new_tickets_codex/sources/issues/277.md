### to-be

- **`preprocessorSerialPool()` 신설** — `maxThreadCount = 1`. `ThreadPools` 3번째 풀. `waitForAllSerialPools(int timeoutMs)` 에 합류. 풀과 게이트는 중복이 아니다 — 게이트는 거부(충돌 ⑵), 풀은 대기·순서 보장·종료 드레인 참여(충돌 ⑴).
- **`PreprocessorGate` 신설 — 배타 단위는 `GUI 진입 1회`다.** 워커 1회 실행이 아니다. 토큰은 진입점에서 잡아 그 진입이 펼치는 Job 전부와 완료 슬롯까지 산다. GUI 잔여 진입점 5곳은 `tryClaim()` 실패로 거부.
- **증명은 두 축으로 갈린다 — `MorphingGate` 동형** — `Witness`/`Claim`/`Reservation`. `Claim` 은 사슬 축(GUI 가 진입점에서 잡아 사슬 끝까지 보유), `Reservation` 은 워커 축(각 Job task 가 `shared_ptr` 로 캡처). 취소 시 GUI 가 `Claim` 을 즉시 놓아도 워커의 `Reservation` 이 원자 워드를 0 이 아니게 유지해 재착수가 거부된다. **DPF 진입 함수는 `const Witness&` 를 요구한다** — 워커 진입뿐 아니라 GUI 잔류 DPF 호출도 포함.
- **공개 진입과 내부 호출을 가른다** — 공개 진입이 토큰을 잡고, 내부 호출은 증명을 인자로 받아 **재획득하지 않는다**. 재획득하면 자기 자신에게 거부된다.
- **Job 경계 = 산출물(XML) 경계** — 샘플 루프는 워커 task 내부에 존치. 근거는 "Design" 대안 비교.
- **데이터 흐름: 워커는 계산만, GUI 완료 슬롯이 조립·저장** — `doc.save` + `emit processFinished` 를 완료 슬롯으로 올린다.
- **`m_preprocessor` 소유를 `std::shared_ptr<IPreprocessorWrapper>` 로** — task 가 값으로 캡처해 **수명이 게이트 정확성에서 독립**한다.
- **`WorkerJob::Task` 에 진행·로그 sink 를 추가한다** — `WorkerResult(const std::atomic<bool>&, const Sink&)`. task 는 `this` 를 캡처하지 않고 sink 로만 통지한다. `Sink` 는 복사 가능하고 내부에 **GUI 스레드 소유 relay(`shared_ptr`)** 를 든다 — `m_cancelled` 와 같은 이유로 Job 포인터를 직접 들지 않는다. `WorkerJob` 소멸 시 relay 를 detach 해 **터미널 잠금 이후의 늦은 통지를 폐기**한다(`Job::finished` 뒤에 `progressed` 가 뜨면 안 된다). 로그 채널로 `WorkerJob::logged(QString)` 을 신설한다 — `Job::progressed(int)` 는 기존.
- **결과 페이로드는 시그니처 밖에 둔다** — task 가 `shared_ptr<Payload>` 를 값 캡처하고 완료 슬롯이 읽는다. `WorkerResult{ok, reason}` 는 무변경. 페이로드 타입이 축마다 다르므로 시그니처화하면 `WorkerJob` 이 템플릿·헤더 전파를 일으킨다. 프로덕션 소비자가 `DashJobRunner.cpp:1395` 1곳 + `tests/` 뿐이라 인자 추가의 전환 비용은 그 2곳이다.
- **`allProcessFinished` 를 3회 → 1회로 줄인다 — 의도적 동작 변경**이다. 소비자가 방출마다 팝업을 띄우므로 사용자에게 보이는 변화(팝업 3개 → 1개)다. 시그널 왕복 수집을 model 소유 `PendingBatch{files, remaining}` 로 대체한다.
- **model `processEvents` 22 → 0.**

### not-to-be

- **per-sample Job 분해 없음** — 근거는 "Design" 대안 비교.
- **XML 포맷 변경 없음** — 중복 제거·포맷 분리는 per-sample 전환과 같은 시점의 별건.
- **GUI 잔여 진입점 5곳 + 잔류 DPF 호출 1곳 워커화 없음** — 진입점 5곳은 게이트로 배제한다. 잔류 호출 1곳은 `DashResponseInitializer`(`processResults:1667`)로, **GUI 에 남긴다**(선결 5). `m_availableResponses` 가 비었을 때만 도는 cold path 이고 `processEvents` 0곳이라 Goal 을 깨지 않는다. 대신 `initialize` 도 `const Witness&` 를 받는다.
- **취소 트리거 신설 없음 — W11 소유**(#215 명시). 취소 **폴링**은 전환 계약 ⑶ 으로 본 티켓이 세운다. 없는 것은 트리거뿐이다. 폴링 정확성은 단위 테스트로 검증한다.
- **진행률 UI 신설 없음** — W11 소유. sink 는 세우되 진행률 표시 소비자는 만들지 않는다.
- **KPI 골격 중복 제거(1,177줄) 없음** — 워커화가 강제하는 공통 형태 이상은 건드리지 않는다.
- **`processResultsWithKPI` 의 KPI/일반 분기 자체는 무변경** — 결과 수집 규약만 비동기로 재정의한다.

## Design

> Step 2.5 트리거: 논리 구조 설계(배제 단위 · Job 경계) · 컴포넌트 hierarchy(풀·게이트) · 파라미터 설계(증명·페이로드 계약).

### 현황 분석

두 축을 갈라야 한다.

```
충돌 ⑴  워커 Job <-> 워커 Job        → 직렬 풀이 처리. 거부가 아니라 대기
충돌 ⑵  워커 Job <-> GUI 동기 호출   → 풀은 못 막는다. 게이트만이 막는다
```

`MorphingGate`(#214)가 존재하는 이유가 ⑵ 다. **같은 구멍이 preprocessor 에도 있다** — 진입점 8곳 중 5곳이 GUI 동기로 남고 전부 동일 인스턴스를 만진다.

per-Job 인스턴스(ThreadingContract 4절)는 대안이 못 된다 — 생성자가 `DashManager::Mgr()` 를 만져 GUI 고정이고, 등급 2 판정이 유지되는 한 인스턴스가 달라도 DLL 배제가 필요하다.

### 배제 단위 — GUI 진입 1회

**초안은 배제 스팬을 "워커 1회 실행" 으로 잡았고, 그것이 이 티켓 최대의 결함이었다.** 반례 3건이 코드에 실재한다.

| 반례 | 좌표 | 워커 스코프 토큰일 때의 결과 |
|---|---|---|
| 위젯이 버튼 한 번에 `processResults` 3연속 호출 | `DashDataProcessorWidget.cpp:978`·`:981`·`:984` | 2·3회차가 `tryClaim()` 실패 → **요청 조용히 유실** |
| `processResultsWithKPI` 가 KPI 연쇄 후 `processResults` 재호출 | `DashDataProcessor.cpp:2094` | 같은 유실 |
| Job 연쇄의 Job k 완료 ~ k+1 착수 사이 | Phase 2·4 | 그 틈에 프리뷰가 `tryClaim()` **성공** → `SetInputFilePathes` 로 인스턴스 오염 → 다음 Job 이 엉뚱한 파일로 계산 |

세 번째가 가장 나쁘다 — 크래시가 아니라 **틀린 숫자가 XML 에 기록**된다. ThreadingContract 4절이 "크래시보다 나쁘다" 고 규정한 계급이고, 되돌릴 수 없다(이미 나간 산출물).

네 번째 위험이 하나 더 있다. **스냅샷 표류** — 사슬이 도는 중 GUI 가 `loadRstDataFromTable` 을 실행하면 `m_currentAnalysisType`·`m_selectedType`(`:911-912`) · `m_lastLoadedInputFiles`(`:934`) · `m_isModalAnalysis`(`:939`) · `m_frequencies`(`:941`) · `m_modalDefs`(`:943`) 를 갈아엎는다. **전부 `ProcessContext` 스냅샷 대상 필드**다.

**선례가 같은 형태다** — `DashJobRunner.h:211` 의 `std::optional<MorphingGate::Claim> m_morphClaim` 은 **멤버**로 연쇄 전체를 살고(`:2281` 획득 · `:1334` 해제), 샘플 task 는 `:1392` 에서 `shared_ptr<Reservation>` 을 따로 잡는다. #215 의 "preprocessor 는 배치 축이 없다" 판정은 진입점 3곳만 센 결과이자, 자기 계획(Job 연쇄)과 모순이었다.

### 대안 비교 — Job 경계

| 방안 | Job 단위 | 산출물 | 장부 | 취소 | 진행률 | 신설 부담 |
|---|---|---|---|---|---|---|
| **A. 산출물 단위** | XML 1개 | Job 내부에서 완결 | 불요 | 샘플 루프 경계 폴링 | 샘플 인덱스 단위 통지 가능 | 풀 1 + 게이트 1 |
| B. per-sample 연쇄 | 샘플 1건 | **없음** — `QDomDocument` 를 Job 사이로 넘겨야 함 | **샘플별 stage 칸 신설 필요** | 샘플 경계 | 동일 | + 장부 확장(#251·#264 급) + 정책 P1~P5 이식 |

### 선택 — 방안 A (산출물 단위)

**선택 근거**

1. **산출물이 샘플 단위가 아니다.** 모핑이 per-sample 인 것은 샘플마다 산출물이 있어서다 — `RunOneSample` 이 `runDir/runKey.vtu` + `.dat` 를 쓰고 장부에 1행을 남기며 후속 stage 가 3단으로 이어진다. KPI·결과처리는 그 4개 조건이 전부 없다.
2. **per-sample 의 이점 둘을 단일 Job 이 거의 다 준다.** 취소는 협조적 폴링이므로 task 내부 샘플 루프 경계에서 성립한다. 진행률은 받아줄 UI 가 없다 — 그 신설은 W11.
3. **잃는 것은 "실패 샘플만 재시도" 하나인데 현재도 없다** — 실패는 `continue` 로 버린다.
4. **B 는 장부 확장과 정책 이식을 이 티켓으로 끌어들인다.**
5. **비용 계급 대비 단위가 잘다** — 샘플당 수백 ms ~ 수 초로 추정된다(`processSingleSample` 이 샘플 1건을 pE 5토막으로 펌프 · `:193` 주석 예시 `runs498`). 함수 총량은 수 분 ~ 수십 분. **런타임 실측은 아니며 코드 구조 근거다.**

**기각된 대안**: B — 산출물·장부·정책·UI 네 전제가 모두 없는 상태에서 단위만 쪼개면 신설 부담만 남는다.

### 게이트 형태 — `MorphingGate` 동형 (`Witness`/`Claim`/`Reservation`)

축이 정확히 대응하므로 형태를 그대로 따른다.

| | `MorphingGate` | `PreprocessorGate` |
|---|---|---|
| 상위 축 (`Claim`) | 모핑 국면 — 배치 전체 | GUI 진입 1회 — 사슬 전체 |
| 하위 축 (`Reservation`) | 샘플 Job 의 DLL 구간 | 요청·출력 Job 의 DPF 구간 |
| 취소 비대칭 | 배치 즉시 해제 · 워커는 DLL 종료 후 | 동일 |

**대안 검토 — `shared_ptr<Claim>` 1형.** `Claim` 을 `shared_ptr` 로 감싸면 마지막 참조 소멸이 `Reservation` 과 같은 비대칭을 주므로 타입 하나로도 정확성은 동일하다. 그럼에도 **기각**한다.

1. **호출부 코드가 같다.** 워커 축은 어느 쪽이든 `shared_ptr` 캡처다 — `DashJobRunner.cpp:1392` 가 이미 `make_shared<MorphingGate::Reservation>(m_morphClaim->reserve())` 다. 차이는 게이트 내부 ~50줄뿐이고 그 50줄은 검증된 코드의 기계적 복제라 설계 리스크가 0 이다.
2. **읽는 비용이 되레 는다.** `MorphingGate` 3형이 이미 머지돼 있으므로 2형 게이트를 추가하면 독자가 두 형태를 모두 알아야 한다.
3. **공용화 경로를 닫는다.** 게이트 3벌의 중복은 #280 시점에 공용 기제로 추출해 해소하는 것이 답인데, 동형이면 추출이 기계적이고 이형이 섞이면 이미 머지된 `MorphingGate` 를 개정해야 해 사실상 불가능해진다. 50줄을 아끼는 대가로는 비싸다.
4. **관측 가능성.** 원자 워드가 축을 구분해 담으므로 "배치가 들고 있는가, 워커만 남았는가" 를 게이트가 안다. `shared_ptr` 로 가면 "누군가 들고 있다" 만 남는다. 현재 소비자는 없지만 되돌리기 어렵다.

**중복의 처분**: 같은 원자 워드 로직이 3벌이 되는 것은 실제 비용이다. 불변식(CAS 의미론 · `busyChanged` 마샬링 · 해제 순서)이 세 곳에서 갈릴 위험이 있다. **#280 이 세 번째 게이트를 세우는 시점에 공용 기제로 추출**한다(후속 작업). 소비처 3개면 추상화 근거가 충분하고, 동형이라 추출이 기계적이다.

`MorphingGate` 는 이미 머지됐으므로 손대지 않는다. **#280 `RwGate` 는 `Reservation` 축이 빠져 있어 보강이 필요하다** — 그쪽 Phase 1 의 "모핑 샘플 Job 이 `RwGate` 를 함께 쥔다" 가 정확히 워커 축을 요구한다.

### 사슬 실패 규약

요청 N개 중 k번째가 실패했을 때의 처리는 현재 동기 대응물이 정해 준다 — `:2031-2035` 가 예외를 삼키고 `continue` 한다. 비동기에서도 **같은 규약을 유지**한다.

| 항목 | 규약 |
|---|---|
| 나머지 Job | **계속 진행**한다 (현행 `continue` 계승) |
| 실패 통지 | 해당 요청분만 `errorOccurred`. 사슬을 중단하지 않는다 |
| `allProcessFinished` | 성공분만 담아 사슬 종료 시 **1회** |
| 게이트 해제 | 성공·실패 무관하게 **사슬의 마지막 Job 완료 슬롯**에서 `Claim` 을 놓는다. 진행 중 `Reservation` 이 남아 있으면 그것이 소멸할 때까지 게이트가 유지된다. 둘 다 RAII 라 예외 경로에서도 닫힌다 |
| 취소 | 미착수분은 착수하지 않고, 진행 1건은 폴링으로 빠져나온다. GUI 축은 즉시 해제 · 워커 축은 DLL 종료 후 |

### 워커 경계 규약

| 대상 | 규약 |
|---|---|
| `this` 캡처 | **금지.** 소유자가 런타임에 파괴된다(선결 4). 통지는 sink 로만 |
| GUI 소유 컨테이너 | **GUI 스레드에서 복사**해 값으로 전달(선결 6). 워커가 GUI 인스턴스에서 복사하지 않는다 |
| `QDomDocument` | 워커가 조립하고 GUI 완료 슬롯이 저장한다. **워커가 완전히 놓은 뒤 GUI 가 잡는다** — 중간에 사본을 만들지 않는다(암시적 공유이고 스레드 안전하지 않다) |
| 스냅샷 시점 | **사슬 착수 시 1회.** Job 마다 다시 뜨면 GUI 변경이 중간에 섞인다 |
| 디스크 쓰기 | **본 축은 GUI 완료 슬롯이 쓴다** — `QDomDocument` 가 메모리에 있어 자연스럽고, 산출 XML 을 다음 실행이 정본으로 읽으므로. **레포 전역 금지가 아니다**(#215 ⒞ 재서술) — 완결 판정은 워커의 반환값이 소유하고, 워커가 쓰는 축은 반환이 안 오면 미완결로 판정한다 |

### per-sample 전환 계약 5항목 (본 티켓이 지금 세운다)

전환 비용은 비대칭이다. **지금 하면 계약 1곳, 나중에 하면 Phase 2~4 의 4곳 재작업**이다. Phase 1 파일럿이 세우고 Phase 2~4 가 복사한다.

1. **결과 페이로드 채널** — task 가 `std::shared_ptr<Payload>` 를 캡처해 값을 담고 GUI 완료 슬롯이 읽는다. `WorkerJob::m_cancelled` 와 동형이라 이 항목은 `WorkerJob` 수정 불요.
2. **파일 쓰기·완료 시그널을 GUI 소유로** — 워커는 DPF 호출과 계산만.
3. **취소 폴링 지점을 샘플 루프 경계에** — 이 지점이 전환 시 그대로 Job 경계가 된다.
4. **진행·로그 sink** — `WorkerJob::Task` 시그니처 확장이 **필요하다**. 현 시그니처(`WorkerJob.h:53`)에 진행 채널이 없고 task 가 Job 보다 오래 살아 Job 포인터 캡처가 금지돼 있으므로(`WorkerJob.cpp:36-38`), `Job::progressed` 에 값을 먹이는 것은 `WorkerJob` 수정 없이 구현 불가다. 로그 텍스트도 이 채널로 나른다.
5. **증명을 값으로 이동** — task 는 `shared_ptr<Reservation>` 을 캡처한다. `const Witness&` 를 워커 task 에 넘기는 시그니처는 댕글링이다 — 참조는 GUI 스레드 동기 호출(내부 2층 · `DashResponseInitializer`)에만 쓴다.

**전환 시 남는 작업 2개**: ⑴ 샘플 루프를 Job 연쇄로 펼치기 ⑵ 샘플별 상태를 담을 장부 칸 신설. 데이터 흐름 재설계는 남지 않는다.

```
controller/async/

```

### 종료 정책 — 실측이 아니라 선언

`waitForAllSerialPools`(`ThreadPools.cpp:37-46`)의 상한은 **원래부터 완료 대기가 아니라 포기 판정**이다(`AppShutdown.cpp:14-15` 주석 · `ThreadPools.h:16-17`). 3풀이 만드는 것은 새 실패 모드가 아니라 **빈도 승격** — 결과 처리는 모핑 배치보다 훨씬 흔해 `_Exit(1)` 이 예외에서 상시가 된다.

`_Exit` 의 해악은 본 티켓의 계약이 실제로 줄인다 — 워커가 디스크에 쓰지 않으므로 반쯤 쓰인 XML 이 남지 않는다. 남는 실해악은 **DPF 핸들·라이선스 미반납** 하나다.

| # | 정책 |
|---|---|
| ⑴ | `_Exit` 상시화를 **수용**한다. 드레인 예산은 튜닝 대상이 아니다 |
| ⑵ | **종료 중 신규 Job 착수 금지** — `AppShutdown` 의 실행 여부를 공개해 진입점이 읽는다. 실제 창은 좁다(`run()` 중에는 GUI 가 `waitForDone` 에 갇혀 큐드 완료 슬롯이 못 돈다). 값싼 보험 |
| ⑶ | **DPF 협조적 취소·라이선스 반납 경로 조사** — Phase 1 조사 항목. 있으면 ⑶ 으로 해결, 없으면 ⑴ 이 유일한 답이고 그 범위를 알고 수용한다 |

초안의 검증 항목("마지막 풀이 `waitForDone(0)` 을 받지 않는다")은 **삭제한다** — 잔여 예산이 지역변수라 외부 관측이 불가하고, 유휴 풀의 `waitForDone(0)` 은 즉시 true 라 합성 짧은 Job 으로만 통과하는 무의미한 테스트다.
