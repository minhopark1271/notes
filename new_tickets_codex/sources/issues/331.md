## 1. DashGizmo 를 앱 내부 단일 빌드로 재배치

### As-is

`libs/DashGizmo` 가 독립 static 라이브러리 타깃이고 앱이 `DashGizmo::DashGizmo` ALIAS 로 링크한다.

원본은 `NumeRealWorks/DashOpti_Gizmo` @ `c6696a166ed18a255a7246415beb0fe169fd9698` ("updated group gizmo logic (#5)", 2026-07-15) 의 `cpp/include` · `cpp/src` 이며, 재동기화 절차가 `libs/DashGizmo/README.md` 에 있다.

#313 이 이 배치를 택한 이유는 **소스를 추적 가능한 위치로 들여오고 앱과 같은 VTK 로 빌드되는 것까지 확인**하는 것이 그 단계의 목표였기 때문이다. `external/` 은 gitignore 대상이라 추적이 안 되고, 앱 소스 트리(`controller/` · `model/` · `view/` · `viewmodel/`)에 바로 넣으면 `GLOB_RECURSE` 에 걸려 들어가면서 원본과의 diff 대응 관계가 흐트러진다.

### To-be

Gizmo 소스가 **앱 소스 트리의 일부**가 되어 `DashOptGUI` 하나로 컴파일된다.

- `add_subdirectory(libs/DashGizmo)` 제거
- `DashGizmo::DashGizmo` ALIAS 제거
- `libs/DashGizmo/CMakeLists.txt` 제거

### 주의 — #313 이 이미 밟은 함정

- **서브 CMakeLists 에서 `find_package(VTK)` 를 다시 부르면 안 된다.** `vtk-config.cmake` 가 `VTK_LIBRARIES` 를 그 호출의 COMPONENTS 로 덮어써 상위 링크 목록과 `vtk_module_autoinit` 을 망가뜨린다(`mesh-ops` 에서 이미 겪어 루트에 워크어라운드가 들어가 있다). 단일 빌드로 합치면 이 문제 자체가 소멸한다
- **VTK COMPONENTS 에 `CommonComputationalGeometry` · `CommonMath` · `CommonTransforms` 가 필요하다.** Gizmo 가 요구하지만 원래 목록에 없던 것들로, 통짜 VTK 설치에서는 우연히 동작하지만 vcpkg 는 요청한 컴포넌트 타깃만 준다
- **원본 저장소와의 diff 대응 관계가 끊어진다.** 재동기화 정책을 먼저 정해야 한다 — fork 유지 / 원본 아카이브 / GUI 를 정본으로 승격 중 택1

### DoD

- `libs/DashGizmo` 디렉터리 부재
- 링크 응답 파일에 `DashGizmo.lib` 부재, unresolved external 0
- Release · Debug 빌드 및 기동 정상

## 2. `libs/DashGizmo` naming convention 정리

> **선행: #321** — 이 항목만 `blocked`

### As-is

`libs/DashGizmo` 는 이관 원본의 레이아웃을 그대로 유지하고 있어 선행 밑줄(`_position` 등) 등 저장소 관례와 다른 표기가 섞여 있다.

#313 은 원본과의 diff 대응을 위해 의도적으로 손대지 않았고, 리뷰에서도 *"나중에 정리하기로 하시죠. 이하 더이상 언급하지 않겠습니다"* 로 명시적으로 미뤘다.

### 선행 조건

**#321** 이 저장소 convention(`.clang-format` · clang-tidy · pre-commit)을 확정해야 한다. 확정 전에는 **"무엇으로 고칠지" 가 없다.**

### 결정 필요

#321 규칙을 `libs/` 이관 코드에도 적용할지, 원본 diff 대응을 위해 예외로 둘지.

**위 1번(단일 빌드 재배치)이 끝나면 `libs/` 가 사라지므로 예외 근거도 함께 소멸한다.** 두 항목을 같은 브랜치에서 처리하는 것이 자연스럽다.

## 3. `MarchingPlaneBound` 상류(mesh-ops) 환원

> [!WARNING]
> **출처가 상류 미머지 브랜치다.** 이 티켓에서 위험도가 가장 높다.

### As-is

`libs/DashMarchingPlane` 에 GUI 저장소가 소스를 **임시 보유**한다.

출처는 `NumeRealWorks/DashOpti_Morphing` 브랜치 `Parallel-Processing` @ `6e13f453` 이고 **main · dev · 모든 태그에 없다.** 상류에 병합되지 않은 코드를 GUI 가 들고 있는 상태다.

상류와의 차이는 두 곳뿐이다 — `DashOptiMorphing/CoreDefines.h` include 와 `DASHMR_API` 를 뺐고, self-include 를 `"MarchingPlaneBound.h"` 로 바꿨다. 재동기화 절차는 `libs/DashMarchingPlane/README.md` 에 있다.

### 왜 들여왔나

사전빌드 `DashOptiMorphing-0.0.4` 의 `DashOptiMorphing.dll` 이 `MarchingPlaneBound` 를 export 했고, **그 패키지가 사라지면 함께 사라진다.** #313 이 사전빌드 4종 소비를 끝내면서 소스로 대체할 수밖에 없었다.

### 기능

주축(StartPoint → EndPoint)을 따라 surface 를 `NumberOfCuts` 개 평면으로 잘라 각 단면의 중심점을 `vtkPolyData` 로 내는 `vtkPolyDataAlgorithm` 파생 필터. 출력 point-data 에 `SectionID` · `Bounds` · `LocalToGlobal` array 를 함께 싣는다.

**소비자는 `controller/DashMorphingController.cpp` 한 곳이다.**

### To-be

mesh-ops 가 이 기능을 **공개 표면에 올리고** GUI 는 `libs/DashMarchingPlane` 을 삭제한다.

### 선행 작업

- 상류 `Parallel-Processing` 브랜치의 운명(머지 / 폐기) 확인
- mesh-ops 공개 표면 추가 협의

**이 항목은 다른 저장소(`DashOpti_MeshOps`)에 의존한다.**
