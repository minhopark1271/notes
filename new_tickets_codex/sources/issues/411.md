## 성격

**검토 티켓이다.** 결론이 "안 바꾼다" 여도 정상 종료다. 상위 티켓의 단기 축(#402 · 선택적 파싱 · 캐시)이 끝난 뒤 **남는 비용**을 보고 판단한다.

## 문제

XML 컨테이너 자체가 지는 불이익이 세 겹이다 (§4.4).

| 겹 | 배율 | 근거 |
|---|---|---|
| base64 | ×4/3 | 디스크·메모리 양쪽 |
| `QDomDocument` 누적 | ×2 + 노드 오버헤드 | 전 샘플을 DOM 에 쌓은 뒤 `doc.save()` · `QDomText` 가 UTF-16 |
| request 수 | ×M | request 마다 별 XML → 지오메트리가 파일 수만큼 재중복 |

```
size ≈ (4/3) × N × [ P·3·4 (node_location) + C·pad·4 (connectivity) + P·ncomp·4 (field) ]
```

생성 피크 메모리는 대략 그 2배 이상. **실측 파일 크기·피크 메모리는 아직 수집되지 않았다** (§9 검증 한계: 근거 강도 "중").

생산(DOM 누적 → 일괄 저장)과 소비(일괄 로드 → 전량 복원) 양쪽이 스트리밍이 아니다 (§4.5).

## 후보

**HDF5 (vtkHDF)** 가 1순위다 — 청크 단위 부분 읽기, 압축, 이진 저장으로 세 겹이 한 번에 사라진다.

> 구 조사는 "`vtkHDFWriter`/`vtkIOHDF` 가 이미 빌드에 포함돼 외부 의존 추가 없이 대체 가능" 을 근거로 들었으나, **`external/` 디렉토리가 레포에서 사라져 현재 확인 불가**다 (§8절 5번에서 "미확인" 으로 낮춤). vcpkg 이행(#336) 이후 `vtkIOHDF` 가 실제로 켜져 있는지 **재확인이 첫 단계**다.

## 결정할 것

1. **의존 추가가 필요한가** — 현 vcpkg 구성에서 `vtkIOHDF` 가용 여부 재확인. 필요하면 메타 저장소 매니페스트·바이너리 캐시 재워밍 비용이 붙는다 (#335 · #374 선례)
2. **외부 계약이 있는가** — 소비처는 인앱이라는 것이 #215 의 판정이지만, ModelBuilder 학습 본체는 **외부 도구가 파일을 직접 읽는다** (§4.5). 그 도구의 리더를 같이 바꿀 수 있는지가 실질 관문이다
3. **마이그레이션** — 구 XML 읽기를 얼마나 유지하나. 기존 프로젝트의 산출물이 읽히지 않으면 회귀다
4. **부분 대안으로 충분한가** — 포맷을 바꾸지 않고 기록 내용만 줄이는 셋이 §7.2 에 있다:
   - `connectivity` 를 파일당 1회로 (모핑은 위상 불변)
   - `paddingTarget` 을 실제 `maxStride` 로 (tet 메시 50% 절감)
   - 조건-only · CAD DOE 에서 `node_location` 도 파일당 1회로

   셋 다 포맷 교체와 **독립적으로 선행 가능**하고 훨씬 싸다. 선행 조건은 외부 학습 도구가 이 둘을 샘플마다 있다고 가정하는지 확인하는 것 — GUI 파서는 확인됐고 도구 내부는 미확인이다.

## 먼저 할 것

측정이다. 실기 DOE 산출물에서 **실측 파일 크기·생성 피크 메모리·샘플 수 대비 증가율**을 수집한다. 4번 부분 대안이 감당하면 포맷 교체는 하지 않는다.

즉 "메시 중복은 XML 안에서 고친다" 는 경로가 지금은 닫혀 있다. 이 티켓을 판단할 때 그 전제가 바뀐 것을 반영해야 한다. 판단 자체는 하지 않았고, 이슈 본문도 수정하지 않았다.
