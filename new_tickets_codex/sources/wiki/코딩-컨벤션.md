# 코딩 컨벤션 (제정 중)

DashOpti_GUI C++ 코드의 서식·네이밍·인코딩 규칙과, git 훅이 그것을 강제하는 범위다.
상위 목차는 [[프로젝트-관리]]. 이슈 #321에서 시작했다.

> **적용 시점: PR [#329](https://github.com/NumeRealWorks/DashOpti_GUI/pull/329)가 dev에 머지된 뒤부터다.**
> 머지 전에는 이 페이지의 규칙도, 저장소의 설정 파일도, 훅도 아무 효력이 없다. 머지되면 각자
> 3절의 로컬 설정을 한 번 해야 훅이 돌기 시작한다 — 클론만으로는 켜지지 않는다.
>
> **컨벤션 자체는 아직 제정 중이다.** 기계적으로 강제되는 서식·인코딩은 이 PR 로 확정되지만,
> 네이밍과 코드 작성 규칙은 논의가 이어지고 있어 바뀔 수 있다. 확정 시점은 별도로 알린다.

규칙의 **원문은 저장소 안**에 있고 훅·설정 파일과 같은 커밋으로 움직인다. 이 페이지는 요약과 진입점이며,
둘이 다르면 저장소 문서가 우선한다.

- [docs/coding-convention.md](https://github.com/NumeRealWorks/DashOpti_GUI/blob/dev/docs/coding-convention.md) — 규칙 원문, 로컬 설정, 에이전트용 지침
- 설정 파일: `.clang-format`, `.clang-tidy`, `.gitattributes`, `.githooks/pre-commit`,
  `scripts/hooks/run-format-checks.sh`, `scripts/hooks/fix-encoding.py`, 자체 검증 `tests/hooks/test-precommit.py`

## 1. 규칙 요약

대상은 **`.h`, `.cpp` 등 C/C++ 소스**다. 외부 라이브러리(Qt, VTK, vcpkg 패키지)와 빌드 시 생성되는
코드는 대상이 아니다.

파일
- BOM 없는 UTF-8. 훅이 커밋 시 **자동 변환**한다: BOM 제거, UTF-16 LE/BE → UTF-8, CP949 → UTF-8.
  거부가 아니라 수정이므로 손댈 것이 없다. 셋 중 무엇으로도 해석되지 않는 파일만 거부된다.
- 줄바꿈은 **LF**. `.gitattributes`가 커밋 시 정규화한다. 작업 디렉터리는 각자의 `core.autocrlf`
  대로 두면 된다.
- 줄 끝 공백, 탭 앞 공백 금지. 이 검사만 C/C++이 아닌 **스테이지된 모든 파일**에 적용된다.

서식 (clang-format)
- 조직 표준 `.clang-format`(Mozilla 기반, 100자)을 쓴다. 버전은 **22.1.8로 고정**한다 — 출력이
  버전에 따라 달라지면 다른 사람이 포맷한 파일을 훅이 거부한다.
- 로컬 예외 둘: 들여쓰기 **4칸**(Mozilla 기본 2칸을 덮어씀. 현행 코드 95%가 4칸),
  `SortIncludes: Never`(순서 의존 헤더가 있어 자동 정렬은 켜지 않는다. 손으로 맞추는 include
  순서 규칙은 아래 표에 있고, 기계 검사는 붙이지 않는다).
- 반환형은 함수 이름과 **같은 줄**에 두고 100자를 넘을 때만 나눈다(`BreakAfterReturnType: Automatic`).
- `InsertBraces: true` — 한 줄 본문에도 중괄호를 clang-format이 **직접 삽입한다**. 서식 옵션 중
  유일하게 코드를 고치는 쪽이며 삽입만 하고 제거는 하지 않는다.
- 브레이스 위치가 갈린다: **함수·클래스·enum은 다음 줄, 제어문과 namespace는 같은 줄.** 한 줄짜리
  getter와 빈 생성자도 예외 없이 펴진다(`AllowShortFunctionsOnASingleLine: None`).

거부되는 대표 패턴은 PR [#329의 코멘트](https://github.com/NumeRealWorks/DashOpti_GUI/pull/329#issuecomment-5675957471)에
"거부 / 고쳐진 모양" 짝으로 정리해 두었다.

네이밍 (Qt 스타일)

| 대상 | 규칙 |
|---|---|
| 클래스·구조체·enum·네임스페이스·typedef·템플릿 파라미터 | PascalCase |
| enum 값 | PascalCase |
| 함수·메서드 | camelCase |
| 변수·파라미터·상수 | camelCase (`k` 접두 없음) |
| 멤버 변수 (private, protected) | camelCase + **`_` 접미** — `jobPool_` |
| 멤버 변수 (public) | camelCase, **접미 없음** — `filePath` |
| 매크로 | UPPER_CASE |

**매크로를 제외한 모든 식별자에 UPPER_CASE 금지. 접두는 전부 금지** — 헝가리안 `m_`, private 표시용
`_`, 상수용 `k`. Qt Designer가 생성하는 `ui->` 멤버가 접두 없는 camelCase라 `m_` 강제는 한 클래스 안에
두 규칙을 혼재시킨다.

접미 `_`를 남긴 이유는 따로다. 멤버 변수와 지역 변수를 이름만 보고 구별할 수 없으면 사람도 코드 생성
에이전트도 둘을 헷갈린다. public 멤버에 붙이지 않는 것은 바깥에서 `obj.field`로 접근하니 그 구별이 이미
문법에 있기 때문이다.

Qt/VTK가 정한 이름(오버라이드, `vtkTypeMacro` 계열, `Q_OBJECT` 등)은 대상이 아니다. 네이밍 자동
수정(`clang-tidy -fix`)은 쓰지 않는다 — 한 파일에서 이름을 바꾸면 다른 파일의 호출자가 깨진다.

코드 작성 규칙 (기계 검사 없음, 리뷰에서 본다)

| 항목 | 규칙 |
|---|---|
| getter / setter | getter는 필드명 `items()`, setter는 `setItems()`. 동명 오버로드는 쓰지 않는다 |
| 헤더 | `#pragma once` 로 시작한다 |
| include 표기 | 디렉터리 경로를 표기한다. `"Utilities/Logger.h"` (O) / `"Logger.h"` (X) |
| include 따옴표 | 이 프로젝트에서 작성한 파일은 `"..."`, 나머지는 `<...>` |
| include 순서 | `<...>` 가 위, `"..."` 가 아래. 각 묶음 안에서 ASCII 순. `.cpp` 는 자기 헤더를 최상단에. include 사이에 빈 줄을 넣지 않는다 |
| 빈 매개변수 | `func()`. `func(void)`는 쓰지 않는다 |
| 후행 반환 타입 | 미기재 허용, 필수 아님. 반환 타입이 인자에 의존할 때는 후행 표기를 쓴다 |
| 오류 처리 | `std::expected` 단일 체계. 오류 타입에 `std::string` 금지 — `dash::core::Result<T>`(`external/core-lib` `Error.hpp`)를 쓴다 |

## 2. 무엇이 기계적으로 강제되는가

**커밋 시점**(`.githooks/pre-commit`)에 도는 것은 서식 검사 셋과 Level 1 테스트다. 서식 검사가 먼저
돌아서, 걸리면 테스트 빌드를 시작하지도 않는다.

| 검사 | 대상 | 동작 |
|---|---|---|
| 줄 끝 공백, 탭 앞 공백 | 스테이지된 **모든** 파일 | 거부 |
| BOM 없는 UTF-8 | C/C++ 소스만 | 거부가 아니라 **자동 수정** |
| clang-format | C/C++ 소스만 | 거부. 파일 전체가 일치해야 한다 |
| 줄바꿈 LF | C/C++ 소스와 셸 스크립트 | git이 커밋 시 자동 변환(`.gitattributes`) |
| Level 1 테스트 | — | 거부 (#359, [[테스트-레벨]]) |

**네이밍은 어디서도 기계적으로 검사하지 않는다.** 이 페이지와 코드 리뷰로 다룬다.

> **결정**: clang-tidy 네이밍 검사는 **저장소 소스가 컨벤션에 정렬된 뒤로 보류한다**
> (이슈 [#386](https://github.com/NumeRealWorks/DashOpti_GUI/issues/386)). 어디서 돌릴지(훅, CI)의
> 문제가 아니라 **언제 시작할지**의 문제다.

정렬 전에 검사를 켜면 이름 하나를 고칠 때 호출자가 열리고, 그 파일의 기존 위반이 요구되고, 그 호출자가
또 열린다. 종료 조건이 없다. 그 연쇄를 막으려면 "이번 변경이 새로 만든 이름만" 같은 장치가 필요한데,
그 기준선을 훅이 고정할 수 없다 — 머지 대상을 모르기 때문이다. 점진 푸시는 경계를 앞으로 밀고,
squash·rebase는 경계를 `dev`로 되돌려 브랜치 전체를 다시 검사한다. 정렬이 끝나면 이 장치가 통째로
필요 없어진다.

규칙 자체는 `.clang-tidy`에 기계가독 형태로 남아 있어서 Visual Studio와 VS Code가 편집 중에 그대로
쓴다. 저장소를 정렬할 때도 이 파일이 기준이 된다.

**훅은 게이트가 아니다.** `--no-verify`로 우회된다. 훅은 실수 방지이고 강제는 CI가 할 일이지만,
현재 이 저장소에는 CI가 없다.

전수 재포맷은 하지 않는다. **커밋에 올라온 파일**에 파일 단위로 적용한다 — 기존 파일을 처음 손대는
커밋에서 그 파일 전체를 맞춘다. 서식 정리 커밋과 기능 커밋은 분리한다.

### 저장소 현황

훅을 켜기 전 상태다. 정렬 작업(#386)의 범위 산정용이며, 집계 원본은
[PR #329 코멘트](https://github.com/NumeRealWorks/DashOpti_GUI/pull/329#issuecomment-5674852495)에 있다.

| | |
|---|---|
| clang-format 위반이 있는 파일 | 340 / 349 (97%) |

## 3. 로컬 설정 (clone당 1회)

```
pip install clang-format==22.1.8
git config core.hooksPath .githooks
```

**클론만으로는 훅이 켜지지 않는다.** git이 의도적으로 그렇게 만들어 두었다 — 저장소가 자기 훅을 자동
설치할 수 있으면 `git clone`이 임의 코드 실행이 된다. 위 두 줄을 각자 한 번 실행해야 한다.
`core.hooksPath`는 `--global` 없이 그 클론의 `.git/config`에만 기록된다.

훅이 쓰는 외부 도구는 **`python`과 `clang-format` 둘뿐**이다. PATH에서 찾고, 없으면 pip의 scripts
디렉터리를 본다. **clang-tidy는 설치하지 않아도 된다** — 네이밍 검사가 보류 상태라 아무것도 그것을
부르지 않는다. IDE에서 편집 중에 네이밍 힌트를 받고 싶으면 따로 설치하면 되고, 그때 `.clang-tidy`를
규칙으로 읽는다.

훅이 커밋을 거부하면 출력된 수정 명령을 그대로 실행하고 다시 커밋한다.

정책이 지켜지는지는 `python tests/hooks/test-precommit.py`로 검증한다(실제 파일에 임시 수정을 스테이지해
17개 시나리오를 돌리고 복원. 십여 초, 인덱스가 비어 있어야 한다).

## 4. IDE에서 서식 적용

Visual Studio와 VS Code 모두 저장소 루트의 `.clang-format`을 자동으로 찾아 쓴다. 저장소에 IDE별 설정 파일은 두지 않는다.

| | Visual Studio | VS Code |
|---|---|---|
| 문서 서식 | `Ctrl+K, Ctrl+D` | `Shift+Alt+F` |
| 선택 영역 서식 | `Ctrl+K, Ctrl+F` | `Ctrl+K, Ctrl+F` |
| 전제 | 도구 > 옵션 > 텍스트 편집기 > C/C++ > 코드 스타일 > 서식 > 일반의 "ClangFormat 지원 사용"(기본 켬) | C/C++ 확장(`ms-vscode.cpptools`). 스타일 설정 기본값 `file`이 `.clang-format`을 가리킨다 |
| 저장 시 자동 서식 | 기본 없음 | 사용자 설정에서 `editor.formatOnSave`를 켜면 저장만으로 훅 통과 상태 |
| 주의 | `.clang-format`을 파일 열 때 캐시한다. 규칙 파일이 바뀌면 파일·솔루션을 다시 연다 | 확장 내장 clang-format을 쓴다. 훅과 같은 바이너리를 쓰려면 `C_Cpp.clang_format_path` |

IDE가 내장 clang-format을 쓰면 버전이 22.1.8과 달라 훅과 결과가 갈릴 수 있다. 훅이 거부하는데 IDE는
멀쩡하다고 하면 이쪽을 먼저 본다.

## 5. 작업자와 에이전트에게

1. 새로 쓰는 코드는 위 규칙을 따른다. 주변 옛 코드의 스타일을 따라가지 않는다.
2. 기존 파일을 수정하면 커밋 전에 `clang-format -i`로 그 파일 전체를 맞춘다. 수정하지 않는 파일은 건드리지 않는다.
3. 식별자 이름을 바꿀 때는 모든 호출자를 함께 고친다. 호출자 파일의 다른 기존 위반은 고치지 않는다.
4. UTF-8(BOM 없음), 줄바꿈 LF, 줄 끝 공백 없음.
