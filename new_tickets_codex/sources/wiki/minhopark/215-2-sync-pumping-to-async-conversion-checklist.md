# 동기 펌핑 → 비동기 전환 — 차이와 선행 항목 (일반론)

> 관련 Issue: [#215](https://github.com/NumeRealWorks/DashOpti_GUI/issues/215)
> 기반 문서: [[215-1-w10-f-design-decision-review-snapshot]]

> 일반론 문서다. 좌표·계수를 규범으로 싣지 않는다 — 코드 위치와 판정의 정본은 각 Issue 본문과 [[215-1-w10-f-design-decision-review-snapshot]] 이고, 여기 실린 이름은 원리를 가리키는 예시다.

## 배경 및 동기

PR [#232](https://github.com/NumeRealWorks/DashOpti_GUI/pull/232)([#208](https://github.com/NumeRealWorks/DashOpti_GUI/issues/208) · model 소비자 3종 위임) 사후 논의를 티켓 밖 일반형으로 정리한다. 출발 질문은 "무엇이 실제로 비동기가 됐나" 였고, 도착점은 **전환의 값은 응답성이 아니라 정책을 쓸 수 있게 되는 것** 이었다. `waitFor*(N) + processEvents()` 펌핑 루프를 없애는 티켓([#279](https://github.com/NumeRealWorks/DashOpti_GUI/issues/279)·[#280](https://github.com/NumeRealWorks/DashOpti_GUI/issues/280)·[#281](https://github.com/NumeRealWorks/DashOpti_GUI/issues/281)·[#282](https://github.com/NumeRealWorks/DashOpti_GUI/issues/282))이 공통으로 마주치는 판정 목록이라 한 자리에 모은다.

## 핵심 질문

1. 펌핑 루프와 비동기 전환은 응답성 말고 무엇이 다른가.
2. 전환이 성립하려면 먼저 정해야 할 정책이 무엇인가.
3. 전환이 없애지 못하는 것은 무엇인가.

## 탐색

### 1. 차이 — 요청이 스택에 쌓이는가 큐에 쌓이는가

응답성만 보면 둘 다 "GUI 가 돈다". 실제 차이는 대기 중에 도착한 요청이 어디에 쌓이는가다.

| 축 | 동기 대기 + `processEvents` 펌핑 | 비동기 완료 통지 |
|---|---|---|
| 재요청 도착 지점 | 호출 스택 — 중첩 | 이벤트 큐 — 직렬 |
| 표현 가능한 정책 | 수락(중첩) · 거부(가드). 대기는 표현 불가 | 수락 · 거부 · 대기 전부 |
| 정책의 기본값 | **전부 수락** — 이벤트를 무차별 배달 | **전부 무응답** — 구독하지 않은 결과는 오지 않음 |
| 최악의 사고 | 재진입 경로가 대기 중 함수의 수신자를 파괴 | 늦은 통지가 다른 세대의 상태를 갱신 |
| 대기 상한 | 루프에 손으로 적는다 (있음) | 없음 — 타임아웃은 별도 정책 |
| 실패 표면 | 반환값 하나로 수렴 | 갈래별 통지 — 마감 경로를 만들어야 함 |
| 취소 | 루프 조건에 심음 | 명령 + 종료 관측 정책 |
| 관측·테스트 | 스택 안에 갇혀 계측 곤란 | 상태 전이가 표면화 — 봉인 테스트 가능 |

위험의 방향이 반대다. 펌핑은 안 막은 경로가 전부 열려 있어 사고가 나고, 비동기는 안 이은 경로가 전부 죽어 있어 사고가 난다.

펌핑 루프 안에서 "대기(큐잉)" 를 구현하려 하면 요청을 보관해 두고 루프 소유자가 반환한 뒤 실행하는 형태가 되는데, 그 순간 비동기를 손으로 재구현한 것이다. 세 정책을 모두 표현할 수 있는 기제는 하나뿐이라, 정책 논의에서 두 기제는 등가가 아니다.

### 2. 재요청 정책 — 수락 / 거부 / 대기

실행 중에 같은 실행 요청이 들어올 때의 처분을 경로마다 정한다. 정하지 않으면 기제의 기본값이 정책을 대신하고, 그 기본값은 기제를 바꿀 때 함께 바뀐다 — 공유 핸들 한 개를 쓰던 시절 프레임워크가 두 번째 기동을 거부해 주던 보호는 "실행 1회 = 객체 1개" 로 바꾸는 순간 사라진다. 기제 교체가 암묵 정책을 삭제하는지 먼저 확인한다.

### 3. 배제의 키 — 객체가 아니라 자원

`m_currentJob` 류의 인스턴스 핸들은 "이 객체에서 하나" 만 뜻한다. 실제 충돌 대상은 출력 디렉터리 · 설정 JSON · 도구 실행 파일 · DLL 세션이고, 서로 다른 소비자가 같은 자원을 쓰면 각자의 핸들 가드는 서로에 대해 무효다. 자원별로 해로움의 실재를 따로 확인해야 한다 — 예컨대 여러 소비자가 같은 도구를 동시에 돌려도 되는지는 그 도구가 작업 디렉터리·출력을 어떻게 쓰는지에 달렸고, 호출하는 쪽에서는 알 수 없다. "자원과 기능을 분리한다" 의 구체적 실행은 **배제 키를 객체 신원에서 자원 ID 로 옮기는 일** 이다.

### 4. 통지의 출처 식별 — 정책의 전제

늦게 도착한 통지가 "누구의" 결과인지 식별할 수 없으면 재요청 정책 자체가 무효화된다. 세대 토큰이나 job ID 비교 없이 완료 핸들러가 현재 핸들을 무조건 비우면, 1번 실행의 완료가 2번 실행의 핸들을 지운다 — 이후 취소는 무동작이 되고 세 번째 실행이 허용된다. 이건 선택지가 아니라 전제다.

### 5. 취소 완료의 정의 — 신호 발신인가 자원 반납인가

취소 요청이 곧 정지 보장은 아니다. kill 은 신호만 쏘고, 상태 기계가 그 자리에서 terminal 로 잠기면 "취소 완료" 와 "자원 반납 완료" 가 분리된다. 다음 실행의 가드는 이미 풀렸는데 파일은 아직 잡혀 있는 창이 생기므로, 취소의 완료 정의를 둘 중 무엇으로 둘지 정하고 후자라면 종료를 관측할 주체를 지정한다.

### 6. 실패·지연 통지의 마감 경로

비동기에서는 성공 · 실패 · 취소 · 기동 실패 · 타임아웃이 서로 다른 경로로 도착한다. 마감을 선언하는 지점이 한 곳이 아니면 소비자마다 갈래별 번역이 중복되고, 기제가 특정 갈래의 통지를 아예 생략하는 경우(기동 실패에 완료 통지가 없는 등)에는 그 갈래가 조용히 사라진다. 실행 엔진이 모든 갈래를 하나의 종결 통지로 번역하고, 최초 종결이 이기는 잠금(terminal lock)으로 취소 뒤 도착하는 늦은 완료를 삼키게 한다.

### 7. 상태의 writer 단일화

프로세스 상태와 외부 도구가 쓰는 상태 파일이 함께 있으면 진실의 출처가 둘이 된다. 상태 기계 쪽에는 종결 잠금이 있어도 파일 쪽에는 없어서, 도구의 늦은 쓰기가 GUI 의 판정을 되돌릴 수 있다. 상태 항목마다 writer 를 하나로 정하고, 늦은 쓰기의 우선순위(마지막 쓰기 승리 vs 종결 고정)를 명시한다. 버튼 활성화 같은 UI 잠금을 상태 파일 폴링에 묶으면 프로세스 상태와 어긋난 창이 그만큼 열린다.

### 8. 프로세스 밖 생존과 재시작 조정

외부 프로세스는 호출한 GUI 보다 오래 산다. 앱이 죽거나 프로젝트를 닫아도 도구는 계속 돌고, 다음 기동 때 상태 파일은 "진행 중" 인데 대응하는 실행 객체는 없다. 그 고아 상태를 어떻게 해석할지(신뢰 · 무효화 · PID 확인) 정하지 않으면 재요청 정책이 첫 화면부터 잘못된 전제로 시작한다.

### 9. 동시성 개방 범위와 자원·기능 분리

"어디까지 동시에 열 것인가" 를 먼저 정하고, 그 범위가 성립하도록 자원과 기능을 쪼갠다. 순서가 뒤집히면 열어 놓고 나서 충돌을 막느라 가드를 덧붙이게 된다. 모범은 자원 하나에 소유자 하나를 붙이고 모든 접근이 그 소유자를 통과하게 하는 형태다 — 스레드 감금(thread confinement)이 그 구현 중 하나이며, 이때 소유자를 leaf 로 유지하는 규칙이 함께 필요하다(12번 항목).

### 10. 큐를 두면 따라오는 정책 4종

"대기" 를 선택하면 네 가지가 새로 생긴다 — ⑴ 큐 깊이 상한 ⑵ 같은 대상 중복 요청의 합치기(coalescing) ⑶ 대기 중 항목의 취소(큐에서 제거 vs 실행 후 취소) ⑷ 순서 보장(FIFO vs 우선순위). "거부" 만 구현하면 이 넷을 피할 수 있고, 그게 대개의 초기 선택이다. 피했다는 사실을 기록해 두지 않으면 나중에 큐를 넣을 때 네 항목이 미결로 드러난다.

### 11. 결정의 UI 관측 가능성

거부가 로그 한 줄이면 사용자에게는 정책이 아니라 무반응으로 보인다. 수락 · 거부 · 대기 세 결정이 화면에서 서로 다르게 보이지 않으면 정책의 존재가 전달되지 않는다. 진행 표시와 버튼 상태의 근거를 상태 파일 폴링이 아니라 실행 상태에 두면 7번 항목과 함께 해소된다.

### 12. 교착 방지 규율

동시성을 열면 교착이 새 위험으로 들어온다. 호출자를 멈추는 마샬링(blocking invoke)으로 자원 소유자를 감금하는 설계는 **소유자가 호출자 쪽 코드를 절대 역호출하지 않는다** 는 규칙에 의존한다. 그 규칙을 문서에 남기지 않으면 나중에 추가되는 콜백 하나가 교착을 만든다. 이 계급은 `waitFor*` 문자열 검색으로 잡히지 않으므로 검사 목록에 형태를 따로 등재해야 한다.

### 13. 전환이 없애지 못하는 것 3종

| 항목 | 내용 |
|---|---|
| 스레드 오프로딩 | 완료 통지 구독은 같은 스레드의 이벤트 루프 위에서 결과를 늦게 받는 것뿐이다. CPU 를 먹는 in-process 작업은 그대로 호출 스레드를 막는다 |
| 블로킹의 이동 | 걷어낸 대기가 RAII 소멸자의 암묵 대기 · blocking 마샬링 · 스레드 join 으로 되살아난다. 계수만 줄고 계급은 남으므로, 검사 대상을 호출 패턴이 아니라 계급으로 정의해야 한다 |
| 외부 부작용 | 취소해도 이미 쓴 파일 · 이미 보낸 요청은 되돌아오지 않는다. 재실행이 같은 자원을 다시 쓴다면 앞선 실행의 잔여물 처리가 별도 정책이다 |

### 14. 선행 순서

```
[Step 1] 자원 목록과 소유자 확정
   │   1. 실행이 만지는 자원 열거 (출력 경로 · 설정 파일 · 도구 · 세션 · 장치)
   │   2. 자원별 소유자 1명 지정
   │   ※ 이 목록이 없으면 이후 모든 판정이 객체 단위로 굳는다
   ▼

[Step 2] 배제 키 결정
   │   1. 키를 자원 ID 로 (객체 신원 금지)
   │   2. 자원별 동시 실행의 해로움 실재 확인 — 미검증은 미검증으로 표기
   ▼

[Step 3] 정책 3종 결정
   │   1. 재요청 — 수락 / 거부 / 대기 (경로별)
   │   2. 취소 완료의 정의 — 신호 발신 / 자원 반납 관측
   │   3. 상태 writer 와 늦은 쓰기 우선순위
   ▼

[Step 4] 기제 구현
   │   1. 통지에 세대 토큰 — 4번 항목은 전제
   │   2. 모든 갈래를 단일 종결로 번역 + terminal lock
   │   3. 큐를 둔다면 10번 항목 4종 동시 결정
   ▼

[Step 5] 표면과 문서
   │   1. 세 결정을 UI 에서 구별 가능하게
   │   2. 재시작 시 고아 상태 해석 규칙
   │   3. 교착 방지 규칙과 검사 절차를 문서에 등재
   ▼

[검증] 상태 전이 봉인 테스트
       기동 실패 · 취소 · 늦은 통지 · 재요청 거부를 각각 고정한다
```

## 종합 정리

| 꼭지 | 정하지 않으면 | 최소 산출물 |
|---|---|---|
| 재요청 정책 | 기제의 기본값이 정책을 대신하고, 기제 교체와 함께 사라짐 | 경로별 처분 표 |
| 배제 키 | 같은 자원을 쓰는 다른 소비자에 무방비 | 자원 → 키 매핑 |
| 통지 출처 식별 | 앞선 실행의 완료가 뒤 실행의 핸들을 지움 | 세대 토큰 비교 |
| 취소 완료 정의 | 가드는 풀렸는데 자원은 안 놓인 창 | 완료 판정 기준 1줄 |
| 마감 경로 | 특정 실패 갈래가 조용히 사라짐 | 단일 종결 + terminal lock |
| 상태 writer | 늦은 쓰기가 판정을 되돌림 | 항목별 writer 지정 |
| 재시작 조정 | 첫 화면부터 잘못된 전제 | 고아 상태 해석 규칙 |
| 개방 범위·자원 분리 | 열고 나서 가드를 덧붙임 | 자원 1개 = 소유자 1명 |
| 큐 4정책 | 큐 도입 시 4항목 미결 노출 | 미도입 사실의 기록 |
| UI 관측 가능성 | 정책이 무반응으로 보임 | 결정 3종의 화면 구분 |
| 교착 방지 | 콜백 추가 1건이 교착 | leaf 규칙 + 검사 절차 |

## Q&A

본문 서술에 대한 질의응답. 본문을 고치지 않고 이해 지점만 보충한다.

### Q1. 펌핑 중 스택이 중첩되면 두 요청이 동시 처리되는 것이고, 자원·공유 객체·전역 값이 충돌하면 죽을 수 있나 (1절)

동시 실행은 아니다. 스레드가 하나이므로 두 요청이 같은 순간에 도는 게 아니고, **첫 요청이 펌핑 지점에 멈춘 채로 두 번째 요청이 그 위에서 끝까지 도는** 중첩 실행이다. 그래서 사고 형태도 데이터 레이스가 아니다 — 재개한 첫 요청이 펌핑 전에 읽어 둔 전제(포인터·인덱스·파일 상태)가 이미 바뀐 것을 모르는 것이고, 최악은 두 번째 요청이 첫 요청의 수신자를 파괴해 반환 지점이 죽은 객체가 되는 것이다. 같은 스레드라 뮤텍스로 막을 수 없고(재진입은 락을 통과하거나 자기 자신과 교착한다), 공유 자원이 하나도 없어도 수명만으로 죽을 수 있다.

### Q2. 취소를 루프 조건에 싣는 것과 명령 + 종료 관측의 차이 (1절 · 5절)

| 축 | 루프 조건 | 명령 + 종료 관측 |
|---|---|---|
| 취소 관측 시점 | 다음 반복 — 지연 = 반복 주기 | 즉시 접수 |
| 취소 가능 구간 | 루프가 도는 동안만 | 실행 상태인 동안 전부 |
| "취소됨" 의 의미 | 루프 탈출 = 끝 | 접수와 종료가 별개 |
| 처리 위치 | 루프 소유자 안 — 경로마다 재작성 | 실행 객체의 명령 — 경로 공통 |

루프 조건은 취소를 "탈출" 로 처리해 kill 이후의 창을 숨기고, 명령 + 관측은 그 창을 드러내 5절 정책을 쓸 수 있게 한다.

### Q3. 3절의 서술은 `DashRwActor`·`DashRwClient` 가 id 로 세션에 접근하게 한 것에 대응하는가

절반 대응한다. **식별·소유는 자원 단위로 옮겼다** — actor 가 session id → module 로 들고, `DashRwClient` 는 그 id 를 가리키는 값 핸들이며 마지막 사본의 소멸이 세션을 닫는다(RAII). "객체 하나에 하나" 가 아니라 "자원마다 하나" 다.

**배제는 자원 단위가 아니다.** 모든 연산이 actor 스레드 1개를 통과하므로 서로 무관한 두 세션도 직렬화된다. 격리는 달성했고 병목 분리는 아직이라는 것이 [[215-1-w10-f-design-decision-review-snapshot]] 사실 10("격리가 병목을 없앤 게 아니라 옮겼다")이다.

### Q4. terminal lock 은 취소·실패 뒤 도착한 완료 통지를 수신자가 무시할 수 있게 하라는 뜻인가 (6절)

그렇고, 필요한 것이 둘이다 — 종결 통지 1회 보장(중복 방출 금지)과 종결 후 도착분의 폐기. 상태 전이 지점 한 곳에서 "이미 종결이면 전이 자체를 무시" 하면 통지도 나가지 않아 둘이 함께 해소된다(`controller/async/Job.h` `setState`). 수신자마다 "이미 끝났나" 를 검사하게 하면 소비자 수만큼 빠뜨릴 자리가 생긴다. 4절과 짝이다 — terminal lock 은 **같은 실행**의 늦은 통지를, 세대 토큰은 **다른 실행**의 통지를 막는다.

### Q5. 프로세스 상태와 상태 파일이 함께 있는 예시 / writer 일원화의 목적 / 파일이 필요한 경우 (7절)

예시는 `DashModelBuilder` 의 학습 status 다. writer 가 둘이다 — 도구가 진행·완료를 config JSON 에 쓰고, GUI 도 시작 시 `"In Progress"`(`model/DashModelBuilder.cpp:645`)와 실패 마감 시 `"Failed"`(`:1445` 조건부)를 쓴다. 읽기는 1초 폴링(`:31`)이다.

**일원화의 목적은 최종 값 결정이 아니라 순서 판정을 없애는 것이다.** writer 가 둘이면 쓸 때마다 "파일의 현재 값이 내 판정보다 새 것인가" 를 물어야 하는데 답할 근거가 없다. 지연 확인(+500ms·+1500ms) 후 조건부 덮어쓰기 같은 장치가 붙는 이유가 그것이다.

상태를 소유·표현하는 객체만 참고하는 편이 낫다는 지적은 프로세스 안에서는 맞다. 파일을 요구하는 조건은 **프로세스 경계가 아니라 시간적 분리**다 — 경계는 파이프(stdio)로 넘을 수 있으므로, 파일이 필요한 것은 라이터와 리더의 생존 구간이 겹치지 않거나 리더가 여럿·미지일 때다.

| 축 | stdio · 이벤트 | 파일 |
|---|---|---|
| 수명 | 연결에 묶임 — 라이터가 죽으면 내용도 사라진다 | 양쪽 프로세스와 무관하게 존속 |
| 생존 구간 | 라이터·리더가 동시에 살아 있어야 한다 | 겹치지 않아도 된다 |
| 리더 수 | 사실상 1 — 파이프를 잡은 쪽 | N — 미지의 도구 · 사후 분석 · 사용자 |
| 표현 | 스트림 — 현재 상태를 알려면 처음부터 재생 | 스냅샷 — 그 자리에서 현재 값 |
| 전달 | 푸시 — 지연 0 | 폴링 또는 파일시스템 감시(네트워크 드라이브에서 불안정) |
| 고유 위험 | 백프레셔 — 리더가 안 읽으면 라이터가 멈춘다 | 찢어진 읽기 — temp + rename 규율이 필요하다 |
| writer 신원 | 연결이 보장한다 | 보장 없음 — 아무나 쓸 수 있다 |

마지막 축이 4절과 이어진다. 파일은 누가 썼는지를 프로토콜이 보장하지 않으므로 writer 규율을 사람이 지켜야 한다.

배치는 둘로 갈린다 — **실시간 통지**(라이터·리더 공존 · 리더 1)는 stdio·이벤트, **시간 분리 · 다중 리더 · 재시작 후 필요**는 파일이다. 다만 8절이 파일 쪽에 한 표를 더 준다: stdio 는 수명이 관계에 묶여 있어서 GUI 가 죽으면 진행 정보가 통째로 사라지고, 재시작 조정을 하려면 남은 기록이 있어야 한다.

두 통로가 다 열려 있으면 같은 사실을 두 번 보내지 않는 것이 규칙이다. 권장 형태는 실시간 status 를 stdout 계약으로 올리고, GUI 가 그것으로 자기 상태 객체를 갱신하고, 영속이 필요한 부분만 GUI 가 자기 파일에 쓰는 것 — writer 가 1명이 되고 폴링이 사라진다. `DashModelBuilder` 의 경우 도구가 이미 `[GUI]` 접두 라인을 stdout 으로 내보내므로 통로는 있으나, status 를 그 통로로 옮기는 것은 도구 쪽 변경이라 이 저장소 밖이다.

### Q6. 취소 시점에 외부 프로세스를 무조건 kill 할 수 없나 — kill 이후 완전 종료까지의 시간 처리 정책인가 (5절 · 8절)

kill 은 이미 무조건 한다. `ProcessJob::cancel` 이 `killProcessTree`(Windows `taskkill /F /T`)로 트리째 죽이고, 명령을 못 띄우면 `QProcess::kill` 로 부트로더만이라도 죽인다. 정책이 필요한 건 그 다음 창이다 — ⑴ kill 발사부터 실제 사망까지 파일 핸들·잠금이 남는 구간 ⑵ 그 구간에 새 실행을 허용할지 ⑶ 사망을 관측할 주체(현재는 없다 — QProcess 를 부모에서 떼어 자기 종료를 자기가 회수한다) ⑷ 반쯤 쓰인 산출물의 처리.

8절은 다른 상황이다 — GUI 가 죽으면 kill 을 발사할 주체 자체가 사라져 도구가 살아남는 경우다.

### Q7. leaf 유지 = 중앙 관리 객체가 자원에 직접 접근하지 않고 자원 소유 객체를 따로 두라는 것인가 (9절)

그렇다. 더해서 **방향 제약**이 핵심이다 — 소유자는 자기 아래(자원 · Qt · 순수 라이브러리)만 보고 위(GUI · 매니저 · 렌더링)를 절대 호출하지 않는다. 호출자를 멈추는 마샬링을 쓰면 이 규칙이 교착 방지의 유일한 근거가 된다: GUI 가 소유자의 결과를 기다리는 동안 소유자가 GUI 를 호출하면 서로를 기다린다. `controller/DashRwActor.h` 의 LEAF RULE 주석이 그 선언이다.

### Q8. 큐 깊이 상한은 몇 개까지·얼마나 오래 받아줄지인가 (10절)

둘 다 정책이지만 별 항목이다. **깊이**는 몇 개까지 보관할지와 초과 시 처분(가장 오래된 것 폐기 / 새 요청 거절)이고, **유효 시간**은 대기 항목이 언제 만료되는지와 만료를 조용히 버릴지 실패로 알릴지다. 합치기(같은 대상 3번 예약 → 1번)를 먼저 결정하면 깊이 문제가 대개 사라지므로 순서상 합치기가 앞이다.

### Q9. 요청 처리 상태(수락·거부·대기)를 소유·관리하는 객체를 두라는 것인가 (11절)

방향은 같고 절이 다르다. 상태의 소유는 7절 몫이고, 11절은 **그 소유 상태를 근거로 화면을 그리라**는 요구다. 실제 어긋남은 표면이 상태 소유자가 아니라 폴링 결과를 볼 때 생긴다 — 버튼 활성화가 실행 상태가 아니라 파일 status 를 근거로 하면 프로세스가 끝난 뒤 폴링 주기만큼 오해의 창이 열린다.

### Q10. blocking invoke 가 무엇인가 / 프로젝트 예시 / 경로 단일화와 가드·게이트의 대비와 같은 이야기인가 (12절)

다른 스레드에 일을 넘기고 결과가 올 때까지 호출 스레드를 멈추는 호출이다. 예시는 `invokeOnActor`(`controller/DashRwActor.h`) — `QMetaObject::invokeMethod(..., Qt::BlockingQueuedConnection)` 으로 RW 스레드에 작업을 넘기고 결과를 받는다. 호출자가 GUI 면 그 RW 연산 1건 동안 GUI 가 멈춘다(이미 RW 스레드에 있는 호출자는 직접 호출로 우회).

대비는 유사하지만 층이 다르다. 경로 단일화는 배제를 **구조**로 해결하고 가드·게이트는 **규약**으로 해결한다 — 후자는 모든 호출자가 지켜야 하므로 새 호출자 하나의 누락이 곧 무효다. 대신 단일화의 대가가 둘이다: 전역 직렬화(무관한 자원끼리 줄을 선다)와 blocking 마샬링(대기가 남는다). 위험이 사라지는 게 아니라 "규약 누락" 이 "교착 + 병목" 으로 교환되고, 교착 쪽 근거가 leaf 규칙이다.

### Q11. 스레드 오프로딩이 무엇인가 / 완료까지의 대기 시간은 동기·비동기가 같은가 (13절)

오프로딩은 계산을 호출 스레드에서 워커 스레드로 옮기는 것이다. 총 소요 시간은 동기·비동기가 같다 — 작업 자체가 빨라지지 않고, 다른 것은 그 시간 동안 호출 스레드가 무엇을 할 수 있는가뿐이다. 외부 프로세스 실행은 계산이 애초에 다른 프로세스에 있으니 통지만 늦게 받으면 GUI 가 자유롭지만, in-process 계산은 완료 통지로 감싸도 계산이 GUI 스레드에서 돌면 그대로 멈춘다. 그 경우에만 오프로딩이 답이고, 이것이 "비동기 전환" 과 "워커화" 가 별 작업인 이유다.

### Q12. RAII 소멸자의 암묵 대기 / blocking 마샬링 / 스레드 join / 계수와 계급 (13절)

- **RAII 소멸자의 암묵 대기** — 소멸자가 정리를 위해 안에서 기다리는 것. `~QProcess` 는 프로세스가 아직 Running 이면 경고 후 `waitForFinished`(기본 30초)를 부른다. 호출부에는 대기 코드가 한 줄도 없는데 객체를 지우는 순간 대기가 생긴다. `ProcessJob::cancel` 이 QProcess 를 부모에서 떼어내는 이유가 이것이다.
- **blocking 마샬링** — Q10 의 그것. 경쟁 대기가 아니라 **위임 대기**다(자원을 다투는 게 아니라 남에게 맡기고 결과를 기다린다). 다만 그 소유자에 요청이 몰리면 줄을 서게 되므로 경쟁 대기도 함께 생긴다.
- **스레드 join** — 스레드가 끝날 때까지 기다려 회수하는 것. Qt 는 `QThread::wait()` 이고, `DashRwActor` 의 Holder 소멸자가 `thread.quit(); thread.wait();` 를 하므로 종료 시 GUI 스레드가 RW 스레드의 마지막 작업이 끝날 때까지 멈춘다. 상한이 없다.
- **계수와 계급** — 계급은 검사 대상의 종류("호출 스레드를 멈추는 대기"), 계수는 그 종류로 센 히트 수다. `waitFor*` 문자열로 세면 위 세 형태 중 첫째만 잡히므로, 대기를 소멸자·마샬링·join 으로 옮기면 **계수는 줄고 계급은 그대로 남는다**. [#279](https://github.com/NumeRealWorks/DashOpti_GUI/issues/279)가 대기 축을 세 형태로 등재한 것이 이 대응이다.

### Q13. 고아가 왜 생기나 — GUI 가 죽기 전에 다 정리하고 죽어야 하는 것이 아닌가 (8절)

정상 종료 경로의 정리는 필요하고, 이 저장소에는 이미 있다 — `main.cpp:41` 이 `aboutToQuit` 에 `ProcessJob::cancelAllRunning()` 을 걸고, 그 함수가 `runningJobs()` 를 순회하며 전부 kill 한다(종료 중 소비자가 도메인 실패로 번역해 모달을 띄우지 않도록 `blockSignals(true)` 선행).

고아는 **그 훅이 돌지 않는 종료 경로**에서 생기고, 그 경로는 없앨 수 없다. 프로세스 A 가 프로세스 B 의 수명을 보장하려면 A 의 코드가 실행돼야 하는데, A 가 죽는 방식 중 코드가 안 도는 방식이 존재한다(크래시 · 강제 종료 · 전원 차단). 정리 자체에도 시간이 걸려 kill 발사와 사망 사이에는 항상 창이 있다. 따라서 정리 코드는 원리상 최선 노력이고, **"정리하고 죽는다" 는 정상 경로의 의무 · "고아를 해석한다" 는 비정상 경로의 대비**로 둘 다 필요하다 — 택일이 아니다.

### Q14. 크래시·강제 종료·OS 종료에서는 GUI 도 죽으니 자식이 죽든 살든 상관없지 않나 — 재시작 얘기인가 (8절)

경로에 따라 다르다. 프로세스 고아와 상태 고아를 나눠야 한다.

| 종료 경로 | 프로세스 고아 | 상태 고아(파일) |
|---|---|---|
| 크래시 | 남는다 — GUI 만 죽고 자식은 계속 돈다 | 남는다 |
| 작업 관리자로 GUI 만 강제 종료 | 남는다 | 남는다 |
| OS 종료·재부팅 | 안 남는다 — OS 가 전부 죽인다 | 남는다 |
| 전원 차단 | 안 남는다 | 남는다 (+ 반쯤 쓰인 산출물) |

"상관없다" 가 성립하는 것은 OS 가 함께 다 죽이는 두 경로뿐이고, 그 경로에서도 상태 고아는 남는다. 문제가 되는 것은 크래시와 GUI 단독 강제 종료이며, **크래시는 사용자가 곧바로 앱을 다시 켤 확률이 가장 높은 경로**다.

피해는 셋이고 첫째는 재시작과 무관하다.

- **계속 먹는다** — CPU/GPU · 메모리 · 라이선스 토큰 · 파일 잠금 · 디스크. 사용자는 앱을 닫았으니 끝났다고 보는데 계산은 돈다. 중지 수단도 함께 사라졌다(kill 발사 주체가 GUI 였다).
- **새 실행과 자원을 다툰다** — 고아가 계속 쓰는 출력 디렉터리에 재시작 후 새 실행이 들어간다. 프로세스 안의 핸들 가드로는 원리적으로 막을 수 없다(가드를 들고 있던 프로세스가 죽었다). 3절의 배제를 프로세스 밖(락 파일 · PID 파일 · OS 잠금)으로 내보내야 하는 사실상 유일한 경우다.
- **거짓 표시 + 무방비 재실행** — 재시작 시 테이블은 `"In Progress"` 인데 Start 는 눌린다. `DashModelBuilderWidget` 의 `startButton` 은 생성 시 활성(`:304`)이고 클릭 핸들러에서만 비활성(`:821`)이며 상태 폴링은 재활성만 한다(`:1187`) — 즉 피해는 버튼 잠김이 아니다. 그 표시를 마감하는 코드는 이 세션의 job 이 끝날 때만 도므로 죽은 세대의 표시가 다음 학습이 덮을 때까지 남는다.

### Q15. 상태 고아는 파일에 상태를 남기기 때문 아닌가 — 파일은 작업 기록의 보전이고 상태는 GUI·자식 내부에 있어야 하지 않나 (7절 · Q5)

구분은 맞다. 다만 파일에서 status 를 빼도 상태 고아는 사라지지 않고 **형태만 바뀐다** — 남는 것이 반쯤 쓰인 산출물이 되고, 그건 문자열보다 해석이 어렵다("이 산출물은 완성인가 쓰다 만 것인가" 를 판단할 근거가 없다). status 문자열은 적어도 "이 실행은 끝났다고 선언되지 않았다" 는 정보를 준다.

규칙은 "파일에 상태를 두지 마라" 가 아니라 **파일에는 상태(state)가 아니라 사실(event)을 append 하라** 다.

| | 파일에 담기는 것 | 시간이 지나면 |
|---|---|---|
| 상태 | `status: "In Progress"` | 거짓이 된다 — 프로세스는 죽었는데 문자열은 남는다 |
| 기록 | `started: T · pid · args` / `finished: T · exit` | 거짓이 되지 않는다 |

기록 형태로 두면 "started 는 있고 finished 는 없다 = 미완 실행" 이라는 판정이 파일에서 파생된다. 현재 상태는 GUI·자식 내부에만 두고, 재기동 시 기록 + 생존 확인으로 상태를 재구성한다 — 상태를 파일에 두지 않으면서 고아를 해석할 수 있는 유일한 조합이다.

### Q16. 크래시·강제 종료로 자식이 남아 돌 때 재시작 시 처리 방법이 있나 (8절)

있다. 탐지 근거를 시작 시점에 남겨 두는 것이 선행이다.

```
[탐지] 시작 시점에 신원을 기록한다
   │   1. PID · 프로세스 생성 시각 · 이미지 경로 (PID 단독은 재사용 위험)
   │   2. 더 견고한 대안 — 이름 있는 Job Object 를 만들고 그 이름을 기록
   │   ※ 현재 코드는 PID 를 메모리에만 쓴다(kill 발사용) — 디스크 기록 0
   ▼

[판정] 재기동 시 생존 확인
   │   1. OpenProcess + GetExitCodeProcess, 또는 OpenJobObject 로 이름 존재 확인
   │   2. 우리가 띄운 그 프로세스인지 생성 시각·이미지 경로로 대조
   │   ※ 기록 가능한 PID 는 부트로더 PID 라(`controller/async/ProcessKill.h`) 트리를 대표하지 못한다
   ▼

[처분] 셋 중 하나
   │   1. 죽인다 — killProcessTree 재사용
   │   2. 재접속한다 — 부분적으로만 가능
   │   3. 사용자에게 묻는다 — "이전 실행이 아직 돌고 있습니다: 계속 / 중지"
   ▼

[정리] 미완 산출물은 어느 처분에서도 남는다
       미완 디렉터리를 새 실행이 재사용하지 않거나 시작 시 청소한다
```

**재접속에는 원리적 한계가 있다.** stdout 파이프는 부모와 함께 닫혔으므로 진행 로그는 영구히 잃고, 남는 관측 수단은 생존 여부와 파일 산출물뿐이다. 재접속은 "완료 감시" 수준까지만 된다 — 진짜 재접속을 원하면 도구가 진행을 stdout 이 아니라 파일이나 소켓으로 보고해야 한다. Q5 의 결론이 여기서 뒤집힌다: **통로 선택이 재접속 가능성을 결정한다.**

사후 처리보다 예방이 싸다. 자식을 이름 있는 Job Object 에 넣고 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 를 걸면 GUI 가 크래시로 죽든 강제 종료되든 커널이 자식 트리를 죽이므로 탐지·판정·처분 3단계가 사라지고 산출물 정리만 남는다(POSIX 대응은 `prctl(PR_SET_PDEATHSIG)` 또는 프로세스 그룹 + SIGHUP). 대가는 정책 확정이다 — "GUI 를 닫으면 진행 중인 실행이 죽는다" 가 고정되고 백그라운드 실행을 남기는 선택지가 사라진다. 전원 차단이 남기는 산출물 고아는 예방으로 덮이지 않으므로 append-only 기록은 어느 선택에서도 필요하다.
