## 0. 이 문서가 답하는 질문

1. 이벤트 기반 / Job 기반 / 코루틴 기반 / 스레드 기반은 **어떻게 다른가?** — 결론부터: 넷은 대등한 경쟁자가 아니라 **서로 다른 층위**의 개념이다(2절).
2. **Qt 시그널**은 무엇인가? (3절)
3. **콜백**은 어떤 경우에 발생하는가? (4절)
4. **Job 상태머신**은 무엇인가? (6절)

## 1. 문제의 본질 — "기다림"을 어디에 두는가

오래 걸리는 작업 자체는 죄가 없다. 문제는 **완료를 기다리는 동안 호출한 스레드가 무엇을 하는가**다.

GUI 앱에는 특수한 제약이 있다: 메인(GUI) 스레드는 **이벤트 루프**를 계속 돌려야 화면이 살아 있다. 이벤트 루프란 대략 이런 무한 반복이다:

```cpp
// QApplication::exec()의 개념적 골격
while (!quit) {
    Event e = eventQueue.takeNext();   // 마우스 클릭, 키 입력, 타이머,
    dispatch(e);                       // 화면 다시 그리기, 큐된 시그널...
}
```

마우스 클릭도, 화면 갱신도, 타이머도, (뒤에서 볼) 큐된 시그널 배달도 전부 이 루프가 처리하는 "이벤트"다. 어떤 슬롯/함수가 오래 걸리면 루프가 다음 이벤트를 못 꺼내니 화면이 얼어붙는다 — Windows가 띄우는 "응답 없음"의 정체다.

식당 비유로 이 문서 전체를 관통하겠다. 나(메인스레드)는 음식(작업 결과)을 주문했다:

| 방식 | 식당에서 | 코드에서 |
|---|---|---|
| **동기 블로킹** | 카운터 앞에 서서 나올 때까지 기다림 — 아무것도 못 함 | `waitForFinished()` — UI 프리즈 |
| **폴링** | 30초마다 카운터에 가서 "나왔어요?" 물어봄 | `while(!done) { msleep(100); processEvents(); }` — 프리즈를 가린 척 |
| **콜백** | "나오면 제 테이블로 갖다주세요" — 직원이 **언제, 어느 방향에서** 올지 모름 | C API 완료 콜백 — 실행 스레드 문맥 불명(4절) |
| **이벤트(시그널)** | **진동벨** — 울리면 내가 편한 타이밍에 받으러 감 | 시그널 → 이벤트 큐 → 내 이벤트 루프가 배달(3절) |
| **스레드** | 일행에게 "네가 기다렸다 받아 와" — 나는 다른 일을 함. 단 일행과 지갑을 같이 쓰면 사고 남 | 워커 스레드 — 공유 상태 레이스 주의(5절) |
| **Job** | 주문번호가 찍힌 **영수증** — 상태 조회·취소가 가능한 손잡이 | Job 객체 = 작업의 1급 시민화(6절) |
| **코루틴** | 주문하고 하던 일을 계속하다, 벨 울리면 **하던 문장 그 지점부터** 이어감 | `co_await` — 콜백 체인을 순차 코드 표기로(7절) |

## 2. 네 가지 "기반"은 층위가 다르다

"이벤트 기반 vs 스레드 기반 vs Job 기반 vs 코루틴 기반"을 한 줄에 놓고 고르려 하면 혼란스러운데, 넷이 **답하는 질문 자체가 다르기** 때문이다:

| 개념 | 답하는 질문 | 한 줄 정의 |
|---|---|---|
| **스레드 기반** | 일을 **어디서** 실행하나 | 오래 걸리는 일을 다른 실행 흐름(스레드)으로 옮긴다 — 기다림 자체를 이전 |
| **이벤트 기반** | 완료를 **어떻게** 통지받나 | 기다리지 않고 "끝나면 알려줘"를 등록한 뒤 즉시 반환 — 통지는 이벤트 루프가 배달 |
| **Job 기반** | 작업을 **어떻게 관리**하나 | 작업을 객체로 승격해 상태·진행·취소를 표준화 — 이벤트 기반 위의 **조직화 계층** |
| **코루틴 기반** | 코드를 **어떻게 표기**하나 | 콜백/시그널 연쇄를 순차 코드처럼 쓰게 하는 **문법 계층** — 통지 원천은 여전히 이벤트 |

```
[층위 1 — 실행 위치] 일을 어디서 하나
   │   1. 메인스레드 (그 자리에서)
   │   2. 워커 스레드 (in-process 다른 흐름)
   │   3. 외부 프로세스 (OS가 병렬성 제공 — exe 실행이 이것)
   ▼

[층위 2 — 통지 방식] 완료·진행을 어떻게 되돌려 받나
   │   1. 블로킹 대기 / 폴링 (통지 없음 — 안티패턴)
   │   2. 콜백 (함수 포인터 — 원시적)
   │   3. 시그널/이벤트 (이벤트 루프가 배달 — Qt 네이티브)
   ▼

[층위 3 — 조직화] 진행 중인 작업을 어떻게 다루나
   │   1. 흩어진 bool 플래그 (현행 — m_waitingFinished 등)
   │   2. Job 객체 + 상태머신 (표준 표면)
   ▼

[층위 4 — 표기법] 여러 단계의 연쇄를 어떻게 쓰나
       1. 콜백/슬롯 체인 (단계마다 함수 분리)
       2. 코루틴 co_await (한 함수 안의 순차 표기)
```

그래서 조합이 가능하다 — DashGUI2의 채택안([[194-1-async-execution-patterns]])은 "외부 프로세스(층위 1-3) + 시그널(층위 2-3) + Job(층위 3-2) + 슬롯 체인(층위 4-1, 코루틴은 보류)"이다. "이벤트 기반이냐 스레드 기반이냐"는 배타 선택이 아니라, **층위 1에서 스레드를 쓰더라도 층위 2는 시그널**로 두는 식으로 섞는 것이 정석이다.

## 3. 이벤트 기반과 Qt 시그널

### 3-1. 이벤트 기반이란

"등록 → 즉시 반환 → 나중에 통지"의 3박자다. 핵심은 **호출자가 기다리지 않는다**는 것 — 진동벨을 받아 들고 자리로 돌아가면, 벨(통지)은 주방(작업)이 아니라 내 손(내 이벤트 루프)에서 울린다.

### 3-2. Qt 시그널/슬롯이란

관찰자(Observer) 패턴의 Qt 구현이다. 어떤 객체가 "사건이 일어났다"고 **방송**(emit)하면, 미리 **구독**(connect)해 둔 함수(슬롯)들이 호출된다.

```cpp
QProcess* proc = new QProcess(this);
connect(proc, &QProcess::finished,          // "끝나면" (시그널 구독)
        this, &MyClass::onSolverFinished);  // "이 함수를 불러줘" (슬롯)
proc->start(exePath, args);                 // 즉시 반환 — 여기서 안 기다림
// ... 메인스레드는 이벤트 루프로 복귀, 화면 정상 동작 ...

void MyClass::onSolverFinished(int exitCode, QProcess::ExitStatus st) {
    // 프로세스가 끝난 뒤, "메인스레드의 이벤트 루프가" 이 슬롯을 호출
}
```

시그널의 정체는 **연결 타입(connection type)**에 따라 갈린다 — 이 구분이 실무의 절반이다:

| 연결 타입 | 슬롯 실행 시점 | 실행 스레드 | 자동으로 선택되는 경우 |
|---|---|---|---|
| `DirectConnection` | emit 지점에서 **즉시** (동기 함수 호출) | **emit한** 스레드 | sender·receiver가 같은 스레드 |
| `QueuedConnection` | 이벤트로 포장해 큐에 넣고 이벤트 루프가 **나중에** 실행 | **수신자(receiver)의** 스레드 | sender·receiver가 다른 스레드 |
| `AutoConnection` (명시 안 하면 이것) | emit **시점에** 판정 → 같은 스레드면 Direct, 다르면 Queued | 위 판정 결과 따름 | connect 5번째 인자 생략 시 |

(그 외 `BlockingQueuedConnection` = Queued처럼 큐에 넣되 emit한 쪽이 슬롯 완료까지 블록 — 수동 지정, 같은 스레드에 걸면 데드락이라 드물게만 사용.)

**연결을 만드는 법** — `connect`에 [보내는 객체 · 시그널 · 받는 객체 · 슬롯 · (옵션)타입] 을 준다:

```cpp
// 멤버 함수 슬롯 (5번째 생략 = AutoConnection)
connect(sender, &Sender::valueChanged, receiver, &Receiver::onChanged);
// 람다 슬롯 (+ context 객체 — 그 객체가 소멸하면 연결 자동 해제)
connect(sender, &Sender::done, receiver, [receiver](int code){ /* ... */ });
// 스레드 경계를 강제로 큐잉
connect(worker, &Worker::finished, this, &Self::onFinished, Qt::QueuedConnection);
// 해제
disconnect(sender, &Sender::done, receiver, nullptr);
```

주의 3가지: ⑴ 수신자 스레드에 **돌아가는 이벤트 루프**가 있어야 Queued가 배달됨(메인은 `app.exec()`로 항상 보유). ⑵ Queued는 인자를 **값 복사**로 넘기므로 커스텀 타입은 `qRegisterMetaType` 필요(`main.cpp:21`의 `qRegisterMetaType<KPIConfig>`가 그 예). ⑶ **"connect 먼저, start 나중"** — 시그널은 재생이 없어 연결 전에 emit되면 통지가 유실된다.

`QueuedConnection`이 바로 "스레드 경계 마샬링"의 원리다: 워커 스레드에서 emit해도 슬롯은 메인스레드에서 실행되므로, 슬롯 안에서 위젯을 만져도 안전하다. 진동벨 비유로: 주방(워커)이 벨을 울리지만, 음식을 받으러 가는 것은 내(메인스레드) 타이밍이다.

**AutoConnection의 판정 (자세히)** — 기본값 AutoConnection은 **매 emit 순간** "emit이 일어난 스레드"와 "수신자 객체가 사는 스레드(thread affinity)"를 비교해 갈린다:

- **다르면 → Queued**: 슬롯 호출을 수신자 스레드의 이벤트 큐에 넣어 **그 스레드가 실행**한다 (워커에서 쏜 완료를 메인이 받아 실행하는 경우가 이것).
- **같으면 → Direct**: 아무 데도 안 옮기고 **그 자리서 즉시** 함수처럼 실행.

두 가지 오해 주의: ⑴ "**항상** 수신자 스레드로 옮겨간다"가 아니다 — **다를 때만** 옮긴다(같으면 제자리 즉시 실행). ⑵ 객체가 물리적으로 이동하는 게 아니라 **슬롯 실행이 수신자 스레드에서 일어나는** 것이다(객체를 실제로 옮기는 건 `moveToThread`가 하는 별개 일). 판정은 connect 시점이 아니라 **매 emit 시점**이라, 같은 연결도 emit 스레드에 따라 그때그때 Direct/Queued로 갈린다.

콜백 대비 시그널의 구조적 안전장치 두 가지:

1. **수명 안전** — 수신자 QObject가 소멸하면 연결이 자동 해제된다. "완료 통지가 왔는데 받을 객체가 이미 죽어 있음"(dangling) 크래시가 구조적으로 사라진다.
2. **일대다** — 하나의 완료 시그널을 진행바·상태바·로그 도크가 동시에 구독할 수 있다. 콜백은 기본 일대일이다.

### 3-3. DashGUI2에서

같은 저장소 안에 두 세계가 공존한다: `DashModelRunner`는 QProcess를 16회 쓰면서 `waitFor*` 0회 — 완전 시그널 구동(모범). 반면 `DashJobRunner`의 일부 경로는 시그널을 두고도 `waitForFile` 폴링으로 우회한다(안티패턴). 자세한 지도는 [[194-1-async-execution-patterns]] 2절.

### 3-4. 계보 — 관찰자 패턴이지, pub/sub은 아니다 (개정 1)

시그널/슬롯을 pub/sub이라 부르는 경우가 있는데, 정확한 계보는 **관찰자(Observer) 패턴의 언어 수준 구현**이다. pub/sub은 관찰자 패턴에 **중개자(브로커/토픽)를 한 겹 더 끼운** 분산 지향 패턴 — "일대다 방송 + 발신자가 수신자를 모름"까지는 공통이고, 그 이후가 갈린다:

| 축 | Qt 시그널/슬롯 (관찰자) | Pub/Sub |
|---|---|---|
| 주소 체계 | **특정 객체의 특정 시그널**에 연결 — 다른 QProcess의 `finished`는 별개 채널 | **토픽(이름/계층)**에 구독 — 누가 발행하든 그 토픽이면 도달 |
| 중개자 | 없음 — sender가 자기 연결 목록을 보유하고 emit 시 순회 호출 | 브로커/이벤트 버스가 발행자·구독자를 완전 분리 |
| 상호 인지 | sender는 수신자를 모르지만, **배선 코드는 양쪽 객체를 다 알아야** 함(connect에 두 포인터 필요) | 발행자·구독자가 서로 전혀 모름 — 토픽 이름만 공유 |
| 전달 보장 | emit 순간 연결돼 있지 않으면 **유실** — 재생(replay)·영속화 없음 | 큐잉·보존(retained)·QoS 등 전달 보장 장치가 흔함 (MQTT, 메시지 큐) |
| 타입 | 컴파일 타임 시그니처 검사 | 직렬화 메시지 — 느슨한 타입 |
| 동기/비동기 | `DirectConnection`은 그냥 **동기 함수 호출** — pub/sub과 가장 다른 지점. `QueuedConnection`이 비동기 배달에 근접 | 원칙적으로 비동기 |

이 계보 차이에서 실무에 직결되는 성질 두 가지가 나온다 — 설계 계약으로의 승격은 [[194-1-async-execution-patterns]] 4절 "구독" 계약 참조:

1. **통지 유실성** — 시그널에는 재생이 없으므로, 연결 전에 emit된 통지는 영원히 사라진다. 귀결: "connect 먼저, start 나중" 순서 규칙 + 늦은 구독자를 위한 동기 상태 조회(pull) 병행.
2. **가시적 배선** — 구독하려면 sender 객체를 건네받아야 하므로 **의존 관계가 코드에 보인다**. 이 "불편"을 없애려고 토픽형 전역 이벤트 버스(진짜 pub/sub)를 앱 안에 만들면 가시성이 사라진다 — "아무나 발행·아무나 구독"은 전역 싱글톤 직접 호출이 만든 추적 불가 결합을 이벤트 평면에 재현하는 것이다.

## 4. 콜백 — 어떤 경우에 발생하는가

### 4-1. 정의

콜백 = "끝나면(또는 진행될 때마다) **이 함수를 불러줘**"라고 함수 자체를 상대에게 건네는 것. 가장 원시적이고 보편적인 통지 형태다. C API에는 시그널이 없으므로 함수 포인터 콜백이 유일한 통지 수단이다.

### 4-2. 콜백이 "발생"(호출)되는 3가지 경우

1. **완료 통지** — 외부 라이브러리가 작업을 마쳤을 때 1회. 예: FELauncher C API — `DashFL_Ansys_CreateAnalysisTask(h, &cfg, onComplete, this)`처럼 등록해 두면 해석이 끝날 때 `onComplete`가 호출된다 (`DashJobRunner.cpp:2015`).
2. **진행 통지** — 작업 도중 주기적으로 여러 회. 예: 모핑 배치의 `statusCallback` — 케이스 하나 끝날 때마다 호출.
3. **넓은 의미** — 시그널/슬롯도 사실 콜백의 일종이다(connect한 슬롯이 콜백). 차이는 **실행 문맥이 규정되어 있는가**: Qt 시그널은 연결 방식으로 실행 스레드가 정해지지만, 날 것의 C 콜백은 다음 함정을 그대로 안는다.

### 4-3. 콜백의 3대 함정 — 그리고 1줄 규칙

| 함정 | 내용 |
|---|---|
| **스레드 문맥 불명** | 콜백이 **어느 스레드에서 호출될지 라이브러리 마음**이다. FELauncher는 자기 워커 스레드에서 부른다 — 그 안에서 위젯을 만지면 Qt 계약 위반(크래시 후보) |
| **수명 관리 수동** | 콜백 등록 시 넘긴 `this`가 호출 시점에 살아 있다는 보장이 없다 — 시그널의 자동 disconnect 같은 안전망 없음 |
| **콜백 지옥** | 다단계 연쇄가 콜백 안의 콜백 안의 콜백으로 깊어짐 — 코루틴(7절)이 고치려는 것이 바로 이 표기 문제 |

**1줄 규칙: 콜백 본문에서는 아무 일도 하지 말고, 즉시 시그널 문맥으로 변환한다.**

```cpp
// C 콜백(워커 스레드에서 호출됨) — DashJobRunner.cpp:1170의 정석 패턴
static void onComplete(Result r, void* user) {
    auto* self = static_cast<DashJobRunner*>(user);
    QMetaObject::invokeMethod(self, [self, r] {   // Qt::QueuedConnection:
        self->handleTaskCompletion(r);            // 메인스레드 이벤트 루프가
    }, Qt::QueuedConnection);                     // 나중에 안전하게 실행
}
```

이렇게 하면 콜백은 "경계 어댑터" 한 줄로 축소되고, 그 뒤는 전부 시그널 세계의 규칙(스레드·수명 안전)을 따른다.

## 5. 스레드 기반 — 일을 다른 실행 흐름으로

### 5-1. 정의와 필요 조건

스레드는 한 프로세스 안의 독립된 실행 흐름이다. 메인스레드가 이벤트 루프를 도는 동안 워커 스레드가 무거운 계산을 대신 한다.

**언제 필요한가**: 우리 프로세스의 CPU를 실제로 오래 점유하는 in-process 작업(파싱·변환·DLL 연산)뿐이다. **외부 exe 실행·대기에는 스레드가 필요 없다** — 외부 프로세스는 이미 OS 수준에서 병렬이고, 우리가 없앨 것은 "대기"뿐인데 대기는 시그널(3절)로 없앤다. 이 구분이 [[194-1-async-execution-patterns]] 판정의 뼈대다.

### 5-2. Qt의 도구와 조합 원칙

```cpp
// 권장 조합: QtConcurrent(층위 1) + QFutureWatcher 시그널(층위 2)
QFuture<Result> future = QtConcurrent::run(pool, [snapshot] {
    return heavyDllWork(snapshot);        // 워커 스레드에서 실행
});
m_watcher.setFuture(future);
connect(&m_watcher, &QFutureWatcher<Result>::finished,
        this, &MyClass::onWorkDone);      // 완료 통지는 메인스레드 슬롯으로
```

스레드와 이벤트는 배타가 아니라 **조합**이다: 일은 워커가 하고, 통지는 시그널로 받는다. `QFutureWatcher`가 그 다리다. DashGUI2의 유일한 기존 사례가 정확히 이 모양이다 (DOE 샘플링 — `DashAnalysisLauncher.cpp:233`).

### 5-3. 대가 — 왜 "스레드부터"가 아닌가

식당 비유: 일행에게 심부름을 시키면 나는 자유롭지만, **일행과 내가 같은 지갑을 동시에 뒤지면** 사고가 난다. 스레드의 대가는 전부 여기서 나온다:

- **공유 상태 레이스** — 두 스레드가 같은 데이터를 무보호로 읽고 쓰면 간헐적·재현 불가 크래시. "프리즈(항상 보임)가 레이스(가끔 터짐)로 바뀐다"는 말의 의미.
- **GUI 접근 금지** — QWidget 등 GUI 클래스는 메인스레드 전용이 Qt의 계약.
- 그래서 순서가 "이벤트 구동 먼저(스레드 0으로 해결되는 것 전부), 워커는 선결 조건 정리 후 선별 투입"이다.

## 6. Job과 Job 상태머신

### 6-1. Job — 작업의 객체화

지금의 실행 코드는 "실행 중인 작업"을 가리킬 방법이 없다 — 상태는 `m_waitingFinished` 같은 bool 플래그들에 흩어져 있고, 취소·진행률·완료 통지는 경로마다 제각각이다.

**Job = 작업 하나를 객체로 승격한 것**(1급 시민화). 식당 영수증처럼, 주문(작업)에 번호가 생기고 그 번호로 상태 조회·취소가 가능해진다:

```cpp
class Job : public QObject {
    Q_OBJECT
public:
    enum class State { Pending, Running, Succeeded, Failed, Cancelled };
    State state() const;
    void cancel();                         // 취소 요청 (협조적)
signals:
    void started();                        // 시작(Running 진입) 방송
    void progressed(int percent);          // 진행 방송
    void finished(State final, QString reason);
};
```

호출자(위젯)는 Job이 **내부적으로 무엇인지**(외부 프로세스인지 워커 스레드인지) 모른 채 시그널만 구독한다 — 이것이 "Job 표면"이다.

### 6-2. 상태머신 — 허용된 상태와 전이의 명세

상태머신은 거창한 프레임워크가 아니라 **"이 객체가 가질 수 있는 상태 목록과, 허용된 이동 경로의 명세"**다:

```
[Pending] 생성됨 — 아직 시작 전
   │   1. start() 호출
   ▼

[Running] 실행 중
   │   1. 정상 완료 → Succeeded
   │   2. 실패(사유 보관) → Failed(reason)
   │   3. cancel() 요청 수용 → Cancelled
   │   ※ Running → Pending 같은 역행은 존재하지 않음 — 불법 전이
   ▼

[종료 상태] Succeeded / Failed / Cancelled — 더 이상 전이 없음
       재실행은 "같은 Job을 되돌림"이 아니라 새 Job 생성
```

왜 필요한가 — 흩어진 bool 플래그의 문제는 **불법 상태 조합이 표현 가능**하다는 것이다(예: "대기 중이면서 동시에 완료됨"). 상태머신은 상태를 enum 하나로 모으고 전이 함수에서만 바꾸므로, 불법 조합·불법 전이가 컴파일/실행 시점에 차단된다. 부수 효과로 좋은 것들이 공짜로 따라온다:

- 전이 지점 = **시그널 방송 지점** (상태가 바뀌는 곳이 한 곳이니 통지 누락이 없다)
- 전이 표 = **테스트 명세** (W9의 "Job 전이 표 테스트"가 이것)
- "실행 중 버튼 비활성화·취소 버튼 활성화" 같은 UI 규칙이 상태 enum 하나에서 유도됨 (W11)

## 7. 코루틴 — 표기법의 개선

### 7-1. 정의

코루틴 = **중간에 일시정지(suspend)했다가, 나중에 그 지점부터 재개(resume)될 수 있는 함수**. 일반 함수는 한 번 return하면 끝이지만, 코루틴은 `co_await`를 만나면 "여기서 멈추고, 기다리던 것이 완료되면 여기부터 이어서"가 된다.

### 7-2. 무엇이 좋아지나 — 같은 로직의 두 표기

3단계 연쇄(STP 생성 → 해석 실행 → 결과 로드)를 비교하면:

```cpp
// 표기 A: 시그널/슬롯 체인 — 단계마다 함수가 쪼개짐
void startStep1() { connect(job1, &Job::finished, this, &X::onStep1); job1->start(); }
void onStep1()    { connect(job2, &Job::finished, this, &X::onStep2); job2->start(); }
void onStep2()    { connect(job3, &Job::finished, this, &X::onStep3); job3->start(); }
void onStep3()    { /* 완료 처리 */ }

// 표기 B: 코루틴 — 한 함수 안의 순차 표기 (개념 예시)
Task<void> runPipeline() {
    co_await job1->run();   // 멈춤 — 그동안 메인스레드는 이벤트 루프로
    co_await job2->run();   // job1 완료 시그널이 오면 여기부터 재개
    co_await job3->run();
    /* 완료 처리 */
}
```

로직이 길고 조건 분기·루프가 섞일수록 표기 B의 가독성 이득이 커진다 — DOE 배치 루프("케이스마다: STP 만들고 → 기다리고 → 해석 돌리고 → 기다리고")가 전형적 수혜자다.

### 7-3. 흔한 오해 두 가지

1. **"코루틴 = 스레드"가 아니다.** `co_await`로 멈춘 동안 스레드는 어디 갇혀 있는 게 아니라 **이벤트 루프로 돌아간다**. 그래서 단일 스레드(메인스레드)에서 성립하고, 레이스도 새로 생기지 않는다.
2. **코루틴은 통지 방식을 대체하지 않는다.** 재개를 촉발하는 것은 여전히 시그널/이벤트다 — 코루틴은 그 위의 **문법 설탕**(표기 계층)이다. 그래서 "시그널 기반 Job을 먼저 만들고, 코루틴은 나중에 additive로"가 성립한다 (판정과 Qt 5.15 제약은 [[194-1-async-execution-patterns]] 3-3절 — QCoro 최신판이 Qt 6.8+ 전용).

## 8. 마샬링 — Qt가 자동으로 해주는 것과 직접 해야 하는 것 (개정 3)

**마샬링(marshaling)** = 한 스레드의 "호출 + 인자"를 다른 스레드로 안전하게 넘겨 **그 스레드에서 실행**시키는 것. 구체적으로 [슬롯 호출 + 인자를 이벤트로 포장 → 인자 값 복사 → 수신자 스레드의 이벤트 큐에 post → 그 스레드의 이벤트 루프가 꺼내 실행]. 앞 절의 "completion-back"·"QueuedConnection이 곧 마샬링의 원리"(3-2절)가 전부 이것이다.

**왜 핵심인가**: 채택 모델(외부/워커에서 일하고 완료는 메인으로 복귀)의 "**안전 복귀**"가 곧 마샬링이다. 이것이 있어 완료 슬롯을 **단일 스레드처럼**(위젯 자유 접근) 짤 수 있다 — 없으면 완료 처리마다 락이 필요하다.

### 8-1. Qt가 자동으로 해주는 마샬링

| 기능 | 자동으로 해주는 것 | 코드 예 |
|---|---|---|
| QueuedConnection / Auto 시그널 배달 | 슬롯 호출을 이벤트로 포장 → 수신자 스레드 큐 → 실행 | 모든 cross-thread `connect` |
| 인자 값 복사 | 각 인자 deep copy (내장/Qt 타입 자동, 커스텀은 `qRegisterMetaType` 1회 등록 후 자동) | `main.cpp:21` `qRegisterMetaType<KPIConfig>` |
| thread affinity 추적 + Auto 판정 | 수신자가 사는 스레드 추적 → emit 시점에 Direct/Queued 자동 선택 (3-2절) | — |
| `QFutureWatcher` | 스레드풀 작업의 완료·진행을 **시그널로** 바꿔 수신자(메인)에 배달 | `DashAnalysisLauncher.cpp:64,233` |
| `QMetaObject::invokeMethod(…, QueuedConnection)` | 같은 기계를 함수/람다로 **수동 트리거** | FE 콜백 `DashJobRunner.cpp:1170` |
| `BlockingQueuedConnection` | 넘긴 호출의 **반환값까지** 회수(완료까지 블록) — 같은 스레드면 데드락, 드묾 | — |

요지: **"스레드 넘어 호출 전달 + 인자 복사"까지는 Qt 자동.**

### 8-2. 자동이 아니라 직접 해야 하는 마샬링

| 수동으로 해야 하는 것 | 왜 자동이 안 되나 | 코드 / 문서 |
|---|---|---|
| **C API 콜백 → Qt 세계로 들이는 트램폴린** | Qt는 외부 C 라이브러리 존재를 **모른다**. 콜백은 Qt 시그널이 아니라 자동 라우팅 대상이 아님 | `DashJobRunner.cpp:2171` 람다 → `:1170` `invokeMethod`. **도구(invokeMethod)는 Qt 것, 트램폴린 작성은 수동** |
| **두 스레드 공유 가변 상태 보호** | 마샬링은 "호출+인자 복사"만 넘김. 공유 싱글톤 멤버·캐시·전역(`cout`) 동시 접근은 **안 지켜줌** | [[194-1-async-execution-patterns]] 5-3절 선결 5건 |
| **포인터/객체 소유권 이전** | 인자를 복사해도 **포인터는 포인터만 복사** → 가리키는 객체는 공유됨. 워커가 만든 `vtkPoints`·QWidget은 자동으로 안전해지지 않음 | 선결 5건 "GUI·VTK 규칙" — 스냅샷/소유권 이전 |
| **DLL 호출 직렬화 정책** | Qt는 `QThreadPool`을 주지만 "같은 서브시스템 한 번에 하나" 순서 보장은 **설계 몫** | 직렬 풀(`maxThreadCount=1`) 수동 선택 |

### 8-3. 한 줄 정리

마샬링(스레드 넘어 호출 전달 + 인자 복사)은 **Qt 자동**(시그널 / QueuedConnection / QFutureWatcher). 단 **① 외부 C 콜백을 그 세계로 들이는 트램폴린**과 **② 두 스레드가 공유하는 상태 보호**는 자동이 아니라 **수동** — 그래서 문서가 "콜백은 즉시 시그널로 변환"(경계 어댑터)과 "선결 5건"을 마샬링과 **나란히** 강조한다.

## 9. 종합 — 층위별 키워드 지도 (개정 2)

앞 절들의 용어에 본문 미등장 키워드를 더해 층위로 정렬한 지도다. 반복하지만 각 층위는 **서로 다른 질문**에 답하므로(2절), 경쟁 관계가 아니라 층위마다 하나씩 골라 조합한다.

**층위 0 — 무대: 이벤트 루프 모델 (1절 · 모든 층위의 전제)**

- **이벤트** — "일어난 일"을 데이터로 만든 것. 마우스 클릭, 키 입력, 타이머 만료, 화면 갱신 요청, 큐된 시그널 배달까지 전부 이벤트.
- **큐** — 처리를 기다리는 줄. 비동기 세계에서 두 가지 얼굴로 등장한다:
    - **이벤트 큐** — 이벤트 루프마다 하나. 통지가 배달되는 우체통.
    - **작업/명령 큐** — 요청을 줄 세워 하나씩 처리하는 직렬화 수단 (데몬 명령 큐, 직렬 풀의 대기열).
- **이벤트 루프** — 이벤트 큐에서 하나씩 꺼내 처리하는 무한 반복(`QApplication::exec()`). GUI가 살아 있는 이유 — 오래 걸리는 처리가 다음 이벤트를 막으면 "응답 없음".
- **동기 vs 비동기** — 호출이 완료까지 기다렸다 결과를 들고 반환하나 / 요청만 걸고 즉시 반환하고 결과는 나중에 받나.
- **블로킹 vs 논블로킹** — 기다리는 동안 호출 스레드를 세워 두나 / 돌려주나. 동기·비동기와 직교하는 축.
- **동시성 vs 병렬성** — 여러 작업이 겹쳐서 *진행*되는 구조(스레드 1개 + 이벤트 루프로도 성립) / 물리적으로 *동시 실행*(멀티코어·멀티프로세스). 시그널 구동 전환은 병렬성을 새로 만들지 않고 동시성만 확보하는 것.

**층위 1 — 실행 위치: 일을 어디서 하나 (5절)**

- **메인(GUI) 스레드** — 이벤트 루프를 돌리는 스레드, Qt에서 위젯을 만질 수 있는 유일한 스레드. 짧은 작업의 기본값.
- **워커 스레드** — 무거운 in-process 계산(파싱·변환·DLL 연산)을 대신 실행하는 별도 흐름. 메인과 메모리를 공유 → 아래 횡단 관심사의 대가가 청구된다.
    - **스레드 풀**(`QThreadPool`) — 워커를 미리 만들어 두고 빌려주는 관리자. 스레드의 실소유자 — Job이 아니다.
    - **직렬 풀** — maxThreadCount=1인 풀. 같은 서브시스템 작업을 구조적으로 한 번에 하나만 실행 → 비재진입 DLL을 락 없이 안전하게.
    - **`QtConcurrent::run`** — 함수를 풀에 던지는 진입구 / **`QFuture`** — 아직 없는 결과를 가리키는 핸들(Future/Promise 개념: 결과가 담길 자리를 먼저 받아 둠) / **`QFutureWatcher`** — 그 완료를 시그널로 바꾸는 다리.
- **외부 프로세스** — 별개 exe. OS가 병렬성을 공짜로 제공하고 크래시·라이선스·전역 상태가 격리됨. **스레드가 필요 없는 축** — 없앨 것은 대기뿐이고 대기는 층위 2가 없앤다.
    - **`QProcess`** — 기동·입출력·종료를 시그널로 알려주는 Qt 래퍼(본래 비동기).
    - **데몬** — 켜 두고 명령을 반복해 받는 상주 프로세스 (NX 데몬).
    - **IPC** — 프로세스 사이 통신 수단: stdout 마커(`[READY]`·`[PROGRESS]`), 파일, 종료 코드.

**층위 2 — 통지 방식: 완료·진행을 어떻게 되돌려 받나 (3·4절)**

- (반면교사) **블로킹 대기**(`waitFor*`) · **폴링/busy-wait** · **고정 슬립**(`msleep`) — 통지가 없어 호출자가 능동적으로 기다리는 안티패턴. **`processEvents`** 는 그 대기 중 이벤트 루프를 강제로 한 바퀴 돌리는 진통제 — 임의 이벤트가 끼어드는 **재진입** 구멍(#64 크래시 계급의 원천).
- **콜백** — 함수 자체(+`void*` user data)를 건네는 원시 통지(4절). C API의 유일한 수단. 실행 스레드 문맥·수신자 수명 보장 없음.
    - **경계 어댑터** — 콜백 본문에서 아무것도 하지 않고 `invokeMethod(Qt::QueuedConnection)`로 즉시 시그널 세계로 넘기는 한 줄 패턴(4-3절).
- **시그널/슬롯** — Qt 네이티브 통지(3절). **시그널** = 사건의 방송(emit), **슬롯** = 구독(connect)된 수신 함수. 타입 안전 + 수신자 소멸 시 자동 disconnect + 일대다.
    - **`DirectConnection`** — emit 지점에서 슬롯을 즉시 함수 호출(같은 스레드 기본값) — 사실상 동기.
    - **`QueuedConnection`** — 슬롯 호출을 이벤트로 포장해 수신자 스레드의 이벤트 큐에 투입 — **마샬링**(스레드 경계 너머 안전 전달)의 원리.
    - **스레드 어피니티** — QObject마다 "속한 스레드"가 있고, 큐된 슬롯은 그 스레드에서 실행됨 — 마샬링의 목적지를 정하는 규칙.
    - **관찰자 패턴 / Pub/Sub / 전역 이벤트 버스** — 시그널/슬롯의 계보는 관찰자(3-4절): 재생 없음(통지 유실성)·배선 가시성이 귀결. 전역 버스는 pub/sub을 앱 안에 만드는 것 — 지양.
- **파일 워처/타이머**(`QFileSystemWatcher`·`QTimer`) — "파일이 생기면"·"시간이 되면"을 폴링 없이 이벤트로 바꿔 주는 통지원.

**층위 3 — 조직화: 진행 중인 작업을 어떻게 관리하나 (6절)**

- (반면교사) **bool 플래그 산개** — `m_waitingFinished` 류. 불법 상태 조합("대기 중이면서 완료됨")이 표현 가능하다는 것이 문제.
- **Job** — 작업 하나의 객체화(1급 시민화). 상태 조회·취소·진행·통지의 표준 손잡이 — 호출자는 내부가 무엇인지 모른 채 시그널만 구독한다(Job 표면).
    - **ProcessJob** — 외부 exe를 감싼 Job. 스레드 0개 — QProcess·데몬 큐의 시그널을 Job 상태로 번역만.
    - **WorkerJob** — in-process 작업을 감싼 Job. 함수를 풀에 던지고 완료를 시그널로 번역 — "비동기 래퍼"의 실체.
- **상태머신** — 허용 상태 enum(Pending → Running → Succeeded/Failed/Cancelled)과 전이 경로의 명세(6-2절). 상태 변경 지점이 한 곳 = 시그널 방송 지점 = 테스트 명세.
- **계약** — Job 표면에 고정된 약속 4종: 취소(협조적)·진행·실패(도메인 enum+reason)·구독(connect 먼저 start 나중 + 상태 pull) — [[194-1-async-execution-patterns]] 4절. 그 위의 사용자 정책(부분 결과·배치 취소 범위·continue-on-error·재시도)은 같은 문서 4-1절.

**층위 4 — 표기법: 여러 단계의 연쇄를 어떻게 쓰나 (7절)**

- **콜백/슬롯 체인** — 단계마다 함수를 쪼개고 완료 시그널로 다음 단계를 잇는 표기 — 채택안.
- **코루틴** — 일시정지(suspend)했다 그 지점부터 재개(resume)되는 함수, `co_await`가 정지점. 멈춘 동안 스레드는 갇히지 않고 이벤트 루프로 복귀 — 새 실행 위치도 새 통지 방식도 아닌 **문법 계층**. 재개를 촉발하는 것은 여전히 시그널이고, 그 접착제가 **awaiter/어댑터**(QCoro — Qt 6.8+ 제약으로 보류).

**횡단 관심사 — 층위 1에서 "워커"를 고르는 순간 따라오는 것 (5-3절)**

- **공유 상태 / 레이스(경쟁 상태)** — 두 스레드의 무보호 동시 접근 → 간헐·재현 불가 오동작. "프리즈(항상 보임)가 레이스(가끔 터짐)로 바뀐다"의 정체.
- **뮤텍스(락)** — 한 번에 한 스레드만 통과시키는 자물쇠. 잘못 겹치면 **데드락**(서로의 락을 기다리며 영원히 정지).
- **원자적 연산**(`std::atomic`) — 락 없이 안전한 최소 단위 읽기/쓰기 — 취소 플래그의 구현 수단.
- **스레드 안전 / 재진입 가능** — 그 코드를 여러 스레드에서 불러도 되는가. DLL은 이 등급(안전/비재진입/격리 필요)에 따라 풀 배정이 갈린다([[194-1-async-execution-patterns]] 5-2절).
- **입력 스냅샷 / 소유권 이전** — 시작 시점에 값을 복사해 고정하고(스냅샷), 결과 객체는 만든 쪽이 손을 떼고 넘긴다(이전) — 공유 자체를 없애는 가장 싼 안전장치.
- **협조적 취소 vs 강제 종료** — 실행 중인 코드가 스스로 플래그를 확인해 멈추는 것(협조적 — DLL 호출 도중엔 불가) vs 밖에서 죽이는 것(kill — 외부 프로세스만 안전).
- **GUI 스레드 규칙** — QWidget 등 GUI 객체는 메인스레드 전용(Qt 계약). VTK 파이프라인 객체도 스레드 간 공유 금지.

DashGUI2 채택 조합으로 다시 읽으면: **외부 작업 = 외부 프로세스(층위 1) + 시그널(층위 2) + Job(층위 3)** — 스레드 0개, **내부 장시간 작업 = 워커 스레드(층위 1) + 시그널(층위 2) + Job(층위 3)** — 선결 조건 후 선별, **표기는 슬롯 체인(층위 4)** — 코루틴 보류. 횡단 관심사는 워커 축에만 청구되는 대가다. 판정 근거 전체는 [[194-1-async-execution-patterns]].
