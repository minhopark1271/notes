# 문서 관리

DashOpti_GUI 의 문서를 어디에 두고 무엇을 담는지의 기준이다. 상위 목차는 [[프로젝트-관리]].
브랜치·PR·릴리스 절차는 [[저장소-관리-수칙]], C++ 서식·네이밍은 [[코딩-컨벤션]] 에서 다룬다.

## 1. 기준

- 문서가 위치할 곳은 문서의 **수명(휘발성)** 이 정한다.
- Slack·메일 등 실시간 대화는 문서가 아니다. 즉시 휘발된다. 남길 것이면 적절한 문서를 만든다.
- 휘발성이 높은 문서를 저장소에 넣으면 관리에 품이 들고 금방 가치를 잃는다.

## 2. 위치별 수명과 담는 것

| 위치 | 수명 | 담는 것 |
|---|---|---|
| GitHub 이슈 | 가장 짧다 | 아이디어, 버그, 개선사항. 코드 작업의 시발점. 정기적으로 폐기하며 제안자가 누구인지는 폐기 기준에 넣지 않는다 |
| 커밋·PR 메시지 | 코드와 같다 | 작업 시점의 근거·의도·유효한 데이터. 문서의 일종으로 취급한다 |
| 저장소 `docs/` | 코드와 같다 (용도 변경 예정 — 표 아래 참고) | 기능·모듈 설명, 설계. 모듈의 구조·동작·입출력 형태만 다루고 이론적 배경은 상세히 쓰지 않는다. 코드를 바꾸면 문서를 개설·편집한다. PR 시점에 에이전트에게 맡겨도 된다. 이후 다른 에이전트도 그 문서로 똑똑해진다 |
| Wiki | 길다 | 일하는 방법, 설계의 이론적 설명, 프로젝트의 의도와 목표. 잘 변하지 않으며 팀의 일하는 방식을 결집한다 |
| 외부 도구(노션 등) | 누적형 | 통계 수치, 작업일지, 회의록. 노션은 Presentation을 바꾸기 쉬운 DB라 Insight를 얻기에 좋다 (현재는 엑셀 시트 사용) |

> **저장소 `docs/` 용도 변경 예정** — 기존 코드베이스를 설명하는 문서는 노션으로 기능이관하고,
> `docs/` 는 `.gitignore` 로 관리해 저장소에 커밋하지 않는다. 이후 이 경로는 작업자 local harness 등
> 에이전트 작업환경 파일과 임시 문서를 두는 자리로 쓴다. 이전이 끝나면 위 표의 `docs/` 행과
> 3절의 경계 기준도 함께 고친다.

## 3. Wiki 와 저장소 `docs/` 의 경계

위 표에서 수명이 같아 보이는 둘을 가르는 기준이다.

- **Wiki**: 일하는 방식. 잘 변하지 않고 저장소 코드와 독립적인 것.
- **저장소 `docs/`**: 코드와 함께 움직이는 것. 코드를 바꾸는 커밋이 문서도 같이 바꾼다.

경계에 걸치는 것은 **원문을 `docs/` 에 두고 Wiki 에는 요약과 진입점만** 둔다. 코딩 컨벤션이 그 예다 —
규칙 원문과 강제 범위 정책은 `docs/coding-convention.md`, `docs/convention-enforcement-scope.md` 에 있고
훅·설정 파일과 같은 커밋에서 관리되며, [[코딩-컨벤션]] 은 그 요약이다. 둘이 다르면 저장소 문서가 우선한다.
